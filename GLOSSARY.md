# Glossary

Canonical terms. Use these exactly; do not introduce synonyms. Tool names are final.

## Platform & strategy

- **Platform** — Watershed as a whole: one AGPL/free-software AI-native work platform for reusable, measurable and reversible agent workflows, composed of three independently usable layers.
- **Platform layer** — One independently usable part of the platform: execution, control or workspace/action.
- **Execution layer** — Flow Agent's role: running repeatable, auditable agent workflows.
- **Control layer** — Meta-Harness's role: orchestrating, observing and measuring agents of any harness across agent hosts, leaving their governance to each harness.
- **Workspace/action layer** — Liquid's role: human/agent workspace co-editing with reversible action history.
- **Agent workflow** — A structured unit of AI-agent work that can be run, observed, measured and improved (in Flow Agent, realized as a Flow).
- **Reversible agent action** — An attributed workspace mutation that can be inspected and reverted (see Action, Workspace action history).
- **Wedge** — The first narrow adoption path used to validate and grow the platform. Flow Agent is the developer/open-source execution wedge, Meta-Harness the orchestration wedge, Liquid the long-term workspace/action wedge.
- **AGPL/free-software posture** — The project's commitment to transparent, inspectable, self-hostable software under the repository's `AGPL-3.0-only` license; not a proprietary/open-core monetization stance.
- **Offline after provisioning** — The state in which installed binaries, approved artifacts, required Global Flow configuration, one Runtime binding and local-runtime readiness are present, so the local core paths run with network interfaces disabled. Requested remote-only actions fail visibly when unavailable; sync waits resumably without blocking local work. Canonical: [VISION.md](VISION.md#local-operation-and-portable-continuity).
- **Topic branch** — Short-lived Git branch for one logical change; can span multiple sessions and is PR'd back to `main`.
- **Git upstream** — Remote-tracking branch a local branch uses by default for pull/push. Topic branches must not track `origin/main` ([git skill](.agents/skills/git/SKILL.md)).
- **Fast-forward pull** — Fetches the Git upstream and advances the local branch only when it has no commits of its own; diverged branches need a merge or rebase in a terminal.
- **Commit metadata** — Commit subject, body, comment text and trailers; metadata changes must not change file content.
- **Unpublished commit** — A commit not yet pushed or otherwise shared; only these may be amended for metadata corrections ([git skill](.agents/skills/git/SKILL.md)).

## Tools

- **Liquid** — Standalone local-first workspace and app-building product built from Pages, Blocks, Views, Sources, Connections and Automations; every client works through a local replica; optional sync, agent integration and headless execution extend rather than replace that product. CLI binary: `liq`.
- **Flow Agent** — Host-local, CLI-only, Rust-core, script-driven deterministic Flow runtime (not a generic coding agent). Guarantees: [SECURITY.md](SECURITY.md#flow-agent-security-contract). Milestone status: [PLAN.md](PLAN.md). CLI binary: `flow`.
- **Meta-Harness** — Self-contained host-scoped headless control plane over CLI agents on one host (session registry, central config resolution, agent schedules/triggers, artifact indexing, AgentPulse), reachable through local or authenticated remote clients. Runs without Liquid; Liquid is its primary rich UI. CLI binary: `meta`.
- **Execution location** — User-editable label for the host and owning Meta-Harness target used to start or control a session. Technical identifiers remain internal while routing authority is preserved.
- **Runtime binding** — Device-local resolution from a Flow's model/runtime requirements to one concrete provider endpoint and its provider/model identity, with optional local artifact and runtime identity, optional credential reference and resource policy. Credential material stays in its Flow-owned protected store. Operational host state, not Global Flow configuration or Conversation authority; [D-059](docs/decisions/open-decisions.html#d-059) owns the exact schema. Canonical: [VISION.md](VISION.md#local-operation-and-portable-continuity).

## Roles & layers

- **Agentic Engineer** — A technically proficient person who configures Flow Agent Building Blocks and their capability limits, and accepts responsibility for the resulting Flow behavior.
- **Operator** — The person or process that invokes Flow Agent and owns its host identity and runtime data. An operator may be an Agentic Engineer or may only run a predefined Flow.
- **Core** — Shared libraries for Building Blocks, invocation-policy validation and protocol types. Each product owns its runtime and enforcement boundaries.
- **Protocol** — The versioned contract over which the tools communicate (the integration seam). Canonical: [PROTOCOL.md](PROTOCOL.md).
- **Meta-Agent** — The agent that _operates_ the Meta-Harness; either Liquid-native or BYOA. May propose configuration changes for underlying agents, which take effect only once approved (ADR-0298).
- **Configuration block** — One named instruction, skill or MCP server in Meta-Harness's central configuration, written into every harness home; not a Flow Agent Building Block (ADR-0298).
- **Configuration proposal** — A change to Meta-Harness's central configuration that takes effect only once someone on the account approves it, which makes a new revision (ADR-0298).
- **Configuration revision** — One state of the central configuration: 0 before the first approval, then one more with each approved proposal (ADR-0298).
- **Harness home** — The configuration folder Meta-Harness owns for one harness, such as Claude Code's `CLAUDE_CONFIG_DIR` or Codex's `CODEX_HOME`, which T3 Code starts the harness with; the person's own harness configuration stays untouched (ADR-0298).
- **Meta-Harness service** — The `meta serve` process that owns a data folder (`META_HARNESS_HOME`, else `~/.meta-harness`), runs the pinned T3 Code server and serves Meta-Harness's API to clients such as `meta` and Liquid (ADR-0297).
- **Meta-Harness API version** — The number a client names in the `meta-harness-api` header of its handshake; the service admits only its own ([V-Spec](docs/concept/V-Spec_MetaHarness.html#surfaces)).
- **Remote access** — The service's listener on this computer's Tailscale addresses, off until a person turns it on (ADR-0299).
- **Pairing code** — The single-use code that `meta invite` issues so that one device or host can pair with this computer's remote access (ADR-0299).
- **Pairing name** — The name a device or host pairs under, unique among the clients paired here; T3 labels a host link's sessions with it, and `meta host revoke` names it (ADR-0300, ADR-0301).
- **Access level** — The level at which a linked host's agents may act here, as T3 names them (`read-only` to `full-access`); the receiving host sets it when it invites the host, and a link may ask for less (ADR-0300).
- **Device token** — The token a device keeps after pairing; what it may reach is in [SECURITY.md](SECURITY.md#meta-harness-service-and-configuration) (ADR-0299).
- **Host token** — The token another host keeps after pairing; what it may reach is in [SECURITY.md](SECURITY.md#meta-harness-service-and-configuration) (ADR-0288, ADR-0299).
- **Host move** — Continuing a session on another host, which then owns it; until the Liquid account exists, only while both hosts answer (ADR-0284, ADR-0308). Canonical: [V-Spec](docs/concept/V-Spec_MetaHarness.html#host-move).
- **Sealed session** — A moved session's thread on the host it left: it takes no new messages, leaves that host's thread list and may be archived or deleted (ADR-0308).
- **Transfer** — One attempt at a host move, named by an id that makes each step repeatable; it ends sealed or released, and a released session stays on its host (ADR-0308).
- **Host link** — A link that lets one host's T3 Code reach another's; Meta-Harness pairs each direction separately, carries it through a host tunnel and renews it (ADR-0285, ADR-0288, ADR-0299). Canonical: [V-Spec](docs/concept/V-Spec_MetaHarness.html#host-links).
- **Host tunnel** — The request-passing path of a host link: a loopback port on the linking host to the other host's remote access, passing only the requests a link makes. Refusals: [SECURITY.md](SECURITY.md#meta-harness-service-and-configuration) (ADR-0300, ADR-0301).
- **Peer link** — T3 Code's own link from one T3 server to another's `/mcp`, which a host link carries (ADR-0288).
- **Login service** — The per-user launchd agent or systemd user unit that keeps `meta serve` running (ADR-0286).
- **BYOA** — "Bring Your Own Agent"; plugging an external agent in as the Meta-Agent.
- **AgentPulse** — Meta-Harness subsystem measuring rework ratio, first-attempt success rate and cost-per-productive-outcome. Meta-Harness computes and stores the metrics; Liquid only renders them. Canonical: [V-Spec](docs/concept/V-Spec_MetaHarness.html#agentpulse).
- **Adapter** — The part of an agent host that translates an external agent's harness into normalized events and commands; on T3 Code, its providers and local ACP commands (ADR-0282). Native agent shapes do not leak past it.
- **Agent event** — One event of the session model the Meta-Harness service gives Liquid's agent surface, translated from T3 Code's thread events and carrying T3's sequence number (ADR-0290). Not a Flow Agent runtime event.
- **Partial output** — What a running tool call has written so far, reported as its whole output while it runs; each report replaces the one before it, unlike a content delta, which appends text.

## Flow Agent primitives

- **Building Block** — The flexible, modular and recursive unit of configuration; every Tool, Instruction, Phase and Flow is a building block. Flows can contain flows.
- **Global Flow configuration** — Flow Agent configuration and Building Blocks resolved only from `FLOW_AGENT_HOME` (default `.flow` beneath the user home). Project-local configuration layers are never discovered; project-specific behavior is expressed by selecting or authoring a Flow. `AGENTS.md` is an instruction channel without technical configuration authority.
- **Building-block registry** — The resolver for addressable Tools, Instructions, Phases and Flows. In v0 it safely catalogs one-block YAML entries under a configured root, then retains only the selected Flow's transitive definition closure, once per unique definition.
- **Canonical serialization** — Deterministic UTF-8 JSON of the validated, registry-resolved selected definition closure; equivalent closures serialize to the same bytes.
- **Tool** — A Phase-scoped capability with an exact command identity (predefined or own script) and typed accepted parameters. The provider may request it but cannot change its invocation contract; the Engineer trusts its complete implementation and dependency chain.
- **Policy artifact** — The canonical JSON that `core-policy` produces for a Tool's validated command and parameter contract. It is not a filesystem, network or process-containment policy. Fixture evaluation proves deterministic invocation decisions, not OS security.
- **Predefined-command registry** — The trusted id-to-executable map for predefined-command Tools. A script names a `command_id`; Flow Agent resolves it to one executable identity, combined with the script's literal base `argv`, without PATH lookup or shell parsing.
- **Predefined-command Tool** — A Tool that names a fixed command id resolved through the predefined-command registry. Fixtures emulate its result; productive execution sends the verified identity through the Executor.
- **Allowed parameter** — A reviewed parameter spec for a Tool: exact name, typed shape, required flag and constraints (enum, pattern/length, integer range). Unknown or invalid parameters are denied before tool launch.
- **Own-script Tool** — A Tool whose reviewed inline `script_body` uses the fixed v0 `posix-sh` contract. Fixtures interpret only their bounded subset; productive execution uses the same Executor as every other Tool.
- **Instruction** — A modular prompt primitive with typed `{{name}}` parameters. A leaf Phase references Instructions and binds their declared values from its complete typed input; an explicitly selected source filename has no authority or naming semantics.
- **Phase** — The recursive workflow unit. A leaf exposes Instructions and Tools to one provider loop and returns a typed result; a composite runs ordered child Phases and selects one child's result. Either may use a bounded declarative loop.
- **Transition** — An ordered inline forward-sibling rule owned by a Flow or composite Phase. It selects a later sibling only when an exact typed equality predicate matches the successful source result; otherwise execution falls through.
- **Flow** — A fully configured deterministic orchestration of ordered Phases and optional subflows. Whole successful results pass forward by default; a Flow is itself a building block.
- **Subflow** — A Flow a Phase starts ([V-Spec](docs/concept/V-Spec_FlowAgent.html#parallel-subflows)).
- **Subflow instance** — One started Subflow: the Run of its own Conversation, in its own `flow` process, named by subflow id and start order across its root Run's tree, such as `scraper-5`.
- **Flow execution plan** — The finite typed, deterministic and side-effect-free description of resolved Flow invocations, lifecycle boundaries, context inputs and Tool intents consumed by runtime apply.
- **Execution request** — One versioned, bounded request for exactly one validated Tool invocation, bound by a canonical digest. Canonical: [PROTOCOL.md](PROTOCOL.md#m12-executor-protocol).
- **Executor** — A Flow Agent execution component that validates one Execution request, waits for Start, establishes Flow-owned write protection, supervises one Tool invocation and returns a bounded result with enforcement receipt or typed error. Observed cleanup is not a universal hostile-descendant guarantee. Canonical: [PROTOCOL.md](PROTOCOL.md#m12-executor-protocol).
- **Default Executor** — The official `flow-executor` companion, using Linux Bubblewrap/seccomp or macOS Seatbelt to establish Flow-owned write protection before Tool launch. Exact release targets and verification status are in [PLATFORMS.md](PLATFORMS.md).
- **Custom Executor** — An administrator-selected implementation of the same Executor protocol on a supported Flow Agent host. Flow Agent documents the protocol but certifies no third party's compatibility, security or operation.
- **Meta-Harness agent executor** — Meta-Harness's host-local component for launching and supervising whole CLI agent processes. It is not a Flow Agent Executor and never selects, configures or manages one.
- **Fixture executor** — The M1 in-process executor enabled only by the canonical fixture profile; it returns deterministic model/Tool doubles and is not a provider, subprocess runner or POSIX shell.
- **Compatibility probe** — A non-authoritative Executor handshake and self-test that can detect known protocol, platform and setup mismatches. Passing it is useful diagnostics, never a compatibility or security guarantee.
- **Enforcement receipt** — The canonical bounded Executor evidence persisted with a terminal Tool attempt: applied backend/platform, active Flow-owned write protection and the request-policy digest. Structural validation does not certify a Custom Executor's truthfulness.
- **Policy emulation** — M1's deterministic in-process evaluation of modeled policy decisions. It proves runtime correctness contracts, not Flow-owned write protection. Canonical: [SECURITY.md](SECURITY.md#m0m1-policy-emulation-scope).
- **Sandbox** — An execution environment whose selected restrictions an operating-system, container or VM mechanism enforces. The term promises neither whole-host containment nor any particular restrictions, so always qualify it: an external sandbox around Flow Agent, a harness's own sandbox (ADR-0252), the macOS App Sandbox (compared, not selected; ADR-0172) or Liquid's App Runtime. Flow Agent provides no Tool sandbox; its Executor enforces only [Flow-owned write protection](SECURITY.md#flow-agent-security-contract).
- **Sandbox backend** — The operating-system, container or VM mechanism enforcing selected restrictions. Flow's native backends are Linux Bubblewrap/seccomp and macOS Seatbelt; a backend does not understand Building Blocks.
- **Container** — A Sandbox form that isolates processes while sharing the host kernel. The Default Executor uses none, a Custom Executor may, and it is not automatically a sufficient security boundary.
- **Virtual machine (VM)** — An isolated guest system with its own kernel.
- **Flow-owned write protection** — The mandatory native restriction blocking Tools and their newly launched children from writing, deleting, replacing or hardlinking this installation's protected Flow files. It is not general filesystem, process or network containment, and reads are not restricted. Independent unconfined services are outside this boundary. Canonical: [SECURITY.md](SECURITY.md#flow-owned-write-protection-and-its-limits).

## Flow Agent runtime surfaces

- **Access-control list (ACL)** — Operating-system permission entries that grant or deny named users or groups access beyond ordinary file-mode permissions. Installation prerequisites are in [PLATFORMS.md](PLATFORMS.md#installation-prerequisites).
- **flow-value-v0** — The closed, explicitly tagged, provider-neutral M1.1 value contract for root input, Phase and Instruction values, Tool parameters and Tool outputs. Canonical: [PROTOCOL.md](PROTOCOL.md#m11-runtime-values).
- **flow-run-input-v0** — The versioned run-input document holding one complete `flow-value-v0` value for the root Flow. Canonical: [PROTOCOL.md](PROTOCOL.md#m11-runtime-values).
- **flow-tool-result-v0** — The fixed Tool-result envelope for status, stdout and stderr flow values, with exit code only when observed. Canonical: [PROTOCOL.md](PROTOCOL.md#m11-runtime-values).
- **flow-m11-performance-evidence-v0** — Release-mode Ubuntu JSONL schema for the finite M1.1 observational workload set; it records exact inputs, raw samples and unadjusted timing and RSS aggregates without performance thresholds.
- **flow-m12-executor-startup-v0** — Release-mode native-host JSONL schema for the fixed M1.2 one-shot Executor startup observation; canonical workload and evidence policy in [`M1_2_STARTUP_EVIDENCE.md`](flow-agent/benchmarks/M1_2_STARTUP_EVIDENCE.md), without a timing threshold.
- **Conversation** — The complete user-facing work history: one append-only tree of navigable entries and all Runs that belong to it. Continuing from an earlier entry creates a branch. Canonical: [PROTOCOL.md](PROTOCOL.md#local-run-storage-and-m11-conversation-trees).
- **Portable continuation** — A verified terminal Conversation checkpoint continued on another device or Runtime binding as a new child Run. It rebinds authority, never replays prior effects, and is distinct from exact interrupted-Run recovery. Canonical: [VISION.md](VISION.md#local-operation-and-portable-continuity).
- **Conversation entry** — One `flow-conversation-entry-v1` history node that links to its parent and to a committed point in one owned linear Run, and binds the terminal recovery snapshot used for compact continuation.
- **Run** — One complete execution of a Flow inside a Conversation, from Flow start to completion or failure; each continuation or branch starts a new Run. Its lowercase, path-safe `run_session_id` is the event `session_id`; replay, Tail and interrupted-Run recovery address it with its `conversation_id`.
- **Steering message** — A chat message delivered to an active Run; the Run takes it after its running provider turn and gives it to the active leaf Phase, without ending the Run. Canonical: [PROTOCOL.md](PROTOCOL.md#acp-binding-flow-acp).
- **Transcript** — The messages and runtime events reachable on a selected conversation branch; the complete tree retains every branch.
- **Durable session history** — The append-only conversation tree plus every owned linear run and referenced immutable source artifact. Provider-context optimization and branch navigation never delete it or roll back external effects.
- **Run Log** — The versioned append-only `run-log.jsonl` of one Run, starting with its definition record; per-Tool Run Logs project only Tool records rather than using separate files. Canonical: [PROTOCOL.md](PROTOCOL.md#local-run-storage-and-m11-conversation-trees).
- **Recovery snapshot** — One bounded, versioned `recovery.jsonl` prefix for a productive Run; it lets the exact Run resume without repeating completed provider or Tool calls. Canonical: [PROTOCOL.md](PROTOCOL.md#local-run-storage-and-m11-conversation-trees).
- **Write-and-sync helper** — The one `fs_guards` boundary every durable Flow Agent file write and sync passes through (ADR-0266). Tests keep a ledger of synced bytes for power-loss simulation, and a source guard refuses writes made outside it.
- **Uncertain attempt** — A durable provider or Tool intent without a committed terminal result. Flow Agent never redispatches it automatically; `PROTOCOL.md` owns reconciliation behavior.
- **Provider reply invalid** — A provider reply that ends but breaks the Responses format. It closes the attempt as `provider_reply_invalid`, is never retried, and differs from both `provider_error` and an uncertain attempt; its contract is in `PROTOCOL.md`.
- **Tool attempt stage** — The `preflight` or `started` stage recorded with a cancelled Tool attempt, stating whether `tool.started` was committed; its contract is in `PROTOCOL.md`.
- **Process cleanup unknown** — The recorded mark that a Tool's processes may outlive its cleanup after the Executor's answer; the attempt keeps that answer and the Run stops with the same reason. Canonical: [SECURITY.md](SECURITY.md#flow-agent-security-contract).
- **Run bundle** — One Run's event/context/recovery segments, Run Log including its definition metadata, and immutable objects.
- **Conversation bundle** — One conversation history plus all owned Run bundles.
- **Host-local session ownership leases** — Exclusive operating-system file leases in the private user-global Workspace store. `PROTOCOL.md` defines their ownership and acquisition contract. Process exit releases leases; none is durable or transferable across hosts.
- **Session marker** — The persistent `session.lock` observability leaf inside a run directory. It is not ownership authority and cannot grant or revoke the lease.
- **Reservation orphan** — An empty run artifact retained and inventoried when rollback cannot prove identity-bound deletion. Its cleanup failure remains visible, and compare-then-unlink never removes it.
- **Event segment** — One append-only canonical JSONL file within a run bundle; rotation bounds individual I/O without starting a new run or resetting sequence/budgets.
- **Resolved flow state** — The current Flow invocation and Phase execution stack, active Instructions and available Tools, typed input/result and runtime state exposed by defined interfaces.
- **OpenAI-compatible endpoint provider** — The `openai-compatible` provider (ADR-0263): one API key kept with its base URL in the protected credential store, speaking the Responses API. Distinct from the subscription login `openai-codex`; [PROTOCOL.md](PROTOCOL.md#m11-openai-compatible-endpoint-provider) owns its contract.
- **Provider context** — The deterministic, bounded projection compiled from resolved flow state and narrowly selected durable history for one model turn; not the full transcript.
- **Context profile** — A versioned deterministic contract for provider-context ordering, budgeting, estimation, projections, hashing and cache boundaries; M1 exposes only `flow-context-v0`. Canonical: [V-Spec](docs/concept/V-Spec_FlowAgent.html#context-compiler).
- **Context manifest** — The reproducible per-provider-turn record of the context profile, budget inputs, ordered included/projected sources, omissions, cache boundaries, token estimate and final context hash.
- **Runtime event** — One normalized event Flow Agent emits over its public contract (see `PROTOCOL.md`); the same events feed JSONL mode, the session store and the [ACP binding](PROTOCOL.md#acp-binding-flow-acp).
- **JSONL event stream** — Flow Agent's headless mode that streams newline-delimited JSON runtime events to stdout for automation/CI/consumers.
- **Session store** — Flow Agent's conversation trees and owned run bundles in a canonical-path-keyed private user-global Workspace store. Runtime state only; **not** a project VCS/history engine.
- **Live-event notification** — A bounded, best-effort wake-up carrying a session's earliest pending and highest committed sequences and no event payload; receivers replay from the authoritative log. Canonical: [PROTOCOL.md](PROTOCOL.md#m1-local-append-and-live-delivery).
- **Persistence-before-notification** — The local guarantee that a session's serial writer appends each event to the authoritative log before updating its high-watermark and notifying; `fsync` is a separate checkpoint. Canonical: [PROTOCOL.md](PROTOCOL.md#m1-local-append-and-live-delivery).
- **Flow registry** — The name/id index used by `flow run <name>` and `flow chat` ([V-Spec](docs/concept/V-Spec_FlowAgent.html#surfaces)).
- **Fixture workspace** — A checked-in test workspace whose explicit canonical fixture profile selects the fixture executor and deterministic stub model.
- **Flow definition ID** — The registry/building-block id of a Flow definition; carried in event payloads as `flow_definition_id`.
- **Runtime flow invocation ID** — The `flow_id` assigned to one root-flow or subflow invocation in a session; distinct from the Flow definition ID and linked to a parent by `parent_flow_id`.
- **Stub model** — A deterministic model double used by tests so golden event streams are byte-stable in CI.
- **Golden flow** — A checked-in flow fixture with a deterministic expected event stream used for capture-and-diff validation.
- **Golden event stream** — A checked-in JSONL event stream with fixed fixture IDs, timestamps, sequence values and canonical event JSONL bytes per `PROTOCOL.md`.
- **Environment allowlist** — A tool-scoped policy-artifact field; its M1 availability and restrictions are defined in [`SECURITY.md`](SECURITY.md).
- **Smoke-flow** — The smallest golden flow: one phase, one tool and one instruction, used as the first localizable gate.
- **Hello-flow** — The showcase golden flow that exercises multiple Phases and scoped Instructions/Tools.
- **Negative fixture** — A tiny flow that intentionally attempts a forbidden operation and must be rejected.
- **HTML render gate** — The CI validation that browser-renders self-contained HTML docs; `pnpm run docs:render-check` invokes `scripts/check-html-render.mjs` at `1440x900` and `390x844`.

## Liquid primitives

- **Workspace** — Top-level owner of Pages, Blocks, Sources, Connections, Automations, Roles, History and settings.
- **Page** — Liquid's authored surface: an ordered composition of Block Views with responsive layout metadata. A Page starts as an empty flow and may later be arranged on a grid.
- **Block** — A canonical, typed and addressable unit of content or functionality, such as text, database, code, formula, media, whiteboard, App or Chat. A text toggle is formatting inside a Section, not a Block Type.
- **Block Type** — The versioned behavior, state contract, supported Views, ports/actions, permissions and responsive capabilities shared by Blocks of one kind.
- **View** — One placement or representation of a Block. Several Views may expose the same Block on different Pages and stay synchronized because they share canonical Block state. Duplicating creates a new Block; adding a View does not. A View of a Table has its own title and View tabs.
- **View tab** — One tab of a View of a Table, as Notion's database views: its own name, layout (Table, Board or Calendar), group, sort and filter over the View's Table. The UI says tab; the app's tabs (ADR-0241) are another thing.
- **Connection** — An explicit typed and permissioned data/action relation among Blocks and Sources. It addresses stable objects and ports independently of active View or layout; visual proximity never grants access.
- **Automation** — A Workspace-owned event/condition/action rule over Liquid objects and permitted external actions. It is distinct from Meta-Harness agent scheduling and orchestration.
- **Source** — An external or shared resource addressable from a Workspace. Sources appear beside Pages in the Explorer and use the same open/navigation flow, but are not authored Pages internally.
- **Explorer** — Liquid's primary Workspace navigation surface, listing Pages and Sources as peer entries.
- **Page template** — A reusable starting composition of Blocks, Views, Connections and Automations for one use case, saved from Arrange mode; it creates an ordinary Page, asking by default for the Chats it shows (ADR-0241).
- **PowerBar** — Liquid's command and creation surface for finding Workspace objects, adding Blocks and invoking permitted actions. Without a prefix it searches and jumps; `/` adds a Block, `>` lists actions and `@` is kept for people, as the approved [Pages mockups](docs/design/mockups/liquid-workspace-pages.html) show (ADR-0236).
- **Slash commands** — The commands `/` lists in a menu at the caret in an empty Paragraph, as in Notion and T3 Code: the Blocks to add, filtered by what follows `/`. The PowerBar's `/` lists the same ([Pages mockups](docs/design/mockups/liquid-workspace-pages.html)).
- **Liquid key** — Caps Lock when the user opts in: a tap opens Liquid from any app, holding it in Liquid reveals shortcuts and ⇪ plus a key runs a Liquid command.
- **Shortcut profile** — Liquid's set of shortcuts: Liquid key, Standard (⌘ only) or Custom.
- **Reveal key** — The key whose hold shows contextual shortcut hints: the Liquid key while it is on, ⌘ otherwise.
- **Role** — A reusable allow-only composition of permissions assigned to users, groups, agent profiles, sessions or Automations; anything not allowed is denied. Templates: Can view, Can edit, Can manage. Canonical: [V-Spec](docs/concept/V-Spec_Liquid.html#permissions).
- **Protected** — A Page, Block or Source that stops inheriting rights from its area or Page, so only Roles allowed on it may change it; the allow-only way to restrict one part of an editable Page (ADR-0235).
- **History** — Liquid's attributed and reversible record of Workspace Actions; also called **workspace action history / workspace VCS** when distinguishing it from project-code VCS. A revert records a new reversing Action; Restore version returns a Page to an earlier save point (ADR-0235). Canonical: [V-Spec](docs/concept/V-Spec_Liquid.html#history).
- **Agent surface** — Liquid's view of one agent session: the sidebar, the Chat with its session card, the Diff panel beside it when open, the input area and the status bar. Its labels follow T3 Code, which calls a session a thread (ADR-0239, ADR-0295).
- **Session card** — The card at the top right of the Chat that holds a session's host and worktree, Git controls, servers, automations, Lineage and statistics, as T3 Code's thread details card; it sits beside the Chat or opens as a popover.
- **Lineage** — The session card's list of a session's related threads, as T3 Code names them: its parent, forks and subagents, earlier ones folded under "Previous agents"; Side chats list the forks T3 opens beside a session.
- **Context window** — The tokens a model takes in one request; the session card shows how much of it the session uses and where the agent compacts it, as the provider reports.
- **Session statistics** — What T3 Code reports for a session (tokens, working and tool time, tool calls by outcome), never estimated (ADR-0279, ADR-0293). The session card shows them as rows; the statistics panel, opened with ⌘U, shows them per turn.
- **Writer model** — The one model the person chooses to write commit messages left blank, pull request text and session titles, which Meta-Harness passes to T3 Code (ADR-0294).
- **Turn** — What an agent does for a prompt: one T3 Code run, numbered by its ordinal, which also numbers its checkpoint and diff. The Diff and the statistics panel both number turns (ADR-0279).
- **Diff panel** — The Diff of the Chat's turns, shown as a panel beside the Chat (⌘D).
- **Start page** — What the agent surface shows before a session's first message: the project's recent sessions to continue and chips to set the new one up.
- **Input area** — The fixed-height area at the bottom of the agent surface: the composer, or in its place an agent question.
- **Git integration** — Git operations on agent projects, run by T3 Code on Meta-Harness's host and shown in Liquid (ADR-0282). Not a Watershed VCS; Liquid's own VCS is History. Canonical: [SECURITY.md](SECURITY.md#mvp-vcs-boundary).
- **CRDT** — Conflict-free replicated data type: a data structure whose independently edited copies merge deterministically to the same state. Liquid sync uses an established CRDT library (ADR-0182): Automerge 3 (ADR-0238).
- **Rust–Flutter bridge** — The asynchronous call and stream boundary between Liquid's Flutter UI and its Rust core. It carries bounded deltas, never whole Pages or Databases (ADR-0182); it uses flutter_rust_bridge v2 (ADR-0186).
- **Liquid replica** — A complete local working copy of an authorized Workspace. Interactive reads and writes never require a remote round trip.
- **Replica key name** — The random name, kept in a small file in the replica's folder, under which the operating system's keychain files the replica's database key (ADR-0275).
- **Sync Server** — Central service in the replica star topology. It stores and exchanges committed Workspace changes resumably; it does not execute App Blocks or control agents.
- **Harness handoff** — Continuing a conversation in another harness as a new session that receives the earlier conversation as bounded text, without native tool or reasoning state (ADR-0231).
- **Area** — A part of a Workspace that Roles, replication and encryption treat as one unit; its key is wrapped for every device and headless replica allowed in it (ADR-0224, ADR-0228). Canonical: [V-Spec](docs/concept/V-Spec_Liquid.html#sync).
- **Agent host** — Where Meta-Harness runs agents: by default the account it is installed on (ADR-0254), or a machine, VM, container or account the person links. A default agent host has no replica; its agents use the person's Liquid through the Workspace CLI/API (ADR-0255).
- **Active agent host** — The agent host new Liquid sessions start on, chosen under Settings → Agent hosts with "Use for sessions"; this Mac when none is chosen. Liquid lists the sessions of every agent host that answers, not only this one (ADR-0295).
- **Subagent** — A thread an agent starts through T3 Code's orchestration tools (ADR-0288), in any harness, with any model and on any agent host, which reports back to it as messages; its authority never exceeds its parent's grant (ADR-0253).
- **Grant** — What a person signs to let an agent act for them in a Workspace: an area, actions and an expiry, never more than that person may do. Revoking it makes the Sync Server refuse the agent's changes (ADR-0223). Canonical: [V-Spec](docs/concept/V-Spec_Liquid.html#agent-grants).
- **Agent-sessions area** — The area where Meta-Harness mirrors agent session records at turn boundaries, so another of the person's agent hosts can continue a session (ADR-0229).
- **Session record** — The folder "Export record" writes into Downloads for one session: T3 Code's record of the thread, `record.json` with its turns, and a `README.txt` of what it leaves out (ADR-0257).
- **Compliance replica** — A replica a company runs with its own key for search, legal hold and data-loss checks (ADR-0228).
- **Recovery key** — The second way to regain a Workspace's keys when no signed-in device can approve a new one. Area keys are also wrapped for it, and the person or their company holds it (ADR-0228).
- **Headless replica** — A Liquid replica without UI, on a server for Automations and schedules or on a separate agent host. It holds only the Workspaces enabled for it and, once selective replication follows the complete M3 replicas, only the areas its Roles allow (ADR-0255).
- **Paragraph** — A body text, heading, list item, to-do or quote inside a Section, ended by ⏎, which starts the next; ⇧⏎ breaks its line without ending it (ADR-0317).
- **Table** — The Block of typed fields and rows, kept in a document of its own, listed in the sidebar's Tables section and shown on Pages through Views, whose View tabs lay it out as Table, Board or Calendar (ADR-0309, ADR-0311). The core calls it the Database Block (ADR-0244).
- **Home Page** — The Page a Block was made on, whose document stores the Block. A Table has none.
- **Code Block** — A Block of code with syntax colors that Liquid never runs; a Paragraph turns into one with ``` or the slash command Code (ADR-0302).
- **Media Block** — A Block that shows an image or a file, kept as an attachment (ADR-0305).
- **Whiteboard Block** — A Block whose Drawing lies on a canvas without edges, drawn on in place (ADR-0306).
- **Drawing** — The strokes, shapes and text of a Whiteboard Block, or the ink on an annotated Media Block's pages, each an element that merges on its own (ADR-0306, ADR-0307).
- **Attachment** — A file's bytes in a Workspace, kept in the encrypted replica in parts and named by the SHA-256 of its bytes, so a file added twice is kept once (ADR-0305).
- **Calculation Block** — A Block of lines that each pair a label with a value or formula, laid out as labels left and values right, for reports in Excel's layout (ADR-0244).
- **Section** — The Block of text: its Paragraphs up to `---`, a Block of another type or the Page's edge, kept as one rich text; Arrange mode places it as one tile (ADR-0317).
- **Chat** — Liquid's one kind of conversation, as in WhatsApp: one-to-one or a group, whose participants are people or agents alike; a Block that Pages can show. A planned replacement for separate agent sessions and projects (ADR-0239, ADR-0241).
- **Inbox** — Liquid's one list of what needs the person, from every Chat and Table: agents' approvals and questions, mentions, direct messages and tasks due soon, ordered by when they are due (ADR-0241).
- **Arrange mode** — The explicit Page state that reveals the responsive grid and resize/reorder handles. Outside Arrange mode, a Page never arranged stays a content-first flow, and an arranged Page shows its tiles.
- **Tile** — In Arrange mode, a Section or another Block's View on the Page's 12-column grid, placed by its column and span; it rises as high as the tiles above it allow, in Page order (ADR-0312).
- **Block SDK** — Versioned contract for reusable built-in and Block Registry Block Types: state/migrations, Views, ports/actions, permissions, lifecycle and responsive behavior. It is for product/community extension, not end-user app creation.
- **Block Registry** — Official distribution catalog for reusable Block Types. Community packages are signed, sandboxed and capability-scoped; the initial model loads no arbitrary third-party native code.
- **App** — Workspace-local interactive functionality with versioned state, declared UI, typed actions and explicit capabilities.
- **App Block** — A Block containing one App. It may expose interactive and code-oriented Views and may be shown through Views on multiple Pages.
- **App SDK** — The user/AI-facing contract for building Workspace-local Apps with minimal code, versioned state, declared UI/actions and explicit capabilities. It is distinct from the Block SDK.
- **App Runtime** — Liquid's local sandbox for App code and declarative UI. Restricted JavaScript/TypeScript is the first target; WASM is a later extension.
- **MCP adapter** — Boundary that maps an external MCP server's capabilities into typed, permissioned Liquid App actions. It may support an App Block or a headless integration.
- **App action** — A typed capability declared by an App, invoked by its UI, a Connection, an Automation or an authorized agent through Liquid's CLI/API.
- **Action** — One recorded Workspace mutation: actor (human/Liquid AI/external agent/Meta-Harness/system), origin (UI/CLI/API/Automation/import/sync), target, operation, before/after-or-patch, permission result, review status, `correlation_id` and revert metadata.
- **Mutation pipeline** — The single permissioned path (validate → permission check → diff → apply → record Action → emit event) every Workspace write takes, including UI, Liquid AI, CLI/API, Automation, App and sync writes. No hidden write bypasses it. Canonical: [SECURITY.md](SECURITY.md#liquid-workspace-access--external-agent-edits).
- **Workspace CLI/API** — Liquid's external surface (`liq …` and local API/service) through which agents and integrations discover permitted state and invoke typed reads, mutations and App actions.
- **Liquid AI** — Liquid's built-in Workspace assistant. It runs as a built-in agent profile on an agent host, limited to Liquid actions, and uses the same Role, capability, mutation and History boundaries as external agents (ADR-0229).
- **External agent** — Any agent or tool, including BYOA and Meta-Harness-orchestrated agents, that uses the Workspace CLI/API. Its effective access is scoped, attributed and reversible.
