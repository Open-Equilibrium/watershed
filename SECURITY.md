# Security

Cross-cutting security model for all tools. Do not re-decide these per tool.

Product targets, available capabilities and native release requirements are canonical in [PLATFORMS.md](PLATFORMS.md). A release target never enables an unproven execution boundary.

## Flow Agent security contract

ADR-0166 sets this boundary and ADR-0176 installation trust and launch. Runtime, invocation policy and Executor wire use trusted Tools with mandatory native self-protection on Linux and macOS. [TESTING.md](TESTING.md#native-verification-status) owns native CI results and remaining acceptance gaps. Integration and passing shared-platform tests do not establish native protection or release readiness.

### Guarantees and owners

| Boundary | Flow Agent must enforce | Engineer / Tool responsibility |
|---|---|---|
| Model requests | Only Tools available in the active Flow/Phase, valid declared parameters, legal transitions and existing execution bounds may proceed. Model text and Tool output cannot grant authority. | Configure a suitable Flow and Tools. An allowed request is not proof that the requested action is sensible. |
| Tool effects | No general host filesystem, network or hostile-code containment promise. Validate the invocation, not every instruction subsequently executed by its program. | Trust the complete executable chain, libraries, helpers, services and any project code run by build/test commands. Implement promised path/action limits for adversarial inputs, not only ordinary use. A descriptive Building Block field is not OS enforcement. |
| Flow-owned files | A mandatory native boundary blocks direct Tool/child writes, metadata changes, new hardlinks, deletion and replacement of this installation's protected Flow configuration, registry, runtime/credential stores and installed program objects. Tools cannot choose the protected set or disable it. Missing protection fails before Tool launch. | Do not treat this as whole-host or cross-installation isolation. Privileged actors, controller/OS compromise and effects delegated to independent unconfined services are excluded. File/object discovery and inherited protection require native proof. |
| Configuration changes | The first Flow Agent release provides no Tool-initiated configuration-change path. Direct protected writes remain blocked; no permission prompt or automatic retry lifts the block. | Administrators change configuration manually outside Tool execution. Later proposals belong to the roadmap, not first-release capabilities. |
| Authority integrity | A Tool cannot grant itself authority, widen its own permission, replace enforcement code or silently change the authority of the current Run. | Administrators remain responsible for trusted installation and deliberate out-of-band changes. |
| Effects and recovery | Retain durable intent before effects, bounded I/O and waiting, cancellation of further dispatch, truthful terminal evidence and no automatic replay of uncertain effects. | A successful command is not proof of a correct result. Tool effects on external systems need their own correctness and recovery design. Unknown descendant cleanup must not be reported as complete. |
| Credentials | Never automatically forward Flow-owned provider credentials through Tool environments, requests, results or logs. Retain the provider-authentication contract below. | Write protection alone is not read isolation or secret classification. Deliberately admitted inputs and Tool-returned data may contain secrets. Do not infer credential confidentiality against arbitrary host-authority code. |

Flow's own configuration, context, provider and storage operations are internal runtime responsibilities, not model-selected Tools. The promise is **controlled invocations and workflows with trusted Tool implementations**, not that every runtime file access appears as a Building Block command.

### Native self-protection and its limits

ADR-0176 sets identical public installation guarantees for Linux and macOS. Direct Tool/child writes, deletion and replacement of this installation's protected objects remain blocked. Administrators must not exchange or modify the active installation during Runs. Both OSes require no-follow ownership/identity admission, complete inventory and alias checks, and reject detected installation changes without fallback; their different launch mechanics grant no stronger public promise. Neither OS promises atomic check-to-exec protection against other unconfined host-authority writers; repeated identity checks do not close that interval. A running Tool's native policy is immutable: changed home or program locations protect only later launches, and previously started helpers may outlive bounded waiting. [PROTOCOL.md](PROTOCOL.md#process-and-framing-contract) owns the launch checks.

ADR-0171 excludes only Workspace-local `AGENTS.md` instruction inputs from Flow-owned write protection. They remain editable when the configured Tool permits it. The global `AGENTS.md` inside `FLOW_AGENT_HOME` stays protected with that home; a Workspace pointing at the global home does not turn it into an editable local exception. Neither instruction source grants technical authority, and editable local instructions can still influence model behavior. The filename does not exempt an alias of a protected object. Native acceptance must distinguish editable local instructions from the protected global file and enforce ADR-0169 alias rules.

ADR-0172 permits deliberate installation/home placement inside a Tool-writable directory after a clear warning identifying the retained protected objects and unavailable ancestor moves/deletion. Location approval never grants direct Tool writes to Flow-owned files. Narrower native restrictions remain mandatory; unsafe aliases, unverifiable inventories and unavailable enforcement still prevent launch rather than becoming warning-only exceptions.

Tools and newly started helpers must inherit the direct-write restriction, including when a helper is compromised. Ordinary helper creation must not escape it. A trusted Tool that asks an already-running editor, automation service or remote system to act delegates to that system's separate authority; such effects are not brought inside the boundary by the request. The Engineer must trust that integration. The narrow protection does not certify malicious Tools as safe, their outputs as truthful or project files as confidential.

ADR-0174 limits the first-release protected inventory to this installation's selected global Flow home, its external Flow-owned platform stores and its installed program objects. It covers the entire home (including the global `AGENTS.md`), the entire platform store directory (including `credentials.json` and `executor.json`), current `flow`, the selected Executor and any present official sibling; [PROTOCOL.md](PROTOCOL.md#process-and-framing-contract) owns their admission. Concurrent Runs sharing that home share its protection; there is no automatic discovery or mutual protection of other independent homes, backups or exported copies. Additional-home protection is only a [later discussion](PLAN.md#later-flow-agent-roadmap), not an approved feature.

ADR-0169 accepts the file-layout restrictions: every hardlink name of a protected file must remain inside the protected set; internal publication aliases remain possible, but an outside alias or unverifiable inventory prevents Tool startup with an explanation, never automatic repair. Tools cannot remove or move ancestors containing protected Flow objects. Ordinary unrelated project-file operations remain outside that restriction. The Mac mechanism follows ADR-0172.

ADR-0170 accepts the first-release compatibility cost of denying Tools direct terminal-device access to protect human review; deferring the configuration review feature (ADR-0173) does not lift it. Some interactive programs may be unavailable; a question over ordinary stdin is not inherently terminal-device access. This accepts the restriction, not a blanket claim that all interactive programs fail or that every noninteractive program works. Do not weaken protection or forward credentials as a workaround. A private interactive Tool terminal remains a separate design decision; mechanism approval supplies no missing native integration evidence.

The native Linux x86_64/macOS ARM64 backends give no exact-mount or runtime-read-profile policy, Tool network denial, process/thread ceiling or absolute hostile-descendant cleanup guarantee; [PROTOCOL.md](PROTOCOL.md#native-backend-contract) owns their mechanics. Networking remains available within the host's authority. Neither backend uses per-Tool runtime profiles or systemd/cgroup capacity enforcement. Bounded output, deadlines and cancellation remain required. No automatic unprotected fallback or Linux VM product path on Mac is permitted.

ADR-0172 selects Seatbelt through `/usr/bin/sandbox-exec` for macOS ARM64, accepting the deprecated-interface and OS-update maintenance risk. The integrated backend applies narrow Flow-owned direct-write and terminal restrictions; it is not a general filesystem/network permission product. Checked admission, inherited protection and fail-before-launch behavior require native revalidation, including after OS updates. Supported-version, complete runtime and installation/signing evidence remain release gates in [TESTING.md](TESTING.md).

An additional external sandbox may further restrict Flow and its Tools. It must permit the required runtime storage, provider access and native protection mechanism. Nested compatibility is deployment-specific and requires real tests; failed readiness cannot disable Flow's mandatory protection. Outer containment can strengthen a deployment but never changes Flow's own advertised guarantee or certifies an unsupported platform.

Concurrent Runs do not imply independent OS security domains. The existing user-global configuration authority remains shared, while Run ownership and storage follow `PROTOCOL.md`. Correct Tools may still race on shared project files or exhaust shared memory, disk, CPU or GPU. Coordination and resource planning remain deployment responsibilities; a particular number of parallel agents is not a safety or performance guarantee.

### Configuration boundary

**First Flow Agent release (ADR-0173): manual configuration administration only.** Implement no Tool configuration-proposal protocol, per-Building-Block `ask`/scoped `allow` configuration policy or approval UI. Direct Tool/child writes to protected Flow objects remain blocked, without converting OS errors into prompts. Existing manual authoring, configuration validation and safe publication remain required, as do Flow's internal runtime/storage writes. This deferral neither freezes runtime state nor grants Tools access to trusted administration paths.

Isolation requirements Flow does not enforce (filesystem, network, runtime-profile or process-capacity fields) are rejected before effects, never accepted as ignored security settings. Standard Tool scope and trust UX remain [D-066](docs/decisions/open-decisions.html#d-066).

The deferred configuration feature is on the [later roadmap](PLAN.md#later-flow-agent-roadmap).

The [security architecture and Mermaid case matrix](docs/concept/flow-agent-executor-architecture.md) explain these boundaries without defining a second policy.

## Trust model

Flow Agent's [contract above](#flow-agent-security-contract) governs its invocation and native self-protection boundary. Other products retain their own capability and mutation contracts.

Watershed combines structured Flows, validated invocations, normalized events, policy gates and metric feedback with Liquid's permissioned workspace mutations and action history. Meta-Harness enforces nothing for a harness (ADR-0252); it records sessions and per-turn checkpoints without claiming completeness (ADR-0257). Flow Agent trusts its admitted Tool code; Liquid and Meta-Harness retain their distinct boundaries below. AGPL/free-software transparency lets users inspect, self-host, fork and verify core behavior; it is not a substitute for enforcement.

## Principle: scripts define; enforcement must match the claim

Scripts define available Tools, executable/argument contracts, declared parameters and workflow structure. The harness compiles an invocation policy per Flow and validates each request before effects. The Executor adds controller-selected native protection of Flow-owned objects. Fixture evaluation does not establish OS protection, and command allowlisting does not constrain every effect of trusted program code.

This paragraph governs Flow Agent scripts. Liquid Apps use the parallel [target principle](docs/concept/V-Spec_Liquid.html#apps): App manifests declare capabilities, and the App Runtime plus Role and capability checks enforce them.

### M1.2 Tool execution trust boundary

1. Before durable productive Run reservation, Flow Agent admits the installed Executor and protected inventory and probes readiness. It validates each Tool invocation and synchronizes durable intent before every provider or Tool dispatch. `Ready` grants no launch authority; the matching `Start`, sent only after `tool.started` is committed, is the effect boundary, so pre-`Start` EOF, cancellation or commit failure cannot launch a Tool. Missing terminal evidence after `Start` is uncertain and never retried automatically; [PROTOCOL.md](PROTOCOL.md#m11-codex-subscription-provider) defines the reconciliation command.
2. The Executor rejects unsupported requests before launch and establishes the native restriction only after `Start`. Before the first Tool instruction it checks protected identities and removes unintended inherited handles. Its receipt binds the exact resolved policy and reports `self_protection_active`.
3. The native boundary denies direct Tool/child modification of the admitted Flow objects and their protected ancestry. Tool code and its complete execution/delegation chain remain Engineer-owned trust decisions. Bounded Tool-root supervision does not prove that all hostile descendants ended.

Assigned Tools run without an extra warning or confirmation under their configured Building-Block limits and Executor boundary (ADR-0135); other users may run predefined Flows without widening their authority. The standard installation includes the Default Executor; explicit Custom selection joins the installation's trusted computing base and still requires the same protocol and protection contract. Only explicit Custom selection permits an absent official sibling; any existing sibling remains required to pass admission and be protected.

Building Blocks, model output and Workspace-local files cannot select or replace an Executor. Missing or failed admission/readiness prevents launch without fallback. Custom evidence is structurally checked, not certified as truthful. [PROTOCOL.md](PROTOCOL.md#m12-executor-protocol) owns the wire and backend mechanics; [TESTING.md](TESTING.md#native-verification-status) owns native proof and its limits.

Because scripts are human-reviewable security/capability artifacts, they pass through one private `core-script` Safe-YAML parser into one unambiguous model. It accepts one YAML 1.2 document and rejects duplicate or merge keys, anchors, aliases, explicit tags, nulls, unknown fields and configured resource-budget violations; there is no fallback parser. The checked-in JSON Schema files document the intended shape, existing semantic and registry validation remains authoritative, and the Flow Agent V-Spec defines canonical bytes.

Installation distributes one version/platform-specific `.tar.gz` containing prebuilt artifacts, the installer, version/platform metadata and license, plus `SHA256SUMS`, rather than `.deb` packages. Users download through the browser and verify the selected archive with existing OS tools before extraction or execution; no online bootstrap is included. Ordinary dependencies are explicit. Missing native mechanisms or incompatible host security policy must produce an actionable failure, not automatic kernel upgrades, AppArmor/sysctl changes or service activation. Administrators decide host-wide changes separately. Flow Agent has no systemd user-manager or delegated-cgroup prerequisite; product execution remains unprivileged.

The first Flow Agent release trusts the official [GitHub Releases channel](https://github.com/Open-Equilibrium/watershed/releases) over verified HTTPS, with checksums for the final download bundles. The initial installer is trusted through that channel and the operating system/browser's HTTPS verification, not through self-verification after launch. Matching checksums detect bytes that differ from the published package; they do not independently authenticate a compromised publication channel. An independent build-provenance verifier or separately managed release-signing key is not required for this download contract. Mac signing/notarization requirements of the selected native mechanism remain separate.

[TESTING.md](TESTING.md#native-verification-status) records native installer and release-artifact results. Before the first Flow Agent release, prove clean native installation without compilation or extra developer tools: verify version, platform and final bundle checksum before executing its payload; reject failed HTTPS verification, missing verification data, altered or wrong-target packages; cover every shipped executable and installer byte after any Mac signing/notarization/stapling. Browser HTTPS verification is the selected transport boundary, not an installer networking implementation. Retain the [create-only installer boundary](README.md#download-installation-on-linux-or-macos): use the intended unused prefix, reject unsafe paths, expose privileges/dependencies and recover only this attempt's own files on failure. This adds no in-place upgrade or updater. Development/publication safeguards remain [D-065](docs/decisions/open-decisions.html#d-065); ordinary branch CI does not prove they are active.

Registry access starts from one opened capability for the Global Flow home. Loading opens every registry directory and YAML leaf without following links. M1.1 authoring must open or create each component relative to its already-open parent without following symbolic links, use exclusive no-replace creation, and verify the opened object's type and identity before descent; it never follows a successful path check with an ambient path reopen. This private boundary applies on Flow Agent's [native targets](PLATFORMS.md).

Flow Agent configuration, registry and runtime state live in the private user-global home defined by `PROTOCOL.md`. Workspace `.flow/config.yaml`, Workspace registries and other ambient project configuration have no technical authority and are never probed, merged or used as fallback; enabling a project's Flows is an [accepted target](docs/concept/V-Spec_FlowAgent.html#accepted-target) (ADR-0221). Missing, invalid, inaccessible, unsafe or conflicting global state fails before Run/session mutation. Optional global-home and harness-start Workspace `AGENTS.md` files remain a separate bounded instruction/context channel; their content cannot configure providers, models, registries, Runtime bindings, credentials or resource policy. The runtime store uses owner-only permissions and fails closed when that boundary cannot be established. Run ownership uses [operating-system leases](PROTOCOL.md#local-run-storage-and-m11-conversation-trees), released automatically at process exit. This is concurrency control, not OS isolation: an unconfined peer with the same OS identity can still corrupt runtime state or tamper with leases, and cross-host or durable ownership remains post-M1. Distinct canonical Workspace paths deliberately use distinct runtime stores, never distinct Flow configuration authorities.

Complete-history validation creates only a private per-command scratch index in that Workspace store; it is never conversation state. Unsafe scratch or insufficient admitted space fails before provider or Tool effects. Success, error and later crash recovery remove only the opened index identity and its verified files; replacement, links, unexpected names or mismatched identities fail closed without deleting foreign bytes. Cleanup assumes cooperative writers under the same OS identity; hostile same-identity replacement is outside the M1.1 guarantee.

Conversation storage maintenance and internal failed-creation rollback are defined in [`PROTOCOL.md`](PROTOCOL.md#local-run-storage-and-m11-conversation-trees).

- **Command allowlisting limits names, not effects.** Interpreters, build scripts and hooks can execute further code. A narrow Tool can enforce a finite input/path contract, but command-name approval cannot confine arbitrary executable effects; safe argument handling and the entire invoked code chain remain essential.
- **Agent intent is untrusted (prompt injection / confused-deputy).** Combining untrusted content, private data and an exfiltration path creates a risk that prompt hardening alone cannot eliminate. Flow controls invocation authority; the Engineer must select Tool implementations and deployment boundaries appropriate to the admitted data and effects.

`flow-context-v0` always includes base runtime/security instructions in mandatory Tier 0 and fails before provider contact if they do not fit. This protects instruction integrity and provider-cache consistency, but prompt text remains defense in depth. M1 policy evaluation is a deterministic correctness boundary, not process isolation; native self-protection supplies only the direct-write boundary defined above for real Tool processes.

## Provider authentication

The exact Flow-owned OAuth wire, cache, refresh and local-logout lifecycle is canonical in [`PROTOCOL.md`](PROTOCOL.md#m11-codex-subscription-provider). Flow Agent owns that current-user-protected cache, never imports another client's credentials, and never inserts its own provider credentials, account ids or authentication bodies into events, conversation history, Run Logs, diagnostics, exports or Tool environments. A definitive provider failure may persist and display the provider's direct message under the bounded contract in `PROTOCOL.md`; provider-supplied content remains the provider's responsibility. Local inference and portable continuation are [accepted targets](docs/concept/V-Spec_FlowAgent.html#accepted-target) with no current guarantee.

## MVP VCS boundary

Flow Agent runs inside normal Git projects in the MVP, but it does not own project history and does not implement project VCS behavior. Auditability comes from deterministic Flow state, structured logs, protocol events, manual configuration records and policy decisions; it does not come from an OS sandbox. Host Git may run only as an explicitly declared Tool and receives the same execution boundary as every other Tool; its implementation and invoked project code remain part of the Engineer's trust decision under ADR-0166.

Meta-Harness Git operations on agent projects (ADR-0190) run on its own host under the host-local execution ownership [below](#meta-harness-execution-ownership); Liquid only presents them.

- **Git and credentials:** they use the host's `git` and `gh`, started without inherited variables that point Git at another repository or index. `git`'s credential helper and `gh`'s login keep the credentials; Watershed never reads them.
- **Watershed runs no Git write without an explicit user action** (ADR-0191), with two exceptions, both as T3 Code does:
  - While a session is open, Meta-Harness fetches the remote of the branch's upstream every 15 seconds. This only updates its remote-tracking branches, without tags, maintenance or credential prompts, and keeps credentials in a remote's URL out of its errors. It holds as far as Git expresses where a fetch writes: its refspecs, remote groups, legacy remote definitions and symbolic refs, which Liquid checks before it fetches. Links placed inside the repository's Git directory belong to the repository, as for Git itself and as for the project Git settings ADR-0210 accepts.
  - Meta-Harness stores the agent project's files at each turn as commits under its own refs in the project repository, so Liquid can show each turn's changes and revert the files to an earlier turn (ADR-0220). They hold no file Git ignores.
- **Revert:** a revert lists its files first and runs only while the project still matches that confirmed list, the branch and the ignored files in its way, refusing before any write otherwise (ADR-0256). It leaves the project's index alone.
- **Running agents lock the checkout:** each running agent marks its checkout with an OS file lock under `<git-dir>/watershed/` (ADR-0234). A revert, committing, pulling, switching branches and stashing, restoring or discarding stashed changes are refused under that lock. Restoring a stash is refused before any write where it would change or delete files inside a nested repository. A window's shown session (ADR-0271) holds a shared lock on a name in `<git-dir>/watershed/shown`; it does not block these writes, but deleting that session is refused while any window of the project holds it.
- **Outside Git:** a turn holds a shared lock in the user's lock folder (ADR-0267), keyed by its canonical project folder, until it ends. The folder is Liquid's app folder under `~/Library/Application Support` on macOS, and on Linux `$XDG_RUNTIME_DIR` or else Liquid's config folder; the temporary folder is never used. Its namespace uses mode `0700`, verifies the current OS user owns it, and refuses links or directories writable by other users. Initialize Git takes it alone, refusing any running agent in that folder across Liquid windows with the revert notice; so does deleting a stored session, which a window showing it also refuses (ADR-0271). A starting turn waits for initialization before taking the checkout lock.
- **Hooks:** Liquid's explicit commit, branch switch, push and pull run the host's Git and project hooks to completion without credential prompts. The agent, which runs with the user's permissions, may have written those hooks.
- **Pull** fetches with the background fetch's destination checks and fast-forwards only. It refuses before Git writes where it would overwrite files Git ignores, and holds the checkout lock through Git and its hooks.
- **Push destination:** push requires one resolved fetch URL and one resolved push URL for the same repository, compared with URL credentials stripped but an SSH URL's user name kept. Separate or multiple push destinations, including URL rewrites and push-remote defaults pointing elsewhere, are refused before any push or hook, with an error notice directing the user to Git and stating that nothing was pushed.
- **What push sends:** push disables submodule recursion and sends only the current branch to its upstream (origin, or the only configured remote, under its own name before its first push). It never forces, and asks before pushing to the remote's default branch, also through a symbolic ref naming it; that approval is bound to the branch, repository, destination and commit. Push needs no checkout lock, so an agent turn does not block it.
- **Fetch on request** uses the background fetch's destination checks too. All fetches serialize across instances, processes and worktrees through a file lock in the common Git directory.
- **Other Git writers:** Liquid does not coordinate external Git writers beyond Git's own protections. Git drops a stash only by its place in the shared list, so Liquid applies and drops only its own entry of a stash commit. Should another Git have shifted the list, Liquid puts any other entry Git dropped, also one of the same commit, straight back with its commit but not always its message before it tries again, or names that stash's commit for recovery when Git refuses to.

Pull requests and worktree removal (implemented; creating worktrees waits for Chats, [Meta-Harness V-Spec](docs/concept/V-Spec_MetaHarness.html#git-integration)):

- **Who sees the material:** the Chat's own model writes a pull request's title and description, so its commit range and diff, and in “Commit, push & create PR” the selected uncommitted files (all start selected, so its first text covers every one listed), go to that Chat's provider and no other. Without a model the latest commit fills them.
- **How the model is asked:** Meta-Harness asks it through a separate one-shot pi in an empty private temporary folder, without session, tools, extensions, MCP, skills, context files or project resources, so the text it reads cannot run anything. pi uses its own login, the commits are named only by full ids, Git runs no external diff, text conversion or signature program, at most 64 KiB of patch goes out, and pi ends by itself or is stopped after 60 seconds.
- **Waiting:** Liquid stops waiting earlier when the dialog closes, Create is pressed or the commits or selected files change, but that never kills pi, which could leave its login half stored; each such user action starts at most one pi. Its answer only fills the editable fields the user has not changed and reaches GitHub only as reviewed.
- **Target and head:** a fork's pull request targets GitHub's parent of the pushed head repository; Push still sends only to the branch's own remote under the checks above. The head must be the branch's pushed upstream under Push's destination checks.
- **gh:** Liquid runs the host's `gh` without prompts and never reads its credentials. A host other than github.com counts as GitHub only when that `gh` has a login for it, which Liquid checks before any request names the host. Text typed in the base dialog reaches the target repository's GitHub as a branch-name search. An SSH alias in an scp-like remote URL counts as github.com only when plain `ssh -G` resolves it to GitHub's SSH host on port 22 or 443; Git's own ssh command must be plain `ssh` too (ADR-0269).
- **Creating:** creating a pull request or reading its status takes no checkout lock and changes no Git state; creation rechecks the reviewed head, base and target first. GitHub creates a pull request from a branch, not a commit, so commits pushed to the head from elsewhere after that recheck join the new pull request unreviewed, an accepted risk as in T3 Code.
- **Removing a worktree:** on request it never forces and is refused while staged, unstaged, untracked, ignored or index-hidden (assumed unchanged or skipped) files remain, or while a detached worktree holds commits no branch has; branch, commits and stashes stay. Liquid removes only a linked worktree Git lists, never the main checkout or the window's own, rechecks it with the repository and that checkout held alone and has Git remove it without force; a file a program outside Liquid writes there during removal is not protected. Removing a worktree takes the exclusive common Git guard and is refused while any turn in the repository runs.

## Meta-Harness execution ownership

Execution ownership is host-local: the Meta-Harness core, embedded in Liquid (ADR-0184), controls only the whole CLI agent processes it starts on its own host. Remote access and command routing are an [accepted target](docs/concept/V-Spec_MetaHarness.html#remote-control).

## Meta-Harness agent sessions

Meta-Harness leaves governance to the harness (ADR-0252): Watershed adds no tool approvals, and the agent, its extensions and every tool call run with the user's operating-system permissions; pi has no sandbox. Agent events waiting for Liquid are bounded by count, not bytes, so a misbehaving agent or extension that sends huge events can exhaust Liquid's memory, an accepted risk of a trusted agent (ADR-0273). A session starts only once pi confirms that it loaded the Watershed extension file the core named, which marks each turn's checkpoints (ADR-0234), and every message that may start a run checks again, since pi loads extensions anew for each session and an extension can switch sessions unseen; a command that switches sessions and starts a run in one step is not caught.

The tool names and targets the chat and Trajectory show, and the Diff tab's file names and lines, write out the characters that could hide or reorder what a call does or changed, such as `<U+202E>`, and the `<` of a literal `<U+`, so no two calls look alike: control, format and bidirectional control characters and those Unicode lets renderers ignore; look-alike letters and right-to-left letters, which still reorder the punctuation and digits beside them, are not marked. In the Diff tab, a carriage return that ends a line, as in Windows line ends, shows as a faint ␍ instead. A line longer than 1,000 characters shows its first 1,000 and a faint …; a change after that point does not show. An agent question closes menus and dialogs above it and takes keys and clicks only 0.5 s after it appears or Liquid comes back in front, so keys typed and clicks made before it could be read answer nothing; no command acts on a held key, so a key held through an answer does nothing more, and a question's field ignores a key held from before it appeared.

The agent can change any file the user can, including settings that run commands: shell profiles, launch agents, pi extensions loaded at pi's next start, and Git settings. The Diff tab's snapshots run the host's `git` in the project with hooks, file monitors and textconv off, but other Git settings, such as clean filters and, when a revert writes files back, smudge filters, still run, so a project can make Liquid itself run a command (ADR-0206); a revert leaves submodules and nested repositories alone and lists ignored files it must delete to restore a file; a Git past its time limit ends together with the programs it started that stay in its process group (ADR-0210). Snapshots override the project settings and index marks known to let Git skip a changed file or its mode, except a skip-worktree mark on a file missing from disk while sparse checkout is on, so that a file outside the sparse set is not listed as deleted and deleting a marked file there does not show; the diff shows what Git sees, so ignored files, the `.git` folder, edits inside submodules or nested repositories, nested repositories without a commit and new commits of a submodule the project's `.gitmodules` ignores do not appear, while new commits that diff settings would hide do; the Diff tab is a convenience and claims no completeness (ADR-0210). Watershed closes only cheap record gaps, such as nested tool calls, and builds no write recording or process tracing to make the Diff or Trajectory complete (ADR-0222). Hiding whitespace changes, a choice Liquid keeps, also hides changes whose whitespace alters meaning, such as a space inside a shell command or Python indentation.

## Liquid workspace access & external-agent edits

Liquid's shipped Workspace core enforces:

- Every Workspace write goes through one mutation pipeline (permission check, validation, atomic apply) and is recorded as an Action with its actor, origin and permission result; no write reaches a Workspace document any other way. The pipeline allows only the Workspace's owner, who holds Can manage, and refuses every other actor.
- Each device keeps its replica in SQLite encrypted with SQLCipher; the key lives in the operating system's keystore ([client architecture](docs/concept/liquid-client-architecture.md#storage), ADR-0237).

Accepted agent-host risk (ADR-0254): Watershed puts no sandbox around a harness (ADR-0252). An agent host runs agents under the account it is installed on, so its agents reach what that account reaches: on a person's own account they can delete or damage Liquid's data folder; the replica key stays Liquid's on macOS, whose keychain releases it only to Liquid, while on Linux the Secret Service and on Windows the Credential Manager release it to any program of the user; and Meta-Harness in WSL sees the Windows drives, Liquid's data folder included, unless WSL's automount is turned off. Whoever wants agents apart sets Meta-Harness up in a VM, a container, another account or on another computer and links it as an agent host.

## Supply chain

Dependency hygiene: committed lockfiles, exact pins and minimal dependencies; CI runs `cargo audit` (RustSec advisories), `cargo deny` (license/bans/sources/advisory policy via `deny.toml`) and `pnpm audit`. `cargo vet` remains an optional later addition. Rust reduces but does not eliminate supply-chain risk (`build.rs`/proc-macros run at build time); future isolated runtimes must limit blast radius regardless of language.

## M0/M1 policy-emulation scope

Fixture execution checks modeled invocation decisions in process; it never proves native protection. The retained `agent-negative` workloads exercise forbidden-write, network/DNS, environment, out-of-phase, link and interpreter failure lifecycles through explicit fixture labels. Those scenario names do not grant or assert productive filesystem/network containment. Own-script fixture output remains create-only: an existing leaf rejects before runtime or temporary-file mutation; output replacement remains [D-056](docs/decisions/open-decisions.html#d-056).

### M0 policy artifact contract

`core-policy` emits canonical invocation-policy JSON for review and deterministic tests. Serialization follows [PROTOCOL.md](PROTOCOL.md#canonical-protocol-json-serialization-v0), with a final LF. It has no OS target, filesystem/network policy, runtime-read profile or process/thread capacity field; isolation fields are rejected by the closed schema.

| Field | Contract |
|---|---|
| `policy_version` | Fixed string `"0"`. |
| `source_flow_definition_id` | Resolved Flow definition id. |
| `commands` | Tool invocation records; canonical shape and validation live in [CommandPolicy](core/core-policy/src/artifact/command.rs). |
| `phase_scope` | `{phase_id, tool_ids}` records defining available Tools. |
| `runtime_limits` | `{headless, timeout_ms}`; Boolean headless flag and integer deadline. |

Each command records `tool_id`, `tool_kind`, `command_id`, `executable`, literal `argv`, `allowed_parameters`, `environment` and, only for own-script Tools, `script_runtime: "posix-sh"`. Predefined commands resolve through the trusted registry; own-script commands use `script:<tool-id>` and the fixed POSIX-shell runner. Productive invocation uses the verified executable and literal arguments without `PATH` lookup, shell parsing, expansion or globbing by Flow. Parsing the reviewed own-script body remains part of that Tool's trusted semantics. U+0000 in execution-vector strings rejects before spawn.

Parameter contracts define exact names, kinds, required values and their applicable enum/string/path/integer constraints. Unknown parameters, extra positional arguments and invalid values reject before launch; their rendering is canonical in [PROTOCOL.md](PROTOCOL.md#m11-runtime-values).

`environment` is `{default: "clear", allow}`, with exact Engineer-selected host variable names matching `^[A-Z_][A-Z0-9_]{0,63}$`. The current script compiler emits `allow: []`. Artifacts/events contain no environment values; the resolved request carries only explicitly admitted values. Flow performs no automatic secret classification of configured values, and never forwards its own provider credentials.

Commands sort by `tool_id`; allowed parameters by `name`, enum values and environment names lexicographically; Phase scopes by `phase_id` and their Tool ids lexicographically. Literal `argv` order is preserved. New arrays must preserve schema order or define a sort key before fixture publication.
