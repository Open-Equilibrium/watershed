# Security

Cross-cutting security model for all tools. Do not re-decide these per tool.

Product targets, available capabilities and native release requirements are canonical in [PLATFORMS.md](PLATFORMS.md). A release target never enables an unproven execution boundary.

## Flow Agent security contract

ADR-0166 sets this boundary and ADR-0176 installation trust and launch. Runtime, invocation policy and Executor wire use trusted Tools with mandatory Flow-owned write protection on Linux and macOS. [TESTING.md](TESTING.md#native-verification-status) owns native CI results and remaining acceptance gaps. Integration and passing shared-platform tests do not establish Flow-owned write protection or release readiness.

### Guarantees and owners

| Boundary | Flow Agent must enforce | Engineer / Tool responsibility |
|---|---|---|
| Model requests | Only Tools available in the active Flow/Phase, valid declared parameters, legal transitions and existing execution bounds may proceed. Model text and Tool output cannot grant authority. | Configure a suitable Flow and Tools. An allowed request is not proof that the requested action is sensible. |
| Tool effects | No general host filesystem, network or hostile-code containment promise. Validate the invocation, not every instruction subsequently executed by its program. | Trust the complete executable chain, libraries, helpers, services and any project code run by build/test commands. Implement promised path/action limits for adversarial inputs, not only ordinary use. A descriptive Building Block field is not OS enforcement. |
| Flow-owned files | Mandatory Flow-owned write protection blocks direct Tool/child writes, metadata changes, new hardlinks, deletion and replacement of this installation's protected Flow configuration, registry, runtime/credential stores and installed program objects. Tools cannot choose the protected set or disable it. Missing protection fails before Tool launch. | Do not treat this as whole-host or cross-installation isolation. Privileged actors, controller/OS compromise and effects delegated to independent unconfined services are excluded. File/object discovery and inherited protection require native proof. |
| Configuration changes | The first Flow Agent release provides no Tool-initiated configuration-change path. Direct protected writes remain blocked; no permission prompt or automatic retry lifts the block. | Administrators change configuration manually outside Tool execution. Later proposals belong to the roadmap, not first-release capabilities. |
| Authority integrity | A Tool cannot grant itself authority, widen its own permission, replace enforcement code or silently change the authority of the current Run. | Administrators remain responsible for trusted installation and deliberate out-of-band changes. |
| Effects and recovery | Retain durable intent before effects, bounded I/O and waiting, cancellation of further dispatch, truthful terminal evidence and no automatic replay of uncertain effects. A Tool whose processes may outlive its cleanup keeps its Executor answer, records that cleanup is unknown and stops the Run; a surviving group after any other answer fails stop. | A successful command is not proof of a correct result. Tool effects on external systems need their own correctness and recovery design. Unknown descendant cleanup must not be reported as complete. |
| Credentials | Never automatically forward Flow-owned provider credentials through Tool environments, requests, results or logs. Retain the provider-authentication contract below. | Write protection alone is not read isolation or secret classification. Deliberately admitted inputs and Tool-returned data may contain secrets. Do not infer credential confidentiality against arbitrary host-authority code. |

Flow's own configuration, context, provider and storage operations are internal runtime responsibilities, not model-selected Tools. The promise is **controlled invocations and workflows with trusted Tool implementations**, not that every runtime file access appears as a Building Block command.

### Flow-owned write protection and its limits

ADR-0176 sets identical public installation guarantees for Linux and macOS. Direct Tool/child writes, deletion and replacement of this installation's protected objects remain blocked. Administrators must not exchange or modify the active installation during Runs. Both OSes require no-follow ownership/identity admission, complete inventory and alias checks, and reject detected installation changes without fallback; their different launch mechanics grant no stronger public promise. Neither OS promises atomic check-to-exec protection against other unconfined host-authority writers; repeated identity checks do not close that interval. A running Tool's native policy is immutable: changed home or program locations protect only later launches, and previously started helpers may outlive bounded waiting. [PROTOCOL.md](PROTOCOL.md#process-and-framing-contract) owns the launch checks.

ADR-0171 excludes only Workspace-local `AGENTS.md` instruction inputs from Flow-owned write protection. They remain editable when the configured Tool permits it. The global `AGENTS.md` inside `FLOW_AGENT_HOME` stays protected with that home; a Workspace pointing at the global home does not turn it into an editable local exception. Neither instruction source grants technical authority, and editable local instructions can still influence model behavior. The filename does not exempt an alias of a protected object. Native acceptance must distinguish editable local instructions from the protected global file and enforce ADR-0169 alias rules.

ADR-0172 permits deliberate installation/home placement inside a Tool-writable directory after a clear warning identifying the retained protected objects and unavailable ancestor moves/deletion. Location approval never grants direct Tool writes to Flow-owned files. Narrower native restrictions remain mandatory; unsafe aliases, unverifiable inventories and unavailable enforcement still prevent launch rather than becoming warning-only exceptions.

Tools and newly started helpers must inherit the direct-write restriction, including when a helper is compromised. Ordinary helper creation must not escape it. A trusted Tool that asks an already-running editor, automation service or remote system to act delegates to that system's separate authority; such effects are not brought inside the boundary by the request. The Engineer must trust that integration. The narrow protection does not certify malicious Tools as safe, their outputs as truthful or project files as confidential.

ADR-0174 limits the first-release protected inventory to this installation's selected global Flow home, its external Flow-owned platform stores and its installed program objects. It covers the entire home (including the global `AGENTS.md`), the entire platform store directory (including `credentials.json` and `executor.json`), current `flow`, the selected Executor and any present official sibling; [PROTOCOL.md](PROTOCOL.md#process-and-framing-contract) owns their admission. Concurrent Runs sharing that home share its protection; there is no automatic discovery or mutual protection of other independent homes, backups or exported copies. Additional-home protection is only a [later discussion](PLAN.md#later-flow-agent-roadmap), not an approved feature.

ADR-0169 accepts the file-layout restrictions: every hardlink name of a protected file must remain inside the protected set; internal publication aliases remain possible, but an outside alias or unverifiable inventory prevents Tool startup with an explanation, never automatic repair. Tools cannot remove or move ancestors containing protected Flow objects. Ordinary unrelated project-file operations remain outside that restriction. The Mac mechanism follows ADR-0172.

ADR-0170 accepts the first-release compatibility cost of denying Tools direct terminal-device access to protect human review; deferring the configuration review feature (ADR-0173) does not lift it. Some interactive programs may be unavailable; a question over ordinary stdin is not inherently terminal-device access. This accepts the restriction, not a blanket claim that all interactive programs fail or that every noninteractive program works. Do not weaken protection or forward credentials as a workaround. A private interactive Tool terminal remains a separate design decision; mechanism approval supplies no missing native integration evidence.

The native Linux x86_64/macOS ARM64 backends give no exact-mount or runtime-read-profile policy, Tool network denial, process/thread ceiling or absolute hostile-descendant cleanup guarantee; [PROTOCOL.md](PROTOCOL.md#native-backend-contract) owns their mechanics. Networking remains available within the host's authority. Neither backend uses per-Tool runtime profiles or systemd/cgroup capacity enforcement. Bounded output, deadlines and cancellation remain required. No automatic unprotected fallback or Linux VM product path on Mac is permitted.

ADR-0172 selects Seatbelt through `/usr/bin/sandbox-exec` for macOS ARM64, accepting the deprecated-interface and OS-update maintenance risk. The integrated backend applies narrow Flow-owned direct-write and terminal restrictions; it is not a general filesystem/network permission product. Checked admission, inherited protection and fail-before-launch behavior require native revalidation, including after OS updates. Supported-version, complete runtime and installation/signing evidence remain release gates in [TESTING.md](TESTING.md).

Bubblewrap below 0.12.0 follows a symlink when it creates a mount destination during setup ([CVE-2026-87766](https://github.com/containers/bubblewrap/security/advisories/GHSA-pxhw-h44j-8pfx)), and Ubuntu 24.04's package has no fix yet. Flow's arguments create no destination: every bind target exists, and every ancestor of a protected object is itself a bind point, which a Tool in an earlier sandbox cannot rename or replace. A process outside every Flow sandbox could swap a path, but it already writes with the same account's authority.

An additional external sandbox may further restrict Flow and its Tools. It must permit the required runtime storage, provider access and the native mechanism for Flow-owned write protection. Nested compatibility is deployment-specific and requires real tests; failed readiness cannot disable Flow's mandatory protection. Outer containment can strengthen a deployment but never changes Flow's own advertised guarantee or certifies an unsupported platform.

Concurrent Runs do not imply independent OS security domains. The existing user-global configuration authority remains shared, while Run ownership and storage follow `PROTOCOL.md`. Correct Tools may still race on shared project files or exhaust shared memory, disk, CPU or GPU. Coordination and resource planning remain deployment responsibilities; a particular number of parallel agents is not a safety or performance guarantee.

### Configuration boundary

**First Flow Agent release (ADR-0173): manual configuration administration only.** Implement no Tool configuration-proposal protocol, per-Building-Block `ask`/scoped `allow` configuration policy or approval UI. Direct Tool/child writes to protected Flow objects remain blocked, without converting OS errors into prompts. Existing manual authoring, configuration validation and safe publication remain required, as do Flow's internal runtime/storage writes. This deferral neither freezes runtime state nor grants Tools access to trusted administration paths.

Isolation requirements Flow does not enforce (filesystem, network, runtime-profile or process-capacity fields) are rejected before effects, never accepted as ignored security settings. Standard Tool scope and trust UX remain [D-066](docs/decisions/open-decisions.html#d-066).

The deferred configuration feature is on the [later roadmap](PLAN.md#later-flow-agent-roadmap).

The [security architecture and Mermaid case matrix](docs/concept/flow-agent-executor-architecture.md) explain these boundaries without defining a second policy.

Report suspected vulnerabilities privately to **b-weber@gmx.at** — please do not open public issues for security problems. Include reproduction steps and affected files/components where possible. Reports are handled on a **best-effort basis**: this project gives **no guarantees** of response time, fixes, or any warranty of any kind; the software is provided "as is" (see `LICENSE`, AGPL-3.0-only §15–16). ## Trust model

Flow Agent's [contract above](#flow-agent-security-contract) governs its invocation and Flow-owned write protection. Other products retain their own capability and mutation contracts.

Watershed combines structured Flows, validated invocations, normalized events, policy gates and metric feedback with Liquid's permissioned workspace mutations and action history. Meta-Harness enforces nothing for a harness (ADR-0252); its T3 server records sessions and per-turn checkpoints without claiming completeness (ADR-0257). Flow Agent trusts its admitted Tool code; Liquid and Meta-Harness retain their distinct boundaries below. AGPL/free-software transparency lets users inspect, self-host, fork and verify core behavior; it is not a substitute for enforcement.

## Principle: scripts define; enforcement must match the claim

Scripts define available Tools, executable/argument contracts, declared parameters and workflow structure. The harness compiles an invocation policy per Flow and validates each request before effects. Executed and sent text is the reviewed text: non-NFC definition text and Executor argument or environment values are refused, never converted ([PROTOCOL.md](PROTOCOL.md#m11-authoring-cli-grammar)). The Executor applies controller-selected Flow-owned write protection. Fixture evaluation does not establish OS protection.

This paragraph governs Flow Agent scripts. Liquid Apps use the parallel [target principle](docs/concept/V-Spec_Liquid.html#apps): App manifests declare capabilities, and the App Runtime plus Role and capability checks enforce them.

### M1.2 Tool execution trust boundary

1. Before durable productive Run reservation, Flow Agent admits the installed Executor and protected inventory and probes readiness. It validates each Tool invocation and synchronizes durable intent before every provider or Tool dispatch. `Ready` grants no launch authority; the matching `Start`, sent only after `tool.started` is committed, is the effect boundary, so pre-`Start` EOF, cancellation or commit failure cannot launch a Tool. Missing terminal evidence after `Start` is uncertain and never retried automatically; [PROTOCOL.md](PROTOCOL.md#m11-codex-subscription-provider) defines the reconciliation command.
2. The Executor rejects unsupported requests before launch and establishes the native restriction only after `Start`. Before the first Tool instruction it checks protected identities and removes unintended inherited handles. Its receipt binds the exact resolved policy and reports `flow_owned_write_protection_active`.
3. Flow-owned write protection denies direct Tool/child modification of the admitted Flow objects and their protected ancestry. Tool code and its complete execution/delegation chain remain Engineer-owned trust decisions. Bounded Tool-root supervision does not prove that all hostile descendants ended.

Assigned Tools run without an extra warning or confirmation under their configured Building-Block limits and the Executor (ADR-0135); other users may run predefined Flows without widening their authority. The standard installation includes the Default Executor; explicit Custom selection joins the installation's trusted computing base and still requires the same protocol and protection contract. Only explicit Custom selection permits an absent official sibling; any existing sibling remains required to pass admission and be protected.

Building Blocks, model output and Workspace-local files cannot select or replace an Executor. Missing or failed admission/readiness prevents launch without fallback. Custom evidence is structurally checked, not certified as truthful. [PROTOCOL.md](PROTOCOL.md#m12-executor-protocol) owns the wire and backend mechanics; [TESTING.md](TESTING.md#native-verification-status) owns native proof and its limits.

Because scripts are human-reviewable security/capability artifacts, they pass through one private `core-script` Safe-YAML parser into one unambiguous model. It accepts one YAML 1.2 document and rejects duplicate or merge keys, anchors, aliases, explicit tags, nulls, unknown fields and configured resource-budget violations; there is no fallback parser. The checked-in JSON Schema documents the intended shape, existing semantic and registry validation remains authoritative, and the Flow Agent V-Spec defines canonical bytes.

Installation distributes one version/platform-specific `.tar.gz` containing prebuilt artifacts, the installer, version/platform metadata and license, plus `SHA256SUMS`. Users download through the browser and verify the selected archive with existing OS tools before extraction or execution; no online bootstrap is included. Ordinary dependencies are explicit. Missing native mechanisms or incompatible host security policy must produce an actionable failure, not automatic kernel upgrades, AppArmor/sysctl changes or service activation. Administrators decide host-wide changes separately. Product execution remains unprivileged.

The first Flow Agent release trusts the official [GitHub Releases channel](https://github.com/Open-Equilibrium/watershed/releases) over verified HTTPS, with checksums for the final download bundles. The initial installer is trusted through that channel and the operating system/browser's HTTPS verification, not through self-verification after launch. Matching checksums detect bytes that differ from the published package; they do not independently authenticate a compromised publication channel. An independent build-provenance verifier or separately managed release-signing key is not required for this download contract. Mac signing/notarization requirements of the selected native mechanism remain separate.

[TESTING.md](TESTING.md#native-verification-status) records native installer and release-artifact results. Browser HTTPS verification is the selected transport boundary, not an installer networking implementation. Release acceptance is in [TESTING.md](TESTING.md#replacement-acceptance-matrix). Retain the [create-only installer boundary](README.md#download-installation-on-linux-or-macos): use the intended unused prefix, reject unsafe paths, expose privileges/dependencies and recover only this attempt's own files on failure. This adds no in-place upgrade or updater. Development/publication safeguards remain [D-065](docs/decisions/open-decisions.html#d-065); ordinary branch CI does not prove they are active.

Registry access starts from one opened capability for the Global Flow home. Loading opens every registry directory and YAML leaf without following links. M1.1 authoring must open or create each component relative to its already-open parent without following symbolic links, use exclusive no-replace creation, and verify the opened object's type and identity before descent; it never follows a successful path check with an ambient path reopen. This private boundary applies on Flow Agent's [native targets](PLATFORMS.md).

Flow Agent configuration, registry and runtime state live in the private user-global home defined by `PROTOCOL.md`. Workspace `.flow/config.yaml`, Workspace registries and other ambient project configuration have no technical authority and are never probed, merged or used as fallback; enabling a project's Flows is an [accepted target](docs/concept/V-Spec_FlowAgent.html#accepted-target) (ADR-0221). Missing, invalid, inaccessible, unsafe or conflicting global state fails before Run/session mutation. Optional global-home and harness-start Workspace `AGENTS.md` files remain a separate bounded instruction/context channel; their content cannot configure providers, models, registries, Runtime bindings, credentials or resource policy. The runtime store uses owner-only permissions and fails closed when that boundary cannot be established. Run ownership uses [operating-system leases](PROTOCOL.md#local-run-storage-and-m11-conversation-trees), released automatically at process exit. This is concurrency control, not Flow-owned write protection: an unconfined peer with the same OS identity can still corrupt runtime state or tamper with leases, and cross-host or durable ownership remains post-M1. Distinct canonical Workspace paths deliberately use distinct runtime stores, never distinct Flow configuration authorities.

Complete-history validation creates only a private per-command scratch index in that Workspace store; it is never conversation state. Unsafe scratch or insufficient admitted space fails before provider or Tool effects. Success, error and later crash recovery remove only the opened index identity and its verified files; replacement, links, unexpected names or mismatched identities fail closed without deleting foreign bytes. Cleanup assumes cooperative writers under the same OS identity; hostile same-identity replacement is outside the M1.1 guarantee.

Conversation storage maintenance and internal failed-creation rollback are defined in [`PROTOCOL.md`](PROTOCOL.md#local-run-storage-and-m11-conversation-trees).

- **Command allowlisting limits names, not effects.** Interpreters, build scripts and hooks can execute further code. A narrow Tool can enforce a finite input/path contract, but command-name approval cannot confine arbitrary executable effects; safe argument handling and the entire invoked code chain remain essential.
- **Agent intent is untrusted (prompt injection / confused-deputy).** Combining untrusted content, private data and an exfiltration path creates a risk that prompt hardening alone cannot eliminate. Flow controls invocation authority; the Engineer must select Tool implementations and deployment boundaries appropriate to the admitted data and effects.

`flow-context-v0` always includes base runtime/security instructions in mandatory Tier 0 and fails before provider contact if they do not fit. This protects instruction integrity and provider-cache consistency, but prompt text remains defense in depth. M1 policy evaluation is a deterministic correctness boundary, not process isolation; Flow-owned write protection supplies only the direct-write boundary defined above for real Tool processes.

## Provider authentication

The exact Flow-owned OAuth wire, cache, refresh and local-logout lifecycle is canonical in [`PROTOCOL.md`](PROTOCOL.md#m11-codex-subscription-provider). Flow Agent owns that current-user-protected cache, never imports another client's credentials, and never inserts its own provider credentials, account ids or authentication bodies into events, conversation history, Run Logs, diagnostics, exports or Tool environments. A definitive provider failure may persist and display the provider's direct message under the bounded contract in `PROTOCOL.md`; provider-supplied content remains the provider's responsibility. The [M1.1 budget matrix](flow-agent/benchmarks/M1_1_BUDGETS.md) selects the provider parser and temporal bounds, whose evidence must pass before productive behavior is enabled.

The OpenAI-compatible endpoint provider ([ADR-0263](docs/adr/ADR-LOG.md), [PROTOCOL.md](PROTOCOL.md#m11-openai-compatible-endpoint-provider)) keeps its API key in the same owner-only credential store as the subscription record, in its own slot beside the base URL it was issued for, so the key is sent only to that host. The base URL must be `https`, or `http` only for a loopback IP literal, and the key is never sent to a redirect target. The endpoint operator receives the prompts and Tool results of every Run it serves; this is accepted because the operator chose the endpoint. The key never appears in events, Run Logs, diagnostics or errors, and its `Debug` output is redacted.

Local inference and portable continuation are [accepted targets](docs/concept/V-Spec_FlowAgent.html#accepted-target) with no current guarantee.

## MVP VCS boundary

Flow Agent runs inside normal Git projects in the MVP, but it does not own project history and does not implement project VCS behavior. Auditability comes from deterministic Flow state, structured logs, protocol events, manual configuration records and policy decisions; it does not come from an OS sandbox. Host Git may run only as an explicitly declared Tool and receives the same execution boundary as every other Tool; its implementation and invoked project code remain part of the Engineer's trust decision under ADR-0166.

Git on agent projects is T3 Code's, with its behavior as shipped (ADR-0282): Meta-Harness's own T3 server runs it on its host, and Liquid only presents it. Watershed adds no Git rule of its own and claims none of T3's behavior as its guarantee.

- **Checkpoints:** T3 stores each turn's files as commits under `refs/t3/` in the project's repository and restores files only for a session in its own worktree, which T3 keeps under its data folder.
- **Writes:** T3 runs the host's `git`, its hooks and the provider login it finds (for GitHub, `gh`'s token); Watershed never reads these credentials. Commit, push, pull request, its Ready and Merge actions, and publish run only on the person's action; T3's background fetch updates remote-tracking branches.
- **Writer model:** a commit message left blank, a pull request's title and description and a session's title are written by the one writer model the person chose (ADR-0294), so the staged changes, the branch's commits and diff go to that model's provider, whichever provider the session uses.

## Meta-Harness execution ownership

Execution ownership is host-local: the Meta-Harness service controls only the whole CLI agent processes its T3 Code server starts on its own host. Remote access and command routing are an [accepted target](docs/concept/V-Spec_MetaHarness.html#remote-control).

## Meta-Harness agent sessions

Meta-Harness starts its own T3 Code server at the pinned version (ADR-0281) on 127.0.0.1 only, with telemetry off and without the activity publishing that `t3 connect` would set up. It authenticates as T3's owner with a bearer token it issues locally for each connection and never logs. T3's data folder belongs to one Meta-Harness service. Before a new T3 server starts, the process named in the folder's `server-runtime.json` is stopped if it still runs the pinned `t3 serve`, such as a server a dead Meta-Harness left running.

Meta-Harness leaves governance to the harness (ADR-0252). What an agent may do without asking is T3's Permissions choice, Full access by default as in T3; then the agent and every tool call run with the user's operating-system permissions. The queue to Liquid is bounded by count, not bytes: at most 256 events are sent and unconfirmed and at most 256 more wait, merged; past that, waiting streaming text is dropped and Liquid reloads the Chat from a snapshot (ADR-0272, ADR-0290). A misbehaving agent that sends huge events can still exhaust Liquid's memory, an accepted risk of a trusted agent (ADR-0273).

The tool names and targets, the approval prompts with their reasons, options and warnings, the questions with their headers, options and descriptions the Chat shows, the names, titles and statuses of the session card and the Git dialogs, and the Diff panel's file names and lines, write out the characters that could hide or reorder what a call does or changed, such as `<U+202E>`. Links from the session card open in the default browser only over `https`, or over `http` to the loopback.

“Export record” writes T3's record of the session, with its prompts and tool output, into a new folder in Downloads, along with each turn's changed file paths and line counts; it copies no file contents. The copies are plain files with the person's permissions, unencrypted, and Watershed never sends them anywhere; the record claims no completeness (ADR-0257).

The agent can change any file the user can, including settings that run commands, such as shell profiles, launch agents and Git settings. The Diff panel shows what T3's checkpoints captured and claims no completeness (ADR-0222). Hiding whitespace changes also hides changes whose whitespace alters meaning, such as Python indentation.

A move of a session to another host (ADR-0308) refuses every call that changes the session except Stop, messages included, from its start until it is released and for good once it is sealed; deletion and archiving are refused only while the move is open. This holds for calls through Meta-Harness; T3's own clients on that host are not covered. The target's record of a transfer decides it: landed or refused, and the source follows that record. The exception is Cancel move while the target does not answer: the source is released without that record, so a session the target already started runs on both hosts, its carried messages on both, until one is deleted (accepted risk). Nothing expires by time and nothing is released at service start, so an open move waits until Liquid finishes it (seal or release), as a repeated call also does. A move-out repeats by its transfer and returns the same package. A target answers a transfer's move-in once; a repeat returns the thread it landed, a launch in progress is adopted, and a refused transfer stays refused. A move never removes a worktree: a move-abort removes only the thread the move launched, and a clean worktree the move left stays for a later move. A move onto a checkout that a live session uses, or onto a branch whose upstream is not a remote branch of the same name (a local upstream included), has no upstream or has unpushed commits, is refused, and a move onto an existing branch of a project with more than one Git remote is refused too (the branch-absent case still gets a new worktree). The dialog's preflight finds these before anything changes, except unpushed commits on a branch no checkout holds: move-in finds those after the source pushed and the target added a worktree, which stays. A queued message with attachments blocks the move, since a move does not carry attachments. A move is refused as raced when the branch changes while its turn stops, or when a turn starts or completes during its push; the queued messages then stay saved for a release. The move check and the thread list name an open move. A message the move cancels is returned once, behind the active turn, under a stable message id, and a message whose id the thread already holds is not sent again; the messages a move carries reach the target only after it commits the landing, in order and once each, and an interrupted delivery resumes on the next move-in, move-status or move-abort call: until every carried message is delivered, a move-status or move-abort on a landed transfer answers starting and a move-in fails, so the source seals only once the target reports the move landed; a move's finish runs to its end even when the caller's connection drops, and a seal or release waits for a move-out in progress on the same transfer, so a release loses no message. A remote URL holding a password, a query string or, on http(s), a username, and a remote written with Git's remote-helper syntax (transport::address), blocks the move, so the credential does not travel, and the move check omits such a URL; SSH and scp users do not. A sealed session may be archived and deleted. A sealed session leaves that host's thread list and its scheduled tasks are paused; the seal and its pending pause are recorded in one step, and a pause that did not finish is retried at each repeated seal and at service start. Git actions on the left checkout are not refused (accepted risk). Bringing the source's configuration with a move makes the target's instructions, skills and MCP servers match the source's, removing those the source lacks: Liquid proposes the changes and approves them itself on the target, MCP server environment values included, so any secret in them travels. The dialog names each change (name, kind and direction, not values) under Show, and nothing is brought if the configuration changed after it was shown.

A persistent agent (ADR-0283) keeps its instructions, name and routines where it can change them itself: `instructions.md` in its memory folder (owner-only) and T3 scheduled tasks bound to its thread. A change it makes in a turn that a routine started, webhook runs included, is undone when the turn ends and waits in its Chat until the person applies or discards it, so text a routine or webhook brings in cannot reprogram the agent unseen. In a turn the person started, by writing to the agent or mentioning it, the agent may change its configuration as asked, and Liquid shows each change with Undo. Accepted risk: in such a turn, content the agent reads (a page, a file, a tool's output) can still lead it to change its configuration, which then shows in the Chat; until the turn ends, a held change is in effect, and a routine it added could run once in that time. Meta-Harness tells whose a change is by the turn that ended last; an edit to `instructions.md` made outside Liquid and Meta-Harness counts as that turn's, so after a routine run it is held too. Moving an agent to another host carries its memory folder, at most 100 MiB, and its routines in the move package through Liquid, as a session's handoff travels; the old host keeps its copy of the memory folder. For that, a message on the service's socket may be up to 176 MiB, which only an admitted caller can send.

## Meta-Harness service and configuration

The service listens on 127.0.0.1 and, with remote access on, on this computer's Tailscale addresses. It admits a local connection only with its bearer token: 256 random bits, new at every start, never logged, kept with the address in `connection.json` in the data folder, which only the user can read (ADR-0297). Another local account reaches the port but not the token, and a web page cannot send the header that carries it. Every process of the user, agents included, can read the token and do through the service whatever the person can, as it can on the account anyway (ADR-0254). One service holds a data folder at a time.

Remote access is off until a person turns it on, and stays on across restarts until turned off; turning it off ends its connections, and a port it cannot bind is retried every 30 seconds (commands: [meta-harness/README.md](meta-harness/README.md#remote-access-and-host-links); ADR-0299). Tailscale is the transport until the Liquid account exists (ADR-0285); Meta-Harness adds no encryption of its own there, and it binds only Tailscale's addresses. A remote connection admits only the token of a paired client; it pings every 30 seconds and ends once silent for 90, and at most 32 handshakes run at once. A pairing code is single use, expires after five minutes, and at most five are live; codes and tokens are kept as SHA-256 digests and compared in constant time. A device token reaches the whole API except remote access, pairing codes and host links. A host token reaches the T3 Code of the host it is paired with through the tunnel, and may ask that host for a pairing code. The receiving host sets each linking host's highest access level when it invites it, `auto` by default; the linking host may ask for less. The code carries only the scopes that level needs, and full access adds settings and source-control writes. The tunnel refuses (403) an approval that names no level or asks for more than that level, and a decision or token exchange whose client_id names another pairing, so a host never obtains a higher level than it was invited at, nor a session under another host's name. The tunnel parses each HTTP request and passes the requests a link uses with their Host header unchanged; a registration takes the host's pairing name as its client name, which T3 signs into the client_id and gives its session. It answers every other request of the linked T3 with 403 without T3 contact; the requests are in the [V-Spec](docs/concept/V-Spec_MetaHarness.html#orchestration) (ADR-0301). T3 checks the request's own credentials, here the scopes of the level. Revoking a client refuses its token from its next connection on and ends its open connections, device and tunnel alike. Revoking a host also ends the T3 sessions its link made, so T3 refuses their tokens from the next request on: token exchanges in flight finish first, so none survives the revoke unless T3 takes over 30 seconds to answer one, and a failure leaves the name to revoke again. Revoking a name with no client still ends that name's sessions. `meta host remove` on the linking host cannot end them, so it names the pairing to revoke on the other host. Pairing names are unique, at most 64 characters, and trimmed as T3 trims a client name, so T3 labels sessions with the name revoke looks for. A peer that does not answer a link within 30 seconds is given up on, and a registration, decision or token exchange whose body does not arrive within 30 seconds, or exceeds 64 KiB, is refused. The tokens this host holds for other hosts sit in the store, which only the user can read. Liquid keeps the device tokens it holds for agent hosts in the operating system's keychain, one item per host address, never in a file.

Configuration changes take effect only once approved, and every proposal, approval and rejection stays in an append-only log in the service's SQLite (ADR-0298). Anyone on the account may approve, so this guards against changes nobody looked at, not against an agent acting as the person: such an agent can approve its own proposal, change the store's file or edit the harness homes directly. The log records the name each client gives itself, which proves nothing.

Approved blocks run with the user's permissions: an MCP server's command and a skill's scripts run whenever a harness uses them. Meta-Harness writes them into homes it owns for Claude Code and Codex, so the person's own `~/.claude` and `~/.codex` do not configure these sessions. Both keep the person's login without a copy: Codex's `auth.json` and `auth.lock` in its home link to the person's Codex home, which Codex follows, and Claude Code gets `CLAUDE_SECURESTORAGE_CONFIG_DIR` set to the person's own configuration folder, empty for the default. That variable is not a published setting: if a Claude Code release drops it, Claude Code asks for a login once in its home instead. Credentials never leave the host.

The login service runs `meta serve` with the installing shell's `PATH`, keeping only absolute folders, and with its `CODEX_HOME` and `CLAUDE_CONFIG_DIR`. At start it runs each `flow` on that `PATH` as `flow acp --help` and registers the first that answers as Flow Agent with T3. The installer follows Flow Agent's [download contract](#m12-tool-execution-trust-boundary): one archive per platform with `SHA256SUMS`, which the person checks before unpacking; it installs without administrator rights and carries the pinned T3 release unchanged. Uninstalling keeps the data folder. It removes nothing when the login service file does not name its data folder, or when the service could not be stopped for a reason other than that it was not loaded; a failed replacement starts the previous service again and reports any failure.

## Liquid workspace access & external-agent edits

Liquid's shipped Workspace core enforces:

- Every Workspace write goes through one mutation pipeline (permission check, validation, atomic apply) and is recorded as an Action with its actor, origin and permission result; no write reaches a Workspace document any other way. The pipeline allows only the Workspace's owner, who holds Can manage, and refuses every other actor. An Automation runs only after one of the owner's own changes, clicks or Tests, as its Role, by default Can edit; a run its Role does not allow is refused, and each run is recorded as one Action by the Automation with its Role. A protected Table keeps only the Roles chosen for it; reading still follows its area (ADR-0317, ADR-0321).
- Each device keeps its replica in SQLite encrypted with SQLCipher; the key lives in the operating system's keystore ([client architecture](docs/concept/liquid-client-architecture.md#storage), ADR-0237). Attachments, the files of Media Blocks and file cells, are kept inside that replica; Save as… writes an unencrypted copy only where the person chooses, and Liquid opens no attachment in another app (ADR-0305). A PDF is parsed only by the operating system's renderer (PDFKit on macOS), inside Liquid's process, which holds the replica's key; no third-party PDF engine is bundled (ADR-0307).

Accepted agent-host risk (ADR-0254): Watershed puts no sandbox around a harness (ADR-0252). An agent host runs agents under the account it is installed on, so its agents reach what that account reaches: on a person's own account they can delete or damage Liquid's data folder, and the replica key stays Liquid's on macOS, whose keychain releases it only to Liquid, while on Linux the Secret Service and on Windows the Credential Manager release it to any program of the user. Whoever wants agents apart sets Meta-Harness up in a VM, a container, another account or on another computer and links it as an agent host.

[Roles for people and agents, Workspace CLI/API access and agent grants](docs/concept/V-Spec_Liquid.html#workspace-access), [sync, headless replicas and enterprise storage](docs/concept/V-Spec_Liquid.html#sync) and [Apps, Block packages and MCP](docs/concept/V-Spec_Liquid.html#apps) are accepted targets in the Liquid V-Spec.

This is Liquid's **workspace** action history (over Liquid's own data), not a project-code VCS. Detail: [`docs/concept/V-Spec_Liquid.html`](docs/concept/V-Spec_Liquid.html).

## Supply chain

Dependency hygiene: committed lockfiles, exact pins and minimal dependencies; CI runs `cargo audit` (RustSec advisories), `cargo deny` (license/bans/sources/advisory policy via `deny.toml`) and `pnpm audit`. Rust reduces but does not eliminate supply-chain risk (`build.rs`/proc-macros run at build time); future isolated runtimes must limit blast radius regardless of language.

A PR that adds a dependency or moves its pin, a Dependabot PR before its merge included, checks the new version and states the result in the PR:

- the real upstream behind the registry link, not a fork or mirror;
- advisories in RustSec, GHSA, OSV and the upstream repository's own;
- that its release line is still supported;
- maintainer activity: authors, releases, and answers to bugs on our platforms;
- for a crate that vendors a C library, the same for that library.

Dependabot (`.github/dependabot.yml`) proposes weekly grouped updates for Cargo, pub, npm and GitHub Actions, each release at least three days old. A monthly dependency audit covers what Dependabot and the advisory gates cannot see (ADR-0320):

- toolchains: both `rust-toolchain.toml` files, Flutter in `liquid/app/pubspec.yaml`, `.node-version` and pnpm;
- the tools and downloads in `.github/workflows/ci.yml`, including the flutter_rust_bridge codegen;
- the T3 Code pin in `meta-harness/t3.lock` and the Node it declares;
- C libraries vendored inside crates, such as SQLCipher and OpenSSL, and the material in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md);
- host packages: Bubblewrap and `sandbox-exec` ([PLATFORMS.md](PLATFORMS.md));
- advisories published only in an upstream repository, for parsers of untrusted input, crypto and native code;
- maintainers: the real upstream behind registry links, bus factor, releases, and answers to bugs on our platforms.

## M0/M1 policy-emulation scope

Fixture execution checks modeled invocation decisions in process; it never proves Flow-owned write protection. Fixture scenarios ([TESTING.md](TESTING.md#fixture-contract)) do not grant or assert productive filesystem/network containment. Own-script fixture output remains create-only: an existing leaf rejects before runtime or temporary-file mutation; output replacement remains [D-056](docs/decisions/open-decisions.html#d-056).

### M0 policy artifact contract

`core-policy` emits canonical invocation-policy JSON for review and deterministic tests. Serialization follows [PROTOCOL.md](PROTOCOL.md#canonical-protocol-json-serialization-v0), with a final LF. It has no OS target, filesystem/network policy, runtime-read profile or process/thread capacity field; isolation fields are rejected by the closed schema.

| Field | Contract |
|---|---|
| `policy_version` | Fixed string `"0"`. |
| `source_flow_definition_id` | Resolved Flow definition id. |
| `commands` | Tool invocation records; canonical shape and validation live in [CommandPolicy](core/core-policy/src/artifact/command.rs). |
| `phase_scope` | `{phase_id, tool_ids}` records defining available Tools. |
| `runtime_limits` | `{headless, timeout_ms}`; Boolean headless flag and integer deadline. |

Each command records `tool_id`, `tool_kind`, `command_id`, `executable`, literal `argv`, `allowed_parameters`, `environment` and, only for own-script Tools, `script_runtime: "posix-sh"`. Predefined commands resolve through the trusted registry; own-script commands use `script:<tool-id>` and the fixed POSIX-shell runner. Productive invocation uses the verified executable and literal arguments without `PATH` lookup, shell parsing, expansion or globbing by Flow. Parsing the reviewed own-script body remains part of that Tool's trusted semantics. U+0000 in execution-vector strings rejects before spawn.

Parameter contracts define exact names, kinds, required values and their applicable enum/string/path/integer constraints. Unknown parameters, extra positional arguments and invalid values reject before launch; their rendering is canonical in [PROTOCOL.md](PROTOCOL.md#m11-runtime-values).

`environment` is `{default: "clear", allow}`, with exact Engineer-selected host variable names matching `^[A-Z_][A-Z0-9_]{0,63}$`. The current script compiler emits `allow: []`. Artifacts/events contain no environment values; the resolved request carries only explicitly admitted values. Flow performs no automatic secret classification of configured values, and never forwards its own provider credentials.

Commands sort by `tool_id`; allowed parameters by `name`, enum values and environment names lexicographically; Phase scopes by `phase_id` and their Tool ids lexicographically. Literal `argv` order is preserved. New arrays must preserve schema order or define a sort key before fixture publication.
