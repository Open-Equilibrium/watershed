Flow Agent - First Release

D-066 - Standard Tools And Executable-Code Trust

Status: Discussion required before the first Flow Agent release. Default Tools should be replaceable; their catalog, behavior and trust presentation are not yet specified. The security contract remains canonical.

Question: Which Tools should ship, what precise actions must they implement safely for hostile model inputs, and how should Engineers understand the code they are authorizing?

  • A - A small maintained default set with explicit contracts. Pro: useful without every Engineer writing basic Tools; each Tool can have meaningful behavioral tests and a clear owner. Con: Watershed must maintain those implementations and disclose where they execute project code, helpers or external services.
  • B - Definitions/examples only, with Engineers supplying implementations. Pro: less bundled code to maintain. Con: greater setup effort and more repeated security-sensitive implementation work.

Recommendation: A, with the smallest useful set. Before choosing it, specify each Tool's input/path/action limits, replacement procedure, dependency/update responsibility and executable-code trust display. A safe file Tool and a build command that executes project code have different responsibilities; neither a description nor a marketplace listing proves safety. Ordinary assigned Tool calls remain prompt-free; first-release configuration administration stays manual under SECURITY.md.

Acceptance criterion: Approve the catalog and user-facing trust explanation, then prove each shipped Tool's promised behavior under adversarial inputs on its declared platforms. Demonstrate replacing a default Tool without widening authority silently. Do not advertise third-party Tool certification or general host isolation.

D-077 - Unicode Form Of Tool Scripts And Arguments

Status: Open before the first Flow Agent release. The same letter can be stored as different bytes, for example "é" as one character or as "e" plus an accent; Unicode NFC is the form that always uses the single character. PROTOCOL.md says Tool text "is preserved as exact UTF-8", but building the registry converts every own-script body and argument literal to NFC, and a core-script test asserts that conversion. The request Flow Agent sends the Executor also converts each argument and environment value to NFC, and environment values come from the host, where they can be in the other form. The published file keeps the authored bytes, so the bytes that run can differ from the bytes on disk. Host paths in an Executor request are already refused when they are not NFC.

Question: May Flow Agent change the bytes of a Tool's script body, arguments and environment values to NFC before running them?

  • A: Refuse script bodies, arguments and environment values that are not NFC when the Tool is created or validated, or, for a value from the host, before the Tool starts. Pro: the stored and the executed bytes always match, and nothing is rewritten silently. Con: an Engineer whose editor or file system produced the other form must convert the text once.
  • B: Keep converting, and say so in PROTOCOL.md. Pro: no change for existing definitions. Con: a script that names a file whose name uses the other form opens a different or missing file on Linux, and the executed text is not the reviewed text.
  • C: Stop converting these fields and run the authored bytes. Pro: matches the documented sentence. Con: the canonical hash of a definition then depends on the form, so two definitions that look identical get different hashes.

Recommendation: A, the rule the Executor request already follows for paths.

Acceptance criterion: PROTOCOL.md states one rule for script bodies, argument literals, patterns, allowed values and the Executor request's arguments and environment values; a test shows a definition in the other form is refused (A), runs converted (B) or runs unchanged (C), and the contradicting test or sentence is gone.

D-078 - A Cut-Off Last Line In A Run's Event Log

Status: Open before the first Flow Agent release. A Run appends one line per event to its event and context logs. If the process is killed or the power fails in the middle of an append, the last line is incomplete. Exact Resume then refuses that Run for good ("prefix must end with LF"), as the recovery matrix and a test require today. The recovery log already drops such an incomplete last line.

Question: Should exact Resume drop an incomplete last line of the event and context logs?

  • A: Keep refusing. Pro: every difference in a log counts as damage, the simplest rule. Con: an ordinary crash at the wrong moment makes the Run impossible to resume.
  • B: Drop the incomplete last line while holding the Run's lock, as for the recovery log. Pro: a crash during an append no longer blocks Resume; a line that never ended was never announced, so no recorded event is lost. Con: the recovery matrix, that test and the Replay and Tail readers change with it.

Recommendation: B.

Acceptance criterion: PROTOCOL.md's recovery matrix states the rule; tests show a Run with a cut-off last event line resuming (B) or being refused (A), and Replay and Tail treating the same file the same way.

D-079 - A Provider Reply That Ends But Breaks The Format

Status: Open before the first Flow Agent release. PROTOCOL.md knows two outcomes for a failed model request: provider_error, carrying the provider's own message, and uncertain, for a reply that stopped early. A reply that ends properly but breaks the format fits neither: a repeated call id, an output item without content, data after the end, or a reply that is not an event stream. Today it is stored as provider_error with Flow Agent's own text in the place of the provider's message.

Question: How is such a reply recorded?

  • A: As uncertain. Pro: no new term. Con: an uncertain model request cannot be settled by hand, so the Run cannot continue past it.
  • B: As a third outcome that closes the attempt and labels the message as Flow Agent's. Pro: truthful, and the Run is not blocked. Con: one more outcome in the event schema, GLOSSARY.md and PROTOCOL.md.
  • C: Keep provider_error and let PROTOCOL.md allow a message Flow Agent wrote. Pro: no code change. Con: a reader can no longer trust that the message came from the provider.

Recommendation: B.

Acceptance criterion: PROTOCOL.md names the outcome for each such reply, and a test per case shows it recorded that way and never retried.

D-080 - A Tool Process On macOS That Outlives Its Tool

Status: Open before the first Flow Agent release. When the Executor exits, Flow Agent ends every process left in the Executor's process group and waits one second. On macOS a Tool's child processes are in that group. If one cannot end in time, such as a process stuck on a hung network drive or one running as root, Flow Agent stops itself at once and discards the Executor's valid answer; the Tool call is then recorded as uncertain and must be settled by hand with flow reconcile-tool. Linux is not affected, because its Tools run in their own process namespace.

Question: What should Flow Agent do when such a process survives the wait?

  • A: Keep stopping at once and record it as an accepted risk in SECURITY.md. Pro: Flow Agent never continues while a process it started may still be acting. Con: a valid result is lost and a person must settle the call.
  • B: Keep the Executor's answer and record that cleanup of the Tool's processes is unknown. Pro: the evidence survives and the Run can continue or stop on a recorded fact. Con: a new recorded state, and a decision on whether the Run may go on.
  • C: Give the Tool its own process group on macOS. Pro: ending the Executor no longer depends on the Tool's children. Con: Flow Agent would then have to end the Tool's group separately, or leave its children running.

Recommendation: B, with the Run stopping after it records the answer.

Acceptance criterion: A macOS test with a child that cannot be ended shows the chosen behavior, and SECURITY.md states it under effects and recovery.

D-088 - A Provider On A Documented API For The First Release

Status: Open before the first Flow Agent release. Flow Agent's only model provider today logs in with a ChatGPT subscription: it uses Codex's public OAuth client id and sends requests to chatgpt.com/backend-api/codex/responses (PROTOCOL.md). Neither is a published API with terms for third-party programs, so OpenAI can change or close it at any time, and a company cannot use its own API keys or contract. PLAN.md names only the long-term provider-neutral local-inference target (ADR-0153, D-059).

Question: Does the first release need a provider on a documented API with an API key?

  • A: Ship with the subscription login only. Pro: no further work. Con: the release depends on an endpoint nobody promised to keep, and companies have no supported way in.
  • B: Add OpenAI's documented Responses API with an API key, keeping the subscription login as an option. Pro: closest to today's request format, so the least work. Con: still one vendor.
  • C: Add one OpenAI-compatible endpoint provider (base URL plus API key), which OpenAI, Azure OpenAI and local servers such as vLLM or Ollama all offer, keeping the subscription login as an option. Pro: one provider reaches several vendors and is a first step toward the local-inference target. Con: the vendors differ in tool-call and streaming details, so each needs its own tests before it is listed as supported.

Recommendation: C, listing only the endpoints that pass the provider tests as supported, and marking the subscription login as relying on an unpublished endpoint.

Acceptance criterion: PROTOCOL.md defines the chosen provider and how its key is stored; provider tests run a Flow against each listed endpoint; the README says which logins rely on unpublished endpoints.

D-090 - The YAML Library Under Flow Definitions

Status: Open before the first Flow Agent release. Flow and Tool definitions are YAML, parsed by core-script with the pre-1.0 library noyalib, pinned exactly at 0.0.53. Watershed adds its own checks on top: no anchors, no merge keys, no duplicate keys, bounded scalars and no nulls (core/core-script/src/script/parser.rs). The parser sits on a security-relevant path, since a definition decides what a Tool may run. noyalib has one maintainer, publishes 0.0.x releases often and may change its API in any of them; it reports passing the official YAML test suite.

Question: Which parser should read Flow definitions?

  • A: Keep noyalib pinned, and add a fixed corpus of hostile definitions (deep nesting, huge scalars, aliases, tags, duplicate keys, odd encodings) that must keep giving the same result. Every version bump is reviewed against it. Pro: no rewrite; the corpus also makes a later switch safe. Con: still depends on one person's 0.0.x crate.
  • B: Switch to saphyr-parser, the maintained successor of yaml-rust, packaged by Debian, and check its event stream ourselves. Pro: wider use. Con: also 0.0.x, and Watershed then owns more of the checking code.
  • C: Define Safe-YAML as a small fixed grammar (block mappings and sequences, plain and quoted scalars) and parse it ourselves. Pro: the smallest trusted code, fully specified by Watershed. Con: a parser to maintain, and Engineers lose YAML features such as flow style.

Recommendation: A now; it costs little and makes B or C a safe swap later.

Acceptance criterion: the corpus runs in CI against the chosen parser, and the dependency's version policy is stated where dependencies are reviewed.

D-092 - A Name That Does Not Promise A Sandbox

Status: Open before the first Flow Agent release. Flow Agent blocks Tools and their new children from writing, deleting, replacing or hardlinking this installation's own files (configuration, registry, runtime and credential stores, installed programs). Otherwise Tools run with the person's own rights, and nothing stops them reading. The docs and CLI call this by nine names: "self-protection", "native self-protection", "native protection", "Flow-file protection", "own-file protection", "Flow-owned write protection", "native boundary", "Executor boundary" and "OS isolation" (PLAN.md's M1.2 heading). Several read as if Tools were contained: 44 places a person reads, plus internal names such as the receipt field self_protection_active and the error code sandbox_setup_failed.

Question: Which single name should the docs, CLI and errors use?

  • A: "Flow-owned write protection". Pro: says what is protected and that only writes are blocked; already the wire value and SECURITY.md's wording. Con: three words; "write" must be defined once to include delete, replace and hardlink.
  • B: "Flow file protection". Pro: short and already used in README and VISION. Con: reads like the Workspace's .flow/ definitions, which are not protected, and does not say "write".
  • C: "Tamper protection", the term security products use. Pro: established. Con: those products also resist administrators, which Flow Agent explicitly does not, so it promises too much.

Recommendation: A. Keep "Executor", since a process runner is not a container; drop "Executor boundary" and "OS isolation"; rename the PLAN.md heading and the misleading CLI and error texts in one docs-and-text change, and the wire names self_protection_active and sandbox_setup_failed in a separate schema change. Examples: flow executor check prints "Executor ready … (Flow-owned write protection active; Tools otherwise run with your permissions)"; GLOSSARY drops "OS isolation" and says under Sandbox that Flow Agent provides no Tool sandbox.

Acceptance criterion: GLOSSARY.md defines the one term; a search for the other eight names finds them only in the changelog's history.

D-093 - Testing Flow Agent Against Power Loss

Status: Open. Two durability defects in Flow Agent were found only by reading the code: a Run Log line not yet on disk when status.json was published, and a Conversation that stopped resuming after about six Runs. A new test matrix now kills the process after every durable step of a Run and of a chain of continuation Runs, then resumes and checks PROTOCOL.md's invariants (TESTING.md). A power loss is harder: writes not yet synced are lost, and the last write may be cut at any byte. To simulate that, the tests must know which bytes each file had synced. Flow Agent syncs in about 20 places across 13 modules, with no single place every write and sync goes through.

Question: How should the tests model a power loss?

  • A: One write-and-sync helper in production code that every durable file write uses, with a test-only record of what was synced. Pro: one durability boundary that later code cannot bypass; the tests then cover every step. Con: a production refactor of about 20 call sites, reviewed like any runtime change.
  • B: A test-only hook at each of the 20 places. Pro: no production change. Con: a new write that forgets its hook goes untested, so coverage drifts.
  • C: Kill a real child process at each step instead of copying files inside one test process. Pro: faithful to a real crash, including the file identities the in-process copy loses. Con: slower, and it still does not model lost unsynced data.

Recommendation: C to finish the crash tests, then A for power loss. A is the only option whose coverage cannot silently drift.

Acceptance criterion: TESTING.md describes the chosen layer; for A, a test proves that a durable write outside the helper fails CI.

D-082 - Replaying A Tool Cancelled Before It Started

Status: Open before the first Flow Agent release. When a Tool call is cancelled before the Executor started it, the live Run records no "Tool started" event. After a crash, recovery replays the call from its durable record, which PROTOCOL.md fixes as exactly {"schema":"flow-attempt-cancelled-v0"} for every stage, so recovery cannot tell when the cancellation happened and always replays a "Tool started" event first. The replayed history then shows a start that never happened.

Question: Should the cancelled record say at which stage the call was cancelled?

  • A: Add the stage (before start or after start) in a new version of the record, as the Executor's stage errors already do. Pro: replay matches what happened. Con: one more durable format version to read and test.
  • B: Keep the record and document that a recovered early cancellation replays with a start event. Pro: no format change. Con: recovered history contains an event that never happened.

Recommendation: A.

Acceptance criterion: PROTOCOL.md defines the record; a test cancels a call before and after start, recovers both Runs and shows the replayed events match the live ones (A), or PROTOCOL.md states the difference (B).

Watershed - Shared Release Safeguards

D-065 - Development And Release Publication Safeguards

Status: Must be decided, implemented and verified before each affected product's first release: Flow Agent, Meta-Harness and Liquid. This entry records open work, not active protection. The approved download contract is canonical in SECURITY.md; it does not require users to install a build-provenance verifier.

Problem: A stolen publishing account or an unsafe build step could place a harmful program in the real GitHub Release, even while the visible source code remains unchanged. HTTPS and a matching checksum would still succeed. The development team must protect that trusted source without making installation harder for users.

Decisions required

  • Who may publish? Select the authorized people and automation, account protection and recovery rules, and required approval for source, release tags and publishing-workflow changes. Decide how the rules work with the actual maintainer team; do not assume a second reviewer exists.
  • What may build code access? Decide how untrusted contributions, dependency/build scripts and third-party automation are separated from publishing and Mac-signing authority. Select minimum automation permissions, credential lifetime/storage and runner isolation; reference the existing dependency safeguards, not a duplicate audit process.
  • Which bytes may be published? Bind the approved source revision, existing required gates, build inputs and final platform bundles to one release record. Decide who checks this record, completes any required Mac signing before final checksums, and authorizes publication. Internal evidence does not add an end-user provenance requirement.
  • Can a published version change? Select tag/asset replacement restrictions and evaluate GitHub's available release protections. Decide the correction procedure so the same version does not silently acquire different programs. The approved browser-download route and verification boundary are canonical in SECURITY.md; no online bootstrap is included.
  • What happens after a suspected compromise? Assign an incident owner and a procedure to halt publication, revoke affected access, withdraw or mark unsafe releases, notify users and publish a corrected version. Decide evidence retention and account/signing recovery; an offline user cannot receive immediate withdrawal information.

Options and recommendation

  • A - A protected release workflow with explicit maintainer approval. Pro: repeatable builds and checks with narrowly scoped publication access. Con: workflow, runner, approval and recovery controls must be configured and maintained.
  • B - Documented manual publication of approved, tested artifacts. Pro: fewer automated publishing permissions and a small initial setup. Con: more human steps and greater risk of uploading the wrong bytes or losing release evidence.

Recommendation: A, sized to the actual team, with narrowly scoped release authority separated from untrusted build work. B is viable only with an equally explicit artifact-check and recovery procedure. Neither option is approved by this entry.

Acceptance criterion: Record the selected controls and responsible owner for every question above. Retain non-secret evidence of the actual repository/workflow settings and a release rehearsal tied to one source revision and final bundle set. In a safe test setup, prove an unauthorized publishing attempt is rejected, untrusted build work lacks publication/signing authority, a mismatched artifact is rejected before publication, and the selected correction/withdrawal procedure works. Pass the canonical native installation checks in SECURITY.md. Maintainer approval of that evidence is required before the first release of each affected product; green branch CI or this checklist alone does not close the decision.

D-048 - HerdR CLI-Agent Backend Integration

Status: Open, M2 blocker before Meta-Harness CLI-agent process execution.

Question: Should Meta-Harness reuse HerdR for host-local terminals, whole CLI agent processes and session persistence while retaining policy, normalized records, shared config, schedules, audit and AgentPulse? This boundary is unrelated to Flow's Executor protocol.

  • A: Integrate HerdR as an optional Meta-Harness agent executor through its versioned CLI/socket API. Pro: reuses terminal multiplexing, process persistence, agent detection and remote attachment while preserving Meta-Harness boundaries. Con: requires stable identity mapping, failure recovery and a maintained adapter.
  • B: Require HerdR as the runtime for all external CLI agents. Pro: one execution path and an existing terminal UI. Con: couples M2 availability and semantics to HerdR's platform support, protocol and roadmap.
  • C: Build the Meta-Harness agent executor independently and use HerdR only as a comparison. Pro: complete control over the CLI-process boundary. Con: duplicates substantial terminal, process and persistence work.

Recommendation: A behind a backend-neutral Meta-Harness agent-executor contract, subject to a bounded integration spike; keep direct semantic adapters where they provide richer events.

Acceptance criterion: The spike starts, steers, observes and restores Codex plus one other CLI agent without an attached HerdR UI; preserves stable Meta-Harness session identity across detach and service restarts; routes every configuration change and control command through the Meta-Harness policy/audit gate; normalizes HerdR events without treating terminal inference as semantic truth; rejects cross-host process claims; and documents fail-closed behavior for unsupported capabilities on the native targets in PLATFORMS.md.

D-074 - Who Starts The Local Meta-Harness Service

Status: Open; decide with the service-mode slice. ADR-0215 settled that Liquid reaches its own host's Meta-Harness as a separate service.

Question: On a Mac or Linux computer, who starts the Meta-Harness service, and does it keep running when Liquid closes?

  • A: Liquid starts it when needed and stops it when it quits, as T3 Code does with its server, restarting it after a crash. Pro: nothing to install or register, and no background process while Liquid is closed. Con: agents end when Liquid quits or updates, and the CLI needs its own instance or must find Liquid's.
  • B: A login service runs it (a launchd user agent on macOS, a systemd user unit on Linux, both without administrator rights); Liquid and the CLI connect to it. Pro: agents keep running through Liquid closing, crashing or updating; one instance serves Liquid, the CLI and remote clients; the operating system restarts it. Con: installation registers the service and removal must unregister it, a process runs while nobody uses it, and updating it must not end running agents.
  • C: Liquid starts it if none runs, and it stays while agents run. Pro: no installation step, and agents finish after Liquid closes. Con: more lifetime rules to get right, and a service nobody stops if they are wrong.

Recommendation: B, which matches the background service D-021 recommends: agents survive the window, and the operating system supervises the service instead of our own restart code.

Acceptance criterion: The ADR log names who starts and stops the service, and tests show Liquid connecting to a running service and reporting one it cannot reach.

D-083 - Where The Lock For Folders Outside Git Lives

Status: Open. In a folder without Git, Meta-Harness stops a session from being deleted or Git from being set up while an agent works there through a lock file in the system's temporary folder (SECURITY.md). That folder comes from the TMPDIR setting, which can differ between two programs of the same person, for example on Linux when Liquid is started once from a terminal and once from the desktop. The two then use different lock files and do not see each other's agent.

Question: Where should that lock live?

  • A: Keep the temporary folder and record the gap as an accepted risk in SECURITY.md. Pro: no change. Con: the protection depends on how the app was started.
  • B: A fixed per-user folder that does not depend on TMPDIR (XDG_RUNTIME_DIR on Linux, Liquid's per-user support folder on macOS), with today's owner-only checks. Pro: every program of the person finds the same lock. Con: one more place Watershed owns, and a one-time switch while an old version still runs.
  • C: The operating system's own per-user temporary folder, ignoring TMPDIR. Pro: no new folder. Con: differs per OS and is less obvious to a reader.

Recommendation: B.

Acceptance criterion: SECURITY.md names the lock's place; a test starts two processes with different TMPDIR values and shows one refusing to delete a session the other's agent uses (B, C), or SECURITY.md lists the accepted risk (A).

D-084 - Commit Attribution When A Turn's Start Checkpoint Is Gone

Status: Open. The commit dialog marks each file as changed by the agent's turns, by the person, or both, by comparing the checkpoints taken at the start and end of each turn. When a turn's start checkpoint is missing, for example after its removal, that turn is skipped and the comparison restarts at the next one. Files changed during the uncovered stretch are then labeled as if attribution were complete, and a test deliberately labels changes before the first available start as the person's.

Question: What should the dialog say about files whose changes fall into a stretch without checkpoints?

  • A: Attribution unavailable for the whole commit when any start checkpoint is missing. Pro: simplest and never wrong. Con: one old gap hides every label.
  • B: Unavailable only for the files changed in the uncovered stretch; the others keep their labels. Pro: precise. Con: the existing test and the dialog's notes change.
  • C: Keep today's labels and document them. Pro: no change. Con: a label can name the person for an agent's edit.

Recommendation: B.

Acceptance criterion: The Meta-Harness V-Spec states the rule; a test removes one start checkpoint and shows the chosen labels.

D-085 - A Byte Limit For Buffered Agent Events

Status: Open. While a session starts, Meta-Harness keeps up to 4,096 agent events until Liquid listens, and later up to 256; each event may be up to 16 MiB. The limits count events, not bytes, so an agent that sends huge events can make Liquid hold many gigabytes. The agent itself runs with the person's permissions (ADR-0252, ADR-0254), so it could exhaust memory in other ways too.

Question: Should buffered agent events have a byte limit?

  • A: A byte limit for the startup buffer only. Pro: small. Con: the later buffer stays unbounded in bytes.
  • B: One byte limit per session for every buffered event, in the core and the bridge. Pro: complete. Con: more code, and a limit to choose and explain.
  • C: Record agent output volume as an accepted risk of a trusted agent in SECURITY.md. Pro: no code. Con: a misbehaving extension can still freeze Liquid.

Recommendation: C now, since the agent is trusted by design; B if agents become untrusted.

Acceptance criterion: SECURITY.md states the bound or the accepted risk; for A or B a test shows the limit refusing the event that crosses it.

D-081 - How Liquid Finds A Workspace's Key

Status: Open before Liquid's first release. Liquid encrypts a Workspace's database and keeps the key in the operating system's keystore, filed under the full path of the Workspace folder. If that path changes, for example when a person renames their macOS account and home folder or moves to a new Mac with Migration Assistant, Liquid looks under the new path, finds no key and refuses to open the Workspace, although the key still exists under the old path. ADR-0249 covers only the opposite case, a key without its file.

Question: What identifies a Workspace's key?

  • A: A random name stored in a small file inside the Workspace folder. Pro: the key is found wherever the folder moves. Con: one more file that must be kept with the database, and existing Workspaces need a one-time move of their key.
  • B: Keep the path, and search all of Liquid's keys when none matches. Pro: no new file. Con: with several Workspaces Liquid cannot tell which key belongs to which and would have to try each.
  • C: Keep the path only. Pro: no change. Con: a renamed home folder locks the Workspace until someone edits the keystore by hand.

Recommendation: A.

Acceptance criterion: A test opens a Workspace, moves its folder and opens it again; SECURITY.md says what identifies the key.

D-086 - Restoring A Chat While A Turn Ends

Status: Open. When Liquid opens or restores a Chat, it reads the conversation, the token usage and the turns in three separate requests. If a turn ends or usage changes between them, Liquid can miss that change until the next restore. Every restore Liquid starts itself runs while the agent is idle, so this happens only when something outside Liquid starts a turn, such as a pi extension.

Question: Should Liquid close this gap?

  • A: One read that names the last event it covers, with newer events applied on top. Pro: exact. Con: a new bridge method and more code.
  • B: Hold live events during the restore and apply them after. Pro: no new bridge method. Con: some events can count twice.
  • C: Record it as an accepted limit while extensions cannot start turns in the MVP. Pro: no code. Con: totals can be off until the next restore.

Recommendation: C, unless turns started by extensions are in MVP scope.

Acceptance criterion: The Meta-Harness V-Spec states the limit (C), or a test ends a turn during a restore and shows it counted once (A, B).

D-087 - The Dark Yellow Tag's Contrast

Status: Open. The design guidelines require WCAG AA text contrast (4.5:1). In dark mode, tag text on the yellow tag color --ws-tag-4 reaches 4.18:1; every other tag passes, the lowest at 5.16:1. No test checks tag colors yet.

Question: How should the yellow tag reach AA?

  • A: Darken the dark yellow slightly, toward #7d5a26. Pro: smallest change; the other nine tags keep Notion's look. Con: yellow looks a little browner.
  • B: Make dark tag text brighter for every tag. Pro: one value. Con: every tag changes.
  • C: Keep Notion's color as a recorded exception. Pro: Notion parity. Con: breaks the guidelines' own rule.

Recommendation: A.

Acceptance criterion: A design-token test checks every tag pair in both themes and passes.

D-056 - Existing Output Security-Metadata Matrix

Status: Open before post-M1 existing-output replacement; not an M1.1 blocker.

Question: Which exact security-metadata fields must atomic own-script output replacement preserve on Flow Agent's native targets in PLATFORMS.md, and what happens when a required field cannot be read or applied?

Decided direction: The create-only output boundary in SECURITY.md rejects every existing output target in M1.1; replacement remains unavailable until this finite per-platform field matrix is decided and implemented.

  • A: Preserve a maintainer-selected native field set and fail when any selected field is unavailable. Pro: explicit, testable preservation. Con: replacements can fail because of privileges or platform support.
  • B: Preserve a smaller maintainer-selected field set and reject targets carrying selected unsupported metadata. Pro: a narrower implementation. Con: detection and rejection rules remain platform-specific.

Recommendation: A; choose the exact fields and unavailable-field behavior only with platform evidence.

Acceptance criterion: Record the exact finite matrix and failure behavior, then pass native fixtures on each supported Flow Agent target for every required field before restoring existing-output replacement.

D-058 - Portable Conversation Archive And Tree Handoff

Status: Open before cross-device Portable continuation or a public tree-navigation/import surface.

Question: Which public archive closure should carry a completed checkpoint to another device while preserving tree navigation, transactional import and the accepted child-Run/branch semantics?

  • A: Export the complete Conversation tree and every referenced immutable artifact. Pro: self-contained history and full tree navigation. Con: archives can be large and repeat old data.
  • B: Export only the selected branch's verified transitive closure. Pro: smaller and sufficient for that continuation. Con: omitted sibling branches need a later union/import rule before one tree can be reconstructed.
  • C: Define content-addressed archive records that support both full export and incremental transfer through one schema. Pro: deduplication and efficient repeated device sync. Con: the first contract, recovery matrix and retention policy are more complex.

Recommendation: A first; keep the schema content-addressable so C can later optimize transport without changing Conversation authority. A Pi-style tree view renders the imported canonical graph and never becomes a second history authority.

Acceptance criterion: Fix the public archive closure, schema, size/resource bounds, content hashes, D-062 authenticated-root/provenance result, access/confidentiality and transfer protection, export/import transaction, version migration, branch-ID collision handling, optional coordinated source/destination fencing and recovery matrix. Exclude credential-store records, Runtime-binding credential references, approvals, Runtime bindings, structural source-host path/authority fields and leases, while treating all recorded user/provider/Tool/artifact content—including embedded path strings—as inert, potentially sensitive evidence. Require the destination actor to select and authorize one canonical Workspace, validate its compatibility and explicitly rebind allowed paths/artifacts before effects. Re-import into an existing Conversation must verify its common prefix by identity and hash, transactionally union non-conflicting descendant branches, be idempotent on repeated input and fail without mutation on conflicting records; it never merges two linear Runs. Prove no completed effect is redispatched; an uncertain provider attempt in the selected checkpoint's reachable state keeps that checkpoint non-executable because it has no reconciliation surface, while a relevant uncertain Tool attempt blocks child-Run creation until existing eligible-Tool reconciliation settles it; unrelated uncertain branches remain history without tainting eligible branches; and two disconnected continuations converge as distinct child branches.

D-059 - Offline Provisioning And Local Inference Binding

Status: Open before claiming offline-after-provisioning productive Flow execution.

Decided boundary: ADR-0153 requires a provider-neutral capability contract and device-local Runtime binding. A binding identifies the endpoint plus the provider/model, local artifact/quantization/runtime, credential-reference and resource-policy fields applicable to that provider; local artifacts and credentials may be absent. Credential material remains in the Flow-owned protected store.

Question: How should a device provision and discover conforming local artifacts, verify their claims and choose among compatible installed bindings without depending on an Internet service?

  • A: The operator installs a signed artifact manifest and explicitly selects one binding; a local probe verifies identity, capabilities and readiness before use. Pro: deterministic choice and small discovery surface. Con: more manual provisioning.
  • B: Flow Agent discovers installed bindings from a protected device-local catalog, probes each and selects only by an explicit deterministic policy. Pro: easier multi-model operation. Con: catalog mutation, tie-breaking and stale entries add state.
  • C: Meta-Harness may manage the same protected host catalog through Flow Agent's public surface, while standalone Flow Agent retains A. Pro: centralized fleet management without breaking standalone use. Con: audit, reconciliation and ownership between both clients need a finite contract.

Recommendation: A first; make its manifest/catalog schema reusable by B and C. Keep model acquisition outside Conversation state and evaluate actual context, latency, memory, energy and tool capabilities rather than model-size labels.

Acceptance criterion: Record the supported artifact/signature, catalog/discovery, capability, provenance, deterministic selection, credential-reference, admission and failure schemas; bind every credential reference to the selected provider and endpoint audience and reject a mismatch before secret resolution; preserve the protected credential store's permissions, locking, refresh and redaction rules; satisfy the local-runtime process boundary selected in D-061; provision one supported local stack; then run a productive Flow with network interfaces disabled and no remote authentication, licensing, telemetry or update dependency while requested remote-only actions fail clearly, sync reports offline/stale and waits resumably, and neither blocks unrelated local work.

D-060 - Offline Approval And Revocation Authority

Status: Open before an imported continuation can use approval-bearing Meta-Harness, Liquid or external actions while disconnected. This decision adds no Flow Agent Tool-approval prompt; ADR-0135 remains authoritative for assigned Tools.

Question: After an imported continuation reauthenticates locally, how may that destination approve sensitive work while it cannot learn later remote Role, policy or identity revocations?

  • A: Require a fresh local approval for each sensitive action. Pro: smallest authority and clearest audit. Con: repetitive for long offline workflows.
  • B: Let the destination issue a local, device-bound grant for an exact action set, resource set and short expiry. Pro: bounded offline automation. Con: expiry, one-use behavior and reconnect reconciliation need careful rules.
  • C: Let an administrator pre-authorize a destination-local offline profile before disconnection. Pro: predictable unattended work. Con: broader stale authority and stronger provisioning/audit requirements.

Recommendation: A initially; consider B only after a finite local key, replay and reconciliation design. The accepted boundary still forbids transferring prior approvals in a Conversation archive.

Acceptance criterion: Define actor/device identity, local grant scope, expiry, one-use behavior, audit records, reconnect reconciliation and the explicit limit that a disconnected device cannot observe later revocation; prove an imported archive alone authorizes no Workspace, Tool, config or external action.

D-061 - Local Inference Process Trust Boundary

Status: Open before D-059 can enable a productive local model runtime.

Question: What may executable local inference code access on the host while it receives model context outside the Tool's native protection boundary?

  • A: Treat the runtime as part of Flow Agent's trusted computing base under the operator's OS identity. Pro: simplest integration and lowest IPC overhead. Con: it may read global config, credentials, sessions and Workspace bytes; signatures prove provenance, not confinement.
  • B: Run it under a separate identity or enforceable Sandbox/service boundary with only a bounded authenticated inference channel and declared model/cache storage. Pro: contains filesystem, secret, process and network access. Con: substantial cross-platform packaging, accelerator and performance work.
  • C: Link the runtime in-process. Pro: smallest transport overhead. Con: maximally expands Flow Agent's memory-safety, dependency and secret-access trust base.

Recommendation: B for the supported offline claim. An explicit A installation may exist only with a clear no-isolation warning and no claim that signed artifacts are contained.

Acceptance criterion: For every option, record the process/identity, IPC, filesystem, credential, config, session, Workspace, model/cache, network, child-process, resource, crash and update boundaries per supported platform and enforce bounded request/result I/O. If B is selected, authenticate the channel and prove the runtime receives only admitted context/capabilities and cannot obtain protected stores or Workspace data outside that contract. If A or C is allowed, name the runtime and dependencies as trusted computing base, display the no-isolation status before use, make no secret/filesystem containment claim and test provenance, update and failure behavior under that stated trust model.

D-062 - Portable Archive Authenticity Root

Status: Open before D-058 may call an imported checkpoint verified or executable.

Question: How does a destination authenticate an archive's root manifest and provenance when an attacker could otherwise rewrite content and recompute ordinary hashes?

  • A: Sign the canonical root manifest with a source device/user key chained to a known identity. Pro: offline attribution and tamper evidence. Con: enrollment, rotation, revocation and lost-device handling are required.
  • B: Authenticate the root with a shared user/Workspace archive key. Pro: compact offline verification across devices. Con: shared-secret distribution weakens sender attribution and increases compromise impact.
  • C: Import as explicitly unauthenticated, non-executable evidence, require human review and let the destination re-seal a new local root before any continuation. Pro: no cross-device key infrastructure. Con: cannot preserve trusted provenance or automatic continuation.

Recommendation: A; retain C as a clearly separate recovery path that never claims verified source history.

Acceptance criterion: For A/B, define canonical signed/MACed bytes, identity binding, key storage/rotation/revocation limits, replay/downgrade rules, attribution and verification errors; tampering with the authenticated root, content, branch links or version must fail before destination mutation or provider/Tool effects. For C, label every record unauthenticated, permit no Portable continuation or effects, define explicit human review and destination resealing as new local evidence, and never claim source attribution or source-history verification.

D-076 - Private Terminal For Tools

Status: Open after the first Flow Agent release. ADR-0170 denies Tools direct access to terminal devices, so a Tool cannot write over or type into the terminal where a person reviews Flow Agent's output. Programs that insist on a terminal, such as password prompts of ssh or sudo, full-screen programs and some interactive shells, then fail or behave differently; ordinary input over stdin still works.

Question: Should Flow Agent give each Tool call its own private terminal?

  • A: Keep no terminal. Pro: the simplest rule, already in place. Con: those programs stay unavailable to Tools.
  • B: A new pseudo-terminal per Tool call that Flow Agent creates and connects to nothing the user sees, as Codex's Seatbelt profile lets commands open new pseudo-terminals but not the user's. Pro: programs that need a terminal run, and the user's terminal stays protected. Con: native work per operating system and sandbox profile; a program can wait for input forever, so a time limit must end it; terminal control codes in its output must be shown safely.
  • C: Connect the Tool's terminal to the user in the CLI or Liquid, so they can answer it. Pro: interactive Tools work fully. Con: a Tool could imitate Flow Agent's own prompts, the risk ADR-0170 removes.

Recommendation: B once a concrete Tool needs it; C only after a new security review.

Acceptance criterion: Native tests on each supported Flow Agent target show a Tool using its own terminal, no Tool reaching the user's terminal, and a waiting Tool ending at its time limit.
