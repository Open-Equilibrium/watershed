M1 - Governance

D-056 - CI Trigger And Branch Protection Scope

Status: Open before declaring M1 protected/PR-ready.

Question: CI currently runs only for pull requests targeting main and pushes to main. Should changing triggers be part of M1, and which GitHub branch protection or ruleset should require the M1 gates?

  • A: Keep CI triggers on main-targeting PRs and main pushes, then protect main with required M1 gates. Pro: simple and matches the PR-only main model. Con: topic branches do not get automatic CI until PR.
  • B: Also run CI on all topic-branch pushes. Pro: earlier feedback before PR. Con: more CI use and possible noise for experimental branches.

Recommendation: A for M1; require the existing M1 job on protected main once the checks are stable.

M2 - Meta-Harness And AgentPulse

Status: Open, M2 blocker.

  • A: Conservative event-derived formulas only. Pro: deterministic and auditable. Con: less nuanced at first.

D-021 - Meta-Harness Packaging

Status: Open implementation detail before M2 implementation; the headless control-plane baseline is accepted in ADR-0018.

Question: Which CLI/service/daemon packaging shape ships first for the already-decided headless MVP?

  • A: Headless CLI plus service/daemon. Pro: useful without Liquid and easy to test. Con: no rich GUI.
  • B: Include only a small status/admin UI after the control plane works. Pro: easier demos. Con: extra packaging surface.

Recommendation: A; no competing full standalone GUI in the MVP.

D-022 - Meta-Harness Deployment Modes

Status: Open before M2 implementation.

Question: Which modes are required for the first control-plane MVP?

  • A: Local daemon/sidecar plus CLI. Pro: simplest and matches local agents. Con: remote teams wait.
  • B: Local plus remote server. Pro: broader use. Con: pulls in auth, hosting and network trust.

Recommendation: A; preserve remote-capable protocol seams.

D-023 - Meta-Harness Service/API Transport

Status: Open before M2 implementation.

Question: Which local service transport should clients use?

  • A: JSON-RPC over local socket/named pipe with event streaming. Pro: small and local-first. Con: browser clients need a bridge.
  • B: HTTP plus server-sent events/WebSocket. Pro: easy for Liquid and tooling. Con: more exposed surface.
  • C: Hybrid: HTTP streaming for Liquid live sync, with JSON-RPC/local commands for CLI and BYOA where useful. Pro: matches both client types. Con: two transport paths need clear ownership.

Recommendation: C for the design direction; keep protocol payloads transport-neutral and pick the smallest M2 subset that serves Liquid live sync plus CLI/BYOA control.

D-024 - Meta-Harness State Storage

Status: Open before M2 implementation.

Question: Where do session registry, config proposals, audit records and metrics live?

  • A: SQLite plus append-only transcript/log files. Pro: queryable and local. Con: migration discipline needed.
  • B: JSONL/files only. Pro: transparent. Con: weaker queries and concurrency.

Recommendation: A for registry/config/metrics, while keeping transcripts append-only and exportable.

D-025 - Liquid/Meta-Harness Boundary

Status: Open implementation detail before Liquid integration work; the one-backend boundary is accepted in ADR-0018.

Question: Which API/data slices expose Meta-Harness-owned capabilities for Liquid to render?

  • A: Meta-Harness exposes session/config/metrics capabilities through its public surfaces; Liquid consumes those surfaces. Pro: one source of truth. Con: Liquid must wait for API coverage.
  • B: Liquid keeps temporary local projections that sync from Meta-Harness without becoming authority. Pro: faster UI prototypes. Con: sync rules need care.

Recommendation: A first; any projection must remain non-authoritative.

Status: Open before M3 scoping freeze.

Question: Which Liquid capabilities are required when no agents are installed?

  • A: Dashboard/component workspace, local scripts, command palette and action history. Pro: proves standalone value. Con: narrower integrations.

D-030 - External-Agent Permissions

Status: Open implementation detail before CLI/API mutation access; scoped, auditable access is the security baseline.

Question: Which scoped grant model allows external actors to read or mutate Liquid workspace data?

  • A: Resource/action-scoped grants with approval for sensitive writes. Pro: clear blast radius. Con: more permission UX.
  • B: Capability bundles scoped by workspace area and command family. Pro: easier administration. Con: coarser permissions.

Recommendation: A.

D-031 - Revert Semantics

Status: Open before action-history implementation.

Question: How does Liquid undo faulty or unwanted mutations?

  • A: Compensating actions, with checkpoint restore on conflicts. Pro: preserves history. Con: conflict handling needed.
  • B: Destructive rollback. Pro: simple. Con: weaker audit trail.

Recommendation: A.

D-032 - Shared Mutation Pipeline

Status: Open implementation detail before any Liquid write surface ships; one recorded mutation path is the accepted product invariant.

Question: Which typed command model lets UI, CLI/API, Liquid AI and external actors share that mutation path?

  • A: One typed command/mutation pipeline. Pro: no hidden writes. Con: stricter component contracts.
  • B: Per-surface adapters that normalize into the same internal command log. Pro: flexible integration. Con: adapters must prove equivalence.

Recommendation: A.

Status: Open, not an M1 blocker.

  • A: Keep internals private through M1, then stabilize a small `loop-agent-core` API. Pro: avoids freezing early mistakes. Con: embedding waits.

D-046 - Positive CIDR Egress Enforcement

Status: Open, post-M1.

Question: Which Linux backend enforces positive CIDR/port network allow entries after ADR-0051's M1 deny-all behavior?

  • A: Network namespace plus firewall rules. Pro: common Linux primitives. Con: needs privilege and CI setup.
  • B: Broker or seccomp user notification. Pro: fine-grained decisions. Con: more moving parts to prove.
  • C: eBPF/cgroup networking. Pro: kernel-level filtering. Con: higher operational complexity and privileges.

Recommendation: Keep M1 fail-closed per ADR-0051; choose the post-M1 backend before allowing non-empty network allowlists in OS-enforced runs.
