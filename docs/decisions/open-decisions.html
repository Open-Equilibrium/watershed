M2 - Meta-Harness And AgentPulse

D-010 - AgentPulse v0 Formulas

Status: Open, M2 blocker.

Question: Should the three scores use only facts already recorded during runs, or also an AI judgment?

  • A: Use recorded run facts only. Pro: the same input always gives the same auditable score. Con: the first version captures fewer nuances.
  • B: Add AI-assigned quality labels. Pro: captures more nuance. Con: scores become subjective and harder to test.

Recommendation: A for M2; reserve model-scored labels for later evaluation.

D-021 - Meta-Harness Packaging

Status: Open implementation detail before M2; ADR-0018 already requires a non-graphical controller.

Question: How should that controller be packaged for its first release?

  • A: A command-line app plus a background service. Pro: useful without Liquid and easy to test. Con: no rich interface.
  • B: Add a small status screen after the controller works. Pro: easier demonstrations. Con: another part to package and maintain.

Recommendation: A; no competing full standalone GUI in the MVP.

D-022 - Meta-Harness Deployment Modes

Status: Open before M2 implementation.

Question: Should the first controller run only on the same computer, or also as a remote server?

  • A: A background process on the same computer plus a command-line app. Pro: simplest for local agents. Con: remote teams wait.
  • B: Local operation plus a remote server. Pro: supports more users. Con: also requires sign-in, hosting and network-security work.

Recommendation: A; preserve remote-capable protocol seams.

D-023 - Meta-Harness Service/API Transport

Status: Open before M2 implementation.

Question: How should local apps send commands to Meta-Harness and receive live updates?

  • A: Use a private app-to-app channel (JSON-RPC over a local socket or named pipe). Pro: small and not exposed to the network. Con: browser-based clients need an adapter.
  • B: Use a local web interface (HTTP with a live update connection). Pro: easy for Liquid and other tools to use. Con: creates a larger security surface.
  • C: Use the web interface for Liquid and the private channel for command-line and external agents. Pro: fits both client types. Con: two paths must stay consistent.

Recommendation: C as the direction, starting with only the parts M2 needs.

D-024 - Meta-Harness State Storage

Status: Open before M2 implementation.

Question: Where do session registry, config proposals, audit records and metrics live?

  • A: SQLite plus append-only transcript/log files. Pro: queryable and local. Con: migration discipline needed.
  • B: JSONL/files only. Pro: transparent. Con: weaker queries and concurrency.

Recommendation: A for registry/config/metrics, while keeping transcripts append-only and exportable.

D-025 - Liquid/Meta-Harness Boundary

Status: Open implementation detail before Liquid integration work; the one-backend boundary is accepted in ADR-0018.

Question: Which Meta-Harness information and actions should Liquid be allowed to show and use?

  • A: Meta-Harness provides sessions, settings and measurements through one official interface; Liquid uses it. Pro: one source of truth. Con: Liquid must wait until the interface supports each need.
  • B: Liquid keeps temporary local copies synchronized with Meta-Harness. Pro: faster interface prototypes. Con: synchronization rules need care.

Recommendation: A first; any projection must remain non-authoritative.

M3 - Liquid

D-005 - Liquid Navigation And Layout

Status: Open before Liquid UI implementation.

Question: What navigation model should the first Liquid workspace use?

  • A: Workspace sidebar plus command palette. Pro: scalable and agent-friendly. Con: more interaction design.
  • B: Dashboard-first tabs. Pro: simple. Con: weaker for many workspaces/actions.

Recommendation: A.

D-009 - Liquid UI Framework

Status: Open before Liquid app shell work.

Question: Which Dart/native UI stack should implement Liquid?

  • A: Flutter. Pro: mature cross-platform tooling. Con: larger runtime surface.
  • B: Lower-level native/Dart stack. Pro: tighter control. Con: higher implementation cost.

Recommendation: Flutter unless a concrete MVP requirement rules it out.

D-026 - Liquid Standalone MVP Scope

Status: Open before M3 scoping freeze.

Question: Which Liquid capabilities are required when no agents are installed?

  • A: Dashboard/component workspace, local scripts, command palette and action history. Pro: proves standalone value. Con: narrower integrations.
  • B: Include rich agent integration first. Pro: stronger platform demo. Con: weakens standalone proof.

Recommendation: A.

D-027 - Liquid CLI/API Surface

Status: Open before external-agent Liquid edits.

Question: Which workspace read and change commands should remain stable in the MVP?

  • A: A small set of specific create, read, update and delete commands. Pro: easy to test and restrict. Con: less flexible.
  • B: One broad document interface. Pro: flexible. Con: harder to secure and change safely.

Recommendation: A.

D-028 - Liquid Action History Model

Status: Open before M3 storage work.

Question: What is the internal workspace history model?

  • A: Append-only action log plus snapshots/checkpoints. Pro: auditable and revertible. Con: compaction work later.
  • B: Mutable state plus periodic backups. Pro: simpler storage. Con: weak audit/revert.

Recommendation: A.

D-029 - Liquid Storage Model

Status: Open before M3 storage work.

Question: Which local-first store backs workspace state and history?

  • A: SQLite-backed local store. Pro: reliable local queries. Con: schema migrations.
  • B: File tree plus JSON. Pro: transparent. Con: weaker consistency and indexing.

Recommendation: A unless sync requirements force a different engine.

D-030 - External-Agent Permissions

Status: Open implementation detail before CLI/API mutation access; scoped, auditable access is the security baseline.

Question: How should outside tools receive limited permission to read or change Liquid workspace data?

  • A: Grant named resources and actions, and ask before sensitive changes. Pro: damage is clearly limited. Con: more permission prompts and settings.
  • B: Offer predefined permission bundles by workspace area. Pro: easier to manage. Con: each bundle gives broader access.

Recommendation: A.

D-031 - Revert Semantics

Status: Open before action-history implementation.

Question: How does Liquid undo faulty or unwanted mutations?

  • A: Compensating actions, with checkpoint restore on conflicts. Pro: preserves history. Con: conflict handling needed.
  • B: Destructive rollback. Pro: simple. Con: weaker audit trail.

Recommendation: A.

D-032 - Shared Mutation Pipeline

Status: Open implementation detail before any Liquid write surface ships; one recorded mutation path is the accepted product invariant.

Question: How should the interface, command line, Liquid AI and outside tools all send changes through one recorded path?

  • A: One shared, defined change pipeline. Pro: no hidden changes. Con: every component must follow a stricter contract.
  • B: A translator for each entry point that writes to the same internal log. Pro: flexible integration. Con: every translator must behave identically.

Recommendation: A.

D-033 - Component Runtime Contract

Status: Open before component implementation.

Question: What information and actions can dashboard components receive and send?

  • A: Small, defined inputs, data and events. Pro: stable and testable. Con: fewer possibilities at first.
  • B: A flexible component model with few restrictions. Pro: expressive. Con: harder to isolate safely and change later.

Recommendation: A.

D-034 - Script Component Runtime

Status: Open before script components.

Question: Where and how should Liquid script components run safely?

  • A: Run locally with access only to explicitly granted abilities. Pro: works offline and actions can be reviewed. Con: safe isolation must be built.
  • B: Run only on a remote service. Pro: isolates the local device. Con: depends on a network service and weakens offline use.

Recommendation: A, with the exact runtime chosen during M3 design.

D-035 - Sync And Collaboration

Status: Open before shared-workspace work.

Question: How should changes stay synchronized among multiple people and agents?

  • A: Keep a change log on each device and send each client updates only for views it uses. Pro: matches offline and performance goals. Con: conflicting changes are harder to resolve.
  • B: Make one central server authoritative. Pro: simpler ownership of shared changes. Con: weaker offline operation.

Recommendation: A, unless M3 constraints force a narrower local-only MVP.

Post-M1 Loop Agent Seams

D-020 - Loop Agent Embedded Core API

Status: Open, not an M1 blocker.

Question: Which small part of Loop Agent should other Rust programs be allowed to call directly?

  • A: Keep internal code private through M1, then publish a small stable loop-agent-core interface. Pro: avoids committing to early mistakes. Con: direct integration waits.
  • B: Publish the direct-call interface during M1. Pro: earlier integration. Con: later changes may break users.

Recommendation: A.

D-046 - Positive CIDR Egress Enforcement

Status: Open, post-M1.

Question: After M1's block-all policy, how should Linux allow connections only to approved network addresses and ports?

  • A: Put the process in an isolated network area with firewall rules. Pro: uses common Linux features. Con: needs extra privileges and CI setup.
  • B: Route connection requests through a checker that approves each one. Pro: precise decisions. Con: more components must work correctly.
  • C: Filter connections inside the Linux kernel (eBPF/cgroups). Pro: strong low-level enforcement. Con: harder to operate and also needs privileges.

Recommendation: Keep M1 block-all; choose and prove one approach before allowing any network destinations.
