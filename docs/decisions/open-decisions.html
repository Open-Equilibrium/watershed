Flow Agent - First Release

D-066 - Standard Tools And Executable-Code Trust

Status: Discussion required before the first Flow Agent release. Default Tools should be replaceable; their catalog, behavior and trust presentation are not yet specified. The security contract remains canonical.

Question: Which Tools should ship, what precise actions must they implement safely for hostile model inputs, and how should Engineers understand the code they are authorizing?

  • A - A small maintained default set with explicit contracts. Pro: useful without every Engineer writing basic Tools; each Tool can have meaningful behavioral tests and a clear owner. Con: Watershed must maintain those implementations and disclose where they execute project code, helpers or external services.
  • B - Definitions/examples only, with Engineers supplying implementations. Pro: less bundled code to maintain. Con: greater setup effort and more repeated security-sensitive implementation work.

Recommendation: A, with the smallest useful set. Before choosing it, specify each Tool's input/path/action limits, replacement procedure, dependency/update responsibility and executable-code trust display. A safe file Tool and a build command that executes project code have different responsibilities; neither a description nor a marketplace listing proves safety. Ordinary assigned Tool calls remain prompt-free; first-release configuration administration stays manual under SECURITY.md.

Acceptance criterion: Approve the catalog and user-facing trust explanation, then prove each shipped Tool's promised behavior under adversarial inputs on its declared platforms. Demonstrate replacing a default Tool without widening authority silently. Do not advertise third-party Tool certification or general host isolation.

Watershed - Shared Release Safeguards

D-065 - Development And Release Publication Safeguards

Status: Must be decided, implemented and verified before each affected product's first release: Flow Agent, Meta-Harness and Liquid. This entry records open work, not active protection. The approved download contract is canonical in SECURITY.md; it does not require users to install a build-provenance verifier.

Problem: A stolen publishing account or an unsafe build step could place a harmful program in the real GitHub Release, even while the visible source code remains unchanged. HTTPS and a matching checksum would still succeed. The development team must protect that trusted source without making installation harder for users.

Decisions required

  • Who may publish? Select the authorized people and automation, account protection and recovery rules, and required approval for source, release tags and publishing-workflow changes. Decide how the rules work with the actual maintainer team; do not assume a second reviewer exists.
  • What may build code access? Decide how untrusted contributions, dependency/build scripts and third-party automation are separated from publishing and Mac-signing authority. Select minimum automation permissions, credential lifetime/storage and runner isolation; reference the existing dependency safeguards, not a duplicate audit process.
  • Which bytes may be published? Bind the approved source revision, existing required gates, build inputs and final platform bundles to one release record. Decide who checks this record, completes any required Mac signing before final checksums, and authorizes publication. Internal evidence does not add an end-user provenance requirement.
  • Can a published version change? Select tag/asset replacement restrictions and evaluate GitHub's available release protections. Decide the correction procedure so the same version does not silently acquire different programs. The approved browser-download route and verification boundary are canonical in SECURITY.md; no online bootstrap is included.
  • What happens after a suspected compromise? Assign an incident owner and a procedure to halt publication, revoke affected access, withdraw or mark unsafe releases, notify users and publish a corrected version. Decide evidence retention and account/signing recovery; an offline user cannot receive immediate withdrawal information.

Options and recommendation

  • A - A protected release workflow with explicit maintainer approval. Pro: repeatable builds and checks with narrowly scoped publication access. Con: workflow, runner, approval and recovery controls must be configured and maintained.
  • B - Documented manual publication of approved, tested artifacts. Pro: fewer automated publishing permissions and a small initial setup. Con: more human steps and greater risk of uploading the wrong bytes or losing release evidence.

Recommendation: A, sized to the actual team, with narrowly scoped release authority separated from untrusted build work. B is viable only with an equally explicit artifact-check and recovery procedure. Neither option is approved by this entry.

Acceptance criterion: Record the selected controls and responsible owner for every question above. Retain non-secret evidence of the actual repository/workflow settings and a release rehearsal tied to one source revision and final bundle set. In a safe test setup, prove an unauthorized publishing attempt is rejected, untrusted build work lacks publication/signing authority, a mismatched artifact is rejected before publication, and the selected correction/withdrawal procedure works. Pass the canonical native installation checks in SECURITY.md. Maintainer approval of that evidence is required before the first release of each affected product; green branch CI or this checklist alone does not close the decision.

D-074 - Who Starts The Local Meta-Harness Service

Status: Open; decide with the service-mode slice. ADR-0215 settled that Liquid reaches its own host's Meta-Harness as a separate service.

Question: On a Mac or Linux computer, who starts the Meta-Harness service, and does it keep running when Liquid closes?

  • A: Liquid starts it when needed and stops it when it quits, as T3 Code does with its server, restarting it after a crash. Pro: nothing to install or register, and no background process while Liquid is closed. Con: agents end when Liquid quits or updates, and the CLI needs its own instance or must find Liquid's.
  • B: A login service runs it (a launchd user agent on macOS, a systemd user unit on Linux, both without administrator rights); Liquid and the CLI connect to it. Pro: agents keep running through Liquid closing, crashing or updating; one instance serves Liquid, the CLI and remote clients; the operating system restarts it. Con: installation registers the service and removal must unregister it, a process runs while nobody uses it, and updating it must not end running agents.
  • C: Liquid starts it if none runs, and it stays while agents run. Pro: no installation step, and agents finish after Liquid closes. Con: more lifetime rules to get right, and a service nobody stops if they are wrong.

Recommendation: B, which matches the background service D-021 recommends: agents survive the window, and the operating system supervises the service instead of our own restart code.

Acceptance criterion: The ADR log names who starts and stops the service, and tests show Liquid connecting to a running service and reporting one it cannot reach.

D-092 - Reaching The Person's Agent Hosts With One Sign-In

Status: Open before M2's remote connection; Meta-Harness, not T3 Code, holds the connection (ADR-0281). ADR-0185 gives Meta-Harness an authenticated remote connection, and ADR-0229 and ADR-0253 assume the person's hosts reach each other, but nothing decides how a phone or another host reaches an agent host outside the local network, or how hosts learn of each other.

Goal (maintainer, 2026-11-12): a person without technical knowledge signs in once on each agent host. Afterwards Liquid on every device shows all of them, and the hosts provide the four durability levels of ADR-0229 and start each other's agents (ADR-0253), without entering an address, port, pairing code or VPN.

How T3 Code does it: with T3 Connect, each host signs in once to a T3 account and gets a tunnel that T3 operates on Cloudflare; other devices sign in to the same account and list the hosts. Without the account it offers the local network, Tailscale or SSH, with a pairing code per device. Linking two hosts for agents needs a pairing code per link either way.

  • A: The Liquid account (ADR-0224) also registers agent hosts. A host signs in once, through a browser link with a short code as T3's CLI does. The Sync Server gives the person's devices and hosts each other's identities and keys. They connect directly where they can, otherwise through a relay that forwards only end-to-end encrypted traffic, using an existing NAT-traversal and relay library (for example iroh) rather than our own. Pro: one account for the Workspace and the hosts; self-hostable; no vendor cloud. Con: a relay to build and run beside the Sync Server, whose operator pays its traffic; every host trusts the Sync Server as broker, so its compromise matters as T3's relay signing key does.
  • B: Tailscale, or self-hosted Headscale. Hosts and devices join the person's tailnet; the Sync Server only lists the hosts. Pro: proven encryption and NAT traversal, nothing to build. Con: a second account and app; Tailscale's coordination server unless Headscale is self-hosted; iOS runs one VPN at a time.
  • C: T3 Connect. Pro: exists, free for up to three machines. Con: a second account at T3, and more machines need a paid T3 Chat plan; traffic through T3's and Cloudflare's cloud, against self-hosting; Liquid would need T3's sign-in; agent links still need pairing codes.
  • D: Local network and pairing codes only; internet access through the person's own VPN. Pro: nothing to build. Con: misses the goal.

Recommendation: A, with B as the interim for engineers until the relay works.

Acceptance criterion: with a laptop and a second computer on different networks, the person signs in once on each; Liquid on a phone lists both hosts and attaches to a session on each; a session continues from one host on the other at a turn boundary; an agent on one host starts a thread on the other; no address, port, code or VPN is entered; removing a host in Liquid ends its access; the relay cannot read session content.

D-102 - Watershed Git Rules T3 Code Does Not Ship

Status: Open; blocks deleting the Git code under ADR-0282. The maintainer wants to discuss each rule separately, and may drop some (2026-11-14). The comparison with T3 Code is still to do.

Question: For each rule in the V-Spec that T3 lacks, keep it in Meta-Harness, propose it to T3, or drop it?

  • The person writes every commit message; nothing generates one.
  • Revert lists the affected files first, runs only while the project still matches that list (ADR-0256), restores only the working tree and is refused while an agent runs in the checkout.
  • Operating-system file locks order turns, reverts, Initialize Git, session deletion and worktree changes across Liquid windows.
  • No branch switch, stash, commit or pull while an agent runs in the checkout.
  • Switching with changes offers to leave them in the branch's one stash or bring them along.
  • The Chat's own model writes pull request text, so the diff reaches only that provider.
  • The worktree root lies outside the data folders, and removal never forces or loses work.
  • Deleting a session deletes its checkpoints; one action removes all of them.

Recommendation: after the comparison, drop rules that only add convenience, and keep or propose upstream those that prevent losing work.

Acceptance criterion: each rule is marked keep, upstream or drop in the ADR log.

D-056 - Existing Output Security-Metadata Matrix

Status: Open before post-M1 existing-output replacement; not an M1.1 blocker.

Question: Which exact security-metadata fields must atomic own-script output replacement preserve on Flow Agent's native targets in PLATFORMS.md, and what happens when a required field cannot be read or applied?

Decided direction: The create-only output boundary in SECURITY.md rejects every existing output target in M1.1; replacement remains unavailable until this finite per-platform field matrix is decided and implemented.

  • A: Preserve a maintainer-selected native field set and fail when any selected field is unavailable. Pro: explicit, testable preservation. Con: replacements can fail because of privileges or platform support.
  • B: Preserve a smaller maintainer-selected field set and reject targets carrying selected unsupported metadata. Pro: a narrower implementation. Con: detection and rejection rules remain platform-specific.

Recommendation: A; choose the exact fields and unavailable-field behavior only with platform evidence.

Acceptance criterion: Record the exact finite matrix and failure behavior, then pass native fixtures on each supported Flow Agent target for every required field before restoring existing-output replacement.

D-058 - Portable Conversation Archive And Tree Handoff

Status: Open before cross-device Portable continuation or a public tree-navigation/import surface.

Question: Which public archive closure should carry a completed checkpoint to another device while preserving tree navigation, transactional import and the accepted child-Run/branch semantics?

  • A: Export the complete Conversation tree and every referenced immutable artifact. Pro: self-contained history and full tree navigation. Con: archives can be large and repeat old data.
  • B: Export only the selected branch's verified transitive closure. Pro: smaller and sufficient for that continuation. Con: omitted sibling branches need a later union/import rule before one tree can be reconstructed.
  • C: Define content-addressed archive records that support both full export and incremental transfer through one schema. Pro: deduplication and efficient repeated device sync. Con: the first contract, recovery matrix and retention policy are more complex.

Recommendation: A first; keep the schema content-addressable so C can later optimize transport without changing Conversation authority. A Pi-style tree view renders the imported canonical graph and never becomes a second history authority.

Acceptance criterion: Fix the public archive closure, schema, size/resource bounds, content hashes, D-062 authenticated-root/provenance result, access/confidentiality and transfer protection, export/import transaction, version migration, branch-ID collision handling, optional coordinated source/destination fencing and recovery matrix. Exclude credential-store records, Runtime-binding credential references, approvals, Runtime bindings, structural source-host path/authority fields and leases, while treating all recorded user/provider/Tool/artifact content—including embedded path strings—as inert, potentially sensitive evidence. Require the destination actor to select and authorize one canonical Workspace, validate its compatibility and explicitly rebind allowed paths/artifacts before effects. Re-import into an existing Conversation must verify its common prefix by identity and hash, transactionally union non-conflicting descendant branches, be idempotent on repeated input and fail without mutation on conflicting records; it never merges two linear Runs. Prove no completed effect is redispatched; an uncertain provider attempt in the selected checkpoint's reachable state keeps that checkpoint non-executable because it has no reconciliation surface, while a relevant uncertain Tool attempt blocks child-Run creation until existing eligible-Tool reconciliation settles it; unrelated uncertain branches remain history without tainting eligible branches; and two disconnected continuations converge as distinct child branches.

D-059 - Offline Provisioning And Local Inference Binding

Status: Open before claiming offline-after-provisioning productive Flow execution.

Decided boundary: ADR-0153 requires a provider-neutral capability contract and device-local Runtime binding. A binding identifies the endpoint plus the provider/model, local artifact/quantization/runtime, credential-reference and resource-policy fields applicable to that provider; local artifacts and credentials may be absent. Credential material remains in the Flow-owned protected store.

Question: How should a device provision and discover conforming local artifacts, verify their claims and choose among compatible installed bindings without depending on an Internet service?

  • A: The operator installs a signed artifact manifest and explicitly selects one binding; a local probe verifies identity, capabilities and readiness before use. Pro: deterministic choice and small discovery surface. Con: more manual provisioning.
  • B: Flow Agent discovers installed bindings from a protected device-local catalog, probes each and selects only by an explicit deterministic policy. Pro: easier multi-model operation. Con: catalog mutation, tie-breaking and stale entries add state.
  • C: Meta-Harness may manage the same protected host catalog through Flow Agent's public surface, while standalone Flow Agent retains A. Pro: centralized fleet management without breaking standalone use. Con: audit, reconciliation and ownership between both clients need a finite contract.

Recommendation: A first; make its manifest/catalog schema reusable by B and C. Keep model acquisition outside Conversation state and evaluate actual context, latency, memory, energy and tool capabilities rather than model-size labels.

Acceptance criterion: Record the supported artifact/signature, catalog/discovery, capability, provenance, deterministic selection, credential-reference, admission and failure schemas; bind every credential reference to the selected provider and endpoint audience and reject a mismatch before secret resolution; preserve the protected credential store's permissions, locking, refresh and redaction rules; satisfy the local-runtime process boundary selected in D-061; provision one supported local stack; then run a productive Flow with network interfaces disabled and no remote authentication, licensing, telemetry or update dependency while requested remote-only actions fail clearly, sync reports offline/stale and waits resumably, and neither blocks unrelated local work.

D-060 - Offline Approval And Revocation Authority

Status: Open before an imported continuation can use approval-bearing Meta-Harness, Liquid or external actions while disconnected. This decision adds no Flow Agent Tool-approval prompt; ADR-0135 remains authoritative for assigned Tools.

Question: After an imported continuation reauthenticates locally, how may that destination approve sensitive work while it cannot learn later remote Role, policy or identity revocations?

  • A: Require a fresh local approval for each sensitive action. Pro: smallest authority and clearest audit. Con: repetitive for long offline workflows.
  • B: Let the destination issue a local, device-bound grant for an exact action set, resource set and short expiry. Pro: bounded offline automation. Con: expiry, one-use behavior and reconnect reconciliation need careful rules.
  • C: Let an administrator pre-authorize a destination-local offline profile before disconnection. Pro: predictable unattended work. Con: broader stale authority and stronger provisioning/audit requirements.

Recommendation: A initially; consider B only after a finite local key, replay and reconciliation design. The accepted boundary still forbids transferring prior approvals in a Conversation archive.

Acceptance criterion: Define actor/device identity, local grant scope, expiry, one-use behavior, audit records, reconnect reconciliation and the explicit limit that a disconnected device cannot observe later revocation; prove an imported archive alone authorizes no Workspace, Tool, config or external action.

D-061 - Local Inference Process Trust Boundary

Status: Open before D-059 can enable a productive local model runtime.

Question: What may executable local inference code access on the host while it receives model context outside the Tool's Flow-owned write protection?

  • A: Treat the runtime as part of Flow Agent's trusted computing base under the operator's OS identity. Pro: simplest integration and lowest IPC overhead. Con: it may read global config, credentials, sessions and Workspace bytes; signatures prove provenance, not confinement.
  • B: Run it under a separate identity or enforceable Sandbox/service boundary with only a bounded authenticated inference channel and declared model/cache storage. Pro: contains filesystem, secret, process and network access. Con: substantial cross-platform packaging, accelerator and performance work.
  • C: Link the runtime in-process. Pro: smallest transport overhead. Con: maximally expands Flow Agent's memory-safety, dependency and secret-access trust base.

Recommendation: B for the supported offline claim. An explicit A installation may exist only with a clear no-isolation warning and no claim that signed artifacts are contained.

Acceptance criterion: For every option, record the process/identity, IPC, filesystem, credential, config, session, Workspace, model/cache, network, child-process, resource, crash and update boundaries per supported platform and enforce bounded request/result I/O. If B is selected, authenticate the channel and prove the runtime receives only admitted context/capabilities and cannot obtain protected stores or Workspace data outside that contract. If A or C is allowed, name the runtime and dependencies as trusted computing base, display the no-isolation status before use, make no secret/filesystem containment claim and test provenance, update and failure behavior under that stated trust model.

D-062 - Portable Archive Authenticity Root

Status: Open before D-058 may call an imported checkpoint verified or executable.

Question: How does a destination authenticate an archive's root manifest and provenance when an attacker could otherwise rewrite content and recompute ordinary hashes?

  • A: Sign the canonical root manifest with a source device/user key chained to a known identity. Pro: offline attribution and tamper evidence. Con: enrollment, rotation, revocation and lost-device handling are required.
  • B: Authenticate the root with a shared user/Workspace archive key. Pro: compact offline verification across devices. Con: shared-secret distribution weakens sender attribution and increases compromise impact.
  • C: Import as explicitly unauthenticated, non-executable evidence, require human review and let the destination re-seal a new local root before any continuation. Pro: no cross-device key infrastructure. Con: cannot preserve trusted provenance or automatic continuation.

Recommendation: A; retain C as a clearly separate recovery path that never claims verified source history.

Acceptance criterion: For A/B, define canonical signed/MACed bytes, identity binding, key storage/rotation/revocation limits, replay/downgrade rules, attribution and verification errors; tampering with the authenticated root, content, branch links or version must fail before destination mutation or provider/Tool effects. For C, label every record unauthenticated, permit no Portable continuation or effects, define explicit human review and destination resealing as new local evidence, and never claim source attribution or source-history verification.

D-076 - Private Terminal For Tools

Status: Open after the first Flow Agent release. ADR-0170 denies Tools direct access to terminal devices, so a Tool cannot write over or type into the terminal where a person reviews Flow Agent's output. Programs that insist on a terminal, such as password prompts of ssh or sudo, full-screen programs and some interactive shells, then fail or behave differently; ordinary input over stdin still works.

Question: Should Flow Agent give each Tool call its own private terminal?

  • A: Keep no terminal. Pro: the simplest rule, already in place. Con: those programs stay unavailable to Tools.
  • B: A new pseudo-terminal per Tool call that Flow Agent creates and connects to nothing the user sees, as Codex's Seatbelt profile lets commands open new pseudo-terminals but not the user's. Pro: programs that need a terminal run, and the user's terminal stays protected. Con: native work per operating system and sandbox profile; a program can wait for input forever, so a time limit must end it; terminal control codes in its output must be shown safely.
  • C: Connect the Tool's terminal to the user in the CLI or Liquid, so they can answer it. Pro: interactive Tools work fully. Con: a Tool could imitate Flow Agent's own prompts, the risk ADR-0170 removes.

Recommendation: B once a concrete Tool needs it; C only after a new security review.

Acceptance criterion: Native tests on each supported Flow Agent target show a Tool using its own terminal, no Tool reaching the user's terminal, and a waiting Tool ending at its time limit.
