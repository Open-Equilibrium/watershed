Release 1 - Native Execution And Distribution

D-063 - Native macOS Tool Security Contract

Status: Proposal for maintainer review, not an accepted security change or a proven backend. Native macOS ARM64 remains required by PLATFORMS.md; the current security contract and refusal to launch unsupported Tools remain unchanged.

Question: Must every native platform promise Linux's exact file-object mounts, preventive per-invocation process-and-thread ceiling and cleanup after an Executor crash, or should Flow distinguish data-access protection from platform-specific resource and cleanup guarantees? A working Mac build does not answer this question.

Options and recommendation

  • A - Retain identical guarantees. Pro: one strong contract, including containment of deliberately hostile process creation. Con: no supported native Mac implementation has been established for the combination; Release 1 remains blocked. More hardware or repeated example tests cannot supply a missing operating-system mechanism.
  • B - Keep a mandatory data-access boundary and declare stronger capabilities separately. Pro: preserves meaningful protection while avoiding Linux-specific availability promises on every platform. Con: Mac file-grant semantics, supported tools and crash behavior need an explicit narrower contract and native proof; feasibility is still unresolved.
  • C - Offer explicitly trusted native execution on Mac. Pro: broad native tool compatibility without a VM. Con: the executed program and its dependencies have the user's host authority; Flow cannot claim filesystem, secret or network containment. This would change the accepted Release 1 Sandbox requirement, not fulfill it.

Recommendation: B as the contract to investigate, not permission to ship an unproven backend. Do not remove Linux's working protections. Do not use C as an automatic fallback. If the mandatory boundary below cannot be enforced with supported Mac facilities, return to the maintainer with that failed criterion instead of silently widening access.

Proposed contract under B

  • Authority and secrets remain mandatory. Agentic Engineers select explicit effective capabilities. Tools and model output cannot widen them. No implicit access to Flow's credential/configuration stores, private home data or another invocation's protected data. Existing environment, descriptor, protocol and credential protections remain required. Data deliberately admitted as input or returned by a Tool is not automatically secret-free.
  • File access remains operating-system enforced. Mac may use an explicitly selected native file/directory grant rather than claim Linux mount-object equivalence. Its exact scope, inherited runtime reads, replacement/link behavior and concurrent-invocation isolation must be specified and proven before approval. An existing exact policy must be rejected if it cannot be honored; it must never be translated into a broader grant automatically. This does not relax identity checks for Flow's own stores.
  • Tool networking remains deny-all. Test direct connections and indirect escape through local sockets, operating-system services and child programs. Provider traffic is a separate Flow-owned path; this proposal does not enable positive network grants or let a Tool reach a local model endpoint.
  • The Linux process/thread ceiling remains a Linux capability. Do not claim an equivalent preventive, invocation-local ceiling on Mac without evidence. Per-process limits or monitoring can improve reliability but do not contain a hostile process/thread explosion. A Flow requiring the stronger capability must fail before launch on an incapable backend.
  • Cancellation must report truthfully. Bound the controller's waiting and output handling, attempt whole-invocation cleanup and verify the supported lifecycle boundary. Without proof, never report a clean stop or a guarantee that no descendant survived an Executor crash. A non-cleanup-guaranteed Mac profile would require a separately approved terminal/recovery rule: persist identity-wide in-flight authority before Start, then block further native Tool launches for that identity whenever cleanup is uncertain, including after controller death/restart. Clear that block only with proof that the invocation cannot still execute, not a process-list snapshot or warning acknowledgement. A warning does not prevent survivors from continuing their admitted effects; this remains a real availability/integrity tradeoff.
  • No whole-computer availability or arbitrary-tool compatibility promise. Limiting process counts alone does not bound aggregate memory, disk, CPU or GPU use. Supported Apple development tools need actual positive tests; unsupported operations fail before launch without requesting broad system permissions. Native Metal inference remains a separate D-061 trust decision, not a reason to expose provider credentials to Tools.

Evidence and implementation limits

Apple's file-access documentation describes app-associated containers, user-selected grants and transferable bookmarks. It explicitly limits executable locations under user-selected-file entitlements. These are not proof of arbitrary host-tool execution, exact retained-object grants or isolation between invocations sharing a container. Its embedded-helper guide supports signed sandbox inheritance, including independent Developer ID distribution; that is a candidate packaging mechanism, not certification of Flow's boundary.

The XNU resource-limit contract defines RLIMIT_NPROC per user ID, not per invocation including threads. The launchd contract describes killing the remaining process group, not every hostile descendant that changes groups. Neither justifies the current Linux-equivalent claim. No private-API workaround, VM path, permanent service or new dependency is approved here.

Finite acceptance before implementation is called supported

  1. Record the selected option and exact capability/receipt/failure contract, including file identity, grant lifetime/revocation, shared-container isolation, resource ceilings and crash-cleanup guarantees, before defining its fixtures. Approving an investigation is not approving its eventual restrictions.
  2. Fix a finite supported executable/interpreter/library graph, signed locations and sandbox identities on native macOS 26 ARM64, including an ordinary shell child and a real Apple compiler/build workload. Establish their supported launch/grant mechanism and prove read-only input, writable output and denied private files. This certifies only that graph, not arbitrary host tools; do not substitute a bundled demonstration helper for the declared Apple-tool workload.
  3. Establish the general authority invariant: no invocation can obtain an object or transferable grant not admitted to its own policy, whether through concurrent or persisted state from another invocation. Exercise links/replacements, disjoint grants, inherited descriptors/environment, shared containers/bookmarks and direct/indirect network attempts against that mechanism. Shared state that bypasses the invariant fails B, whether read-only or writable; an example list alone is not proof.
  4. Exercise child creation, group/session changes, normal exit, timeout, cancellation, forced Executor termination and controller kill/restart across the post-Start persistence boundaries. Prove the identity-wide launch block survives each uncertain case before another Tool can start. Distinguish proven cleanup from unknown survivors; test exact N/N+1 only where a preventive ceiling is actually implemented. If B needs new recovery states, approve them before implementation and test those reachable states.
  5. Verify installation, signing and any first-use authorization on a clean Mac without disabling security settings or requiring a Linux guest. Establish Apple-tool compatibility and separately prove the chosen D-061 Metal runtime boundary before claiming local inference support.
  6. Retain Linux's native matrix and the ordinary test gates. If any mandatory criterion fails, keep Mac Tool execution unavailable and report that concrete blocker; do not enumerate unbounded workarounds or label the overall release ready.

Maintainer decision: Select A, B or C. For B, explicitly decide whether native file grants may differ from exact Linux mounts and whether lack of a preventive thread ceiling or guaranteed crash cleanup is acceptable for an opt-in Mac profile. Backend and packaging details require evidence before the final contract can be accepted.

D-064 - Download Bundle Authenticity

Status: Open before publishing the accepted versioned prebuilt download bundle (ADR-0164). The bundle format is decided; this is not a request to revisit it.

Question: How will users verify that the downloaded programs came from the intended release, rather than merely matching a checksum supplied with the same download?

  • A: Publish through the repository's official HTTPS release channel with checksums. Pro: the smallest distribution path. Con: checksums detect corruption but do not independently authenticate a compromised release channel.
  • B: Add verifiable build provenance bound to the repository's release workflow and exact artifact digest. Pro: ties the download to the intended producer and build. Con: verification tooling, trusted workflow identity and offline behavior must be specified.
  • C: Sign release manifests with a separately managed release key. Pro: supports independent offline verification. Con: key custody, rotation and compromise recovery add maintenance.

Recommendation: B if its verification can be included in the supported installation path without a separate developer-tool setup; otherwise explicitly decide whether A's narrower trust model is sufficient for Release 1. Apple signing/notarization for the selected Mac mechanism is a separate platform requirement, not a Linux authenticity proof.

Acceptance criterion: Decide the verifier trust root, repository/workflow/ref or signing-key identity, offline/revocation limits and verification/failure procedure. Bind version, native target and the final distributable digest to that identity, after any signing, notarization and ticket stapling; verification covers all shipped executables and installer bytes. Prove a clean native install without user compilation, rejection of altered or wrong-target artifacts, transparent prerequisites and unchanged host security. The existing installer contract remains create-only; choosing a download bundle adds neither an updater nor in-place upgrades.

Post-M1.2 - Flow Agent Platform Expansion

D-046 - Approved Network Address Enforcement

Status: Open, post-M1.2 blocker before positive network grants; M1.2 ships deny-all Tool networking.

Question: After M1.2's enforced deny-all policy, how should Linux allow connections only to approved network addresses and ports?

  • A: Put the process in an isolated network area with firewall rules. Pro: uses common Linux features. Con: needs extra privileges and CI setup.
  • B: Route connection requests through a checker that approves each one. Pro: precise decisions. Con: more components must work correctly.
  • C: Let Linux itself filter the process's connections. Pro: strong low-level enforcement. Con: harder to operate and also needs privileges.

Recommendation: Keep block-all until one approach is selected and proven.

Acceptance criterion: Record the backend and runner, then pass a finite matrix for allowed and denied TCP/UDP CIDR/port rules, DNS, DoH, DoT, child processes and indirect connection attempts before enabling any positive grant.

D-010 - AgentPulse v0 Formulas

Status: Open, M2 blocker.

Question: Should the three scores use only facts already recorded during runs, or also an AI judgment?

  • A: Use recorded run facts only. Pro: the same input always gives the same auditable score. Con: the first version captures fewer nuances.
  • B: Add AI-assigned quality labels. Pro: captures more nuance. Con: scores become subjective and harder to test.

Recommendation: A for M2; reserve model-scored labels for later evaluation.

D-021 - Meta-Harness Packaging

Status: Open implementation detail before M2; ADR-0018 already requires a non-graphical controller.

Question: How should that controller be packaged for its first release?

  • A: A command-line app plus a background service. Pro: useful without Liquid and easy to test. Con: no rich interface.
  • B: Add a small status screen after the controller works. Pro: easier demonstrations. Con: another part to package and maintain.

Recommendation: A; no competing full standalone GUI in the MVP.

D-023 - Meta-Harness Service/API Transport

Status: Open before M2 implementation.

Question: How should programs on the same computer, and authenticated Liquid clients on other devices, communicate with Meta-Harness without moving agent ownership off the host?

  • A: Use a private connection that works only on the same computer. Pro: smallest security surface. Con: remote Liquid needs a later gateway.
  • B: Use one protected web connection for local and remote clients. Pro: one network-capable path. Con: larger local security surface.
  • C: Define one shared set of commands, carried by a private local connection on the host and a protected network connection remotely. Pro: fits both topologies. Con: both connections must behave alike.

Recommendation: C as the direction, starting with only the parts M2 needs.

D-024 - Meta-Harness State Storage

Status: Open before M2 implementation.

Question: Where do session registry, config proposals, audit records and metrics live?

  • A: SQLite plus append-only transcript/log files. Pro: queryable and local. Con: migration discipline needed.
  • B: JSONL/files only. Pro: transparent. Con: weaker queries and concurrency.

Recommendation: A for registry/config/metrics, while keeping transcripts append-only and exportable.

D-048 - HerdR CLI-Agent Backend Integration

Status: Open, M2 blocker before Meta-Harness CLI-agent process execution.

Question: Should Meta-Harness reuse HerdR for host-local terminals, whole CLI agent processes and session persistence while retaining policy, normalized records, shared config, schedules, audit and AgentPulse? This boundary is unrelated to Flow's Executor protocol and does not manage Flow Tool Sandboxes.

  • A: Integrate HerdR as an optional Meta-Harness agent executor through its versioned CLI/socket API. Pro: reuses terminal multiplexing, process persistence, agent detection and remote attachment while preserving Meta-Harness boundaries. Con: requires stable identity mapping, failure recovery and a maintained adapter.
  • B: Require HerdR as the runtime for all external CLI agents. Pro: one execution path and an existing terminal UI. Con: couples M2 availability and semantics to HerdR's platform support, protocol and roadmap.
  • C: Build the Meta-Harness agent executor independently and use HerdR only as a comparison. Pro: complete control over the CLI-process boundary. Con: duplicates substantial terminal, process and persistence work.

Recommendation: A behind a backend-neutral Meta-Harness agent-executor contract, subject to a bounded integration spike; keep direct semantic adapters where they provide richer events.

Acceptance criterion: The spike starts, steers, observes and restores Codex plus one other CLI agent without an attached HerdR UI; preserves stable Meta-Harness session identity across detach and service restarts; routes every mutation through the Meta-Harness policy/audit gate; normalizes HerdR events without treating terminal inference as semantic truth; rejects cross-host process claims; and documents fail-closed behavior for unsupported capabilities on the native targets in PLATFORMS.md.

  • A: A small set of resource-specific commands and action schemas. Pro: compact for agents, easy to test and restrict. Con: new capabilities need explicit additions.

D-028 - Liquid Action History Model

Status: Open before M3 storage work.

Question: How should Liquid remember changes so users can inspect and undo them?

  • A: Keep an unchangeable sequence of actions plus occasional full save points. Pro: auditable and reversible. Con: old entries must be combined or archived later.
  • B: Keep only the current state plus periodic backups. Pro: simpler storage. Con: weak audit and undo.

Recommendation: A.

D-029 - Liquid Storage Model

Status: Open before M3 storage work.

Question: How should Liquid store workspace state and history on the user's device?

  • A: Use a SQLite database as the local copy. Pro: reliable offline searches and all-or-nothing updates. Con: upgrades and sharing need careful data conversion.
  • B: Use folders of readable JSON files as the local copy. Pro: transparent. Con: weaker consistency and slower searching.

Recommendation: A unless sync requirements force a different engine.

D-031 - Revert Semantics

Status: Open before action-history implementation.

Question: How should Liquid undo a faulty or unwanted change?

  • A: Record a new action that reverses the earlier one, or restore a save point when changes conflict. Pro: preserves history. Con: conflicts need clear handling.
  • B: Replace history with the earlier state. Pro: simple. Con: weakens the audit trail.

Recommendation: A.

D-035 - Sync Conflict Semantics

Status: Open before shared-workspace work.

Question: When local replicas send concurrent offline changes to the central Sync Server, how should Liquid combine them?

  • A: Combine recorded changes using the same fixed rule for each field and ask the user when no safe combination exists. Pro: preserves local-first behavior and audit history. Con: more merge design.
  • B: Keep the most recent ordinary field value and ask only about deletes or structural changes. Pro: smaller first implementation. Con: can silently discard intent.

Recommendation: A, scoped first to the M3 Block Types and action model.

Post-M1 Flow Agent Seams

D-020 - Flow Agent Embedded Core API

Status: Open before external Rust embedding; not an M1 blocker.

Current scope: Until a post-M1 supported library is selected, only the CLI and protocol are supported Flow Agent interfaces. Rust pub items are workspace implementation detail without a compatibility promise.

Question: Should another Rust application run Flow Agent inside the same program, or start the flow command and communicate through its documented input and output?

  • A: Add a small supported Rust library interface after M1. Pro: direct calls without managing another process. Con: Watershed must keep that interface compatible and tightly couples both programs.
  • B: Keep the current Rust building blocks internal and use the command/protocol boundary. Pro: a smaller public surface and independent crashes/upgrades. Con: the caller must manage a process and adapter.

Recommendation: A only when a concrete post-M1 consumer proves the smallest useful interface; see PROTOCOL.md.

D-056 - Existing Output Security-Metadata Matrix

Status: Open before post-M1 existing-output replacement; not an M1.1 blocker.

Question: Which exact security-metadata fields must atomic own-script output replacement preserve on Flow Agent's native targets in PLATFORMS.md, and what happens when a required field cannot be read or applied?

Decided direction: The ADR-0087/ADR-0088 create-only boundary rejects every existing output target in M1.1; replacement remains unavailable until this finite per-platform field matrix is decided and implemented.

  • A: Preserve a maintainer-selected native field set and fail when any selected field is unavailable. Pro: explicit, testable preservation. Con: replacements can fail because of privileges or platform support.
  • B: Preserve a smaller maintainer-selected field set and reject targets carrying selected unsupported metadata. Pro: a narrower implementation. Con: detection and rejection rules remain platform-specific.

Recommendation: A; choose the exact fields and unavailable-field behavior only with platform evidence.

Acceptance criterion: Record the exact finite matrix and failure behavior, then pass native fixtures on each supported Flow Agent target for every required field before restoring existing-output replacement.

D-058 - Portable Conversation Archive And Tree Handoff

Status: Open before cross-device Portable continuation or a public tree-navigation/import surface.

Question: Which public archive closure should carry a completed checkpoint to another device while preserving tree navigation, transactional import and the accepted child-Run/branch semantics?

  • A: Export the complete Conversation tree and every referenced immutable artifact. Pro: self-contained history and full tree navigation. Con: archives can be large and repeat old data.
  • B: Export only the selected branch's verified transitive closure. Pro: smaller and sufficient for that continuation. Con: omitted sibling branches need a later union/import rule before one tree can be reconstructed.
  • C: Define content-addressed archive records that support both full export and incremental transfer through one schema. Pro: deduplication and efficient repeated device sync. Con: the first contract, recovery matrix and retention policy are more complex.

Recommendation: A first; keep the schema content-addressable so C can later optimize transport without changing Conversation authority. A Pi-style tree view renders the imported canonical graph and never becomes a second history authority.

Acceptance criterion: Fix the public archive closure, schema, size/resource bounds, content hashes, D-062 authenticated-root/provenance result, access/confidentiality and transfer protection, export/import transaction, version migration, branch-ID collision handling, optional coordinated source/destination fencing and recovery matrix. Exclude credential-store records, Runtime-binding credential references, approvals, Runtime bindings, structural source-host path/authority fields and leases, while treating all recorded user/provider/Tool/artifact content—including embedded path strings—as inert, potentially sensitive evidence. Require the destination actor to select and authorize one canonical Workspace, validate its compatibility and explicitly rebind allowed paths/artifacts before effects. Re-import into an existing Conversation must verify its common prefix by identity and hash, transactionally union non-conflicting descendant branches, be idempotent on repeated input and fail without mutation on conflicting records; it never merges two linear Runs. Prove no completed effect is redispatched; an uncertain provider attempt in the selected checkpoint's reachable state keeps that checkpoint non-executable because it has no reconciliation surface, while a relevant uncertain Tool attempt blocks child-Run creation until existing eligible-Tool reconciliation settles it; unrelated uncertain branches remain history without tainting eligible branches; and two disconnected continuations converge as distinct child branches.

D-059 - Offline Provisioning And Local Inference Binding

Status: Open before claiming offline-after-provisioning productive Flow execution.

Decided boundary: ADR-0153 requires a provider-neutral capability contract and device-local Runtime binding. A binding identifies the endpoint plus the provider/model, local artifact/quantization/runtime, credential-reference and resource-policy fields applicable to that provider; local artifacts and credentials may be absent. Credential material remains in the Flow-owned protected store.

Question: How should a device provision and discover conforming local artifacts, verify their claims and choose among compatible installed bindings without depending on an Internet service?

  • A: The operator installs a signed artifact manifest and explicitly selects one binding; a local probe verifies identity, capabilities and readiness before use. Pro: deterministic choice and small discovery surface. Con: more manual provisioning.
  • B: Flow Agent discovers installed bindings from a protected device-local catalog, probes each and selects only by an explicit deterministic policy. Pro: easier multi-model operation. Con: catalog mutation, tie-breaking and stale entries add state.
  • C: Meta-Harness may manage the same protected host catalog through Flow Agent's public surface, while standalone Flow Agent retains A. Pro: centralized fleet management without breaking standalone use. Con: audit, reconciliation and ownership between both clients need a finite contract.

Recommendation: A first; make its manifest/catalog schema reusable by B and C. Keep model acquisition outside Conversation state and evaluate actual context, latency, memory, energy and tool capabilities rather than model-size labels.

Acceptance criterion: Record the supported artifact/signature, catalog/discovery, capability, provenance, deterministic selection, credential-reference, admission and failure schemas; bind every credential reference to the selected provider and endpoint audience and reject a mismatch before secret resolution; preserve the protected credential store's permissions, locking, refresh and redaction rules; satisfy the local-runtime process boundary selected in D-061; provision one supported local stack; then run a productive Flow with network interfaces disabled and no remote authentication, licensing, telemetry or update dependency while requested remote-only actions fail clearly, sync reports offline/stale and waits resumably, and neither blocks unrelated local work.

D-060 - Offline Approval And Revocation Authority

Status: Open before an imported continuation can use approval-bearing Meta-Harness, Liquid or external actions while disconnected. This decision adds no Flow Agent Tool-approval prompt; ADR-0135 remains authoritative for assigned Tools.

Question: After an imported continuation reauthenticates locally, how may that destination approve sensitive work while it cannot learn later remote Role, policy or identity revocations?

  • A: Require a fresh local approval for each sensitive action. Pro: smallest authority and clearest audit. Con: repetitive for long offline workflows.
  • B: Let the destination issue a local, device-bound grant for an exact action set, resource set and short expiry. Pro: bounded offline automation. Con: expiry, one-use behavior and reconnect reconciliation need careful rules.
  • C: Let an administrator pre-authorize a destination-local offline profile before disconnection. Pro: predictable unattended work. Con: broader stale authority and stronger provisioning/audit requirements.

Recommendation: A initially; consider B only after a finite local key, replay and reconciliation design. The accepted boundary still forbids transferring prior approvals in a Conversation archive.

Acceptance criterion: Define actor/device identity, local grant scope, expiry, one-use behavior, audit records, reconnect reconciliation and the explicit limit that a disconnected device cannot observe later revocation; prove an imported archive alone authorizes no Workspace, Tool, config or external action.

D-061 - Local Inference Process Trust Boundary

Status: Open before D-059 can enable a productive local model runtime.

Question: What may executable local inference code access on the host while it receives model context outside the Tool Sandbox?

  • A: Treat the runtime as part of Flow Agent's trusted computing base under the operator's OS identity. Pro: simplest integration and lowest IPC overhead. Con: it may read global config, credentials, sessions and Workspace bytes; signatures prove provenance, not confinement.
  • B: Run it under a separate identity or enforceable Sandbox/service boundary with only a bounded authenticated inference channel and declared model/cache storage. Pro: contains filesystem, secret, process and network access. Con: substantial cross-platform packaging, accelerator and performance work.
  • C: Link the runtime in-process. Pro: smallest transport overhead. Con: maximally expands Flow Agent's memory-safety, dependency and secret-access trust base.

Recommendation: B for the supported offline claim. An explicit A installation may exist only with a clear no-isolation warning and no claim that signed artifacts are contained.

Acceptance criterion: For every option, record the process/identity, IPC, filesystem, credential, config, session, Workspace, model/cache, network, child-process, resource, crash and update boundaries per supported platform and enforce bounded request/result I/O. If B is selected, authenticate the channel and prove the runtime receives only admitted context/capabilities and cannot obtain protected stores or Workspace data outside that contract. If A or C is allowed, name the runtime and dependencies as trusted computing base, display the no-isolation status before use, make no secret/filesystem containment claim and test provenance, update and failure behavior under that stated trust model.

D-062 - Portable Archive Authenticity Root

Status: Open before D-058 may call an imported checkpoint verified or executable.

Question: How does a destination authenticate an archive's root manifest and provenance when an attacker could otherwise rewrite content and recompute ordinary hashes?

  • A: Sign the canonical root manifest with a source device/user key chained to a known identity. Pro: offline attribution and tamper evidence. Con: enrollment, rotation, revocation and lost-device handling are required.
  • B: Authenticate the root with a shared user/Workspace archive key. Pro: compact offline verification across devices. Con: shared-secret distribution weakens sender attribution and increases compromise impact.
  • C: Import as explicitly unauthenticated, non-executable evidence, require human review and let the destination re-seal a new local root before any continuation. Pro: no cross-device key infrastructure. Con: cannot preserve trusted provenance or automatic continuation.

Recommendation: A; retain C as a clearly separate recovery path that never claims verified source history.

Acceptance criterion: For A/B, define canonical signed/MACed bytes, identity binding, key storage/rotation/revocation limits, replay/downgrade rules, attribution and verification errors; tampering with the authenticated root, content, branch links or version must fail before destination mutation or provider/Tool effects. For C, label every record unauthenticated, permit no Portable continuation or effects, define explicit human review and destination resealing as new local evidence, and never claim source attribution or source-history verification.
