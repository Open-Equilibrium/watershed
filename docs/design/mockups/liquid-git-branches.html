Git branches and commits: mockups

The next step of the Liquid Git slice in PLAN.md: the current branch, switching and creating branches, committing, and push and pull state. Pull requests and worktrees follow later; section 10 shows where they attach. Bounds already decided (ADR-0190, ADR-0191, ADR-0220, ADR-0234, SECURITY.md): Meta-Harness runs the host's git and gh and Liquid only presents them, every Git write needs an explicit user action, a checkout with a running agent allows no branch switch, and parallel sessions use their own worktrees. Layout, components and wording follow the agent surface and checkpoint mockups and guidelines.md; Git's own words and T3 Code's Git panel set the wording. Approved 2026-11-01, sections 1–10 as drawn; with section 4 changed the same day to stashing as GitHub Desktop does; see Decisions.

1 · The branch and Git state in every tab

The session header shows the checkout's branch with its commits ahead (↑) and behind (↓) its upstream, and a split button whose main part runs the next Git step, as T3 Code's Git actions do; its arrow opens the Git menu. The session card in the sidebar names the branch beside harness and device, as the approved agent surface mockup draws it. Both read the checkout live, so sessions in one checkout show the same branch. T3 Code puts branch and Git actions in a thread details panel and below the composer; Liquid has neither, so they go into the header, which every tab shares (question 1).

2 · Switching and creating a branch

The branch opens one searchable menu, as T3 Code's branch picker does: local branches with the current one checked, then remote branches. Choosing a branch switches to it; a remote branch gets a local branch that tracks it. Typing a name that no branch has offers "Create branch", which starts from the current commit and switches to it. With uncommitted changes, switching asks where they go, as GitHub Desktop does (section 4); a new branch takes them along, as GitHub Desktop's does. Git's word is "switch"; T3 Code's menu says "ref", which Liquid does not use.

3 · No switch while an agent runs in the checkout

Switching would change files under the running agent, so the branches stay listed but cannot be chosen, and the menu names the session that runs, with the wording of the refused revert. T3 Code allows the switch and only stops the session when it moves to another worktree. A parallel session belongs in its own worktree, which a later step adds (section 10).

4 · Uncommitted changes when switching

With uncommitted changes, choosing another branch asks what happens to them, with GitHub Desktop's dialog and words. "Leave my changes on main" stashes them, untracked files included, for this branch: git stash push --include-untracked with a message naming the branch (question 15). "Bring my changes" switches as git switch does. A branch holds one stash, as in GitHub Desktop (question 16). Back on the branch, its stashed changes show in the Diff tab with "Restore" and "Discard", and the branch menu marks branches that have them. T3 Code has no stash; it switches and shows Git's refusal in a toast.

5 · Committing the project's changes

"Commit changes" uses T3 Code's dialog: the branch, every uncommitted file with its lines and an "Edit" that excludes files, then the message. Unlike T3 Code, a file shows whether this session's turns changed it, since the list also holds edits made outside the agent (question 3). The message is the user's to write (question 4). Git runs the repository's commit hooks, which run project code, as the Diff tab's Git settings already do (ADR-0210). Checkpoints stay as they are: they sit under Watershed's own refs, not on the branch, so every turn keeps its changes in the Diff tab, and a later revert changes files, never a commit.

The menu holds every Git action of this step with its state; an action that cannot run stays visible, dimmed, and says why on hover, as T3 Code's menu does. The split button's main part names the next step (question 8). The first line says when Liquid last asked the remote (question 7).

7 · Pushing

Push sends the branch's commits to its upstream through the host's git, whose credential helper or gh login signs in; Liquid never sees the credentials. A branch without upstream pushes to origin under its own name and tracks it, as T3 Code does. Pushing to the default branch asks first, as T3 Code does (question 9). While Git works, the button shows the step and the seconds, and the result appears as a status bar notice, Liquid's place for messages, where T3 Code shows a toast.

8 · Push rejected and pulling

When the upstream has commits the branch lacks, Git rejects the push. The notice says so in plain words and the branch shows ↓ in warning color. With only commits to pull, Pull fast-forwards the branch (git pull --ff-only), as T3 Code's does; after diverging, Liquid merges or rebases nothing and names the way out (question 10). Pull changes files, so it is refused while an agent runs in the checkout, as switching is.

Push rejected, behind only⚠ Could not push: origin/main has 3 commits that main lacks. Pull them, then push.
Push rejected, diverged⚠ Could not push: main and origin/main have diverged, 1 commit here and 3 there. Merge or rebase in a terminal, then push.

9 · Other states and errors

Each state keeps the header in place and says what is missing; nothing hides. Errors quote Git's own message after a plain first sentence, and say whether anything changed.

Sign-in failed⚠ Could not push: Git could not sign in to origin. Liquid uses the Git login of MacBook; sign in there with git or gh, then push again.
Commit hook failed⚠ Could not commit: the pre-commit hook failed and nothing was committed. “eslint: 2 errors in src/routes/login.ts” · Show output

11 · Open questions for the maintainer

The mockups above draw the recommendation of each question. The maintainer answered them on 2026-11-01; see Decisions.

1 · Where the branch and the Git actions live

  • A · Session header, right side (drawn): visible in Chat, Trajectory and Diff alike; + one place, guideline 8; − the header gets busier.
  • B · Input area bar, beside "Ask" and "Context": + T3 Code's spot for a new thread's branch; − mixes Git writes with prompt settings, hidden while an approval fills the input area.
  • C · Diff tab only: + next to the changes; − the branch is invisible in Chat, where most work happens.

T3 Code: branch picker below the composer and in the thread details panel's "Version Control" section, with the Git split button and a "Changes" row.

Recommendation: A.

2 · "Branch" now names two things

Liquid already says "branch" for the session tree: "Branch from here", "Revert and branch", "Turns of this branch". A Git branch beside them is ambiguous.

  • A · Git keeps "branch"; Liquid's says "session branch" wherever both can meet (Diff menu, revert dialog, Trajectory): + Git's established word stays plain, guideline 9; − renames approved, shipped labels.
  • B · Liquid keeps "branch"; Git's says "Git branch": + no shipped label changes; − bends Git's own term in the place users expect it.
  • C · Both stay "branch", told apart by place and icon: + no change; − "Turns of this branch" next to main misleads.

T3 Code: no conflict; it has no session branches.

Recommendation: A, with a GLOSSARY.md entry.

3 · Which files a commit takes, and the index

  • A · List every uncommitted file, all selected, "Edit" to exclude; commit the selected files whole (drawn): + T3 Code's flow, simple; − replaces what the user staged by hand, so a notice says so.
  • B · Respect the index: if anything is staged, commit only that, else everything: + what git commit does; − the dialog has two modes, and partial staging needs a hunk view Liquid lacks.
  • C · Only the files this session's turns changed: + matches the agent's work; − silently leaves the user's own edits behind.

In A and B, each row says whether this session's turns changed the file, which the checkpoints know.

T3 Code: A; it runs git reset, then git add -A on the selected files, which drops what was staged. ADR-0234 keeps the index the user's for reverts only.

Recommendation: A, with the staged-parts notice.

4 · The commit message

  • A · The user writes it; Commit stays disabled while it is empty (drawn): + no model call, nothing leaves the host; − more typing.
  • B · Optional; an empty message is generated by a model: + fastest; − sends the diff, including the user's own edits, to a provider without a separate choice (enterprise data privacy).
  • C · A, plus a "Generate" button that asks the session's model on click: + help only on request; − one more control and a model call path in this step.

T3 Code: B, "Leave empty to auto-generate".

Recommendation: A now, C as a later addition.

5 · Commit and pull while an agent runs in the checkout

Switching is refused by ADR; commit and pull are open.

  • A · Refuse both (drawn), with the revert's lock and notice: + one rule for every Git write that touches the checkout; a commit hook cannot rewrite files under the agent; − waiting for long turns.
  • B · Allow commit, refuse pull: + commit does not change files; − may commit a half-done turn, and hooks can change files.
  • C · Allow both: + no waiting; − pull changes files under the agent.

T3 Code: allows both.

Recommendation: A.

6 · Uncommitted changes when switching

  • A · Git's behavior (drawn): changes come along; if Git refuses, list its files and offer Commit: + no Liquid rule on top of Git; − the user may not notice the changes came along, so the menu says so.
  • B · Refuse any switch with uncommitted changes: + nothing surprising; − stricter than Git, more commits for nothing.
  • C · Offer "Stash and switch": + one step; − adds stash and its restore to this step's scope.
  • D · Ask, as GitHub Desktop does (drawn in section 4): leave the changes stashed on the branch, or bring them along: + nothing is lost or carried unnoticed; − adds stash, restore and discard to this step.

T3 Code: A, with Git's error as a toast. GitHub Desktop: D.

Recommendation: A. The maintainer chose D.

7 · How fresh ahead and behind are

git fetch updates the repository's remote-tracking refs, so it may count as a Git write that needs an explicit action (ADR-0191).

  • A · Fetch only on request (drawn): a "Fetch" menu entry, and before Push and Pull; the menu says when it last fetched: + no write and no network call without a click; − counts can be stale.
  • B · Fetch in the background, without credential prompts: + counts stay current; − a regular network call and ref write nobody asked for.
  • C · Fetch when the Git menu opens: + fresh where it matters; − opening a menu becomes a network action.

T3 Code: B, every 15 seconds, with credential prompts turned off.

Recommendation: A.

8 · The split button's main part

  • A · The next single step (drawn): Commit, Push or Pull by state: + one click, each write visible on its own; − the label changes.
  • B · Also combined steps, "Commit & push": + fewest clicks; − one click makes two writes, one of them outward.
  • C · Always "Commit", the rest in the menu: + stable label; − push and pull are one click further away.

T3 Code: B, including "Commit, push & create PR".

Recommendation: A; reconsider B with pull requests.

9 · When a push asks first

  • A · Only for the default branch (drawn): + T3 Code's rule, the risky case; − a first push publishes a new branch without asking.
  • B · Default branch and first push: + nothing appears on the remote unasked; − one more dialog for the common case.
  • C · Never: + fastest; − a click on main publishes at once.

T3 Code: A, offering "Check out feature branch & continue" with a generated name; Liquid's "Create branch…" asks for the name.

Recommendation: A.

10 · Pulling

  • A · Pull fast-forward only (drawn); diverged states name the terminal: + safe, no conflicts in Liquid; − diverged branches need a terminal.
  • B · No pull in Liquid, state only: + smallest; − the common "behind" case needs a terminal.
  • C · Pull with merge or rebase: + complete; − brings conflict resolution into Liquid.

T3 Code: A, "Pull/rebase first" for diverged branches.

Recommendation: A.

11 · A folder without Git

  • A · Offer "Initialize Git" (drawn): + one explicit action, and checkpoints work from the next turn; − one more Git write in this step.
  • B · Only say so: + smallest; − the user leaves Liquid to run git init.

T3 Code: A, "Initialize Git".

Recommendation: A.

12 · Detached HEAD

  • A · Commit and push need a branch (drawn): the button offers "Create branch…": + no commits that are easy to lose; − one step more.
  • B · Allow committing on a detached HEAD: + what Git allows; − the commit is easy to lose on the next switch.

T3 Code: its main button is disabled with "Create and checkout a ref before pushing", but its menu still commits.

Recommendation: A.

13 · Uncommitted changes in the Diff tab

  • A · Add "Uncommitted changes" to the Diff tab's turn menu, comparing the checkout with its last commit: + the user reviews everything before committing, including their own edits; − the Diff tab gets a scope that is not a turn.
  • B · The commit dialog's list only: + smallest; − commits files whose changes nobody saw in Liquid.

T3 Code: A, its Diff panel offers "Uncommitted".

Recommendation: A.

14 · The sidebar's branch for a session

  • A · The checkout's branch, live (drawn): + always Git's truth; − an old session shows today's branch, not the one it worked on.
  • B · The branch of the session's last turn: + history stays true; − can differ from the checkout, which the header then contradicts.

T3 Code: a local thread follows the checkout's branch live.

Recommendation: A for sessions of the open checkout; a closed session shows the branch of its last turn.

15 · How Liquid marks a branch's stash

Git's stash is one list for the whole repository, so each entry's message has to say which branch it belongs to.

  • A · Liquid's own message, Liquid: changes left on main: + reads plainly in git stash list and other tools; − GitHub Desktop does not show Liquid's stashes, nor Liquid Desktop's.
  • B · GitHub Desktop's message, !!GitHub_Desktop<main>: + both apps show and restore the same stash; − depends on another app's internal format and reads oddly elsewhere.

T3 Code: no stash. GitHub Desktop: B, its own marker; other entries stay out of its list.

Recommendation: A; other stashes stay untouched and unlisted either way. The maintainer chose A.

16 · A branch that already has stashed changes

  • A · One stash per branch; leaving new changes replaces it after a warning (drawn): + GitHub Desktop's model, one place to look; − the older stash is deleted, so the dialog says so and the button says "Replace stash".
  • B · Keep every stash and list them all: + nothing is lost; − several stashes per branch need a list and choosing which to restore.

GitHub Desktop: A, asking once more before it replaces the stash.

Recommendation: A. The maintainer chose A.

Not covered here: shortcuts for the branch menu and the commit dialog follow in the shortcuts mockup once placement is decided; adding a remote or publishing a repository, which T3 Code offers, is left out.

Decisions

  1. The branch and the Git actions live at the right of the session header, in every tab (question 1).
  2. Git keeps "branch"; Liquid's own branches are "session branches", in labels too ("Branch from here" stays, "Turns of this session branch") (question 2).
  3. A commit preselects every uncommitted file with "Edit" to leave files out and commits whole files, saying so when the user staged parts (question 3).
  4. The user writes the commit message; it is required and nothing is generated (question 4).
  5. Commit and pull are refused while an agent runs in the checkout, with the revert's lock and notice (question 5).
  6. Switching with uncommitted changes asks, as GitHub Desktop does: leave them stashed on the branch, or bring them along; a branch's stashed changes show in the Diff tab with Restore and Discard, and stash, restore and discard are refused while an agent runs in the checkout (question 6).
  7. Liquid fetches in the background every 15 seconds while the session is open, as T3 Code does, so ahead and behind stay current; "Fetch" in the menu fetches at once. This is the one Git write without a user action besides checkpoints, recorded in the ADR log (question 7).
  8. The split button's main part runs the next single step: commit, push or pull (question 8).
  9. A push asks first only for the default branch (question 9).
  10. Pull is fast-forward only; when the branches diverged, Liquid points to the terminal (question 10).
  11. A folder without Git offers "Initialize Git" (question 11).
  12. With a detached HEAD, commit and push need a branch; the button offers "Create branch …" (question 12).
  13. The Diff tab's turn menu gets "Uncommitted changes" (question 13).
  14. The sidebar shows the checkout's live branch; a closed session shows the branch of its last turn (question 14).
  15. A stash's message names its branch in Liquid's own words, Liquid: changes left on main; other stashes stay untouched and unlisted (question 15).
  16. A branch holds one stash; leaving new changes replaces it after the dialog's warning (question 16).
