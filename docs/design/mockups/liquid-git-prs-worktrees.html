Git pull requests and worktrees: mockups

The next step of the Liquid Git slice, following the merged branch, commit, push and pull work. These drawings extend the approved branch flow §10 inside the current app structure (ADR-0241): rail, Pages and Sources, Chats, and tabs. They use the agent Chat and the current Workspace components at Notion's scale.

Decided bounds come from ADR-0011/0190/0191/0220/0234 and SECURITY.md. Layout follows the app frame, Chats, Workspace Pages, Blocks, History, Sections and the guidelines. Git keeps “branch”; a path through the conversation is a session branch. Approved 2026-11-03, sections 1–12 as drawn; see Decisions. Paths, titles, times and PR numbers are examples. State cards and tables are review annotations; every screen is drawn in the current app frame.

1 · Create pull request in the Git menu and after Push

The split button keeps the approved single next step; its menu offers “Commit, push & create PR…” and, for an already pushed branch, “Create pull request…”, as T3 Code does. After a successful push, a widget directly above the input area offers “Create pull request…” until it is dismissed or the pull request exists; it opens the review dialog and never creates a PR on its own. Branch chip, PR chip and split button sit at the right of the Chat header, and at narrow widths they move into the header's ··· menu; the folder and model stay beside the agent name.

2 · Commit, push & create PR, or create for a pushed branch

“Commit, push & create PR…” is the approved commit dialog, whole files with attribution and the user's message, plus a pull request part; the approved confirmation before pushing to the default branch stays. “Create pull request…” shows only the pull request part. Both show the target repository, head and base before a write. The Chat's own model, already working in this repository, writes the title and description from the commit range and diff; the fields stay editable, the title is required and the description optional. The base is the branch this one was created from, which Liquid records in its own data per repository and branch; without a record it is the verified GitHub default, and if that is unknown the user chooses. Liquid does not guess “main”. Changing the base refreshes the comparison before Create is enabled. “Create as draft” starts unchecked; checking it renames the button “Create draft pull request”.

T3 Code generates title and body from the commit range, diff, optional template, writing policy and thread context, resolves the base from its thread's recorded branch, and creates without a draft flag. Liquid uses the Chat's own model, so the commits and diff reach only the provider that Chat already uses; no other provider is called. It stores the base per repository and branch, not per Chat, never falls back to a guessed “main”, and offers draft unchecked. Create sends only the reviewed title, description, target, base and draft choice. Repository templates are not promised by these mockups.

3 · Needs Push, refused creation and partial results

A pull request compares pushed commits; uncommitted files and checkpoint commits are not included. “Commit, push & create PR” runs commit, push and create in order and stops at the first failure; the result names each completed step and what remains. The standalone “Create pull request…” needs a pushed branch: without an upstream, or with local commits ahead, it shows what needs pushing and hands off to Push or the combined action. Recheck the repository, head commit, base and existing PR before submission; if they changed, keep the text and ask the user to review again.

Existing-PR detection uses the GitHub repository and head branch, including its owner; a PR with another base still counts and is shown, rather than silently retargeted. 4 · A pull request beside the branch

The PR chip joins the branch in the Chat header, beside the Git action. Diff and Trajectory stay on the changed answer, as in the current Chat; they are no longer navigation tabs. The PR chip opens a small summary with state, base, checks, review status, last successful update and “Open in browser”. T3 Code has a richer PR detail surface with checks and review information; Liquid shows this summary and leaves review, merging and closing to GitHub. PR status never changes the branch or starts a Git write. Status is read when the summary opens, when the window regains focus, on Refresh and when the branch or its upstream changes, never by polling; the last successful update time always shows.

5 · GitHub, gh and host errors

The host is the machine running Meta-Harness, which may differ from the machine displaying Liquid. Liquid uses that host's git and gh; it offers no token field, credential storage or silent installation. T3 Code's inspected GitHub provider can use credentials directly and calls GitHub's API; Liquid follows its host-specific setup guidance but keeps the decided git/gh boundary. GitHub.com and GitHub Enterprise hosts the host's gh has a login for work through gh. For a fork, the target repository is preselected from GitHub's parent of the pushed head repository and stays editable, the head reads owner:branch, and pushing still goes only to the branch's own remote. Other providers are refused with an explanation.

Errors give a plain first sentence, a safe command message and the completed steps. Credentials in remote URLs or command output must not appear. The T3 Code source says “GitHub is not authenticated. Run `gh auth login` (or set GH_TOKEN) and retry.” Liquid keeps only the gh login guidance; it does not expose a token setup flow. No Git repository or unavailable Git uses the approved states.

6 · Open a branch in a new worktree

A worktree is another folder for the same Git repository, with its own checked-out files, index and branch. “Open in a new worktree…” in the branch menu opens a new Chat whose composer is preset to New worktree with that branch (§7), at ~/.liquid/worktrees/acme-api/feature-retry-after. Nothing is created until its first message is sent; the current Chat stays in its folder. T3 Code can reuse a branch's existing worktree or create one. Git normally permits a branch in only one checkout: Liquid never uses force to bypass that rule.

As in T3 Code, the path is a central worktree root / repository name / branch with “/” replaced by “-”; each host has its own root, by default ~/.liquid/worktrees, changeable per host in Settings. It lies outside Liquid's and Meta-Harness's data folder, which agents cannot reach (ADR-0229); the agent sandbox grants each worktree as that Chat's project folder. Unlike T3 Code, the user writes the branch name; there is no temporary branch or generated name, and a name whose folder is taken is refused. A branch that already has a worktree uses that folder; a new Chat there still needs the checkout guard.

7 · Start a Chat: Current checkout or New worktree

A new Chat opens without a dialog. Its composer carries a compact checkout toolbar, following T3 Code's BranchToolbar and its labels. New worktree is preselected: a new branch from the remote default branch, shown as “From origin/main ⌄” and selectable, at the worktree root. Current checkout uses the folder's branch and uncommitted files; its branch chip is a picker that switches at once through the approved branch switch flow, with its stash choice and checkout guard, as T3 Code's branch selector does in local mode. The mode menu also lists existing worktrees with their branches, T3 Code's “Current worktree”. Choosing creates nothing: sending the first message fetches the base through the existing fetch serialization and destination checks, creates the worktree and starts the agent. No agent starts unless creation and the checkout guard succeed; a failure keeps the typed message in the composer. After the first message the mode is fixed, as T3 Code locks an established worktree's mode.

T3 Code creates the worktree during launch and starts from the remote when its “New worktrees start from remote” setting is on; it also runs setup scripts and generates branch names. Liquid starts from the remote default unless the user picks another base, and neither runs setup scripts nor generates names. Ignored dependencies, secrets and local configuration are not copied. Outside Git, New worktree is unavailable and says “Initialize Git before creating a worktree”; Current checkout retains the existing per-folder guard.

8 · Worktrees and branches inside Chats

Worktrees and branches appear only inside Chats. The Chat header's folder chip names the worktree beside the branch chip. Its popover shows the full path and host and holds the worktree actions. The Chats list keeps its approved filters, Pinned, sections and Recent; a Chat in a linked worktree adds only a small indicator to its row, like T3 Code's SidebarThreadRow. The Chat's files and Diff always come from that folder.

9 · Moving an idle Chat to another worktree

The Chat header's branch chip menu marks a branch checked out in another worktree “in a worktree”. Choosing it opens “Move this Chat to another worktree?”, as T3 Code's branch selector points a thread at the worktree that holds the branch and stops its runtime. Only an idle Chat moves: while its agent runs, those rows are disabled with the reason, and Liquid never stops a Chat as a side effect. The agent session restarts in the new folder and the conversation stays. Turns before the move keep Diff and Trajectory but offer no Revert: their checkpoints belong to the old folder, and Liquid never restores files into another checkout.

10 · Remove a worktree

“Remove worktree…” is in the Chat header's folder chip popover (§8); Settings › Worktrees lists every worktree Git registers, so one without any Chat can be removed too, following T3 Code's settings surface. Both are separate from “Delete Chat” and “Remove all checkpoints” and open the same removal dialog. Deleting the last Chat linked to a worktree asks, after the approved Delete Chat confirmation and in T3 Code's words, “Delete the worktree too?”; the Settings choice “Always delete clean worktrees” skips the question. Removal keeps the branch, commits, repository-wide stashes and other Chats. It deletes the folder and its index, so with staged, unstaged, untracked or ignored files it never happens and is never forced: the worktree stays and Liquid says why. Unpushed commits stay on the retained branch and are called out, not mistaken for uncommitted files.

T3 Code asks “This thread is the only one linked to this worktree:” and “Delete the worktree too?” when deleting the last linked thread unless automatic cleanup is enabled. It stops that thread's runtime before deletion, then requests worktree removal with force: true. Liquid asks the same, but removes only a clean worktree, never with force, and never deletes the branch. Otherwise a worktree is removed only through the removal dialog (§10).

11 · Checkpoints, stash and checkout locks

This section adds the worktree lifecycle rule to the decided locks. A checkout is a particular worktree's files and index; linked worktrees share Git objects, refs and the stash list. Different worktrees are not a protection boundary against tools that can reach their folders. Liquid coordinates its own Git operations across windows and processes, not external Git writers beyond Git's own protections.

ActionScopeWhat the user sees
Run a turnThis folder / checkoutThe decided OS guard is per canonical folder outside Git, or under this checkout's Git directory after initialization. Different existing worktrees can run in parallel.
Switch, commit, pull, stash, restore, discard or revertThis checkoutRefused while any agent runs here, including another Liquid window. Name the Chat and offer Show; another worktree's turn does not block these actions.
Push or FetchRemote / shared Git directoryPush sends committed branch state and does not need the checkout lock. Fetch, including a new worktree's base at send, serializes through the existing common Git lock. Keep the approved destination checks and default-branch confirmation.

Worktree creation refused by the exclusive common Git guard
Stashed changes in the selected worktree

A new worktree begins from its selected commit, not from a checkpoint or stash. Checkpoints remain under refs/watershed/checkpoints/<session>/<turn>/<start|end> in the common repository, are not normal branch commits and are not included by pushing the current branch. Revert remains scoped to the Chat's original working folder, previews affected files, changes only the working tree and starts a new session branch. Removing a worktree preserves refs but makes its file actions unavailable until the original checkout is restored; deleting the Chat separately removes its refs. Moving an idle Chat never redirects an old revert into the new worktree.

The approved one-stash-per-branch rule remains: Restore requires no uncommitted changes and the saved tree; Discard needs confirmation; leaving another stash on the same branch warns before replacement. The stash list is shared, so removing one worktree cannot discard stashes for it or for other worktrees. T3 Code's branch picker switches without Liquid's stash flow or checkout guard; Liquid's Current checkout picker uses both. T3 Code's path change stops its own runtime; Liquid moves only an idle Chat.

Decisions

  1. “Commit, push & create PR…” is one dialog: the approved commit dialog plus title, description, base and draft; the default-branch push confirmation stays. A failed step stops the rest, and the result names the completed steps and what remains (decided 2026-11-03).
  2. “Create pull request…” stays for already pushed branches, as in T3 Code; the split button's menu offers both (decided 2026-11-03).
  3. With nothing to commit but commits to push, “Commit, push & create PR…” stays enabled and skips the commit step, as T3 Code does: the dialog is “Push & create PR” without files or commit message. It is disabled only with nothing to commit and nothing to push (decided 2026-11-06).
  4. In the combined dialog the Chat's model writes from the branch's commits the base lacks, as far as Git has the base locally (else those since the upstream), plus the selected files, and writes again when editing the file selection ends with a change. Target, base and gh are checked when it opens; if the pull request part cannot be prepared, it says why before anything is committed or pushed (decided 2026-11-06).
  5. The Chat's own model writes the title and description from the commit range and diff, as T3 Code does, so the content goes only to that Chat's provider; the fields stay editable, with a generating and a failure state that falls back to the latest commit's subject and body. Without a Chat no model is used and the latest commit fills them. Title required, description optional (decided 2026-11-03). Meta-Harness asks that model through a separate one-shot pi, as T3 Code runs its own provider process, at thinking level low, with the commit messages, the changed files and at most 64 KiB of patch, within 60 seconds; its isolation and stopping are in SECURITY.md. Generated text never replaces a field the user has edited, and until Liquid has agent names the notes name the model id where this mockup says “Coder's model” (decided 2026-11-06).
  6. The base is the branch this one was created from, recorded in Liquid's own data per device, repository and branch, then the verified GitHub default, else a required choice; never guessed (decided 2026-11-03).
  7. “Create as draft” starts unchecked and the button reads “Create pull request”; checking it renames the button “Create draft pull request” (decided 2026-11-03).
  8. PR status refreshes on open, window focus, Refresh and when the branch or its upstream changes, never by polling, and always shows the last successful update (decided 2026-11-03).
  9. GitHub.com and GitHub Enterprise hosts the host's gh has a login for through gh, plus forks: the target repository is preselected from GitHub's parent of the pushed head repository, editable, and the head shows as owner:branch; pushing stays to the branch's own remote. Other providers are refused with an explanation (decided 2026-11-03).
  10. Branch chip, PR chip and the split button sit at the right of the Chat header; at narrow widths they move into its ··· menu (decided 2026-11-03).
  11. After a push, “Create pull request…” is a widget directly above the input area until dismissed or the pull request exists (decided 2026-11-03).
  12. New Chats choose their checkout in the composer, without a dialog; the worktree is created on the first send, and the mode is fixed after the first message (decided 2026-11-03).
  13. Worktrees and branches are shown only inside Chats (header chips, optional row indicator), never as Sources or pages (decided 2026-11-03).
  14. Worktrees live under a central root per host, by default ~/.liquid/worktrees/<repository>/<branch with “/” as “-”>, changeable per host in Settings › Worktrees (App group), outside the data folder agents cannot reach; the sandbox grants each worktree as a project folder (ADR-0229). The user writes the branch name; collisions are refused (decided 2026-11-03).
  15. A new Chat preselects New worktree from the remote default branch, fetched at send with the existing fetch serialization and destination checks; the base is shown and selectable. An unreachable remote keeps the message and offers the local base or Current checkout; without a remote the current local branch is the preselected, editable base (decided 2026-11-03).
  16. The mode menu lists existing worktrees with their branches, T3 Code's “Current worktree” (decided 2026-11-03).
  17. In Current checkout the branch is a picker that switches at once through the approved branch switch flow (decided 2026-11-03).
  18. When the chosen branch is already checked out, the new branch name starts empty and send stays disabled until it is named (decided 2026-11-03).
  19. “Open in a new worktree…” opens a new Chat preset to that branch (decided 2026-11-03).
  20.   21. Deleting the last Chat linked to a worktree asks “Delete the worktree too?”; the Settings choice “Always delete clean worktrees” skips the question.   22. “Remove worktree…” lives in the header's folder chip popover; Settings › Worktrees holds each host's root, the cleanup choice and Git's registered worktrees per repository, including ones created outside Liquid, each with “Remove…” opening the same removal dialog (decided 2026-11-03).
