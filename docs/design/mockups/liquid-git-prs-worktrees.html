Git pull requests and worktrees: mockups

Draft, not approved. The next step of the Liquid Git slice, following the merged branch, commit, push and pull work. These drawings extend the approved branch flow §10 inside the current app structure (ADR-0241): rail, Pages and Sources, Chats, and tabs. They use the agent Chat and the current Workspace components at Notion's scale.

Decided bounds come from ADR-0011/0190/0191/0220/0234 and SECURITY.md. Layout follows the app frame, Chats, Workspace Pages, Blocks, History, Sections and the guidelines. Git keeps “branch”; a path through the conversation is a session branch. All new choices below are proposals, drawn as recommended in §13; none is a decision. Paths, titles, times and PR numbers are examples. State cards and tables are review annotations; every screen is drawn in the current app frame.

1 · Create pull request in the Git menu and after Push

“Create pull request” joins the Git menu immediately below Push. After a successful push, a proposed confirmation below the answer offers the same action (question 14); it opens the same review dialog, never creates a PR on its own. The Git action keeps the approved single next step: Commit, then Push. The proposed control cluster sits at the right of the current Chat header (question 13); the folder and model stay beside the agent name. T3 Code also offers a combined action, including the confirmation label “Commit, push & create PR”; Liquid's recommendation keeps the separate steps and makes the final write explicit (question 1).

2 · Review the title, description, base branch and draft

Both entry points show the repository, head branch and remote base before a write. Proposed defaults: the latest commit's subject and body, an editable description, the verified GitHub default branch, and “Create as draft” checked (questions 2–4). An empty description is allowed; an empty title disables creation. If the default branch cannot be read, the user chooses a base; Liquid does not guess “main”. Changing the base refreshes the commit comparison before enabling Create. A draft is visible on GitHub but is not ready for review.

Pushed branch, ready to create a draft
Choose a base; title still needed

T3 Code's inspected creation path generates title and body from the commit range, diff, optional template, writing policy and thread context; it resolves the base automatically and creates without a draft flag. Liquid's proposed form differs: no automatic model call or hidden content generation. It sends the edited title, description, chosen base and draft choice only on Create. Repository templates and a “Generate” action are not promised by this draft (question 2).

3 · Needs Push, refused creation and partial results

A pull request compares pushed commits. Uncommitted files and checkpoint commits are not included. A branch without an upstream, or with local commits ahead, shows what needs pushing; “Push…” hands off to the approved push flow and returns to review. T3 Code's “create_pr” action pushes first when needed. Liquid proposes a separate explicit Push, then Create (question 1). Recheck the repository, head commit, base and existing PR before submission; if they changed, keep the text and ask the user to review again.

4 · A pull request beside the branch

The PR chip joins the branch in the Chat header, beside the Git action (question 13). Diff and Trajectory stay on the changed answer, as in the current Chat; they are no longer navigation tabs. The PR chip opens a small summary with state, base, checks, review status, last successful update and “Open in browser”. T3 Code has a richer PR detail surface with checks and review information; Liquid proposes this summary and leaves review, merging and closing to GitHub. 5 · GitHub, gh and host errors

The host is the machine running Meta-Harness, which may differ from the machine displaying Liquid. Liquid uses that host's git and gh; it offers no token field, credential storage or silent installation. T3 Code's inspected GitHub provider can use credentials directly and calls GitHub's API; Liquid follows its host-specific setup guidance but keeps the decided git/gh boundary. 6 · Open a branch in a new worktree

A worktree is another folder for the same Git repository, with its own checked-out files, index and branch. “Open in a new worktree…” in the branch menu opens a new Chat whose composer is preset to New worktree with that branch (§7). Nothing is created until its first message is sent; the current Chat stays in its folder. T3 Code can reuse a branch's existing worktree or create one. Git normally permits a branch in only one checkout: Liquid never uses force to bypass that rule.

T3 Code builds the path as its configured worktrees directory / repository name / branch with “/” replaced by “-”. Its default worktrees directory is in its host data folder; Settings can change it. It can begin with a temporary branch and generate its final name. Liquid proposes an editable branch name before creation, no automatic model call, and an explicit location preview (question 7). A branch that already has a worktree uses that folder; a new Chat there still needs the checkout guard.

7 · Start a Chat: Current checkout or New worktree

A new Chat opens without a dialog. Its composer carries a compact checkout toolbar, following T3 Code's BranchToolbar and its exact “Current checkout” and “New worktree” labels, and every choice stays editable until the first message. Current checkout uses the folder's existing branch and uncommitted files. New worktree starts a new branch from the displayed base commit, with its own files, at the previewed location (question 7). Choosing creates nothing: sending the first message creates the worktree and starts the agent. No agent starts unless creation and the checkout guard succeed; a failed creation keeps the typed message in the composer. After the first message the mode is fixed, as T3 Code locks an established worktree's mode. The default mode and base remain question 8.

T3 Code creates the worktree during launch and supports fetching a remote base, setup scripts and generated branch names. Liquid's recommendation uses the displayed local commit without an implicit pull; the user can Fetch and deliberately select a remote branch instead. Ignored dependencies, secrets and local configuration are not copied. Outside Git, New worktree is unavailable and says “Initialize Git before creating a worktree”; Current checkout retains the existing per-folder guard.

8 · Worktrees and branches inside Chats

Worktrees and branches appear only inside Chats. The Chat header's folder chip names the worktree beside the branch chip. Its popover shows the full path and host and holds the worktree actions. The Chats list keeps its approved filters, Pinned, sections and Recent; a Chat in a linked worktree adds only a small indicator to its row, like T3 Code's SidebarThreadRow. The Chat's files and Diff always come from that folder.

9 · Changing the checkout of an existing Chat

T3 Code's branch selector can point a thread at another worktree; when the path changes it requests that thread's runtime stop and updates its metadata. Its environment selector also locks an established worktree's mode. Liquid has decided that a running agent's checkout cannot switch. For idle Chats, the recommendation is to keep their original checkout and start a new Chat in the target, avoiding a conversation whose checkpoint file actions silently change folders (question 10).

10 · Remove a worktree

“Remove worktree…” belongs to the folder chip's popover in the Chat header (§8), separate from “Delete Chat” and “Remove all checkpoints”. Proposed removal keeps the branch, commits, repository-wide stashes, chats and checkpoint refs. It deletes the folder and its index, so the preview must cover staged, unstaged, untracked and ignored files. The recommendation refuses removal with local files to preserve and offers no force option (question 11). Unpushed commits stay on the retained branch and are called out, not mistaken for uncommitted files.

T3 Code asks “This thread is the only one linked to this worktree:” and “Delete the worktree too?” when deleting the last linked thread unless automatic cleanup is enabled. It stops that thread's runtime before deletion, then requests worktree removal with force: true. Its Settings also expose cleanup rules. Liquid's recommendation differs: no automatic cleanup on merge, Chat deletion or age, no forced deletion and no branch deletion. Deleting a Chat still follows its approved confirmation and removes that Chat's checkpoints; it does not also remove a worktree.

11 · Checkpoints, stash and checkout locks

This section distinguishes the decided locks from the proposed worktree lifecycle rule. A checkout is a particular worktree's files and index; linked worktrees share Git objects, refs and the stash list. Different worktrees are not a protection boundary against tools that can reach their folders. Liquid coordinates its own Git operations across windows and processes, not external Git writers beyond Git's own protections.

ActionScopeWhat the user sees
Run a turnThis folder / checkoutThe decided OS guard is per canonical folder outside Git, or under this checkout's Git directory after initialization. Different existing worktrees can run in parallel.

Worktree creation refused under the proposal
Stashed changes in the selected worktree

A new worktree begins from its selected commit, not from a checkpoint or stash. Checkpoints remain under refs/watershed/checkpoints/<session>/<turn>/<start|end> in the common repository, are not normal branch commits and are not included by pushing the current branch. Revert remains scoped to the Chat's original working folder, previews affected files, changes only the working tree and starts a new session branch. Removing a worktree preserves refs but makes its file actions unavailable until the original checkout is restored; deleting the Chat separately removes its refs. Liquid must not redirect an old revert into a different worktree.

The approved one-stash-per-branch rule remains: Restore requires no uncommitted changes and the saved tree; Discard needs confirmation; leaving another stash on the same branch warns before replacement. The stash list is shared, so removing one worktree cannot discard stashes for it or for other worktrees. T3 Code's branch picker switches without Liquid's stash flow or checkout guard; its path change stops its own runtime instead. The proposed common lifecycle guard is deliberately broader and needs approval (question 12).

13 · Open questions for the maintainer

Questions 1–8 and 10–14 remain open; question 9 is decided (see Decisions) and question 8 keeps only its open part. The drawings show recommendations for review. No ADR is recorded by this draft.

1 · Separate Git steps or a combined action?

Creating a PR may first require a commit and a push. A combined action can finish some steps before a later one fails.

  • A · Commit, Push, then review and Create (drawn): + every write has an explicit, bounded action and the existing controls stay familiar; − more clicks.
  • B · “Commit, push & create PR” with one review of all steps: + faster; − a partial result needs more recovery states and must preserve the approved commit and push confirmations.

T3 Code: combined actions and standalone create; create pushes first when needed.

Recommendation: A for this slice.

2 · Defaults for the PR title and description

A description must explain the whole branch, which may contain several commits. Generating it with a model sends repository content to a provider.

  • A · Latest commit subject/body, editable (drawn): + local and predictable, no extra model call; − the user must describe earlier commits.
  • B · Blank fields: + no misleading summary; − repeated typing.
  • C · Model-generated draft on an explicit Generate action: + can summarize the range; − another integration and a content-sharing choice. Repository templates could be a separate later addition.

T3 Code: its inspected creation path automatically generates title/body using the range, diff, optional template, policy and thread context.

Recommendation: A; keep description optional and title required.

3 · Which base branch is selected?

The base is where the change will merge. The branch a feature started from may differ from the repository's default.

  • A · Verified GitHub default, editable (drawn): + familiar, no hidden branch metadata; − stacked changes need a manual base choice. If unknown, require a selection.
  • B · Remember the branch it started from: + useful for stacked PRs; − more persistent metadata and stale-base handling.

T3 Code: recorded branch base, then a different same-repository upstream, provider default, remote default, finally “main”.

Recommendation: A; never guess a missing default.

4 · Draft by default?

A draft can run checks and be shared, but signals that review is not requested yet.

  • A · “Create as draft” checked (drawn): + avoids accidentally asking for review; − users must uncheck it for finished work.
  • B · Ready for review by default: + one less choice for completed changes; − can notify reviewers too early.

T3 Code: draft display and conversion exist; the inspected creation call passes no draft flag and creates a regular PR.

Recommendation: A, with the button naming the draft.

5 · How often does PR status refresh?

Checks and reviews can change on GitHub while Liquid is open. Old data must not look current.

  • A · On open, window focus and explicit Refresh (drawn): + bounded requests, clear retry; − background changes can remain stale until focus or refresh.
  • B · Also poll while the PR is visible: + fresher status; − needs a separately approved interval, rate-limit handling and host lifecycle.

T3 Code: a live PR surface shares summaries with detail checks, marks stale checks and supports refreshing from the host; this draft does not borrow an unverified polling interval.

Recommendation: A, always showing the last successful update.

6 · GitHub host and fork scope

GitHub Enterprise uses another host name; a fork publishes a head branch in another repository. A wrong mapping can publish to the wrong place.

  • A · GitHub.com and explicitly resolved Enterprise hosts through gh; same-repository PRs only (drawn): + matches the decided host tools and existing push destination checks; − forks require Git/gh outside Liquid.
  • B · GitHub.com only: + smaller first slice; − excludes Enterprise users.
  • C · A plus forks: + common contribution workflow; − requires head-owner/base-repository selection and agreement with the existing push boundary.

T3 Code: its inspected provider supports host context and cross-repository PRs, and the source-control surface supports other providers. That API credential path is outside Liquid's contract.

Recommendation: A; show an explanation for forks and other hosts, never silently choose another provider.

7 · Worktree folder and branch naming

Each worktree needs a real folder on the agent's host. Branch names can contain slashes, and different names can flatten to the same folder name.

  • A · Sibling worktrees folder, editable path and user-written branch (drawn): + easy to find beside the project folder, no model call; − users choose another path when names collide.
  • B · Host data folder with a configurable worktree root: + T3 Code's central organization; − requires a setting and is less visible beside the project.
  • C · Ask for every path without a default: + no location policy; − more setup for every Chat.

T3 Code: configured host root / repository / slash-flattened branch; launch can generate and rename a temporary branch.

Recommendation: A, preview the full path and refuse collisions; the sibling location shown is an example pending approval.

8 · New Chat default mode and base

The composer placement and creation on the first message are decided. Still open: which mode a new Chat preselects, and which base a new worktree starts from. Current checkout includes local edits; a new worktree begins at a commit and has none of the source folder's uncommitted or ignored files.

  • A · Current checkout by default; New worktree from the displayed local base commit (drawn): + minimal surprise, no implicit network access; when the checkout is busy, sending is disabled and New worktree is offered; − users Fetch and choose a remote base themselves when needed.
  • B · Always default to New worktree, starting from the remote default: + isolation and a fresh base; − more folders, remote access and local setup missing from each.

T3 Code: both labels, selectable bases and configurable remote-start behavior.

Recommendation: A.

10 · Can an idle Chat move to another worktree?

The conversation and its checkpoint refs survive a folder change, but an old revert must not restore files into an unrelated checkout. A running Chat cannot switch under the decided contract.

  • A · Keep existing Chats bound; start a new Chat in the target (drawn): + preserves checkpoint meaning and folder ownership; − less convenient than moving a conversation.
  • B · Allow an explicit move of an idle Chat: + continuous conversation; − needs a separate checkpoint-origin, context-reset and file-action contract before implementation.

T3 Code: path selection can rebind a thread and requests its runtime stop when the path changes; the established worktree's environment mode is locked.

Recommendation: A for this slice; never stop and move a running Chat implicitly.

11 · Removal and automatic cleanup

Removing a folder can destroy uncommitted or ignored files. A checkpoint excludes ignored files, and a stash is not a complete backup.

  • A · Explicit removal only, after no staged, unstaged, untracked or ignored files remain (drawn): + narrow, reviewable and no forced loss; − generated files and local configuration may need manual cleanup first. Keep branches, stashes and Chat history.
  • B · Also offer a separate confirmed discard-and-remove: + convenient cleanup; − adds an irreversible force path and needs a complete file-loss preview.
  • C · Automatic cleanup on merge, Chat deletion or age: + fewer leftover folders; − background destructive behavior is outside the explicit-action contract and requires a separate maintainer decision.

T3 Code: optional last-thread cleanup prompt, forced removal after thread deletion, plus configurable cleanup rules.

Recommendation: A; deleting a Chat and removing a worktree remain separate actions.

12 · Worktree lifecycle versus running turns

Worktrees have independent files, but creation and removal change shared repository metadata. Existing checkpoint operations already use a common Git guard. The new lifecycle lock scope is not decided.

  • A · Exclusive common guard for create/remove, plus the affected checkout check (drawn): + uses the existing repository-wide exclusion and gives a finite race boundary; − cannot create or remove any worktree while a turn in that repository runs. Existing worktrees can still run in parallel.
  • B · A separate lifecycle lock that permits other worktrees' turns: + can provision parallel work immediately; − requires an approved ordering and shared-ref/checkpoint concurrency contract before implementation.

T3 Code: inspected creation/removal invokes Git; changing a thread's path requests its runtime stop. It does not establish Liquid's cross-window checkout/common-guard invariant.

Recommendation: A for the first slice; approve B only with a bounded lock-order and checkpoint interaction contract.

13 · Git controls in the current Chat header

The current header names the agent, work folder and model. Branch, PR and Git actions need a place without restoring the old Chat / Trajectory / Diff navigation.

  • A · Branch and PR chips plus the next Git action at the right of the Chat header (drawn): + visible branch and PR state while reading; − a wider header, especially with long branch names.
  • B · Branch and PR chips in the header, actions inside its existing more menu: + calmer and narrower; − Commit and Push require another click.

T3 Code keeps branch and Git actions near the thread; Liquid's current participant header and answer-level details remain the reference.

Recommendation: A for desktop review; approve the placement and compact-width behavior before implementation. The scaled drawings do not decide a responsive product layout.

14 · Where does the post-Push action appear?

The current Chat has no old session status bar. A successful Push still needs its confirmation and the explicit Create pull request action from §1.

  • A · Below the changed answer (drawn): + keeps the result with the files it published; − it can scroll out of view.
  • B · As a widget directly above the input area: + stays visible beside the next action, following the guidelines' widget position; − occupies input-area space until dismissed.

T3 Code offers Create alongside its other Git actions; Liquid's current Chat needs an approved place for this extra post-Push entry point.

Recommendation: A for review; confirm its placement and lifetime before implementation.

Decisions

  1. New Chats choose Current checkout or New worktree in the composer, without a dialog; the choice stays editable until the first message.
  2. Worktrees and branches are shown only inside Chats (header chips, optional row indicator), never as Sources or pages.
