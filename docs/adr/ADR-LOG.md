# ADR Log

Agent-facing index of accepted decisions that still constrain further work and that intuition would likely get wrong. Each entry names the decision and why it is deliberate; detail lives in the linked canonical docs. Implemented, trivial or superseded decisions are not listed, and their IDs are not reused.

Policy: decision flow and hygiene rules live in [AGENTS.md](../../AGENTS.md#decision-flow).

Format: `ID | date | status | decision — canonical context`

## Decisions

- **ADR-0001 / ADR-0219** | 2026-06-05–2026-10-29 | Accepted | Watershed ships no Node runtime: Flow Agent, the Meta-Harness core and Liquid are Rust and Flutter, and Node in the repository is development tooling. The only product TypeScript is Watershed's pi extension, because pi loads only JavaScript or TypeScript extensions; it runs inside the user's own pi. Liquid never bundles pi or Node, also not for office users: the user installs pi (ADR-0219) — [TESTING.md](../../TESTING.md#development-toolchain), [liquid/README.md](../../liquid/README.md#run).
- **ADR-0011 / ADR-0190 / ADR-0191 / ADR-0220** | 2026-06-09–2026-10-29 | Accepted; Diff tab shipped, the rest planned | Liquid versions its own Workspace data in History, as Notion or AppFlowy do; Watershed builds no VCS for project code, and Flow Agent owns no project history. The Git integration for agent projects is no VCS either: Meta-Harness runs the host's `git` and, for pull requests, `gh` on its host, Liquid only presents it, and Watershed never reads their credentials. The one exception, taken from T3 Code: without asking, Meta-Harness stores the agent project's files at each turn as commits under its own refs in the project repository, to show each turn's changes and to return the files to an earlier turn, writes them off the UI path and deletes them with their session; D-075 holds the remaining details (ADR-0220). Other Git writes need an explicit user action; a checkout with a running agent allows no branch switch, and parallel sessions use their own worktrees — `AGENTS.md`, [SECURITY.md](../../SECURITY.md#mvp-vcs-boundary), [PLAN.md](../../PLAN.md#liquid-git-integration--next-slice).
- **ADR-0069 / ADR-0141 / ADR-0182** | 2026-07-22–2026-10-04 | Accepted; planned for M3 | Liquid replicas never sync peer to peer: they form a star around one Sync Server, and an optional headless replica needs Workspace opt-in. The M3 MVP replicates complete Workspaces as plaintext to every authorized device, so Roles constrain Liquid surfaces, not the device owner or same-identity processes; selective replication first needs its own resource-closure decision (ADR-0141). Sync merges only durably committed changes through an established CRDT library, without custom conflict logic; ADR-0182's other client invariants are binding in the client architecture — [PROTOCOL.md](../../PROTOCOL.md), [SECURITY.md](../../SECURITY.md#liquid-workspace-access--external-agent-edits), [client architecture](../concept/liquid-client-architecture.md).
- **ADR-0135 / ADR-0166 / ADR-0169 / ADR-0170 / ADR-0171 / ADR-0172 / ADR-0173 / ADR-0174 / ADR-0176 / ADR-0178** | 2026-08-10–2026-10-01 | Accepted; integrated | Flow Agent trusts complete Tool code and promises no general filesystem or network containment; instead, native self-protection of this installation's Flow-owned objects is mandatory, without an unprotected fallback (ADR-0166, ADR-0174). Assigned Tools run without a prompt (ADR-0135), and Tool-initiated configuration changes wait until after the first release (ADR-0173). Accepted costs that look like defects: outside aliases and ancestor moves of protected objects block Tools (ADR-0169); Tools get no direct terminal-device access (ADR-0170); Workspace-local `AGENTS.md` stays Tool-writable while the global one is protected (ADR-0171); macOS relies on the deprecated `/usr/bin/sandbox-exec` (ADR-0172) and on Apple's JavaScript/Objective-C bridge for installer ACL checks instead of another shipped executable (ADR-0178); neither OS guarantees atomic check-to-exec against unconfined host writers (ADR-0176) — [SECURITY.md](../../SECURITY.md#accepted-flow-agent-security-target), [PLATFORMS.md](../../PLATFORMS.md).
- **ADR-0152 / ADR-0153 / ADR-0154 / ADR-0155 / ADR-0221** | 2026-08-23–2026-10-29 | Accepted; global configuration implemented; project Flows, offline and portable clauses pending | `FLOW_AGENT_HOME` is Flow Agent's only configuration and registry authority: unlike most tools it never probes or merges Workspace `.flow` files, project behavior is an explicit Flow, and `AGENTS.md` files are instructions, never configuration. Only once the Agentic Engineer enables a project's `.flow` Flows does Flow Agent read them, and only the exact content they approved; those Flows may only combine Building Blocks already installed in the global home and never add Building Blocks or widen their boundaries, so the Agentic Engineer still configures both (ADR-0221). Device-local Runtime bindings allow network-disabled operation, and Portable continuation moves context, not authority: it creates a reauthorized child Run and never redispatches completed effects. D-058–D-062 own the open choices — [PROTOCOL.md](../../PROTOCOL.md#configuration-and-accepted-post-m11-target-invariants), [SECURITY.md](../../SECURITY.md#accepted-post-m11-target-local-inference-and-portable-continuation).
- **ADR-0163 / ADR-0200 / ADR-0201 / ADR-0218 / ADR-0226** | 2026-09-06–2026-10-30 | Accepted | Support is per product and capability in [PLATFORMS.md](../../PLATFORMS.md), not a workspace-wide promise. Flow Agent gets no native Windows support and macOS no Linux-VM product path (ADR-0163); Meta-Harness gets no native Windows version: on Windows 11 it runs as its Linux build in WSL, never on earlier Windows, and a native version is reconsidered only on shown need, such as Windows-native projects or companies that block WSL (ADR-0226). The Windows Liquid client embeds no Meta-Harness core; as T3 Code does with its server, it installs, updates and starts the Linux Meta-Harness in a WSL distribution, connects over a loopback port, authenticated as the remote connection is (ADR-0185), and also reaches remote hosts, and projects belong in the WSL file system (ADR-0201). The Liquid client runs natively on Windows 11 ARM64 from Release 1, and Meta-Harness follows there through WSL with Linux ARM64 after Release 1; earlier Windows and Intel Macs stay unsupported (ADR-0218). Liquid's macOS releases ship outside the Mac App Store without the App Sandbox, which would prevent starting the user's agents and tools (ADR-0200) — [liquid/README.md](../../liquid/README.md#run).
- **ADR-0184 / ADR-0185 / ADR-0215** | 2026-10-05–2026-10-27 | Accepted; service mode planned | Ahead of M2 and M3a the Meta-Harness core runs inside the Liquid app process; even there the core, never the Liquid UI, owns agent processes, and Liquid sees only its agent-neutral session model. Meta-Harness offers one command set over a private local and an authenticated remote connection. Once it runs as its own service, Liquid reaches the service on its own host like any client and drops the embedded core — [PLAN.md](../../PLAN.md#liquid-agent-surface--early-slice), [Meta-Harness V-Spec](../concept/V-Spec_MetaHarness.html).
- **ADR-0186 / ADR-0213 / ADR-0216 / ADR-0217** | 2026-10-05–2026-10-27 | Accepted | Liquid's Rust–Flutter bridge stays flutter_rust_bridge v2 while it holds the [client architecture](../concept/liquid-client-architecture.md) invariants, also for the Workspace core once the embedded Meta-Harness core leaves; a bridge-caused limit reopens the choice. Because it has one main maintainer, the Workspace crosses it only through a few message-shaped calls, so replacing it touches only those (ADR-0216), and its exact pins and the CI regeneration check stay (ADR-0217); its Dart events stay flat structs without the freezed generator. The bridge compiles in a Dart build hook through native_toolchain_rust, not flutter_rust_bridge's default cargokit and CocoaPods, so `liquid/liquid-bridge/rust-toolchain.toml` deliberately repeats the root Rust pin and adds the build targets (ADR-0213) — [liquid/README.md](../../liquid/README.md), [TESTING.md](../../TESTING.md#development-toolchain).
- **ADR-0188 / ADR-0189 / ADR-0195 / ADR-0206 / ADR-0208 / ADR-0210 / ADR-0222** | 2026-10-23–2026-10-30 | Accepted; implemented in the agent-surface slice, ADR-0222 planned | Tool approvals are a control, not a protection boundary: the Meta-Harness core decides, Watershed's pi extension only asks, and only pi's own reading tools count as read-only, never a tool's own `readOnlyHint` (ADR-0188, ADR-0208). pi's session files are the authoritative session store on their host, with Liquid's records as custom pi entries (ADR-0189); the Workspace holds only a portable copy at turn boundaries (ADR-0229). Until service mode the core's agent events use T3 Code's provider runtime vocabulary, not the PROTOCOL.md v0 families (ADR-0195). The Diff tab is a convenience that claims no completeness, and its snapshots apply project Git settings, which can run commands; this is accepted and explained to users (ADR-0206, ADR-0210). Diff and Trajectory say exactly what they cover; Watershed closes only the cheap gaps, every approval decision with its reason and nested tool calls, adds per-turn checkpoints (ADR-0220), and builds no sandbox, write recording or process tracing to claim completeness (ADR-0222) — [SECURITY.md](../../SECURITY.md#meta-harness-tool-approvals), [meta-harness/README.md](../../meta-harness/README.md), [PROTOCOL.md](../../PROTOCOL.md).
- **ADR-0223 / ADR-0224** | 2026-10-30 | Accepted; target, planned for M3 | Agents act with their own identity and a grant the person signs (area, actions, expiry), never with more authority than that person; they write only through their host replica's CLI/API, the replica holds only their Roles' areas once selective replication follows the complete M3 replicas, a grant may waive the Role's sensitive-change approvals, and revoking it makes the Sync Server refuse further changes (ADR-0223). Enterprise sign-in and sync: passkey accounts plus OIDC/SAML and SCIM, per-device keys, signed changes the Sync Server checks against Roles from M3, a refused change visibly undone on its device, an exportable server audit log, secrets only as references, Liquid Cloud with region and customer keys plus self-hosting, and a data model divided into areas so selective replication can follow complete M3 replicas (ADR-0224); server and device storage follow ADR-0228 — [SECURITY.md](../../SECURITY.md#liquid-workspace-access--external-agent-edits), [V-Spec](../concept/V-Spec_Liquid.html#permissions).
- **ADR-0225 / ADR-0227** | 2026-10-30 | Accepted; planned | Unlike T3 Code, Watershed keeps harness configurations centrally and across devices: Liquid is where they are edited and stored per harness, and Meta-Harness materializes them per session into a home it owns, such as `PI_CODING_AGENT_DIR`, `FLOW_AGENT_HOME` or `CODEX_HOME`, linking the user's credentials instead of copying them; Liquid sends changes as proposals the host applies after approval with audit, credentials never leave the host, and Flow Agent needs a public way to replace a home's configuration (ADR-0227). Every harness can use local inference: Meta-Harness materializes endpoints per host, Flow Agent uses its device-local Runtime binding, Liquid knows each model's context window and tool support, and an area may be kept to local models, checked when a session starts; what a model provider does with prompts is not Liquid's responsibility (ADR-0225) — [SECURITY.md](../../SECURITY.md#meta-agent-configuration-writes), [Meta-Harness V-Spec](../concept/V-Spec_MetaHarness.html).
- **ADR-0228** | 2026-10-30 | Accepted; target, attachments and area keys from M3 | Liquid ships native apps only, no web client. Content is one store with three views: Pages and Blocks in M3, later files like a drive and media like a photo library. Metadata lives in one CRDT document per Page, grouped into areas for Roles, replication and keys; moving a Block between Pages changes both documents in one History action, and a reference to a Page a device does not hold shows a placeholder; contents are content-addressed, chunked, encrypted blobs loaded on demand, indexed by each device when it first loads them; files that cannot merge keep both versions, and M3 builds attachments only. Devices encrypt per area: each area key is wrapped for every allowed device and agent host and, unless a Workspace chooses end-to-end encryption, for the Sync Server, so choosing it later only removes the server's copy. A company may run a compliance replica with its key for search, legal hold and data-loss checks. A signed-in device approves a new one; otherwise a recovery key restores access: area keys are also wrapped for it, and the person or their company holds it. Key approval, rotation, revocation and recovery get dedicated tests, because a fault there loses data. Agent hosts sync through the Sync Server in M3, and a later offline path through the device's Liquid is required for local inference and offline agent work; the server verifies signed changes either way — [SECURITY.md](../../SECURITY.md#liquid-workspace-access--external-agent-edits), [V-Spec](../concept/V-Spec_Liquid.html#model).
- **ADR-0229** | 2026-10-30 | Accepted; target | On a person's device agents run under a sandbox profile that blocks Liquid's data folder and, as Codex's workspace-write does, lets them write only in the project and temporary folders unless the person explicitly allows more, Seatbelt on macOS and Bubblewrap or Landlock on Linux, rechecked after operating-system updates as Flow Agent's are, and Liquid's database key is released only to Liquid; managed company devices use a separate operating-system account, and on Windows 11 agents run in WSL under the Linux profile, which also blocks Liquid's data folder on the Windows drive and starting Windows programs, so neither a path under /mnt nor a Windows process escapes it; projects on Windows drives stay reachable. Liquid AI is a built-in agent profile on a Meta-Harness host, local or remote, limited to Liquid actions. Durability covers four levels through Meta-Harness on every host: clients attach to its service; it journals events before display in short group commits and tool intents before they run and resumes harnesses itself, rerunning only replay-safe tools and reporting others as interrupted, which for Flow Agent applies only to Tools declared replay-safe; it mirrors session records into an agent-sessions area at turn end, their content as blobs with only metadata in the CRDT, so another of the person's hosts continues at a turn boundary from Git checkpoint refs with its own credentials and the person's grant; linked hosts hand each other tasks and later tools — [SECURITY.md](../../SECURITY.md#liquid-workspace-access--external-agent-edits), [Meta-Harness V-Spec](../concept/V-Spec_MetaHarness.html#durability).
- **ADR-0230** | 2026-10-30 | Accepted; target, from M3 | An agent reply shows Liquid content as a reference, never a copy: a Page or Block with a revision, "latest" or a History id. - **ADR-0231** | 2026-10-30 | Accepted; target | A session continues in another harness only as a handoff, as in T3 Code: the target harness starts a new session that receives the conversation so far as text, at most 16,000 tokens by default, marked as context rather than a new request and without attachments or native tool and reasoning state. - **ADR-0232 / ADR-0233** | 2026-10-30 | Accepted; target | Several people share a live session first as T3 Code's guest share does: whoever may access its agent-sessions area watches it live and proposes prompts that the owner sends or dismisses, and the agent keeps the owner's grant; later, team agents take their grant from a Role, and only people who hold that grant's rights themselves steer them, each input attributed to its sender (ADR-0232).
