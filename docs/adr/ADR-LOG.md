# ADR Log

Agent-facing index of accepted decisions that still constrain further work and that intuition would likely get wrong. Each entry names the decision and why it is deliberate; detail lives in the linked canonical docs. Implemented, trivial or superseded decisions are not listed, and their IDs are not reused.

Policy: decision flow and hygiene rules live in [AGENTS.md](../../AGENTS.md#decision-flow).

Format: `ID | date | status | decision — canonical context`

## Decisions

- **ADR-0011 / ADR-0190 / ADR-0191** | 2026-06-09–2026-10-23 | Accepted; Diff tab shipped, the rest planned | Liquid versions its own Workspace data in History, as Notion or AppFlowy do; Watershed builds no VCS for project code, and Flow Agent owns no project history. The Git integration for agent projects is no VCS either: Meta-Harness runs the host's `git` and, for pull requests, `gh` on its host, Liquid only presents it, and Watershed never reads their credentials. Git writes need an explicit user action; a checkout with a running agent allows no branch switch, and parallel sessions use their own worktrees — `AGENTS.md`, [SECURITY.md](../../SECURITY.md#mvp-vcs-boundary), [PLAN.md](../../PLAN.md#liquid-git-integration--next-slice).
- **ADR-0069 / ADR-0141 / ADR-0182** | 2026-07-22–2026-10-04 | Accepted; planned for M3 | Liquid replicas never sync peer to peer: they form a star around one Sync Server, and an optional headless replica needs Workspace opt-in. The M3 MVP replicates complete Workspaces as plaintext to every authorized device, so Roles constrain Liquid surfaces, not the device owner or same-identity processes; selective replication first needs its own resource-closure decision (ADR-0141). Sync merges only durably committed changes through an established CRDT library, without custom conflict logic; ADR-0182's other client invariants are binding in the client architecture — [PROTOCOL.md](../../PROTOCOL.md), [SECURITY.md](../../SECURITY.md#liquid-workspace-access--external-agent-edits), [client architecture](../concept/liquid-client-architecture.md).
- **ADR-0135 / ADR-0166 / ADR-0169 / ADR-0170 / ADR-0171 / ADR-0172 / ADR-0173 / ADR-0174 / ADR-0176 / ADR-0178** | 2026-08-10–2026-10-01 | Accepted; integrated | Flow Agent trusts complete Tool code and promises no general filesystem or network containment; instead, native self-protection of this installation's Flow-owned objects is mandatory, without an unprotected fallback (ADR-0166, ADR-0174). Assigned Tools run without a prompt (ADR-0135), and Tool-initiated configuration changes wait until after the first release (ADR-0173). Accepted costs that look like defects: outside aliases and ancestor moves of protected objects block Tools (ADR-0169); Tools get no direct terminal-device access (ADR-0170); Workspace-local `AGENTS.md` stays Tool-writable while the global one is protected (ADR-0171); macOS relies on the deprecated `/usr/bin/sandbox-exec` (ADR-0172) and on Apple's JavaScript/Objective-C bridge for installer ACL checks instead of another shipped executable (ADR-0178); neither OS guarantees atomic check-to-exec against unconfined host writers (ADR-0176) — [SECURITY.md](../../SECURITY.md#accepted-flow-agent-security-target), [PLATFORMS.md](../../PLATFORMS.md).
- **ADR-0152 / ADR-0153 / ADR-0154 / ADR-0155** | 2026-08-23–2026-08-25 | Accepted; global configuration implemented; offline and portable clauses pending | `FLOW_AGENT_HOME` is Flow Agent's only configuration and registry authority: unlike most tools it never probes or merges Workspace `.flow` files, project behavior is an explicit Flow, and `AGENTS.md` files are instructions, never configuration. Device-local Runtime bindings allow network-disabled operation, and Portable continuation moves context, not authority: it creates a reauthorized child Run and never redispatches completed effects. D-058–D-062 own the open choices — [PROTOCOL.md](../../PROTOCOL.md#configuration-and-accepted-post-m11-target-invariants), [SECURITY.md](../../SECURITY.md#accepted-post-m11-target-local-inference-and-portable-continuation).
- **ADR-0163 / ADR-0200 / ADR-0201 / ADR-0218** | 2026-09-06–2026-10-28 | Accepted | Support is per product and capability in [PLATFORMS.md](../../PLATFORMS.md), not a workspace-wide promise. Flow Agent and Meta-Harness get no native Windows support, and macOS no Linux-VM product path (ADR-0163). In Release 1 the Windows Liquid client embeds no Meta-Harness core and reaches agents only remotely; starting pi through WSL stays a later option (ADR-0201). Windows on ARM64 stays unsupported because Liquid abstracts the operating system, so ARM hardware runs it on Linux (ADR-0218). Liquid's macOS releases ship outside the Mac App Store without the App Sandbox, which would prevent starting the user's agents and tools (ADR-0200) — [liquid/README.md](../../liquid/README.md#run).
- **ADR-0184 / ADR-0185 / ADR-0215** | 2026-10-05–2026-10-27 | Accepted; service mode planned | Ahead of M2 and M3a the Meta-Harness core runs inside the Liquid app process; even there the core, never the Liquid UI, owns agent processes, and Liquid sees only its agent-neutral session model. Meta-Harness offers one command set over a private local and an authenticated remote connection. Once it runs as its own service, Liquid reaches the service on its own host like any client and drops the embedded core — [PLAN.md](../../PLAN.md#liquid-agent-surface--early-slice), [Meta-Harness V-Spec](../concept/V-Spec_MetaHarness.html).
- **ADR-0186 / ADR-0213 / ADR-0216 / ADR-0217** | 2026-10-05–2026-10-27 | Accepted | Liquid's Rust–Flutter bridge stays flutter_rust_bridge v2 while it holds the [client architecture](../concept/liquid-client-architecture.md) invariants, also for the Workspace core once the embedded Meta-Harness core leaves; a bridge-caused limit reopens the choice. Because it has one main maintainer, the Workspace crosses it only through a few message-shaped calls, so replacing it touches only those (ADR-0216), and its exact pins and the CI regeneration check stay (ADR-0217); its Dart events stay flat structs without the freezed generator. The bridge compiles in a Dart build hook through native_toolchain_rust, not flutter_rust_bridge's default cargokit and CocoaPods, so `liquid/liquid-bridge/rust-toolchain.toml` deliberately repeats the root Rust pin and adds the build targets (ADR-0213) — [liquid/README.md](../../liquid/README.md), [TESTING.md](../../TESTING.md#development-toolchain).
- **ADR-0188 / ADR-0189 / ADR-0195 / ADR-0206 / ADR-0208 / ADR-0210** | 2026-10-23–2026-10-27 | Accepted; implemented in the agent-surface slice | Tool approvals are a control, not a protection boundary: the Meta-Harness core decides, Watershed's pi extension only asks, and only pi's own reading tools count as read-only, never a tool's own `readOnlyHint` (ADR-0188, ADR-0208). pi's session files are the only session store, with Liquid's records as custom pi entries (ADR-0189). Until service mode the core's agent events use T3 Code's provider runtime vocabulary, not the PROTOCOL.md v0 families (ADR-0195). The Diff tab is a convenience that claims no completeness, and its snapshots apply project Git settings, which can run commands; this is accepted and explained to users (ADR-0206, ADR-0210) — [SECURITY.md](../../SECURITY.md#meta-harness-tool-approvals), [meta-harness/README.md](../../meta-harness/README.md), [PROTOCOL.md](../../PROTOCOL.md).
