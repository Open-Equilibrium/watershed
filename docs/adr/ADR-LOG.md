# ADR Log

Agent-facing index of accepted decisions that still constrain further work and that intuition would likely get wrong. Each entry names the decision and why it is deliberate; detail lives in the linked canonical docs. Implemented, trivial or superseded decisions are not listed, and their IDs are not reused.

Policy: decision flow and hygiene rules live in [AGENTS.md](../../AGENTS.md#decision-flow).

Format: `ID | date | status | decision — canonical context`

- **ADR-0001 / ADR-0219** | 2026-06-05–2026-10-29 | Accepted | Watershed ships no Node runtime: Flow Agent, the Meta-Harness core and Liquid are Rust and Flutter, and Node in the repository is development tooling. - **ADR-0011 / ADR-0190 / ADR-0191 / ADR-0220 / ADR-0234** | 2026-06-09–2026-11-06 | Accepted; Diff tab, revert, deleting sessions, removing checkpoints, the branch with its background fetch, switching and creating branches, stashing, whole-file commits, the uncommitted Diff scope, Git initialization, push, fast-forward pull, Fetch on request, pull requests and removing worktrees shipped, creating worktrees planned with Chats | Liquid versions its own Workspace data in History, as Notion or AppFlowy do; Watershed builds no VCS for project code, and Flow Agent owns no project history. The Git integration for agent projects is no VCS either: Meta-Harness runs the host's `git` and, for pull requests, `gh` on its host, Liquid only presents it, and Watershed never reads their credentials. For checkpoints, as in T3 Code: without asking, Meta-Harness stores the agent project's files at each turn as commits under its own refs in the project repository, to show each turn's changes and to revert the files to an earlier turn, writes them off the UI path and deletes them with their session (ADR-0220). As in T3 Code, a turn gets one checkpoint at its start and one at its end, holding tracked and new files but none Git ignores; reverting to a turn restores the files below the working folder, deletes new files Git does not ignore and never moves the branch, the Diff tab reads from the checkpoints, and a folder without Git gets none and says so. Unlike T3 Code, they live under `refs/watershed/checkpoints/<session>/<turn>`, one action removes all of them, and a revert first lists the affected files, restores only the working tree, so the project's index stays the user's, and is refused while an agent runs in the same checkout; a turn cannot start if opening its Git repository or registering its checkout guard fails; a failed snapshot after guard acquisition stays nonfatal and keeps Git writes blocked until the turn settles; outside Git a turn holds the same shared lock mechanism in the system temporary folder, keyed by the canonical project folder, until it ends; Initialize Git takes that folder lock alone, refuses a running agent across Liquid windows with the revert notice, and starting turns wait for it; after initialization turns hold the checkout lock; each Git turn holds an OS file lock under the checkout's Git directory (`<git-dir>/watershed/`), which a revert takes alone, so other Liquid windows count too, and one in the Git directory all worktrees share, which deleting a session or removing all checkpoints takes alone, as the refs are shared. Like T3 Code's "Edit from here", a revert continues the session from before the turn with its prompt back in the input area, but on a new pi branch, so the undone turns keep their branch and checkpoints; deleting a session in Liquid deletes its pi session file and checkpoints after confirmation (ADR-0234, [mockups](../design/mockups/liquid-checkpoints.html)). Other Git writes need an explicit user action, but for a background fetch every 15 seconds while a session is open, as in T3 Code, which only updates remote-tracking refs as far as Git expresses its destinations (refspecs, remote groups, legacy remotes, symbolic refs), while links inside the Git directory belong to the repository; a checkout with a running agent allows no branch switch, stash, commit or pull, and parallel sessions use their own worktrees. Branches and commits live in the session header; Git keeps "branch" and Liquid's own are "session branches"; switching with uncommitted changes asks, as GitHub Desktop does, whether to leave them in the branch's one stash or bring them along, and, as there, stashed changes are restored only into a checkout without changes and, unlike there, only while the branch is at the tree they were left on, as Git otherwise merges them and can restore them in part or write paths no check sees; each new stash message appends a short unique operation token after the branch (`Liquid: changes left on main · 7f3a9c0123456789`), and save identity comes only from that operation's message in the stash list, never its tip; missing identity preserves every stash and reports recovery through Git, and older messages without tokens remain listed, restorable and discardable; a stash is applied by its commit and dropped by its place only once Git names that commit as dropped, so another Git storing a stash meanwhile loses nothing; a commit takes whole files the user wrote a message for; attribution presentation follows the mockup’s 2026-11-03 decision, and pull is fast-forward only; Push requires the same single resolved fetch/push repository, with URL credentials stripped for comparison and other destinations refused before any push or hook (2026-11-03, [SECURITY.md](../../SECURITY.md#mvp-vcs-boundary)) ([mockups](../design/mockups/liquid-git-branches.html)). Pull requests and worktrees (2026-11-03, [mockups](../design/mockups/liquid-git-prs-worktrees.html)): as in T3 Code, the Chat's own model writes a pull request's title and description, so its commit range and diff reach only that Chat's provider, through a separate one-shot pi at thinking level low with at most 64 KiB of patch and a 60-second limit (2026-11-06); “Commit, push & create PR” skips the commit with nothing to commit, checks the pull request part before any write and gives the model the selected files too (2026-11-06); a fork's pull request targets GitHub's parent while Push still sends only to the branch's own remote; worktrees live under a per-host root outside the data folder agents cannot reach, and the sandbox grants each worktree as a project folder (ADR-0229); a new Chat defaults to a new worktree from the remote default branch, fetched at send under the existing fetch checks; only an idle Chat moves to another worktree, its session restarting there and its earlier turns losing Revert; worktree removal, on request or with its last Chat, never forces, never happens with staged, unstaged, untracked, ignored or index-hidden files, or while a detached worktree holds commits no branch has, and keeps branch, commits and stashes; creating and removing a worktree take the exclusive common Git guard, so they are refused while any turn in the repository runs; until Chats exist, Settings › Worktrees lists and removes the window's repository's worktrees, and creating them waits for Chats (2026-11-06) — `AGENTS.md`, [SECURITY.md](../../SECURITY.md#mvp-vcs-boundary), [PLAN.md](../../PLAN.md#liquid-git-integration--next-slice).
