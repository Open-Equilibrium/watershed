# ADR Log

Agent-facing index of accepted decisions that still constrain further work and that intuition would likely get wrong. Each entry names the decision and why it is deliberate; detail lives in the linked canonical docs. Implemented, trivial or superseded decisions are not listed, and their IDs are not reused.

Policy: decision flow and hygiene rules live in [AGENTS.md](../../AGENTS.md#decision-flow).

Format: `ID | date | status | decision — canonical context`

## Decisions

- **ADR-0001 / ADR-0219** | 2026-06-05–2026-10-29 | Accepted | Watershed ships no Node runtime: Flow Agent, the Meta-Harness core and Liquid are Rust and Flutter, and Node in the repository is development tooling. The only product TypeScript is Watershed's pi extension, because pi loads only JavaScript or TypeScript extensions; it runs inside the user's own pi. Liquid never bundles pi or Node, also not for office users: the user installs pi (ADR-0219) — [TESTING.md](../../TESTING.md#development-toolchain), [liquid/README.md](../../liquid/README.md#run).
- **ADR-0011 / ADR-0190 / ADR-0191 / ADR-0220 / ADR-0234** | 2026-06-09–2026-11-06 | Accepted; shipped but creating worktrees, which waits for Chats | Liquid versions its own Workspace data in History; Watershed builds no VCS for project code, and Flow Agent owns no project history. The Git integration for agent projects is no VCS either: Meta-Harness runs the host's `git` and `gh`, Liquid presents it, and Watershed never reads their credentials. As in T3 Code, each turn gets a checkpoint at its start and end, stored without asking as commits under Watershed's own refs (`refs/watershed/checkpoints/<session>/<turn>`) with tracked and new files but none Git ignores; the Diff tab reads them, a folder without Git gets none and says so, and one action removes all of them. Like T3 Code's "Edit from here", reverting to a turn first lists the affected files, restores only the working tree, never the index or the branch, continues the session on a new pi branch and is refused while an agent runs in the same checkout. A turn cannot start without its repository and checkout guard: operating-system file locks under the Git directory, or outside Git in the temporary folder, order turns, reverts, Initialize Git, session deletion and worktree changes across Liquid windows. Other Git writes need an explicit user action but for T3 Code's background fetch every 15 seconds; a checkout with a running agent allows no branch switch, stash, commit or pull, and parallel sessions use their own worktrees. Switching with changes offers GitHub Desktop's choice to leave them in the branch's one stash or bring them along; a stash is restored only into a checkout without changes at the tree it was left on and is identified by a unique token in its message; commits take whole files, pull is fast-forward only, and Push needs one resolved fetch and push repository. The Chat's own model writes a pull request's title and description through a one-shot pi, so the diff reaches only that Chat's provider. Worktrees live under a per-host root; a new Chat defaults to a new worktree from the remote default branch, only an idle Chat moves to another, and removal never forces or loses changes, commits or stashes — [SECURITY.md](../../SECURITY.md#mvp-vcs-boundary), [checkpoints](../design/mockups/liquid-checkpoints.html), [branches](../design/mockups/liquid-git-branches.html) and [pull request](../design/mockups/liquid-git-prs-worktrees.html) mockups, [PLAN.md](../../PLAN.md#liquid-git-integration--next-slice).

The M3 MVP replicates complete Workspaces as plaintext to every authorized device, so Roles constrain Liquid surfaces, not the device owner or same-identity processes; selective replication first needs its own resource-closure decision (ADR-0141). Sync merges only durably committed changes through an established CRDT library, without custom conflict logic; ADR-0182's other client invariants are binding in the client architecture — [PROTOCOL.md](../../PROTOCOL.md), [SECURITY.md](../../SECURITY.md#liquid-workspace-access--external-agent-edits), [client architecture](../concept/liquid-client-architecture.md).

- **ADR-0228** | 2026-10-30 | Accepted; target, attachments and area keys from M3 | Liquid ships native apps only, no web client. - **ADR-0235** | 2026-11-01 | Accepted; planned for M3a | Liquid's Workspace foundation, decided while planning the M3a mockups: M3a Sources are local files and folders, read-only, because History cannot revert writes outside Workspace data.
