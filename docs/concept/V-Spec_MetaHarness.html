Self-contained headless control plane for many agents. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Meta-Harness is a self-contained, host-scoped headless control plane. It centralizes configuration, starts and monitors CLI agents on its own host, normalizes their events, runs agent schedules and triggers, and computes AgentPulse metrics. External coding agents (Codex CLI, Claude Code and future agents) plug in through adapters — Codex is an adapter/target, not a Flow Agent base or fork.

Meta-Harness is the Watershed platform's control layer and its orchestration wedge (see PLAN.md). Standalone job: orchestrate, observe and measure agents of any harness, durably across agent hosts. It is a vendor-neutral, self-hostable control plane for heterogeneous host-local CLI agents, not limited to Flow Agent.

Native targets and current availability follow PLATFORMS.md. The clean product model across the three Watershed tools:

Flow Agent    = standalone agent runtime
Meta-Harness  = standalone headless many-agent control plane
Liquid        = standalone native workspace / app-building product

Meta-Harness can run without Liquid. Its CLI/API/service may be reached locally or, with authenticated transport, from another device. Remote API reachability never grants ownership of a CLI process on another host. Liquid is the primary rich UI, not a prerequisite; Meta-Harness does not ship a competing rich GUI in the MVP (packaging: ADR-0286).

2. Product boundary

Meta-Harness owns

  • multi-agent session registry;
  • agent adapter model;
  • central configuration resolution;
  • schedules;
  • event-driven agent triggers and orchestration of threads across harnesses, model providers and devices, including agents that start, message and steer other agents (orchestration, ADR-0253);
  • the four durability levels;
  • materializing the harness configurations Liquid manages;
  • monitoring and observability of harness sessions;
  • event/transcript ingestion from agents;
  • artifact/log/handoff indexing;
  • AgentPulse metric computation;
  • policy-gated configuration writes;
  • approval/audit flow for configuration changes;
  • Git operations on agent projects for Liquid's Git integration;
  • BYOA/API access for external agents and tools;
  • host-local execution plus local-or-remote client surfaces.

Meta-Harness does not own

  • Liquid Pages, Blocks or rendering;
  • mobile/desktop app UX;
  • PowerBar UX;
  • the visual workspace model;
  • Flow Agent runtime internals;
  • governance inside a harness, such as tool approvals and sandboxes, which the harness brings and Meta-Harness neither adds nor changes (ADR-0252);
  • agent execution on another host;
  • a project VCS/history engine;
  • a full separate rich GUI in the MVP.

Session record (ADR-0257): “Export record” writes what Meta-Harness holds about one session as a folder in Downloads: T3's record of the thread (thread.json), record.json ("schema": "watershed-session-record-v2") with each turn's times, how it ended and the files its end checkpoint changed, and a README.txt that says what it leaves out. It is observe-only, adds no gate or recording, and claims no completeness (ADR-0222).

3. Relationship to Flow Agent

Meta-Harness consumes Flow Agent; it does not own it. Flow Agent is a standalone CLI product usable without Meta-Harness or Liquid.

Flow Agent
  owns one local agent runtime
  owns deterministic flow execution
  owns local transcript/session persistence
  owns run/replay/tail/resume and JSONL runtime surfaces

Meta-Harness
  launches Flow Agent on the same host
  consumes its public runtime surfaces
  manages host-local agents and sessions
  normalizes events across providers
  resolves shared config to target CLIs
  computes cross-agent metrics

Meta-Harness integrates through Flow Agent's public runtime surfaces: run/replay/tail/resume and JSONL now; RPC/control and export when implemented; embedding only if D-020 selects it. Its agent executor and each whole CLI agent process share a host, but Meta-Harness never reads Flow Agent's private session store directly or reaches into Flow Agent internals. It does not replace Flow Agent's runtime kernel, deterministic FSM or transcript persistence. Cross-host process control is outside the architecture.

4. Relationship to Liquid

Meta-Harness
  headless control plane
  CLI / API / service
  session / config / metric / agent-schedule backend

Liquid
  native UI / workspace
  Pages, Blocks, Views, PowerBar
  visual session / config / metric surfaces

Projections from one or more Meta-Harness instances may be combined visually, but every record retains instance identity, freshness and authority; every live command routes back to the owning instance.

Liquid must not duplicate a Meta-Harness session registry, adapter logic, config resolution, AgentPulse engine or scheduling engine, and it must not invent global cross-instance authority.

Liquid is a standalone local-first workspace product, not merely Meta-Harness's UI. Workspace sync is independent from this live control plane. When an owning Meta-Harness is unreachable, Liquid may render cached state only as offline/stale and must not queue commands as if success were guaranteed. Meta-Harness and its agents access Liquid only through the workspace CLI/API/mutation pipeline, never Liquid storage internals.

A provisioned local Meta-Harness may start a same-host Flow Agent backed by a local model endpoint without Internet access. This does not let a remote client control an unreachable host. Cross-device Portable continuation uses Flow Agent's future public export/import surface and creates a child Run at the destination; Meta-Harness never copies Flow Agent's private store or transfers a live process claim. Exact archive/ownership behavior remains D-058, archive authenticity remains D-062, and local inference process trust remains D-061.

Git integration

Accepted; implemented on macOS (ADR-0282, ADR-0294, ADR-0295). T3 Code runs Git for every harness with its behavior as shipped, and Liquid's session card and dialogs copy T3's desktop app; Watershed keeps no Git rules of its own. Its trust boundary is in SECURITY.md.

  • Checkpoints and revert: T3 stores each turn's files under refs/t3/ in the project's repository. “Edit from here” rewinds the session to before a prompt and returns it to the input area; “Revert files too” restores the files only for a session in its own worktree, otherwise T3 rewinds the conversation only.
  • Git actions: T3's quick action and menu (Commit, Push, Create PR, Publish repository), its commit dialog, the confirmation on the default branch and its ref picker with Checkout pull request. One writer model writes commit messages left blank, pull request text and session titles (ADR-0294).
  • Worktrees: a new session starts in a new worktree from the default branch, T3's default, which T3 creates under its data folder and names; deleting a worktree's only session asks whether to delete the worktree too.

Session card and statistics

Accepted (ADR-0279, ADR-0287, ADR-0293). The session card copies T3 Code 0.1.9's thread details card and its “Choose what to show” menu: the host and worktree; branch and pull request with its checks and actions (Ready, Merge, Fix, Resolve); the next Git step; Changes against the branch's base or uncommitted; the servers the agent runs, opened in the default browser since Liquid has no browser panel; the session's automations; Lineage and Side chats; then Liquid's statistics, usage limits and the context window, the last two hidden by default as in T3. Project scripts wait until Liquid has a terminal, and “Open in editor” is left out. Its Statistics row or ⌘U opens the statistics panel, laid out like T3 Code's Usage page per turn, with a tool breakdown and a turn breakdown. Liquid shows only what T3 reports and never estimates:

  • Turns: a turn is a T3 run, numbered by its ordinal, which also numbers its end checkpoint and diff; a reverted run leaves the count.
  • Tokens: each provider turn's input, cache reads and writes, output and reasoning, by model. T3 reports no cost per turn, so the Cost row says none is reported.
  • Time: a turn's working time from its start to its end, and each tool call's time; T3 times no single model request, so model time shows a dash.
  • Tool calls: by tool and outcome: succeeded, failed, cancelled and running.
  • Context window: the latest provider turn's context use, window and compaction threshold, when the provider reports them.
  • Interpretations: “Ask the agent about this session…” puts a question into the input area and sends nothing.

5. Deployment modes

Mode A — local service (default single-user)

Liquid Desktop
  connects to the local Meta-Harness service
    starts/monitors Flow Agent, Codex CLI, Claude Code, ...
    stores local sessions/config/metrics

Liquid reaches the Meta-Harness on its own host over the private local connection, like any client (ADR-0215); a login service starts it (ADR-0286). PowerBar commands go to the service, which owns the CLI processes on that host; Liquid Blocks render sessions, transcripts, metrics and the approvals a harness itself asks for. After local provisioning, this mode may bind Flow Agent to a device-local model runtime and operate its core path with network interfaces disabled.

Mode B — server-host Meta-Harness

Liquid Desktop/Mobile → authenticated Meta-Harness API
                             → CLI agents on server host

The API client is remote; execution is not. The server instance owns only its host-local agents, sessions, config, metrics and scheduled work.

Mode C — headless Meta-Harness only (no Liquid)

meta serve
meta run ...
meta sessions
meta schedule ...
meta metrics ...

CI, server automation, power users, external tools, BYOA agents, and early development before Liquid exists.

The host-scoped ownership invariant applies to every mode. M2 implements the local service and preserves authenticated remote API reachability as a protocol seam; execution ownership never crosses hosts.

Implemented (ADR-0303, ADR-0299); meta help describes each command, and remote access and host links are in the README; the config commands print JSON. Target, not yet built: meta sessions, attach, run, schedule, metrics.

API / protocol surface

  • session registry;
  • live event stream;
  • transcript stream;
  • artifact/log/handoff queries;
  • config read/write proposals;
  • agent schedule and trigger control;
  • AgentPulse metric queries;
  • BYOA command surface;
  • answers to a harness's own approvals and questions;
  • approval, rejection and revert of configuration-change proposals.

Accepted target (ADR-0185): an agent executor controls only whole CLI agent processes created or adopted on its own host under an explicit local identity and rejects cross-host process claims. Exposing the API to another device requires authenticated, integrity-protected transport and does not expand agent-executor authority. Liquid must route live commands to the instance that owns the addressed session/configuration and must not treat cached state as controllable while that instance is unreachable.

Service / daemon surface

Implemented on macOS and Linux (ADR-0215, ADR-0286, ADR-0304). meta serve runs the service in its own process; the login service starts it at login and again after it ends. It owns its data folder, META_HARNESS_HOME or else ~/.meta-harness: the configuration store meta-harness.sqlite, T3's data in t3/, the harness homes in harness/ and service.log; a second service on the same folder refuses to start. It serves one WebSocket on 127.0.0.1 at a free port, as T3 Code serves its clients, and admits only connections with the bearer token it writes, with its address, into connection.json (trust limits). With remote access on (ADR-0299), it serves the same WebSocket on this computer's Tailscale addresses as well.

  • Messages: JSON text frames, defined in meta-harness-core/src/api.rs: a call gets one answer; a stream gets a first value, such as a thread's snapshot (ADR-0290), then items until it ends or the client cancels it. Every thread call names its project and thread, so a client that reconnects goes on without opening anything again. Each connection names its API version in the meta-harness-api header; the service refuses any other or missing version with HTTP 426. The message set stays internal until the BYOA deliverable in PLAN.md.
  • Clients: meta and Liquid's agent surface, which keeps nothing of the core or T3 running in its process and leaves the service and its agents running when it quits. A lost connection fails the calls it left unanswered, which are never sent again, and ends its streams; Liquid retries only a lost or missing connection, and any other error ends that follow; a reader that falls 4,096 items behind loses its stream and restores from a snapshot.
  • Remote clients: a device or another host pairs once with a single-use code (ADR-0299), then presents its token to this computer's remote access; a host's code gives its link the access level the receiving host sets (ADR-0300); trust limits state what each token reaches. Until the Liquid account exists, Tailscale carries the connection (ADR-0285); execution ownership never moves with it.

7. Architecture

Agent host on T3 Code

Accepted (ADR-0280 to ADR-0282, ADR-0286); implemented on macOS and Linux as the Meta-Harness service. The pipeline further down predates building on T3 Code and follows it once reworked.

  • Start: Meta-Harness runs the pinned t3 itself with serve --host 127.0.0.1, its own T3CODE_HOME, T3CODE_TELEMETRY_ENABLED=false and T3CODE_OTEL_SDK_DISABLED=true, reads the port from userdata/server-runtime.json and takes an owner token from t3 auth session issue. Before starting, it stops the pinned t3 serve the data folder records as running, such as one a dead Meta-Harness left; one data folder belongs to one Meta-Harness.
  • Protocol: Effect RPC JSON messages on /ws?orchestrationProtocol=2 over tokio-tungstenite, acknowledging every streamed message (ADR-0292). A followed thread keeps T3's projection, updated by each event as T3's own client applies it. T3 closes a socket when its session expires, so the client reconnects with a new 24 h owner token, sends its open streams again, and a thread restarts from the snapshot T3 then sends, so Liquid reloads its Chat.
  • Version pin and contract tests (ADR-0281): meta-harness/t3.lock holds the T3 version and each archive's SHA-256 from the release's SHA256SUMS. The contract tests start that T3 with an empty data folder and a scripted local ACP agent as the provider, with no model or account, and check what Meta-Harness relies on; live providers stay a manual check.

Crates: meta-harness-core (T3's server and client, the session model, the service and its API, the central configuration and the client Liquid uses) and meta-harness-cli (meta); Liquid consumes the API and duplicates no backend logic.

  • Control plane: session registry, task state, attention state and schedules for this instance/host.
  • Config resolver: writes the configuration blocks into each harness home (central config).
  • Meta-Harness agent executor: host-local supervisor for whole CLI agents. It validates that every launched or controlled CLI process belongs to this instance's host; cross-host execution is outside the architecture.

  • Artifact index: logs, summaries, checkpoints, handoff packs and host-provided diffs.
  • Policy gate: every configuration change is a proposal that needs approval (approval and log); control commands leave governance to the harness (ADR-0252).

8. Central config

Unlike T3 Code, Meta-Harness keeps harness configurations centrally (ADR-0225, ADR-0227, ADR-0298). Implemented for Claude Code and Codex: a revision holds three kinds of configuration blocks, each named with letters, digits, - and _, and Meta-Harness writes the current one into a home per harness it owns, which T3 starts each harness with (CLAUDE_CONFIG_DIR, CODEX_HOME, through T3's provider settings).

BlockClaude Code homeCodex home
Instructions, joined in name orderCLAUDE.mdAGENTS.md
Skills: a folder of text files with a SKILL.mdskills/<name>/skills/<name>/
MCP servers: a command, or an http(s) addressmcp.json, passed with --mcp-configconfig.toml

The person's own ~/.claude and ~/.codex stay unchanged and do not configure these sessions; both harnesses keep the person's login (SECURITY.md). Files a harness keeps in its home, and skills Meta-Harness did not write, stay; Meta-Harness replaces only what it wrote. A change is a list of configuration blocks to set or remove:

meta config propose change.json "Test first"
[{"instruction": {"name": "rules", "text": "Run the tests."}},
 {"instruction": {"name": "old", "text": null}},
 {"skill": {"name": "review",
   "files": {"SKILL.md": "# Review"}}},
 {"mcp_server": {"name": "docs",
   "server": {"command": {"command": "docs-mcp",
     "args": ["--stdio"]}}}},
 {"mcp_server": {"name": "wiki",
   "server": {"url": {"url": "https://example.com/mcp"}}}}]

A skill needs a SKILL.md and relative file paths; a proposal holds at most 256 changes.

Until Liquid syncs (M3c), the configuration lives in Meta-Harness's SQLite on its host and changes through meta config and the API; Liquid then edits it across devices, after approved mockups. Flow Agent joins with ACP and needs a public way to replace a home's configuration; its target stays global-only, with project behavior as explicit Flows in its global authority (PROTOCOL.md). A host's Runtime binding stays device-local and is not copied into shared configuration. Target (ADR-0225): every harness can use local inference; Meta-Harness will write endpoints per host, and Flow Agent uses its device-local Runtime binding. Configuration is not a project VCS.

Approval and log (ADR-0298): every change, from any client, is a proposal that takes effect only once approved, and anyone on the account approves or rejects it through the CLI or the API. Proposals, revisions and the log only grow: the log keeps each proposal, approval and rejection with its time and the client's own name for itself, and a revert proposes an earlier revision's blocks, approved like any change. Harness sessions started after an approval use the new revision. An approval counts only once both homes took the new revision; otherwise nothing changes, and a service whose homes cannot take its current revision still starts, so a revert stays possible. Trust limits: SECURITY.md. An area may later be kept to local models, which Meta-Harness checks before a session starts (ADR-0225).

9. AgentPulse

AgentPulse belongs to Meta-Harness, not Liquid. Each instance computes and stores metrics from normalized events/artifacts produced on its host. Liquid may render them through Blocks/Views and visually compare instances, but never rewrites their ownership. Metrics are queryable through the CLI/API.

  • rework ratio;
  • first-attempt success;
  • cost-per-productive-outcome;
  • flow comparison across agents/configs.

AgentPulse is the last, low-priority roadmap item; its formulas are open in D-010.

10. Agent scheduling & orchestration

Meta-Harness owns schedules, triggers and orchestration for agent sessions on its host. Liquid may render and configure them through the public API. These are distinct from Liquid Workspace Automations, which connect Liquid events, conditions and actions and may call an authorized Meta-Harness action. Examples owned by Meta-Harness:

  • recurring tasks;
  • event-driven agent starts;
  • session follow-ups;
  • memory-building / "dreaming" jobs;
  • central-config research;
  • automated metric collection;
  • policy-gated config-improvement proposals.

Agents orchestrating agents

Accepted target (ADR-0288): agents use T3 Code's own orchestration tools, and a tool that takes an environmentId acts on another host through T3's peer links. Meta-Harness builds no tools of its own for this.

WatershedT3 Code, unchangedHarness or outside agentHost connection

Linking two hosts: once per direction, without a person
  1. Both hosts are signed in to the Liquid account (ADR-0285); the receiving host's switch accepts agents from other hosts.
  2. Meta-Harness on the receiving host has its T3 issue a pairing code, as that T3's owner, at the access level it sets for that host (ADR-0300).
  3. The code travels end-to-end encrypted to Meta-Harness on the linking host.
  4. That Meta-Harness runs t3 environment link with the code, its tunnel's address and the access level its policy sets.
  5. The linking T3 signs in to the other T3's /mcp as an OAuth client and keeps the token in its secret store; the receiving T3 lists it under Settings → Connections, where it can be revoked.

Linked work cannot use the receiving host's own links, so every pair of hosts gets its own link, six for three hosts; Meta-Harness adds and removes them.

  • Interim (ADR-0299): until the Liquid account exists, the same link runs over Tailscale. The receiving host issues a pairing code; the linking host's Meta-Harness pairs with that host's remote access, starts a loopback tunnel on a port that stays the same, and has T3 link through it (ADR-0288). A link older than 25 days is made again, while T3 links last 30 days. The tunnel passes only the requests a link makes: GET /.well-known/t3/environment; POST to /oauth/mcp/register, /oauth/mcp/decision and /oauth/mcp/token; and GET, POST and DELETE on /mcp, which linked agents use. It answers every other request with 403, and refuses a decision that asks for a level above the one the receiving host invited (ADR-0300, ADR-0301). Commands: README.
  • Authority: the caller's mode limits the remote work, so a subagent never exceeds its parent (ADR-0223); a plan-mode agent cannot start full-access work.
  • Below full access linked work changes only threads of its own origin and no projects, settings or schedules, and setup scripts are skipped; it can still read every thread on that host. At full access it runs as the receiving host's user, unfenced, still stamped with its origin.
  • The person sees each child under its parent in Liquid and can stop it.
  • Spike result (T3 0.1.9): all three checks pass, so the fallback is not needed. Two T3 servers linked through a byte-forwarding tunnel on http://127.0.0.1:<port>, and a Claude Code thread on one ran delegate_task on the other.
    • Address: t3 environment link accepts plain http only on loopback or Tailscale names and https elsewhere; it refuses loopback only when a person picks a known machine in T3's UI. The tunnel must keep the HTTP Host header unchanged, because the receiving T3 binds the link's OAuth token to it, and each peer keeps a stable local port, because T3 refuses the same peer at a second address while a link lives.
    • Pairing: t3 auth pairing create --json mints a single-use code valid for 5 minutes; linking needs no approval on either side. The link's session lasts 30 days, then Meta-Harness pairs again.
    • Switch: linkedEnvironmentsEnabled is a plain key in T3's settings.json, off by default and needed on both hosts; T3 watches the file, and only an administrator's T3 policy file can lock it.

11. Durability

Restoring the Chat (ADR-0290): one snapshot of T3's projection carries the transcript, turns and pending requests with its stream position; Liquid ignores live events up to that position and applies later ones, so each counts once. When Liquid falls behind or turns are reverted, it restores from a new snapshot.

Accepted target (ADR-0229). Durable work has four levels, and Meta-Harness with T3 Code on every host covers all four: agents depend on the files, tools and credentials of a machine, so every host needs its own supervisor, and Liquid sync plus Git checkpoints give the hosts a shared state.

Persistent agents

Accepted target (ADR-0283), once host moves and host links work: an agent profile has a name, a memory folder, its central configuration and its own T3 routines and webhooks. Each wake-up is a turn in the profile's thread; a full context hands off to a new thread, as Grok Bot keeps the bot, not a thread, as its lasting unit.

Another harness (ADR-0231): a session moves to another harness, such as from Claude Code to Codex, only as a handoff, as in T3 Code. The target starts a new session that receives the conversation so far as text, at most 16,000 tokens by default, marked as context, not a new request; attachments and the provider's tool and reasoning state do not move. A target that already saw part of the conversation receives only what followed; the files come from T3's Git checkpoint ref.

12. BYOA / external control

Meta-Harness exposes itself to other tools and agents through its API/CLI. Typical BYOA interactions:

  • an external agent asks Meta-Harness for current sessions;
  • an external agent starts or steers a session;
  • an external agent proposes a config change;
  • an external tool queries AgentPulse;
  • an external CLI monitors live transcripts.

Configuration changes from any client are proposals that need approval (approval and log).
