V-Spec — Meta-Harness

Self-contained headless control plane for many agents. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Meta-Harness is a self-contained headless control plane. It can be used directly through CLI/API/service mode, and Liquid is the primary rich UI that consumes it. It centralizes configuration, starts and monitors sessions across many agents, normalizes their events, runs schedules and automations, and computes AgentPulse metrics. External coding agents (Codex CLI, Claude Code, Pi Agent) plug in here as adapters — Codex is an adapter/target, not a Loop Agent base or fork (ADR-0028).

Meta-Harness is the Watershed platform's control layer and its team/control/governance wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: control, observe, measure, and govern many agents. It is a vendor-neutral, self-hostable headless control plane for heterogeneous AI agents — not a dashboard for Loop Agent only — and addresses multi-agent sprawl as an open, self-hostable, AGPL-aligned control problem.

The clean product model across the three Watershed tools:

Loop Agent    = standalone agent runtime
Meta-Harness  = standalone headless many-agent control plane
Liquid        = standalone native workspace / app-building product

Meta-Harness can run without Liquid. It is reachable through CLI, an API/protocol surface and a local/remote service, so CI, servers, power users and external (BYOA) agents can drive it headlessly. Liquid is the primary rich UI on top of those surfaces, not a prerequisite. Meta-Harness should not ship a competing full standalone GUI in the MVP; a minimal admin/status UI may be possible later but must not duplicate Liquid (packaging is D-021).

2. Product boundary

Meta-Harness owns

  • multi-agent session registry;
  • agent adapter model;
  • central configuration resolution;
  • schedules;
  • event-driven automations;
  • event/transcript ingestion from agents;
  • artifact/log/handoff indexing;
  • AgentPulse metric computation;
  • policy-gated configuration writes;
  • approval/audit flow for sensitive changes;
  • BYOA/API access for external agents and tools;
  • local and (later) remote execution/control surfaces.

Meta-Harness does not own

  • Liquid dashboards;
  • component rendering;
  • mobile/desktop app UX;
  • PowerBar UX;
  • the visual workspace model;
  • Loop Agent runtime internals;
  • Loop Agent local execution;
  • a project VCS/history engine;
  • a full separate rich GUI in the MVP.

3. Relationship to Loop Agent

Meta-Harness consumes Loop Agent; it does not own it. Loop Agent is a standalone CLI product usable without Meta-Harness or Liquid.

Loop Agent
  owns one local agent runtime
  owns deterministic loop execution
  owns local transcript/session persistence
  owns JSONL/tail/export runtime surfaces and future RPC/SDK seams

Meta-Harness
  consumes Loop Agent's public runtime surfaces
  manages many agents and sessions
  normalizes events across providers
  resolves shared config to target CLIs
  computes cross-agent metrics

Meta-Harness integrates through Loop Agent's public runtime surfaces: the JSONL event stream, RPC mode when implemented, explicit tail/export commands over the event stream, and a future embedded/API surface if available. It never reads Loop Agent's .loop/sessions store directly. It does not replace Loop Agent's runtime kernel, deterministic FSM, sandbox or transcript persistence, and must not reach into Loop Agent internals. No Watershed project-history/VCS engine is required in the MVP.

4. Relationship to Liquid

Meta-Harness
  headless control plane
  CLI / API / service
  session / config / metric / automation backend

Liquid
  native UI / workspace
  dashboards, views, components, PowerBar
  visual session / config / metric / approval surfaces

Liquid consumes Meta-Harness for: the live session dashboard; live transcripts; the artifact/diff/log inbox; approval requests; central-config editor data; AgentPulse dashboards; schedules and automations; PowerBar commands that start/steer sessions; and mobile/desktop monitoring and control.

Liquid must not duplicate Meta-Harness's session registry, adapter logic, config resolution, AgentPulse engine or scheduling engine. The integration boundary is D-025. See the Liquid V-Spec.

Liquid is a standalone workspace/app-building product, not merely Meta-Harness's UI. Liquid is useful with no Meta-Harness present; when Meta-Harness is present, Liquid renders it. Conversely, when Meta-Harness or the agents it orchestrates need to read or edit Liquid workspace data, they go through Liquid's workspace CLI/API/mutation pipeline (recorded in Liquid's action history) and do not mutate Liquid storage internals. See the Liquid V-Spec (§7–8).

5. Deployment modes

Mode A — local embedded sidecar (default single-user)

Liquid Desktop
  starts local Meta-Harness sidecar
    starts/monitors Loop Agent, Codex CLI, Claude Code, Pi Agent, ...
    stores local sessions/config/metrics

The user installs Liquid; Liquid starts Meta-Harness locally; the user usually does not think about it as a separate process. PowerBar starts loops/sessions; dashboards show sessions, transcripts, metrics and approvals.

Mode B — remote Meta-Harness server (team/server)

Liquid Desktop/Mobile
  connects to remote Meta-Harness
    manages many agents/runners
    stores team sessions/config/metrics
    exposes shared dashboards and approvals

Team orchestration, remote runners, shared config, central AgentPulse, long-running scheduled automations and mobile monitoring/control.

Mode C — headless Meta-Harness only (no Liquid)

meta start
meta run ...
meta sessions
meta schedule ...
meta metrics ...

CI, server automation, power users, external tools, BYOA agents, and early development before Liquid exists.

Which modes are in MVP scope is D-022 (recommended: local daemon/sidecar + headless CLI in M2; remote server as a later extension).

Recommended structure (crate names remain provisional until M2 implementation planning):

  session registry, control plane, config resolver,
  schedule/automation engine, policy gate,
  AgentPulse engine, artifact index

meta-harness-adapters
  Loop Agent adapter, Codex CLI adapter,
  Claude Code adapter, Pi Agent adapter, future adapters

meta-harness-service
  local daemon / remote server, API/protocol transport,
  event subscriptions, authentication/permissions hooks

meta-harness-cli
  headless user/admin CLI; run/session/config/metrics commands

liquid integration
  consumes the Meta-Harness API; does not duplicate backend logic
  • Control plane: session registry, task state, attention state, schedules and routing.
  • Config resolver: maps Watershed building blocks to agent-specific CLI config and launch commands.
  • Executors: local executor first; remote execution is an extension point.
  • Adapters: normalize native events into PROTOCOL.md families.
  • Artifact index: logs, summaries, checkpoints, handoff packs and host-provided diffs.
  • Policy gate: config writes and sensitive commands follow the review/audit rules in SECURITY.md.

8. Central config

Meta-Harness is responsible for central config management across agents. It defines shared Watershed building blocks once and resolves them into target-specific runtime configuration for Loop Agent, Codex CLI, Claude Code, Pi Agent and future adapters. Config is made of reusable building blocks, not agent-specific vocabulary (example, not final syntax):

shared block: "review-rust-change"
  instructions: ["review safety", "review tests"]
  tools: ["read", "search", "run-tests"]
  targets:
    loop-agent:  loop script + building blocks
    codex-cli:   instruction pack + command args
    claude-code: instruction pack + command args
    pi-agent:    instruction pack + command args

Meta-Harness config resolution is not a project VCS/history engine. Config changes must be auditable, reviewable and policy-gated. The storage mechanism is an open decision (D-024); it must still be auditable and reviewable regardless of choice.

9. AgentPulse

AgentPulse belongs to Meta-Harness, not Liquid. Meta-Harness computes and stores AgentPulse metrics from normalized events/artifacts received from Loop Agent and other adapters; Liquid only renders the dashboards and views. Metrics are queryable through the CLI/API.

  • rework ratio;
  • first-attempt success;
  • cost-per-productive-outcome;
  • loop comparison across agents/configs.

The formulas are open in D-010. No M2 implementation should guess them.

10. Scheduling & automations

Meta-Harness owns scheduling and event-driven automations. Liquid renders and configures them visually but does not own the automation engine. Examples:

  • recurring tasks;
  • event-driven automations;
  • session follow-ups;
  • memory-building / "dreaming" jobs;
  • central-config research;
  • automated metric collection;
  • policy-gated config-improvement proposals.

11. BYOA / external control

Meta-Harness exposes itself to other tools and agents through its API/CLI. Typical BYOA interactions:

  • an external agent asks Meta-Harness for current sessions;
  • an external agent starts or steers a session;
  • an external agent proposes a config change;
  • an external tool queries AgentPulse;
  • an external CLI monitors live transcripts.

All sensitive commands go through the permission/policy gates in SECURITY.md.

12. M2 implementation packet

M2 defines Meta-Harness as a self-contained headless control plane (see PLAN.md M2). It should define or implement:

  • Meta-Harness CLI;
  • local service/daemon shape;
  • API/protocol surface for Liquid/BYOA;
  • session registry;
  • Loop Agent adapter + at least one external CLI adapter;
  • central config resolver;
  • event/transcript ingestion;
  • artifact/log/handoff indexing;
  • AgentPulse v0 (after formulas are decided);
  • schedule/automation skeleton;
  • approval/audit model for config writes;
  • no rich standalone GUI.

M2 pass/fail includes: Meta-Harness runs without Liquid; Liquid integration is possible through the public API/protocol; Loop Agent integration uses Loop Agent public runtime surfaces; at least two agents are represented through one normalized session/event model; config resolution needs no duplicate per-agent config directories for the same capability; AgentPulse metrics are computed by Meta-Harness and queryable through CLI/API; sensitive config writes create review/audit records.
