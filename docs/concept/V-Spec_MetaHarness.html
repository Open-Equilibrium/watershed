V-Spec — Meta-Harness

Self-contained headless control plane for many agents. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Meta-Harness is a self-contained, host-scoped headless control plane. It centralizes configuration, starts and monitors CLI agents on its own host, normalizes their events, runs agent schedules and triggers, and computes AgentPulse metrics. External coding agents (Codex CLI, Claude Code and future agents) plug in through adapters — Codex is an adapter/target, not a Flow Agent base or fork.

Meta-Harness is the Watershed platform's control layer and its orchestration wedge (GLOSSARY.md, VISION.md, PLAN.md). It is a vendor-neutral, self-hostable control plane for heterogeneous host-local CLI agents, not limited to Flow Agent.

The three-layer model is in VISION.md; native targets and current availability follow PLATFORMS.md.

Meta-Harness can run without Liquid. Its CLI/API/service may be reached locally or, with authenticated transport, from another device; execution ownership stays host-local (PROTOCOL.md). Liquid is the primary rich UI, not a prerequisite; Meta-Harness does not ship a competing rich GUI in the MVP (packaging: ADR-0286).

2. Product boundary

Meta-Harness owns

  • multi-agent session registry;
  • agent adapter model;
  • central configuration resolution;
  • schedules;
  • event-driven agent triggers and orchestration of threads across harnesses, model providers and devices, including agents that start, message and steer other agents (orchestration, ADR-0253);
  • the four durability levels;
  • materializing the harness configurations Liquid manages;
  • monitoring and observability of harness sessions;
  • event/transcript ingestion from agents;
  • artifact/log/handoff indexing;
  • AgentPulse metric computation;
  • policy-gated configuration writes;
  • approval/audit flow for configuration changes;
  • Git operations on agent projects for Liquid's Git integration;
  • BYOA/API access for external agents and tools;
  • host-local execution plus local-or-remote client surfaces.

Meta-Harness does not own

  • Liquid Pages, Blocks or rendering;
  • mobile/desktop app UX;
  • PowerBar UX;
  • the visual workspace model;
  • Flow Agent runtime internals;
  • governance inside a harness, such as tool approvals and sandboxes, which the harness brings and Meta-Harness neither adds nor changes (ADR-0252);
  • agent execution on another host;
  • a project VCS/history engine;
  • a full separate rich GUI in the MVP.

Session record (ADR-0257): “Export record” writes what Meta-Harness holds about one session as a folder in Downloads: T3's record of the thread (thread.json), record.json ("schema": "watershed-session-record-v2") with each turn's times, how it ended and the files its end checkpoint changed, and a README.txt that says what it leaves out. It is observe-only and adds no gate or recording; trust limits are in SECURITY.md.

3. Relationship to Flow Agent

Meta-Harness consumes Flow Agent; it does not own it. Flow Agent is a standalone CLI product usable without Meta-Harness or Liquid.

Flow Agent's ownership is in its V-Spec. Meta-Harness launches it on the same host and integrates through its public runtime surfaces: run/replay/tail/resume, JSONL and flow acp now; export when implemented; embedding only if D-020 selects it. Its agent executor and each whole CLI agent process share a host, but Meta-Harness never reads Flow Agent's private session store directly or reaches into Flow Agent internals. It does not replace Flow Agent's runtime kernel, deterministic FSM or transcript persistence. Cross-host process control is outside the architecture.

4. Relationship to Liquid

Meta-Harness
  headless control plane
  CLI / API / service
  session / config / metric / agent-schedule backend

Liquid
  native UI / workspace
  Pages, Blocks, Views, PowerBar
  visual session / config / metric surfaces

Projections from one or more Meta-Harness instances may be combined visually; their ownership rules are in PROTOCOL.md.

Liquid must not duplicate a Meta-Harness session registry, adapter logic, config resolution, AgentPulse engine or scheduling engine, and it must not invent global cross-instance authority.

Liquid is a standalone local-first workspace product, not merely Meta-Harness's UI. When an owning Meta-Harness is unreachable, Liquid may render cached state only as offline/stale and must not queue commands as if success were guaranteed. Boundaries: VISION.md and PROTOCOL.md.

A provisioned local Meta-Harness may start a same-host Flow Agent backed by a local model endpoint without Internet access. This does not let a remote client control an unreachable host. Cross-device Portable continuation uses Flow Agent's future public export/import surface and creates a child Run at the destination; Meta-Harness never copies Flow Agent's private store or transfers a live process claim. Exact archive/ownership behavior remains D-058, archive authenticity remains D-062, and local inference process trust remains D-061.

Git integration

Accepted; implemented on macOS (ADR-0282, ADR-0294, ADR-0295). Liquid's session card and dialogs copy T3 Code's desktop app, and Git runs as T3 ships it; trust boundary: SECURITY.md.

  • Checkpoints and revert: T3 stores each turn's files under refs/t3/ in the project's repository. “Edit from here” rewinds the session to before a prompt and returns it to the input area; “Revert files too” restores the files only for a session in its own worktree, otherwise T3 rewinds the conversation only.
  • Git actions: T3's quick action and menu (Commit, Push, Create PR, Publish repository), its commit dialog, the confirmation on the default branch and its ref picker with Checkout pull request. The writer model (GLOSSARY.md) writes commit messages left blank, pull request text and session titles (ADR-0294).
  • Worktrees: a new session starts in a new worktree from the default branch, T3's default, which T3 creates under its data folder and names; deleting a worktree's only session asks whether to delete the worktree too.

Session card and statistics

An answer's menu offers Fork from this response, and chart colours run data-1 to data-3 after swapping the last two for colour-blind contrast (ADR-0287).

Accepted (ADR-0279, ADR-0287, ADR-0293). The session card copies T3 Code 0.1.9's thread details card and its “Choose what to show” menu: the host and worktree; branch and pull request with its checks and actions (Ready, Merge, Fix, Resolve); the next Git step; Changes against the branch's base or uncommitted; the servers the agent runs, opened in the default browser since Liquid has no browser panel; the session's automations; Lineage and Side chats; then Liquid's statistics, usage limits and the context window, the last two hidden by default as in T3. Project scripts wait until Liquid has a terminal, and “Open in editor” is left out. Its Statistics row or ⌘U opens the statistics panel, laid out like T3 Code's Usage page per turn, with a tool breakdown and a turn breakdown. Liquid shows only what T3 reports and never estimates:

  • Turns: a turn is a T3 run, numbered by its ordinal, which also numbers its end checkpoint and diff; a reverted run leaves the count.
  • Tokens: each provider turn's input, cache reads and writes, output and reasoning, by model. T3 reports no cost per turn, so the Cost row says none is reported.
  • Time: a turn's working time from its start to its end, and each tool call's time; T3 times no single model request, so model time shows a dash.
  • Tool calls: by tool and outcome: succeeded, failed, cancelled and running.
  • Context window: the latest provider turn's context use, window and compaction threshold, when the provider reports them.
  • Interpretations: “Ask the agent about this session…” puts a question into the input area and sends nothing.

5. Deployment modes

Mode A — local service (default single-user)

Liquid Desktop
  connects to the local Meta-Harness service
    starts/monitors Flow Agent, Codex CLI, Claude Code, ...
    stores local sessions/config/metrics

Liquid reaches the Meta-Harness on its own host over the private local connection, like any client (ADR-0215); a login service starts it (ADR-0286). PowerBar commands go to the service, which owns the CLI processes on that host; Liquid Blocks render sessions, transcripts, metrics and the approvals a harness itself asks for. After local provisioning, this mode may bind Flow Agent to a device-local model runtime and operate its core path with network interfaces disabled.

Mode B — server-host Meta-Harness

Liquid Desktop/Mobile → authenticated Meta-Harness API
                             → CLI agents on server host

The API client is remote; execution is not. The server instance owns only its host-local agents, sessions, config, metrics and scheduled work.

Mode C — headless Meta-Harness only (no Liquid)

meta serve
meta run ...
meta sessions
meta schedule ...
meta metrics ...

CI, server automation, power users, external tools, BYOA agents, and early development before Liquid exists.

The host-scoped ownership invariant applies to every mode. M2 implements the local service and preserves authenticated remote API reachability as a protocol seam; execution ownership never crosses hosts.

Service / daemon surface

Implemented; platform availability is in PLATFORMS.md (ADR-0215, ADR-0286, ADR-0297). meta serve runs the service in its own process; the login service starts it at login and again after it ends. It owns its data folder, META_HARNESS_HOME or else ~/.meta-harness: the configuration store meta-harness.sqlite, T3's data in t3/, the harness homes in harness/ and service.log. It serves one WebSocket on 127.0.0.1 at a free port, as T3 Code serves its clients, and admits only connections with the bearer token it writes, with its address, into connection.json (trust limits). With remote access on (ADR-0299), it serves the same WebSocket on this computer's Tailscale addresses as well.

  • Messages: JSON text frames, defined in meta-harness-core/src/api.rs: a call gets one answer; a stream gets a first value, such as a thread's snapshot (ADR-0290), then items until it ends or the client cancels it. Every thread call names its project and thread, so a client that reconnects goes on without opening anything again. Each connection names its API version in the meta-harness-api header; the service refuses any other or missing version with HTTP 426. The message set stays internal until the BYOA deliverable in PLAN.md.
  • Clients: meta and Liquid's agent surface, which keeps nothing of the core or T3 running in its process and leaves the service and its agents running when it quits. A lost connection fails the calls it left unanswered, which are never sent again, and ends its streams; Liquid retries only a lost or missing connection, and any other error ends that follow; a reader that falls 4,096 items behind loses its stream and restores from a snapshot. A connection holds at most 256 requests in progress, calls and open streams together; one more, or a client that does not read the error replies to malformed requests, ends the connection.
  • Remote clients: a device or another host pairs once with a single-use code (ADR-0299), then presents its token to this computer's remote access; a host's code gives its link the access level the receiving host sets (ADR-0300); trust limits state what each token reaches. Until the Liquid account exists, Tailscale carries the connection (ADR-0285); execution ownership never moves with it.

7. Architecture

Agent host on T3 Code

Accepted (ADR-0280 to ADR-0282, ADR-0286); implemented as the Meta-Harness service, with platforms in PLATFORMS.md. The pipeline further down predates building on T3 Code and follows it once reworked.

  • Start: Meta-Harness runs the pinned t3 itself on 127.0.0.1 with its own T3CODE_HOME and telemetry off (SECURITY.md), reads the port from userdata/server-runtime.json and takes an owner token from t3 auth session issue. Before starting, it stops a pinned t3 serve that the data folder records as running, such as one a dead Meta-Harness left.
  • Protocol: Effect RPC JSON messages on /ws?orchestrationProtocol=2 over tokio-tungstenite, acknowledging every streamed message (ADR-0292). A followed thread keeps T3's projection, updated by each event as T3's own client applies it. T3 closes a socket when its session expires, so the client reconnects with a new 24 h owner token, sends its open streams again, and a thread restarts from the snapshot T3 then sends, so Liquid reloads its Chat.
  • Version pin and contract tests (ADR-0281): meta-harness/t3.lock holds the T3 version and each archive's SHA-256 from the release's SHA256SUMS. The contract tests start that T3 with an empty data folder and a scripted local ACP agent as the provider, with no model or account, and check what Meta-Harness relies on; live providers stay a manual check.

8. Central config

Unlike T3 Code, Meta-Harness keeps harness configurations centrally (ADR-0225, ADR-0227, ADR-0298). Implemented for Claude Code and Codex: a revision holds three kinds of configuration blocks, each named with letters, digits, - and _, and Meta-Harness writes the current one into a home per harness it owns, which T3 starts each harness with (CLAUDE_CONFIG_DIR, CODEX_HOME, through T3's provider settings).

BlockClaude Code homeCodex home
Instructions, joined in name orderCLAUDE.mdAGENTS.md
Skills: a folder of text files with a SKILL.mdskills/<name>/skills/<name>/
MCP servers: a command, or an http(s) addressmcp.json, passed with --mcp-configconfig.toml

The person's own ~/.claude and ~/.codex stay unchanged and do not configure these sessions; both harnesses keep the person's login (SECURITY.md). Files a harness keeps in its home, and skills Meta-Harness did not write, stay; Meta-Harness replaces only what it wrote. A change is a list of configuration blocks to set or remove:

meta config propose change.json "Test first"
[{"instruction": {"name": "rules", "text": "Run the tests."}},
 {"instruction": {"name": "old", "text": null}},
 {"skill": {"name": "review",
   "files": {"SKILL.md": "# Review"}}},
 {"mcp_server": {"name": "docs",
   "server": {"command": {"command": "docs-mcp",
     "args": ["--stdio"]}}}},
 {"mcp_server": {"name": "wiki",
   "server": {"url": {"url": "https://example.com/mcp"}}}}]

A skill needs a SKILL.md and relative file paths; a proposal holds at most 256 changes.

Until Liquid syncs (M3c), the configuration lives in Meta-Harness's SQLite on its host and changes through meta config and the API; Liquid then edits it across devices, after approved mockups. Flow Agent joins with ACP and needs a public way to replace a home's configuration; its target stays global-only, with project behavior as explicit Flows in its global authority (PROTOCOL.md). A host's Runtime binding stays device-local and is not copied into shared configuration. Target (ADR-0225): every harness can use local inference; Meta-Harness will write endpoints per host, and Flow Agent uses its device-local Runtime binding.

Approval and log (ADR-0298): a change from any client is a proposal (GLOSSARY.md) that takes effect only once approved through the CLI or the API. Proposals, revisions and the log only grow: the log keeps each proposal, approval and rejection with its time and the client's own name for itself, and a revert proposes an earlier revision's blocks, approved like any change. Harness sessions started after an approval use the new revision. An approval counts only once both homes took the new revision; otherwise nothing changes. If the homes cannot even be restored, or did not take the current revision at start, they count as not reconciled until an approval's write succeeds, and meta status says so. A service whose homes cannot take its current revision still starts, so a revert stays possible. Trust limits: SECURITY.md. An area may later be kept to local models, which Meta-Harness checks before a session starts (ADR-0225).

10. Agent scheduling & orchestration

Meta-Harness owns schedules, triggers and orchestration for agent sessions on its host. Liquid may render and configure them through the public API. Liquid Automations are a separate concept (GLOSSARY.md). Examples owned by Meta-Harness:

  • recurring tasks;
  • event-driven agent starts;
  • session follow-ups;
  • memory-building / "dreaming" jobs;
  • central-config research;
  • automated metric collection;
  • policy-gated config-improvement proposals.

Agents orchestrating agents

Accepted target (ADR-0288): agents use T3 Code's own orchestration tools, and a tool that takes an environmentId acts on another host through T3's peer links. Meta-Harness carries each link over the host connection (ADR-0285), pairs the T3 servers itself and sets each link's access level by policy; it builds no tools of its own for this unless a spike shows pairing needs a person or T3 refuses the tunnel's address.

Linking two hosts: once per direction, without a person
  1. Both hosts are signed in to the Liquid account (ADR-0285); the receiving host's switch accepts agents from other hosts.
  2. Meta-Harness on the receiving host has its T3 issue a pairing code, as that T3's owner, at the access level it sets for that host (ADR-0300).
  3. The code travels end-to-end encrypted to Meta-Harness on the linking host.
  4. That Meta-Harness runs t3 environment link with the code, its tunnel's address and the access level its policy sets.

Linked work cannot use the receiving host's own links, so every pair of hosts gets its own link, six for three hosts; Meta-Harness adds and removes them.

    • Switch: linkedEnvironmentsEnabled is a plain key in T3's settings.json, off by default and needed on both hosts; T3 watches the file, and only an administrator's T3 policy file can lock it.

11. Durability

Restoring the Chat (ADR-0290): one snapshot of T3's projection carries the transcript, turns and pending requests with its stream position; Liquid ignores live events up to that position and applies later ones, so each counts once. When Liquid falls behind or turns are reverted, it restores from a new snapshot.

Accepted target (ADR-0229). Durable work has four levels, and Meta-Harness with T3 Code on every host covers all four: agents depend on the files, tools and credentials of a machine, so every host needs its own supervisor, and Liquid sync plus Git checkpoints give the hosts a shared state.

Moving a session to another host

Until the account exists, a live move (ADR-0308) carries a session while both hosts answer; a host too old for moves is not offered. The source ends its running turn and pushes the session's branch through the project's Git remote. The target starts the session on that branch, in a clean checkout it already has or a new worktree, from a handoff of at most 16,000 bytes, keeps the earlier transcript as the move record and delivers the queued messages the move carried; only then does it report the move landed, and the source seals the session. Each move has a transfer id and every step can be repeated. The target's record decides an interrupted move: landed seals the source; once the target has refused the transfer for good, the source is released; while the target does not answer, the session waits. The Liquid that started the move finishes it; any other Liquid can from five minutes after the move began or was handed over. A person can cancel: the target refuses the transfer and the source is released; a target still starting the session refuses the cancel, and one that already landed it finishes the move. If the target does not answer, the source is released anyway, and a session the target already started runs on both hosts. A move never removes a checkout. The calls are in meta-harness-core/src/api.rs.

Accepted target (ADR-0284, ADR-0289). Usually the old host is gone, for example crashed, so the move asks the person for as little as possible and feels like a compaction: only the transcript becomes a summary, and every other part of the session is restored.

Persistent agents

Built on macOS and Linux, with Liquid's screens (ADR-0283; design guidelines). The agent profile, not a thread, is the lasting unit, as with Grok Bot.

  • Profile: a fixed id, a name, a project, a model and a permission mode (approval-required by default) in the service's SQLite, and a private memory folder, <home>/agents/<id>/memory (mode 0700), outside any repository. Its instructions are instructions.md there (mode 0600), whose first line, # name, is the agent's name. meta agent create makes a named profile; Liquid makes one from a first message, and the agent names itself by writing that line.
  • Thread: the profile owns one current T3 thread in the project's checkout. Its first message names the agent, its instructions file and memory folder and, for a new agent, ends with the person's words, which are all Liquid shows of it.
  • Routines: T3 scheduled tasks bound to that thread in continue mode, made by meta agent routine add, Liquid's Add routine, or the agent itself with T3's schedule_task tool. A routine runs on an interval of at least a minute, at a time on chosen weekdays, once, or per webhook request on T3's /api/hooks/<task>/<token> path. Each wake-up is a turn in the current thread, marked with its routine.
  • Changes: after each turn Meta-Harness compares the instructions file and the routines with what it saw last and records each change the agent made, with the turn; Undo restores the instructions or routine before it. Changes made through Meta-Harness, by a person, are not recorded. Model and permission mode change only by hand.
  • Mentions: @name in another Chat sends the person's words to the agent's thread with a T3 thread reference to that Chat, which the agent may read; Meta-Harness reports the turn's answer for that Chat.
  • Full context: when a turn ends and T3 reports the context window at least 80% full, Meta-Harness opens the next thread. The new thread starts with the same opening plus the host-move handoff text (ADR-0231), the routines move to it, and the old thread stays, listed as an earlier thread. A next thread is stored before it starts, so a restart finishes the switch.
  • Removal: meta agent remove or Liquid deletes the profile's routines and keeps its memory folder and threads.
  • Target, sharing: with the Liquid account, the creator always edits an agent and grants other members the Role Can use (write to it, mention it) or Can edit (also instructions, routines, model, permission mode). An approval goes to the person whose message caused it; a routine's to the creator or an editor.
  • Open: moving a profile with its memory to another host.

Another harness (ADR-0231): a session moves to another harness, such as from Claude Code to Codex, only as a handoff, as in T3 Code. The target starts a new session that receives the conversation so far as text, at most 16,000 tokens by default, marked as context, not a new request; attachments and the provider's tool and reasoning state do not move. A target that already saw part of the conversation receives only what followed; the files come from T3's Git checkpoint ref.

12. BYOA / external control

Meta-Harness exposes itself to other tools and agents through its API/CLI. Typical BYOA interactions:

  • an external agent asks Meta-Harness for current sessions;
  • an external agent starts or steers a session;
  • an external agent proposes a config change;
  • an external tool queries AgentPulse;
  • an external CLI monitors live transcripts.

Configuration changes from any client are proposals that need approval (approval and log).
