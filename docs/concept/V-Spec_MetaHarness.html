V-Spec — Meta-Harness

Self-contained headless control plane for many agents. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Meta-Harness is a self-contained, host-scoped headless control plane. It centralizes configuration, starts and monitors CLI agents on its own host, normalizes their events, runs agent schedules and triggers, and computes AgentPulse metrics. External coding agents (Codex CLI, Claude Code and future agents) plug in through adapters — Codex is an adapter/target, not a Flow Agent base or fork (ADR-0028).

Meta-Harness is the Watershed platform's control layer and its team/control/governance wedge (see PLAN.md and ADR-0018). Standalone job: control, observe, measure, and govern many agents. It is a vendor-neutral, self-hostable control plane for heterogeneous host-local CLI agents, not limited to Flow Agent.

The clean product model across the three Watershed tools:

Flow Agent    = standalone agent runtime
Meta-Harness  = standalone headless many-agent control plane
Liquid        = standalone native workspace / app-building product

Meta-Harness can run without Liquid. Its CLI/API/service may be reached locally or, with authenticated transport, from another device. Remote API reachability never grants ownership of a CLI process on another host. Liquid is the primary rich UI, not a prerequisite; Meta-Harness does not ship a competing rich GUI in the MVP (packaging: D-021).

2. Product boundary

Meta-Harness owns

  • multi-agent session registry;
  • agent adapter model;
  • central configuration resolution;
  • schedules;
  • event-driven agent triggers and orchestration;
  • event/transcript ingestion from agents;
  • artifact/log/handoff indexing;
  • AgentPulse metric computation;
  • policy-gated configuration writes;
  • approval/audit flow for sensitive changes;
  • BYOA/API access for external agents and tools;
  • host-local execution plus local-or-remote client surfaces.

Meta-Harness does not own

  • Liquid Pages, Blocks or rendering;
  • mobile/desktop app UX;
  • PowerBar UX;
  • the visual workspace model;
  • Flow Agent runtime internals;
  • agent execution on another host;
  • a project VCS/history engine;
  • a full separate rich GUI in the MVP.

3. Relationship to Flow Agent

Meta-Harness consumes Flow Agent; it does not own it. Flow Agent is a standalone CLI product usable without Meta-Harness or Liquid.

Flow Agent
  owns one local agent runtime
  owns deterministic flow execution
  owns local transcript/session persistence
  owns run/replay/tail/resume and JSONL runtime surfaces

Meta-Harness
  launches Flow Agent on the same host
  consumes its public runtime surfaces
  manages host-local agents and sessions
  normalizes events across providers
  resolves shared config to target CLIs
  computes cross-agent metrics

Meta-Harness integrates through Flow Agent's public runtime surfaces: run/replay/tail/resume and JSONL now; RPC/control and export when implemented; embedding only if D-020 selects it. Its agent executor and each whole CLI agent process share a host, but Meta-Harness never reads Flow Agent's private session store directly or reaches into Flow Agent internals. This process supervisor is not a Flow Executor: it does not select, configure or manage Flow's Tool Sandbox. It also does not replace Flow Agent's runtime kernel, deterministic FSM or transcript persistence. Cross-host process control is outside the architecture.

4. Relationship to Liquid

Meta-Harness
  headless control plane
  CLI / API / service
  session / config / metric / agent-schedule backend

Liquid
  native UI / workspace
  Pages, Blocks, Views, PowerBar
  visual session / config / metric / approval surfaces

Projections from one or more Meta-Harness instances may be combined visually, but every record retains instance identity, freshness and authority; every live command routes back to the owning instance.

Liquid must not duplicate a Meta-Harness session registry, adapter logic, config resolution, AgentPulse engine or scheduling engine, and it must not invent global cross-instance authority.

Liquid is a standalone local-first workspace product, not merely Meta-Harness's UI. Workspace sync is independent from this live control plane. When an owning Meta-Harness is unreachable, Liquid may render cached state only as offline/stale and must not queue commands as if success were guaranteed. Meta-Harness and its agents access Liquid only through the workspace CLI/API/mutation pipeline, never Liquid storage internals.

A provisioned local Meta-Harness may start a same-host Flow Agent backed by a local model endpoint without Internet access. This does not let a remote client control an unreachable host. Cross-device Portable continuation uses Flow Agent's future public export/import surface and creates a child Run at the destination; Meta-Harness never copies Flow Agent's private store or transfers a live process claim. Exact archive/ownership behavior remains D-058, archive authenticity remains D-062, and local inference process trust remains D-061.

5. Deployment modes

Mode A — local sidecar (default single-user)

Liquid Desktop
  starts local Meta-Harness sidecar
    starts/monitors Flow Agent, Codex CLI, Claude Code, ...
    stores local sessions/config/metrics

Liquid starts Meta-Harness locally. PowerBar commands go to the sidecar, which owns the CLI processes on that host; Liquid Blocks render sessions, transcripts, metrics and approvals. After local provisioning, this mode may bind Flow Agent to a device-local model runtime and operate its core path with network interfaces disabled.

Mode B — server-host Meta-Harness

Liquid Desktop/Mobile → authenticated Meta-Harness API
                             → CLI agents on server host

The API client is remote; execution is not. The server instance owns only its host-local agents, sessions, config, metrics and scheduled work.

Mode C — headless Meta-Harness only (no Liquid)

meta start
meta run ...
meta sessions
meta schedule ...
meta metrics ...

CI, server automation, power users, external tools, BYOA agents, and early development before Liquid exists.

The host-scoped ownership invariant applies to every mode. M2 implements the local sidecar/daemon and preserves authenticated remote API reachability as a protocol seam; execution ownership never crosses hosts.

Recommended structure (crate names remain provisional until M2 implementation planning):

meta-harness-core
  session registry, control plane, config resolver,
  agent schedule/trigger engine, policy gate,
  AgentPulse engine, artifact index

meta-harness-adapters
  Flow Agent adapter, Codex CLI adapter,
  Claude Code adapter, future adapters

meta-harness-service
  local daemon / server-host service, API/protocol transport,
  event subscriptions, authentication/permissions hooks

meta-harness-cli
  headless user/admin CLI; run/session/config/metrics commands

liquid integration
  consumes the Meta-Harness API; does not duplicate backend logic
  • Control plane: session registry, task state, attention state and schedules for this instance/host.
  • Config resolver: maps Watershed building blocks to agent-specific CLI config and launch commands.
  • Meta-Harness agent executor: host-local supervisor for whole CLI agents. It validates that every launched or controlled CLI process belongs to this instance's host; cross-host execution is outside the architecture. It is not a Flow Executor and has no Tool-Sandbox responsibility.
  • Adapters: normalize native events into PROTOCOL.md families.
  • Artifact index: logs, summaries, checkpoints, handoff packs and host-provided diffs.
  • Policy gate: config writes and sensitive commands follow the review/audit rules in SECURITY.md.

8. Central config

Meta-Harness is responsible for central config management across agents. It defines shared Watershed building blocks once and resolves them into target-specific runtime configuration for Flow Agent, Codex CLI, Claude Code and future adapters. The Flow Agent target is global-only: it receives no project-local config layer, and project-specific behavior is an explicit Flow in its global authority. Other adapters retain their own documented scope. A host's Runtime binding—endpoint plus capability-dependent model/runtime, optional local-artifact, optional typed credential-reference and resource-policy fields—remains device-local operational state and is not copied into portable shared config; credential material stays in the target's protected store. Config is made of reusable building blocks, not agent-specific vocabulary (example, not final syntax):

shared block: "review-rust-change"
  instructions: ["review safety", "review tests"]
  tools: ["read", "search", "run-tests"]
  targets:
    flow-agent:  flow script + building blocks
    codex-cli:   instruction pack + command args
    claude-code: instruction pack + command args

Meta-Harness config resolution is not a project VCS/history engine. Config changes must be auditable, reviewable and policy-gated. Meta-Harness may manage Flow Agent's global authority only through a public config surface; it never writes target-private storage directly. Meta-Harness storage remains D-024, while Flow Agent's exact global path, authoring and local-config migration remain D-057.

9. AgentPulse

AgentPulse belongs to Meta-Harness, not Liquid. Each instance computes and stores metrics from normalized events/artifacts produced on its host. Liquid may render them through Blocks/Views and visually compare instances, but never rewrites their ownership. Metrics are queryable through the CLI/API.

  • rework ratio;
  • first-attempt success;
  • cost-per-productive-outcome;
  • flow comparison across agents/configs.

The formulas are open in D-010. No M2 implementation should guess them.

10. Agent scheduling & orchestration

Meta-Harness owns schedules, triggers and orchestration for agent sessions on its host. Liquid may render and configure them through the public API. These are distinct from Liquid Workspace Automations, which connect Liquid events, conditions and actions and may call an authorized Meta-Harness action. Examples owned by Meta-Harness:

  • recurring tasks;
  • event-driven agent starts;
  • session follow-ups;
  • memory-building / "dreaming" jobs;
  • central-config research;
  • automated metric collection;
  • policy-gated config-improvement proposals.

11. BYOA / external control

Meta-Harness exposes itself to other tools and agents through its API/CLI. Typical BYOA interactions:

  • an external agent asks Meta-Harness for current sessions;
  • an external agent starts or steers a session;
  • an external agent proposes a config change;
  • an external tool queries AgentPulse;
  • an external CLI monitors live transcripts.

All sensitive commands go through the permission/policy gates in SECURITY.md.
