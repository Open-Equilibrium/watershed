V-Spec — Meta-Harness

Self-contained headless control plane for many agents. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Meta-Harness is a self-contained, host-scoped headless control plane. It centralizes configuration, starts and monitors CLI agents on its own host, normalizes their events, runs agent schedules and triggers, and computes AgentPulse metrics. External coding agents (Codex CLI, Claude Code and future agents) plug in through adapters — Codex is an adapter/target, not a Flow Agent base or fork.

Meta-Harness is the Watershed platform's control layer and its orchestration wedge (see PLAN.md). Standalone job: orchestrate, observe and measure agents of any harness, durably across agent hosts. It is a vendor-neutral, self-hostable control plane for heterogeneous host-local CLI agents, not limited to Flow Agent.

Native targets and current availability follow PLATFORMS.md. The clean product model across the three Watershed tools:

Flow Agent    = standalone agent runtime
Meta-Harness  = standalone headless many-agent control plane
Liquid        = standalone native workspace / app-building product

Meta-Harness can run without Liquid. Its CLI/API/service may be reached locally or, with authenticated transport, from another device. Remote API reachability never grants ownership of a CLI process on another host. Liquid is the primary rich UI, not a prerequisite; Meta-Harness does not ship a competing rich GUI in the MVP (packaging: D-021).

2. Product boundary

Meta-Harness owns

  • multi-agent session registry;
  • agent adapter model;
  • central configuration resolution;
  • schedules;
  • event-driven agent triggers and orchestration of threads across harnesses, model providers and devices, including agents that start, message and steer other agents (orchestration, ADR-0253);
  • the four durability levels;
  • materializing the harness configurations Liquid manages;
  • monitoring and observability of harness sessions;
  • event/transcript ingestion from agents;
  • artifact/log/handoff indexing;
  • AgentPulse metric computation;
  • policy-gated configuration writes;
  • approval/audit flow for configuration changes;
  • Git operations on agent projects for Liquid's Git integration;
  • BYOA/API access for external agents and tools;
  • host-local execution plus local-or-remote client surfaces.

Meta-Harness does not own

  • Liquid Pages, Blocks or rendering;
  • mobile/desktop app UX;
  • PowerBar UX;
  • the visual workspace model;
  • Flow Agent runtime internals;
  • governance inside a harness, such as tool approvals and sandboxes, which the harness brings and Meta-Harness neither adds nor changes (ADR-0252);
  • agent execution on another host;
  • a project VCS/history engine;
  • a full separate rich GUI in the MVP.

Session record (ADR-0257): “Export record” writes what Meta-Harness already records about one stored session as a folder in Downloads: pi's session file unchanged, and record.json ("schema": "watershed-session-record-v1") with each turn's times, how it ended, its checkpoint commits and the files it changed, plus a README.txt that says what it leaves out. It is observe-only, adds no gate or recording, and claims no completeness (ADR-0222). Its turns are only those that ran through Meta-Harness, and its file changes are those between checkpoints, in files Git does not ignore.

3. Relationship to Flow Agent

Meta-Harness consumes Flow Agent; it does not own it. Flow Agent is a standalone CLI product usable without Meta-Harness or Liquid.

Flow Agent
  owns one local agent runtime
  owns deterministic flow execution
  owns local transcript/session persistence
  owns run/replay/tail/resume and JSONL runtime surfaces

Meta-Harness
  launches Flow Agent on the same host
  consumes its public runtime surfaces
  manages host-local agents and sessions
  normalizes events across providers
  resolves shared config to target CLIs
  computes cross-agent metrics

Meta-Harness integrates through Flow Agent's public runtime surfaces: run/replay/tail/resume and JSONL now; RPC/control and export when implemented; embedding only if D-020 selects it. Its agent executor and each whole CLI agent process share a host, but Meta-Harness never reads Flow Agent's private session store directly or reaches into Flow Agent internals. It does not replace Flow Agent's runtime kernel, deterministic FSM or transcript persistence. Cross-host process control is outside the architecture.

4. Relationship to Liquid

Meta-Harness
  headless control plane
  CLI / API / service
  session / config / metric / agent-schedule backend

Liquid
  native UI / workspace
  Pages, Blocks, Views, PowerBar
  visual session / config / metric surfaces

Projections from one or more Meta-Harness instances may be combined visually, but every record retains instance identity, freshness and authority; every live command routes back to the owning instance.

Liquid must not duplicate a Meta-Harness session registry, adapter logic, config resolution, AgentPulse engine or scheduling engine, and it must not invent global cross-instance authority.

Liquid is a standalone local-first workspace product, not merely Meta-Harness's UI. Workspace sync is independent from this live control plane. When an owning Meta-Harness is unreachable, Liquid may render cached state only as offline/stale and must not queue commands as if success were guaranteed. Meta-Harness and its agents access Liquid only through the workspace CLI/API/mutation pipeline, never Liquid storage internals.

A provisioned local Meta-Harness may start a same-host Flow Agent backed by a local model endpoint without Internet access. This does not let a remote client control an unreachable host. Cross-device Portable continuation uses Flow Agent's future public export/import surface and creates a child Run at the destination; Meta-Harness never copies Flow Agent's private store or transfers a live process claim. Exact archive/ownership behavior remains D-058, archive authenticity remains D-062, and local inference process trust remains D-061.

Git integration

Accepted (ADR-0011, ADR-0190, ADR-0191, ADR-0220, ADR-0234); shipped except creating worktrees, which waits for Chats. Meta-Harness runs the host's git and gh on agent projects and Liquid presents it; it is no VCS. Its security boundary and exact mechanics are canonical in SECURITY.md; the worktree UI still to build is in the pull request and worktree mockups.

  • Checkpoints: as in T3 Code, each turn gets one at its start and one at its end, stored without asking as commits under Watershed's own checkpoint refs, with tracked and new files but none Git ignores; the Diff tab reads them. A folder without Git gets none and says so; deleting a session deletes its checkpoints, and one action removes all of them.
  • Revert: like T3 Code's “Edit from here”, reverting to a turn first lists the affected files, runs only while the project still matches that confirmed list (ADR-0256), restores only the working tree, never the index or the branch, leaves repositories inside the project alone, continues the session on a new pi branch with the turn's prompt back in the input area, so the undone turns stay in the session tree, and is refused while an agent runs in the same checkout.
  • Guards: a turn cannot start without its repository and checkout guard. These operating-system file locks under the Git directory, or outside Git in the user's lock folder, order turns, reverts, Initialize Git, session deletion and worktree changes across Liquid windows.
  • Branches and commits: every other Git write needs an explicit user action, except T3 Code's background fetch every 15 seconds. A checkout with a running agent allows no branch switch, stash, commit or pull, and parallel sessions use their own worktrees. Switching with changes offers GitHub Desktop's choice to leave them in the branch's one stash or bring them along; a stash is restored only into a checkout without changes at the tree it was left on and is identified by a unique token in its message. The user writes the commit message, which Liquid never generates; commits take whole files and need a branch, pull is fast-forward only, and Push needs one resolved fetch and push repository.
  • Pull requests: the Chat's own model writes the title and description through a one-shot pi, so the diff reaches only that Chat's provider.
  • Worktrees: they live under a per-host root; a new Chat defaults to a new worktree from the remote default branch, only an idle Chat moves to another, and removal never forces or loses changes, commits or stashes. Accepted target with Chats: the root lies outside Liquid's and Meta-Harness's data folders; a worktree is also removed with its last Chat under the same removal rules; creating one takes the exclusive common Git guard and is refused while any turn in the repository runs.

5. Deployment modes

Mode A — local service (default single-user)

Liquid Desktop
  connects to the local Meta-Harness service
    starts/monitors Flow Agent, Codex CLI, Claude Code, ...
    stores local sessions/config/metrics

Liquid reaches the Meta-Harness on its own host over the private local connection, like any client (ADR-0215); who starts the service is D-074. PowerBar commands go to the service, which owns the CLI processes on that host; Liquid Blocks render sessions, transcripts, metrics and the approvals a harness itself asks for. After local provisioning, this mode may bind Flow Agent to a device-local model runtime and operate its core path with network interfaces disabled.

Mode B — server-host Meta-Harness

Liquid Desktop/Mobile → authenticated Meta-Harness API
                             → CLI agents on server host

The API client is remote; execution is not. The server instance owns only its host-local agents, sessions, config, metrics and scheduled work.

Mode C — headless Meta-Harness only (no Liquid)

meta start
meta run ...
meta sessions
meta schedule ...
meta metrics ...

CI, server automation, power users, external tools, BYOA agents, and early development before Liquid exists.

The host-scoped ownership invariant applies to every mode. M2 implements the local service and preserves authenticated remote API reachability as a protocol seam; execution ownership never crosses hosts.

Command names below are target shape, not final implementation.

CLI surface

API / protocol surface

  • session registry;
  • live event stream;
  • transcript stream;
  • artifact/log/handoff queries;
  • config read/write proposals;
  • agent schedule and trigger control;
  • AgentPulse metric queries;
  • BYOA command surface;
  • answers to a harness's own approvals and questions;
  • approval, rejection and revert of configuration-change proposals.

Accepted target (ADR-0185): an agent executor controls only whole CLI agent processes created or adopted on its own host under an explicit local identity and rejects cross-host process claims. Exposing the API to another device requires authenticated, integrity-protected transport and does not expand agent-executor authority. Liquid must route live commands to the instance that owns the addressed session/configuration and must not treat cached state as controllable while that instance is unreachable.

Service / daemon surface

The service runs in its own process on the host, started by Liquid or as a login service (D-074), or as a server-host service; Liquid embeds no Meta-Harness core once the service exists (ADR-0215). Until then the core runs inside the Liquid app process (ADR-0184); even there the core, never the Liquid UI, owns agent processes, and Liquid sees only its agent-neutral session model. This changes client reachability, not Meta-Harness agent-executor ownership. One command set travels over a private local connection on the host and an authenticated network connection remotely (ADR-0185); state storage is D-024. Flow Agent's designed local control transport baseline is JSON-RPC over stdio.

  • Control plane: session registry, task state, attention state and schedules for this instance/host.
  • Config resolver: maps Watershed building blocks to agent-specific CLI config and launch commands.
  • Meta-Harness agent executor: host-local supervisor for whole CLI agents. It validates that every launched or controlled CLI process belongs to this instance's host; cross-host execution is outside the architecture.
  • Adapters: normalize native events into PROTOCOL.md families. Accepted target (ADR-0239): the pi adapter carries Watershed's pi extension in its binary, writes it into Meta-Harness's own data folder and passes it with -e; never into ~/.pi/agent/extensions/, which every pi run would load, nor into the project's .pi/extensions/, which the agent writes.
  • Artifact index: logs, summaries, checkpoints, handoff packs and host-provided diffs.
  • Policy gate: configuration-change proposals (ADR-0227) and control commands follow the policy gate.

8. Central config

Meta-Harness is responsible for central config management across agents. It defines shared Watershed building blocks once and resolves them into target-specific runtime configuration for Flow Agent, Codex CLI, Claude Code and future adapters. The Flow Agent target is global-only: it receives no project-local config layer, and project-specific behavior is an explicit Flow in its global authority. Other adapters retain their own documented scope. A host's Runtime binding—endpoint plus capability-dependent model/runtime, optional local-artifact, optional typed credential-reference and resource-policy fields—remains device-local operational state and is not copied into portable shared config; credential material stays in the target's protected store. Config is made of reusable building blocks, not agent-specific vocabulary (example, not final syntax):

shared block: "review-rust-change"
  instructions: ["review safety", "review tests"]
  tools: ["read", "search", "run-tests"]
  targets:
    flow-agent:  flow script + building blocks
    codex-cli:   instruction pack + command args
    claude-code: instruction pack + command args

Meta-Harness config resolution is not a project VCS/history engine. Config changes must be auditable, reviewable and policy-gated. Meta-Harness may manage Flow Agent's FLOW_AGENT_HOME authority only through a public config surface; it never writes target-private storage directly. Meta-Harness storage remains D-024; Flow Agent's global path and authoring boundary are canonical in PROTOCOL.md.

Accepted target (ADR-0225, ADR-0227): unlike T3 Code, harness configurations live centrally and across devices. Liquid is where they are edited and stored per harness; Meta-Harness materializes them per session into a home it owns, such as PI_CODING_AGENT_DIR, FLOW_AGENT_HOME or CODEX_HOME, linking the user's credentials instead of copying them. Liquid sends changes as proposals the host applies after approval with audit, and Flow Agent needs a public way to replace a home's configuration. Every harness can use local inference: Meta-Harness materializes endpoints per host, Flow Agent uses its device-local Runtime binding, and Liquid knows each model's context window and tool support. What a model provider does with prompts is not Liquid's responsibility.

Accepted target (ADR-0225, ADR-0227), policy gate: a Meta-Agent may reconfigure underlying agents only through it. Low-risk configuration changes apply only through the configured review/audit flow; sensitive ones (permission, tool, network, schedule and external-credential settings) require human approval. Every change is recorded with who/what/when, is monitorable and is revertible according to the chosen config-storage model, so the human always knows what changed. Harness configuration changes arrive as proposals through this gate, and credentials never leave the host. An area may be kept to local models, which Meta-Harness checks before a session starts. The same gate applies to all Meta-Harness control surfaces: its CLI, API/service and BYOA/external command surface. Meta-Harness runs headlessly (without Liquid), so the policy/audit gate, not a UI confirmation dialog, is the boundary: configuration changes and control commands from any client must be authorized and audited identically.

9. AgentPulse

AgentPulse belongs to Meta-Harness, not Liquid. Each instance computes and stores metrics from normalized events/artifacts produced on its host. Liquid may render them through Blocks/Views and visually compare instances, but never rewrites their ownership. Metrics are queryable through the CLI/API.

  • rework ratio;
  • first-attempt success;
  • cost-per-productive-outcome;
  • flow comparison across agents/configs.

AgentPulse is the last, low-priority roadmap item; its formulas are open in D-010.

10. Agent scheduling & orchestration

Meta-Harness owns schedules, triggers and orchestration for agent sessions on its host. Liquid may render and configure them through the public API. These are distinct from Liquid Workspace Automations, which connect Liquid events, conditions and actions and may call an authorized Meta-Harness action. Examples owned by Meta-Harness:

  • recurring tasks;
  • event-driven agent starts;
  • session follow-ups;
  • memory-building / "dreaming" jobs;
  • central-config research;
  • automated metric collection;
  • policy-gated config-improvement proposals.

Agents orchestrating agents

Accepted target (ADR-0253), with T3 Code as the model: an agent starts, messages, reads, steers and stops other threads across harnesses, model providers and agent hosts. A Codex thread on a Mac can start a Claude Code subagent on a Windows 11 computer linked as an agent host, whose Meta-Harness runs in WSL, talk with it and steer it.

  • Tools: Meta-Harness offers every session it starts its orchestration as MCP tools, as T3 Code offers its agents: list the agent hosts and the harnesses and models each offers; start a thread with a harness, model, host and first message as the caller's subagent; send it a message, also while it runs; read its messages and state; wait for its result; stop it; ask to link another agent host.
  • Execution: a call goes to the caller's own Meta-Harness, which forwards it to the other agent host; that host starts and supervises the harness itself, so execution stays host-local and a process another host claims is refused.
  • Subagents and messages: a subagent is a thread with its parent; each message is attributed to the thread that sent it, and the subagent's results reach the parent as messages, as T3 Code delivers a delegated task's result.
  • Authority: a subagent's grant comes from its parent's grant and is never larger (ADR-0223); the person sees and stops every thread in Liquid.
  • Linking agent hosts: they pair over the authenticated remote connection (ADR-0185), as T3 Code links environments: an agent may only ask to link an agent host, and the person completes the pairing on that host; each host keeps its own credentials.

11. Durability

Today's limit (ADR-0274): Liquid restores a Chat with separate reads of its transcript, usage and turns, so a turn that something outside Liquid, such as a pi extension, ends during a restore may be missing until the next restore.

Accepted target (ADR-0229). Durable work has four levels, and Meta-Harness on every host covers all four: agents depend on the files, tools and credentials of a machine, so every host needs its own supervisor, and Liquid sync plus Git checkpoints give the hosts a shared state.

  • A · Switch the client: Meta-Harness runs as a service; Liquid on any device attaches over the authenticated remote connection (ADR-0185) and sees the same live session. The Workspace copy of the session record lets every device show its history without a connection.
  • B · Survive a crash: every harness event is journaled before Liquid shows it, in short group commits rather than once per token, and every tool intent before the tool runs. After a crash Meta-Harness restarts the harness with its session; pi's own reading tools and Tools declared replay-safe run again, any other tool reports "interrupted" to the model, which continues without a restart click. A model answer cut off mid-stream is requested again.
  • C · Move an agent: at a turn boundary another of the person's hosts takes the session over: the record from Liquid, the files from the Git checkpoint ref (ADR-0220), its own credentials and the person's grant (ADR-0223). At each turn end Meta-Harness mirrors the session record into the agent-sessions area, its content as blobs with only metadata in the CRDT. The Sync Server gives the session to one host; two hosts continuing offline create two branches.
  • D · Several hosts: agent hosts hand each other tasks and messages and return results, as T3 Code's linked environments do; a harness's own approvals stay with the host that runs the work. Running single tools on another host follows later.

Each adapter reports which levels it reaches. The harness's own session file stays authoritative on its host, and pi keeps Liquid's records as custom entries in it; the Workspace record is the portable copy (ADR-0189). Without a Git project only the conversation moves.

Another harness (ADR-0231): a session moves to another harness, such as from pi to Codex, only as a handoff, as in T3 Code. The target starts a new session that receives the conversation so far as text, at most 16,000 tokens by default, marked as context, not a new request; attachments and the provider's tool and reasoning state do not move. A target that already saw part of the conversation receives only what followed; the files come from the Git checkpoint ref. Within pi, switching model or provider stays pi's own switch inside the session.

12. BYOA / external control

Meta-Harness exposes itself to other tools and agents through its API/CLI. Typical BYOA interactions:

  • an external agent asks Meta-Harness for current sessions;
  • an external agent starts or steers a session;
  • an external agent proposes a config change;
  • an external tool queries AgentPulse;
  • an external CLI monitors live transcripts.

Configuration-change proposals and control commands go through the policy gate.
