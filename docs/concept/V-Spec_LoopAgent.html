V-Spec — Loop Agent

CLI-only, Rust-core, script-driven, event-based deterministic agent-loop harness (CLI binary: loop, ADR-0013). Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Loop Agent is a standalone CLI agent product first: a local harness that runs deterministic, script-defined AI-native processes. It exists for agentic engineers who need control, repeatability, bounded tool execution and measurable loop quality. It is usable on its own — by humans at a terminal, headlessly by scripts/CI/automation, and later embeddable as a core library — with Pi-style runtime integration surfaces.

A Meta-Harness on the same host may integrate through Loop Agent's public runtime surfaces; neither Meta-Harness nor Liquid is required to run Loop Agent. Loop Agent exposes only its CLI and public event stream. Liquid reaches agent sessions through Meta-Harness and owns the optional UI.

Loop Agent is the Watershed platform's execution layer and its developer/open-source credibility wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: run repeatable, auditable AI-agent workflows from my CLI. It is a deterministic, auditable, reusable agent-loop runtime — not another generic coding agent.

2. Product boundary

Loop Agent is a standalone host-local CLI agent product, similar in product boundary to a Pi-style CLI agent. Meta-Harness is an optional same-host consumer; Liquid is an optional client of Meta-Harness. Neither is a prerequisite.

Loop Agent owns

  • local execution;
  • deterministic FSM behavior;
  • the building-block / script runtime;
  • sandboxed tool execution;
  • local runtime events;
  • local transcript/session persistence;
  • its standalone CLI integration surfaces.

Loop Agent does not own

Meta-Harness responsibilities: same-host multi-agent process ownership, central config, AgentPulse, scheduling and a local-or-remote client API.

Liquid responsibilities: local-first Pages, Blocks, Views, responsive desktop/mobile UI, workspace data, action history and workspace CLI/API. Liquid may render Loop Agent sessions through Meta-Harness-backed Blocks; neither layer reads Loop Agent storage directly, and Liquid edits use Liquid's mutation pipeline.

Meta-Harness consumes Loop Agent's public surfaces from the same host (see Meta-Harness V-Spec); it does not own the runtime internals. M1 ships the human CLI plus machine-readable event stream; local machine control and embedding are designed-for seams (ADR-0035).

3. Standalone runtime surfaces

Loop Agent must expose the M1 surfaces below and preserve the designed-for seams. The CLI renders the same authoritative persisted events as automation modes and owns its output transport. CLI/fixture behavior is decided by ADR-0034; surface scope by ADR-0035.

A. Human CLI

loop run hello-loop
loop run "hello-loop"
loop chat
/hello-loop
loop resume <session-id>
loop sessions
loop tail <session-id>

Direct human use; nice terminal rendering is allowed. /hello-loop is entered inside the interactive loop chat terminal, not in the OS shell.

B. Headless JSONL event stream

loop run smoke-loop --emit jsonl
loop run hello-loop --emit jsonl

The CLI owns stdout and streams newline-delimited committed events for automation, CI, custom terminal UIs and same-host Meta-Harness ingestion. CI captures and diffs this stream against the ADR-0034 goldens.

C. Local machine-control surface (designed-for)

loop --mode rpc
# or: loop rpc

Bidirectional external control is a post-M1 seam. ADR-0055 selects local JSON-RPC over stdio (ADR-0029) with a minimal loop.start, loop.status, loop.cancel, loop.tail and loop.export command set; it carries the same runtime events instead of adding cmd.* event types.

D. Embedded core API (future)

let session = create_agent_session(config).await?;
let loop_def = load_loop_definition(config).await?;
let mut events = session.subscribe();
session.start(loop_def).await?;
while let Some(event) = events.next().await {
    handle_event(event);
}

A future Rust-first embedding surface, analogous in concept to pi-agent-core. M1 implements only the bounded notification and sequence-replay boundary in PROTOCOL.md; the stabilized session API remains D-020.

E. Local session/transcript persistence

Loop Agent owns its own local session store, independent of Meta-Harness, mirroring the public event stream:

.loop/sessions/<session_id>.jsonl
.loop/logs/<session_id>.log
.loop/logs/<session_id>.contexts.jsonl

This append-only JSONL log is kept by default in M1 and defers rotation/pruning (ADR-0037). Each event is appended here before a bounded live notification is attempted (ADR-0059, ADR-0062). The log enables resume, replay, tail and debugging; Meta-Harness ingestion uses public runtime surfaces, while export remains future. This is not project VCS/history handling — it is Loop Agent's local runtime/session transcript store; .loop stays a protected path per SECURITY.md.

The .log resume-metadata sidecar records definition identity; the context-manifest sidecar stores the per-provider-turn records defined in §6. Neither is a runtime event stream.

The <session_id> filename segment is the lowercase path-safe v0 session_id token defined in PROTOCOL.md. Replay, tail and resume reject invalid, uppercase or path-like IDs before touching .loop/sessions.

Minimum local M1 semantics: loop replay <session-id> emits stored event objects unchanged in original sequence order; loop tail <session-id> emits the current valid prefix in order and then newly appended events; loop resume <session-id> is local-only, valid only for a non-terminal session owned by this Loop Agent instance, rejects registry or loop-definition drift before side effects, reconstructs state from the valid log prefix, then appends a new session.resumed event with the next sequence. None of these commands rewrites prior events. Replay and resume reject corrupt or incomplete logs before tool side effects. Active sessions create .loop/sessions/<session_id>.lock; run/resume refuses a locked session and never auto-steals stale locks, while replay/tail remains read-only. Manual recovery requires verifying no Loop Agent process owns the session, preserving or inspecting the log if needed, removing the lock, then resuming.

M1 session-log reads are capped at 16 MiB (ADR-0054). Replay and resume require complete valid JSONL. Tail validates complete prefixes against previously observed events, uses a sequence cursor, buffers an incomplete trailing line while the session is active and rejects bytes after a terminal event.

Ownership is authorship, not durability: local M1 append and notification follow the flush/sync boundaries in PROTOCOL.md, so machine or power loss may lose only the tail after the last durability boundary, never expose an event that was not first appended. In ephemeral/cloud runs, replication plus durable storage—not container lifetime—provides survival; a persistent .loop volume covers standalone use. Remote replication cadence, crash recovery and a durable session-ownership lease remain post-M1 under ADR-0039.

4. Differentiators / core principles

Recursive building blocks

Tools, Instructions, Phases and Loops share one modular configuration model. A Loop is itself a building block, so loops can contain subloops without a second abstraction.

Simpler terminology

Scripts, instructions, connections and loops replace agent-specific vocabulary such as skills directories, agent markdown files and runtime-tool lists.

Deterministic FSM

The harness controls phase order, step transitions, available tools, instruction loading and event handling deterministically. LLM/tool outputs are inputs; the state machine remains deterministic. This is determinism of orchestration, not of model output (see §7).

Event-driven runtime

Normal progress is driven by events, not polling. M1 emits implemented completion and failure events; designed timeout and attention emitters join the same protocol after M1.

Loops as AI-native processes

Each loop run can be measured and compared. This enables optimizing specific loops rather than endlessly tuning one generalized agent setup.

Security by construction

Scripts declare capabilities; the runtime compiles them into sandbox policy. Prompt intent never becomes a security boundary.

5. MVP boundary

In scope: standalone CLI, scripts, deterministic FSM, public event stream, JSONL headless mode, local session/transcript store, deterministic bounded in-process fixture interpretation, context manifests, sandbox policy, subloops and golden loops.

Out of scope: Loop Agent UI, cross-host process control, central Meta-Harness behavior, Liquid Pages/Blocks, marketplace/plugins unless needed for a stub, and any Watershed project-history/VCS engine.

A same-host Meta-Harness is an optional consumer; Liquid is an optional client of Meta-Harness. Neither is required to run Loop Agent.

Loop Agent may run inside normal Git projects. Git operations are just tool commands when explicitly declared and sandboxed; Loop Agent does not own commits, branches, slices or history in the MVP. The local session store (§3E) is runtime state, not project VCS/history.

  • CLI: accepts a loop script, inputs and implemented output/event mode (human or JSONL); future RPC/control mode follows ADR-0055 after M1.
  • Building-block registry: parses Tools, Instructions, Connections, Phases, Loops and Subloops.
  • FSM engine: owns deterministic state transitions.
  • Instruction loader: resolves active loop/phase/step instructions; the agent does not self-load them.
  • Context compiler: produces the bounded, reproducible provider context and manifest defined below.
  • Runtime kernel: interprets declared fixture tools deterministically in process with bounded inputs and policy checks. External subprocess timeouts, bounded stdout/stderr and per-tool run logs are post-M1.
  • Session manager: uses one serial writer to append each canonical event before a bounded non-blocking notification; callers replay committed events by sequence and own delivery (§3E; PROTOCOL.md).
  • Protocol adapter: emits normalized events per PROTOCOL.md.

Crate boundaries (ADR-0033)

The runtime engine and the CLI front-end are separate crates so the engine can be headlessly tested and later embedded (§3D):

  • core/core-script — building-block model, parser, registry and composition rules.
  • core/core-policy — capability model and policy→sandbox compiler.
  • proto/ — proto: event schema and serialization.
  • loop-agent/loop-agent-core — FSM engine, runtime kernel, session manager, local log, bounded live notification and embeddable entry.
  • loop-agent/loop-agent-cli — interactive terminal, slash commands, machine-readable mode, loop run, tail/replay/resume.

The building-block model lives in core-script and is serializable over proto. Same-host Meta-Harness consumes it through core-script as a config resolver; Liquid renders derived state through Meta-Harness-backed Blocks. Neither consumes Loop Agent internals.

Build strategy & reuse

Orchestration is built in-house; non-differentiating plumbing (model/provider I/O, tool execution, OS-sandbox wrappers, MCP client and context handling) is reused via general-purpose crates where it fits. Loop Agent is not built on or forked from Codex; Codex integrates as a Meta-Harness adapter. Rationale/licensing: ADR-0028.

Deterministic Tiered Context Compiler v0 (ADR-0050, ADR-0058)

M1 has one internal context compiler and one public, fixed profile: loop-context-v0. It minimizes model-visible tokens subject to preserving the best achievable task outcome, deterministic orchestration, provenance and replay. M1 exposes neither user-configurable per-source budgets nor a general context-document format.

Durable session history

The complete append-only event history and source artifacts. It is authoritative for resume, replay, audit, debugging and future retrieval. Context optimization never deletes it.

Resolved loop state

The current invocation, phase, step, active instructions/tools, connections and runtime state, plus values supplied by runtime interfaces whose source/schema is defined.

Provider context

The deterministic, bounded projection compiled for one model turn. It is deliberately smaller than durable session history.

Budget, identity and cache-stable order

input budget = model context limit - fixed output reserve - fixed safety margin. The selected versioned model/context profile fixes all three values plus tokenizer or estimator identity. An exact provider tokenizer is used when available; otherwise M1 uses the conservative utf8-byte-v0 estimator (one estimated token per canonical UTF-8 byte). The same durable state, resolved loop state, loop definition, model profile, runtime version and context-profile version produce the same ordered canonical provider-context bytes and lowercase SHA-256 context hash.

Tier 0 is serialized in this exact order:

  1. base runtime and security instructions;
  2. active loop instructions;
  3. active phase instructions;
  4. active step instructions;
  5. only tool definitions available to the active phase or step;
  6. a compact snapshot of current FSM and loop state;
  7. typed inputs arriving through explicit connections to the current step;
  8. the current user input;
  9. unresolved call/result state required to continue the turn.

Resolved declaration order is preserved for instructions, tools and connections; canonical maps sort keys. Inactive instructions, unavailable tools, unrelated outputs and incidental volatility such as collection iteration order are excluded. The first five, scope-stable sections form the longest reusable provider-cache prefix; turn-specific state and inputs follow, then Tier 1. Cache-boundary metadata is deterministic and recorded in the manifest. Provider-specific cache hints may annotate those boundaries but must not reorder content, alter the logical context or change its context hash.

The current M1 CLI/stub runtime has no decided user-input value, predefined-command invocation-value, typed connection-value or artifact/tool-output source schema. The corresponding Tier 0 sections carry deterministic absence markers, and M1 emits no artifact/tool-output projection. Values or projections enter provider context only after their runtime source and schema are decided.

All Tier 0 content is mandatory. If it exceeds the input budget, Loop Agent emits the existing typed error event with code context_budget_exceeded and fails before contacting the provider. It never silently drops mandatory content or relies on provider-side truncation.

Tier 1: bounded continuity

Only the remaining budget may be used, in this selection order, for: the current incomplete turn when applicable; at most the most recent complete interaction turn; once their runtime source/schema is defined, bounded projections of directly referenced artifacts or tool outputs not already represented by typed connection inputs; and a compact deterministic checkpoint required to interpret state. Optional units are ordered by source sequence, then by this category order. If they do not fit, the oldest optional unit is omitted first. Ordinary user/assistant messages remain whole, and tool calls stay paired with their results. A directly connected typed output and unresolved continuation state belong to Tier 0, not this historical tail.

Tier 2 and Tier 3: retained, not sent in M1

Older turns beyond the single Tier 1 tail, unrelated phase/step outputs, inactive instructions, unavailable tool schemas, full old tool logs, full large artifacts and diagnostic history are omitted from M1 provider context, never deleted from durable history or artifact storage. M1 does not use model-generated compaction, embeddings, semantic RAG, adaptive relevance ranking, nondeterministic selection or regenerated summaries during resume/replay.

Conditional projections and manifest

When a directly referenced artifact source/schema is defined, it may use only a versioned deterministic projection algorithm registered by loop-context-v0; an unregistered type is omitted rather than heuristically summarized. The algorithm's decided parameters and manifest fields must make the projection byte-reproducible, and the complete source remains outside provider context.

Every provider turn stores a reproducible context manifest with its durable session data; this is an implementation artifact, not a new runtime event family. The manifest records context-profile ID/version, model profile/context limit, tokenizer or estimator ID/version, output reserve, safety margin, ordered included source IDs and any projection hashes, deterministic cache boundaries, omitted-source counts by category, estimated input tokens and final context hash. Complete ordinary messages are never cut; tool calls/results remain paired; a result never appears without its call; unresolved required calls, current user input and required instructions are never silently removed. Resume uses the recorded context-profile version and the same compiler.

Post-M1 context architecture

The following evolution is explicitly outside M1. Persisted structured compactions may be generated once, stored with provenance and reused unchanged on resume/replay; originals are never deleted and summaries are never regenerated during replay. Future provider context may combine active typed loop state, a persisted checkpoint/summary, a small raw tail, direct connection inputs and explicitly retrieved evidence.

Retrieval should first use deterministic graph identities and relationships—loop, phase, step, connection, artifact, tool-call and message IDs, tags and content hashes. Optional semantic retrieval may follow only with versioning, recorded queries/results, provenance, quality/token evaluation and a deterministic fallback. A retrieval subloop receives isolated declared inputs/instructions/tools and returns a small typed result with citations; its transcript does not leak into the parent. Later versions retain lazy scoped instructions/tools and are accepted only when evaluation shows token savings without measurable task-quality loss.

7. Deterministic FSM

The FSM is deterministic over declared loop state and inputs — deterministic orchestration over a non-deterministic generator, not identical output. The LLM may produce stochastic content; the harness consumes it as data for deterministic transition rules, giving four guarantees: bounded (a step can only do what its phase declares), reproducible structure (same phases/steps/tool-scopes every run), measurable (runs compare because the scaffold is held constant), and governable (every transition is attributable). The trade is autonomy for control — strongest for processes run more than once or that must be trusted, wrong for open-ended exploration.

  • Phase order is declared by the script.
  • Available tools/instructions are a pure function of current phase/step.
  • Subloops start through explicit building-block references.
  • Failures become typed events in M1; designed timeout and attention events remain post-M1.
  • Tests assert transitions, allowed tool sets, instruction loading and event ordering.

8. Building-block scripts

Scripts use YAML 1.2 with strict parser validation and canonical serialization (ADR-0031). Checked-in JSON Schema files document the intended shape, but M1 does not run a separate schema engine. They are human-reviewable security/capability artifacts, so the parser must produce one unambiguous model for reviewers, audits and golden tests, including when scripts are machine-generated.

Example registry entries below are separate files under one registry root; each file contains exactly one top-level block.

registry/tools/read-file.yaml

tool:
  id: read-file
  name: ReadFile
  tool_kind: predefined-command
  command:
    command_id: agent-read
    argv: []
  allowed_parameters:
    - name: "--file"
      value_type: workspace-relative-path
      required: true
  read_scope: ["workspace"]
  write_scope: []
  protected_path_grants: []
  network: deny

registry/instructions/summarize-findings.yaml

instruction:
  id: summarize-findings
  name: SummarizeFindings
  prompt: "Summarize only facts from tool output."

registry/phases/research.yaml

phase:
  id: research
  name: Research
  tool_refs: [read-file]
  instruction_refs: [summarize-findings]
  steps:
    - id: gather
      name: Gather
    - id: summarize
      name: Summarize
      connection_refs: [research-refresh]

registry/connections/research-refresh.yaml

connection:
  id: research-refresh
  name: ResearchRefresh
  connection_kind: refresh
  from_ref: research.gather
  to_ref: research.summarize

registry/loops/hello-loop.yaml

loop:
  id: hello-loop
  name: HelloLoop
  phase_refs: [research]
  subloop_refs: []
  connection_refs: [research-refresh]

Minimum v0 schema surface: every block requires id and name; references use explicit id/name values and the resolver rejects missing or ambiguous references. Tools require tool_kind (predefined-command or own-script), exact command, allowed_parameters, read_scope, write_scope, protected_path_grants and network. A predefined-command tool uses command as an object with command_id and literal argv; command_id matches ^[a-z][a-z0-9_-]{0,63}$ and resolves through the predefined-command registry, not PATH lookup, a shell, environment expansion or globbing. Runtime execution uses fixture stubs for predefined commands. Parameter-token validation is canonical in SECURITY.md; the current M1 CLI/stub supplies no invocation parameter tokens. An own-script tool uses command: script:<tool-id>, requires script_runtime: posix-sh and script_body as UTF-8 source owned by that Tool block, and forbids host script paths, shebang-selected interpreters and runtime-specific extra args in v0. Loop Agent selects the fixed runner for posix-sh; M1 interprets the fixture write subset and post-M1 sandbox backends apply the compiled policy to runner processes and children. Instructions require prompt. Phases require ordered instruction_refs, tool_refs and steps; every step requires id and name, may declare ordered connection_refs, and step_id events use the step id. Step ids are phase-local; connection endpoint references to steps use <phase_id>.<step_id>. Connections require connection_kind (data, trigger or refresh), from_ref and to_ref, and endpoints may target Tools, Instructions, Phases, Loops or scoped Steps. Loops require ordered phase_refs plus optional subloop_refs and connection_refs; every Step connection_ref must resolve to a Connection also listed by the enclosing Loop. Runtime step.started/step.completed payloads emit connection_ids and connection_kinds in the resolved Step connection_refs order. Checked schema files and parser fixtures enforce this contract; no additional top-level block kind is added without a new decision.

Tool network is either scalar deny or { default: deny, allow: [...] }, with default fixed to deny. Allow entries and enforcement scope are canonical in SECURITY.md. core-policy copies the resolved grammar into commands[].network (ADR-0051, ADR-0052).

Workspace configuration

.loop/config.yaml
registry_root: registry

registry_root is required and workspace-relative. Checked-in deterministic fixtures additionally pair fixture_profile: stub-model with stub_model: deterministic; normal workspaces omit both.

Composition happens through the building-block registry with explicit by-name/id references; Safe-YAML acceptance is canonical in SECURITY.md. The v0 registry container is a configured registry root discovered recursively; every .yaml/.yml file is one UTF-8 YAML 1.2 document containing exactly one top-level block key (tool, instruction, phase, connection or loop) and one block object. Multi-document streams, files with multiple blocks, top-level block arrays/maps and non-registry YAML files are rejected. File paths are stable addresses for review and diagnostics only; identity and references come from the block id/name. The registry indexes by kind + id and kind + name, rejects duplicates or ambiguous references, resolves only within the configured root, allows recursive loop composition, rejects cycles and rejects nesting deeper than 64 levels in M1 (ADR-0053). Later package/archive formats may provide registry entries, but they must normalize to the same one-block entry model before parsing. Connections must make data/control flow explicit instead of hiding it in agent-specific config files.

M1 registry reads are capped before parse/resolve work: each registry file is limited to 1 MiB and the total registry input is limited to 16 MiB (ADR-0054).

Canonical serialization is deterministic UTF-8 JSON of the strictly parsed and validated, registry-resolved block model, not a re-emission of source YAML. Object keys are sorted lexicographically; parser defaults are materialized; optional fields without defaults are omitted; arrays preserve declared order except allowed_parameters, which sorts by name; unordered collections are represented as maps keyed by id/name; strings are NFC-normalized; comments and source formatting are discarded; null is rejected unless explicitly allowed; NaN and infinity are always rejected. Canonical bytes are the review/audit/golden-test form.

9. Events & measurement

Loop Agent's event stream is a stable public runtime contract, not just an internal log. Every meaningful runtime transition appends one normalized event; JSONL mode (§3B), future RPC mode (§3C) and replay from the local session log (§3E) expose the same events. Live notifications carry only the latest committed sequence, never a second event copy. Golden loops compare expected event streams, which makes individual loops measurable and optimizable.

These are the same normalized events defined in PROTOCOL.md (single source of truth for the event-envelope fields and runtime event families). Exact v0 names are decided by ADR-0036; do not introduce a competing naming convention. Command/request shape is a separate post-M1 surface selected by ADR-0055.

PROTOCOL.md defines the envelope, canonical JSONL, event families and lifecycle; TESTING.md defines the emitted ADR-0034 test subset; PERFORMANCE.md defines delivery budgets.
