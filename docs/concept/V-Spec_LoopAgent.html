V-Spec — Loop Agent

CLI-only, Rust-core, script-driven, event-based deterministic agent-loop harness (CLI binary: loop, ADR-0013). Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Loop Agent is a standalone CLI agent product first: a local harness that runs deterministic, script-defined AI-native processes. It exists for agentic engineers who need control, repeatability, bounded tool execution and measurable loop quality. It is usable on its own — by humans at a terminal, headlessly by scripts/CI/automation, and later embeddable as a core library — with Pi-style runtime integration surfaces.

Meta-Harness and Liquid integrate with Loop Agent through its public runtime surfaces; they are not required to run Loop Agent. No UI in Loop Agent — Liquid owns the future UI. Loop Agent exposes a CLI and a public event stream.

Loop Agent is the Watershed platform's execution layer and its developer/open-source credibility wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: run repeatable, auditable AI-agent workflows from my CLI. It is a deterministic, auditable, reusable agent-loop runtime — not another generic coding agent.

2. Product boundary

Loop Agent is a standalone CLI agent product, similar in product boundary to a Pi-style CLI agent. Meta-Harness and Liquid are optional consumers/integrators, never prerequisites.

Loop Agent owns

  • local execution;
  • deterministic FSM behavior;
  • the building-block / script runtime;
  • sandboxed tool execution;
  • local runtime events;
  • local transcript/session persistence;
  • its standalone CLI integration surfaces.

Loop Agent does not own

Meta-Harness responsibilities: multi-agent orchestration; central config across different agents; AgentPulse across providers; scheduling across agents; Liquid dashboards.

Liquid responsibilities: standalone workspace/app-building product — UI, dashboards/views/components, mobile/desktop app shell, workspace data, workspace action history/VCS and the workspace CLI/API. Liquid may render Loop Agent sessions/transcripts as optional components, but Loop Agent does not mutate Liquid storage internals — it is consumed through public runtime surfaces, and any Liquid edits flow through Liquid's own CLI/API/mutation pipeline.

Meta-Harness consumes Loop Agent's public surfaces later (see Meta-Harness V-Spec); it does not own the Loop Agent runtime. M1 ships the human CLI plus machine-readable event stream; remote-control and embedding are designed-for seams (ADR-0035).

3. Standalone runtime surfaces

Loop Agent must expose the M1 surfaces below and preserve the designed-for seams. The terminal renderer consumes the same internal event stream as automation modes — rendering is a view over events, not a separate path. CLI/fixture behavior is decided by ADR-0034; surface scope by ADR-0035.

A. Human CLI

loop run hello-loop
loop run "hello-loop"
loop chat
/hello-loop
loop resume <session-id>
loop sessions
loop tail <session-id>

Direct human use; nice terminal rendering is allowed. /hello-loop is entered inside the interactive loop chat terminal, not in the OS shell.

B. Headless JSONL event stream

loop run smoke-loop --emit jsonl
loop run hello-loop --emit jsonl

Streams newline-delimited JSON events to stdout for automation, CI, external dashboards, custom terminal UIs and Meta-Harness later. CI captures and diffs this stream against D-015 goldens.

C. Remote-control surface (designed-for)

loop --mode rpc
# or: loop rpc

Bidirectional external control is a post-M1 seam. ADR-0055 selects local JSON-RPC over stdio (ADR-0029) with a minimal loop.start, loop.status, loop.cancel, loop.tail and loop.export command set; it carries the same runtime events instead of adding cmd.* event types.

D. Embedded core API (future)

let session = create_agent_session(config).await?;
let loop_def = load_loop_definition(config).await?;
let mut events = session.subscribe();
session.start(loop_def).await?;
while let Some(event) = events.next().await {
    handle_event(event);
}

A future Rust-first embedding surface, analogous in concept to pi-agent-core. Scope is D-020; not implemented in M1.

E. Local session/transcript persistence

Loop Agent owns its own local session store, independent of Meta-Harness, mirroring the public event stream:

.loop/sessions/<session_id>.jsonl

This append-only JSONL log mirrors the event stream, is kept by default in M1 and defers rotation/pruning (ADR-0037). It enables resume, replay, tail, export, debugging and later Meta-Harness ingestion through public event-stream/tail/export surfaces. This is not project VCS/history handling — it is Loop Agent's local runtime/session transcript store; .loop stays a protected path per SECURITY.md.

The <session_id> filename segment is the lowercase path-safe v0 session_id token defined in PROTOCOL.md. Replay, tail and resume reject invalid, uppercase or path-like IDs before touching .loop/sessions.

Minimum local M1 semantics: loop replay <session-id> emits stored event objects unchanged in original sequence order; loop tail <session-id> emits the current valid prefix in order and then newly appended events; loop resume <session-id> is local-only, valid only for a non-terminal session owned by this Loop Agent instance, rejects registry or loop-definition drift before side effects, reconstructs state from the valid log prefix, then appends a new session.resumed event with the next sequence. None of these commands rewrites prior events. Corrupt or partial logs surface an error and do not perform tool side effects. Active sessions create .loop/sessions/<session_id>.lock; Loop Agent refuses locked sessions and never auto-steals stale locks. Manual recovery requires verifying no Loop Agent process owns the session, preserving or inspecting the log if needed, removing the lock, then replaying or resuming.

M1 session-log reads are capped at 16 MiB (ADR-0054). Tail validates the existing prefix once, tracks its byte offset, reads only newly appended bytes, validates complete appended JSONL lines against accumulated state before emission and keeps an incomplete trailing line buffered until the next poll.

Ownership is authorship, not durability: in ephemeral/cloud runs the run survives via replication + durable storage, not container lifetime — live Meta-Harness ingestion over the public event stream holds a replica (a kill loses at most the un-flushed tail), a persistent .loop volume covers the standalone case, and because the transcript is the replayable event stream a session can resume on a new container. Flush cadence, remote crash-recovery and a durable session-ownership lease are decided by ADR-0039.

4. Differentiators / core principles

Recursive building blocks

Tools, Instructions, Phases and Loops share one modular configuration model. A Loop is itself a building block, so loops can contain subloops without a second abstraction.

Simpler terminology

Scripts, instructions, connections and loops replace agent-specific vocabulary such as skills directories, agent markdown files and runtime-tool lists.

Deterministic FSM

The harness controls phase order, step transitions, available tools, instruction loading and event handling deterministically. LLM/tool outputs are inputs; the state machine remains deterministic. This is determinism of orchestration, not of model output (see §7).

Event-driven runtime

Normal progress is driven by events, not polling. Tool completion, timeouts, attention requests and subloop completion all emit protocol events.

Loops as AI-native processes

Each loop run can be measured and compared. This enables optimizing specific loops rather than endlessly tuning one generalized agent setup.

Security by construction

Scripts declare capabilities; the runtime compiles them into sandbox policy. Prompt intent never becomes a security boundary.

5. MVP boundary

In scope: standalone CLI, scripts, deterministic FSM, public event stream, JSONL headless mode, local session/transcript store, bounded/headless tools, logs, sandbox policy, subloops, golden loops.

Out of scope: Loop Agent UI, central Meta-Harness control, Liquid dashboards, marketplace/plugins unless needed for a stub, and any Watershed project-history/VCS engine.

Meta-Harness and Liquid are optional consumers and are not required to run Loop Agent.

Loop Agent may run inside normal Git projects. Git operations are just tool commands when explicitly declared and sandboxed; Loop Agent does not own commits, branches, slices or history in the MVP. The local session store (§3E) is runtime state, not project VCS/history.

6. Architecture

→

→
FSM engine
→
Instruction loader
→
Runtime kernel + sandbox
→
Event bus → events + session log
  • CLI: accepts a loop script, inputs and implemented output/event mode (human or JSONL); future RPC/control mode follows ADR-0055 after M1.
  • Building-block registry: parses Tools, Instructions, Connections, Phases, Loops and Subloops.
  • FSM engine: owns deterministic state transitions.
  • Instruction loader: injects phase/step-scoped instructions; the agent does not self-load them.
  • Runtime kernel: runs tools with declared capability policy, timeout, bounded IO and headless behavior.
  • Event bus + session manager: publishes the public runtime event stream and persists it to the local session log (§3E).
  • Protocol adapter: emits normalized events per PROTOCOL.md.

Crate boundaries (ADR-0033)

The runtime engine and the CLI front-end are separate crates so the engine can be headlessly tested and later embedded (§3D):

  • core/core-script — building-block model, parser, registry and composition rules.
  • core/core-policy — capability model and policy→sandbox compiler.
  • proto/ — proto: event schema and serialization.
  • loop-agent/loop-agent-core — FSM engine, runtime kernel, session manager, local log, event bus and embeddable entry.
  • loop-agent/loop-agent-cli — interactive terminal, slash commands, machine-readable mode, loop run, tail/replay/resume.

The building-block model lives in core-script and is serializable over proto. Meta-Harness consumes it through core-script as a config resolver; Liquid consumes it through proto/API for render/edit loops. Neither consumes Loop Agent internals.

Build strategy & reuse

Orchestration is built in-house; non-differentiating plumbing (model/provider I/O, tool execution, OS-sandbox wrappers, MCP client and context handling) is reused via general-purpose crates where it fits. Loop Agent is not built on or forked from Codex; Codex integrates as a Meta-Harness adapter. Rationale/licensing: ADR-0028.

M1 context handling is deliberately narrow (ADR-0050): deterministic rule/window selection over explicit inputs, instructions, transcript prefix and fixture data only. Embeddings, RAG and adaptive compaction are post-M1.

7. Deterministic FSM

The FSM is deterministic over declared loop state and inputs — deterministic orchestration over a non-deterministic generator, not identical output. The LLM may produce stochastic content; the harness consumes it as data for deterministic transition rules, giving four guarantees: bounded (a step can only do what its phase declares), reproducible structure (same phases/steps/tool-scopes every run), measurable (runs compare because the scaffold is held constant), and governable (every transition is attributable). The trade is autonomy for control — strongest for processes run more than once or that must be trusted, wrong for open-ended exploration.

  • Phase order is declared by the script.
  • Available tools/instructions are a pure function of current phase/step.
  • Subloops start through explicit building-block references.
  • Timeouts, failures and attention requests become typed events.
  • Tests assert transitions, allowed tool sets, instruction loading and event ordering.

8. Building-block scripts

Scripts use YAML 1.2 with strict parser validation and canonical serialization (ADR-0031). Checked-in JSON Schema files document the intended shape, but M1 does not run a separate schema engine. They are human-reviewable security/capability artifacts, so the parser must produce one unambiguous model for reviewers, audits and golden tests, including when scripts are machine-generated.

Example registry entries below are separate files under one registry root; each file contains exactly one top-level block.

registry/tools/read-file.yaml

tool:
  id: read-file
  name: ReadFile
  tool_kind: predefined-command
  command:
    command_id: agent-read
    argv: []
  allowed_parameters:
    - name: "--file"
      value_type: workspace-relative-path
      required: true
  read_scope: ["workspace"]
  write_scope: []
  protected_path_grants: []
  network: deny

registry/instructions/summarize-findings.yaml

instruction:
  id: summarize-findings
  name: SummarizeFindings
  prompt: "Summarize only facts from tool output."

registry/phases/research.yaml

phase:
  id: research
  name: Research
  tool_refs: [read-file]
  instruction_refs: [summarize-findings]
  steps:
    - id: gather
      name: Gather
    - id: summarize
      name: Summarize
      connection_refs: [research-refresh]

registry/connections/research-refresh.yaml

connection:
  id: research-refresh
  name: ResearchRefresh
  connection_kind: refresh
  from_ref: research.gather
  to_ref: research.summarize

registry/loops/hello-loop.yaml

loop:
  id: hello-loop
  name: HelloLoop
  phase_refs: [research]
  subloop_refs: []
  connection_refs: [research-refresh]

Minimum v0 schema surface: every block requires id and name; references use explicit id/name values and the resolver rejects missing or ambiguous references. Tools require tool_kind (predefined-command or own-script), exact command, allowed_parameters, read_scope, write_scope, protected_path_grants and network. A predefined-command tool uses command as an object with command_id and literal argv; command_id matches ^[a-z][a-z0-9_-]{0,63}$ and resolves through the predefined-command registry, not PATH lookup, a shell, environment expansion or globbing. Runtime execution uses fixture stubs for predefined commands. allowed_parameters is an ordered array of parameter specs: name (exact flag), value_type (none, string, integer, workspace-relative-path or enum), required boolean, and type-specific constraints: allowed_values for enum, value_pattern/max_length for string, and optional min/max for integer. Unknown parameters, extra positional arguments and values that fail type/path validation are rejected before launch. An own-script tool uses command: script:<tool-id>, requires script_runtime: posix-sh and script_body as UTF-8 source owned by that Tool block, and forbids host script paths, shebang-selected interpreters and runtime-specific extra args in v0. Loop Agent selects the fixed runner for posix-sh; M1 interprets the fixture write subset and post-M1 sandbox backends apply the compiled policy to runner processes and children. Instructions require prompt. Phases require ordered instruction_refs, tool_refs and steps; every step requires id and name, may declare ordered connection_refs, and step_id events use the step id. Step ids are phase-local; connection endpoint references to steps use <phase_id>.<step_id>. Connections require connection_kind (data, trigger or refresh), from_ref and to_ref, and endpoints may target Tools, Instructions, Phases, Loops or scoped Steps. Loops require ordered phase_refs plus optional subloop_refs and connection_refs; every Step connection_ref must resolve to a Connection also listed by the enclosing Loop. Runtime step.started/step.completed payloads emit connection_ids and connection_kinds in the resolved Step connection_refs order. The M0 scaffold turns this contract into checked-in schema files and parser fixtures; no additional top-level block kind is added without a new decision.

Tool network is either scalar deny or a mapping { default: deny, allow: [...] }. default is always deny. Each allow item uses the same CIDR-only typed entry shape as SECURITY.md: kind: cidr, transport, cidr and port. Hostname grants, DNS resolution, schemes, wildcards, suffix matching and implicit network access are not part of v0. core-policy copies the resolved tool grammar into commands[].network. M1 Linux-target policy denies network by default and rejects non-empty allowlists; positive CIDR egress enforcement is post-M1 (ADR-0051, ADR-0052).

Composition happens through the building-block registry with explicit by-name/id references. YAML anchors and merge keys are not part of the model. The v0 registry container is a configured registry root discovered recursively; every .yaml/.yml file is one UTF-8 YAML 1.2 document containing exactly one top-level block key (tool, instruction, phase, connection or loop) and one block object. Multi-document streams, files with multiple blocks, top-level block arrays/maps and non-registry YAML files are rejected. File paths are stable addresses for review and diagnostics only; identity and references come from the block id/name. The registry indexes by kind + id and kind + name, rejects duplicates or ambiguous references, resolves only within the configured root, allows recursive loop composition, rejects cycles and rejects nesting deeper than 64 levels in M1 (ADR-0053). Later package/archive formats may provide registry entries, but they must normalize to the same one-block entry model before parsing. Connections must make data/control flow explicit instead of hiding it in agent-specific config files.

M1 registry reads are capped before parse/resolve work: each registry file is limited to 1 MiB and the total registry input is limited to 16 MiB (ADR-0054).

Canonical serialization is deterministic UTF-8 JSON of the strictly parsed and validated, registry-resolved block model, not a re-emission of source YAML. Object keys are sorted lexicographically; parser defaults are materialized; optional fields without defaults are omitted; arrays preserve declared order except allowed_parameters, which sorts by name; unordered collections are represented as maps keyed by id/name; strings are NFC-normalized; comments and source formatting are discarded; null is rejected unless explicitly allowed; NaN and infinity are always rejected. Canonical bytes are the review/audit/golden-test form.

9. Events & measurement

Loop Agent's event stream is a stable public runtime contract, not just an internal log. Every meaningful runtime transition emits one normalized event; JSONL mode (§3B), future RPC mode (§3C) and the local session log (§3E) all carry the same events. Golden loops compare expected event streams, which makes individual loops measurable and optimizable.

These are the same normalized events defined in PROTOCOL.md (single source of truth for the event-envelope fields and runtime event families). Exact v0 names are decided by ADR-0036; do not introduce a competing naming convention. Command/request shape is a separate post-M1 surface selected by ADR-0055.

Envelope (field types and payload minima: PROTOCOL.md)

protocol_version, event_id, event_type, lowercase path-safe session_id, optional runtime invocation loop_id/parent_loop_id, monotonic sequence per session, timestamp, source, typed payload including loop_definition_id on loop events, optional correlation_id.

Golden streams and session logs use the canonical event JSONL serialization defined in PROTOCOL.md.

Runtime event families (v0)

session.started | session.paused | session.resumed | session.completed | session.failed
loop.started | loop.completed | loop.failed
phase.entered | step.started | step.completed
message.delta | message.completed
tool.started | tool.progress | tool.completed | tool.failed | tool.timed_out
attention.requested
artifact.logged | metric.sample | error

M1 emits the D-015 runtime subset. session.paused, tool.timed_out, attention.requested, artifact.logged and metric.sample are designed v0 names for later emitters.

message.delta and tool.progress are first-class so consumers get near-real-time transcript sync.

10. M0/M1 implementation packet

M0 must define

  • Rust crate layout incl. the loop-agent-core/loop-agent-cli split (ADR-0033).
  • Local JSON-RPC-over-stdio transport for future control plus runtime event schema v0 (ADR-0029, ADR-0036); minimal post-M1 control command set selected by ADR-0055.
  • CLI command names/flags: loop run <name> --emit jsonl, by-name registry resolution, loop chat and in-session /hello-loop.
  • YAML 1.2 script schema, canonical serialization, registry composition and fixtures (ADR-0031).
  • D-015 three-fixture suite: smoke-loop, hello-loop and sandbox-negative fixtures, with expected JSONL event streams per TESTING.md and a stub model.
  • Local session/transcript store path, retention assumptions and local replay/tail/resume semantics (ADR-0037).
  • Sandbox artifact shape per SECURITY.md and sandbox-negative tests (ADR-0032).
  • Linux + macOS CI commands, including pnpm run docs:render-check for the HTML render gate (ADR-0043, ADR-0045).
  • Pass/fail checklist from PLAN.md — Codex must not have to invent these surfaces.

M1 implements

  • Standalone CLI run path.
  • Headless JSONL stream.
  • Local session log.
  • Deterministic FSM.
  • Script parser/registry.
  • Recursive loop composition with cycle detection and a 64-level nesting cap.
  • Deterministic M1 context window selection.
  • Bounded/headless tool execution.
  • Public event emission.
  • Initial resume/tail/replay behavior over the event log, with bounded reads and suffix-only tail reads.
  • Deterministic in-process policy execution/emulation for modeled decisions, including deny-all Linux-target network policy and rejection of non-empty network allowlists; Linux Landlock/seccomp and macOS Seatbelt OS enforcement are post-M1.
  • D-015 golden-loop diffs and sandbox-negative tests, plus event-ordering and transcript-persistence tests.
