V-Spec — Flow Agent

M1 Flow Agent deterministic runtime foundation (CLI binary: flow, ADR-0013). Implementation complete on this branch; pending maintainer review and merge. Canonical shared docs: GLOSSARY.md, VISION.md, PLAN.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Flow Agent is a standalone CLI agent product first. M1 is its deterministic, script-defined runtime foundation: it validates Flow definitions, plans and runs explicit fixture/stub profiles, emits canonical events and persists replayable sessions. It is not yet a practical general provider/process agent. M1.1 adds that execution stage; M1.2 adds OS isolation. Direct Rust embedding remains D-020.

A Meta-Harness on the same host may integrate through Flow Agent's public runtime surfaces; neither Meta-Harness nor Liquid is required to run Flow Agent. Flow Agent exposes only its CLI and public event stream. Liquid reaches agent sessions through Meta-Harness and owns the optional UI.

Flow Agent is the Watershed platform's execution layer and its developer/open-source credibility wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: run repeatable, auditable AI-agent workflows from my CLI. It is a deterministic, auditable, reusable agent-flow runtime — not another generic coding agent.

2. Product boundary

Flow Agent is a standalone host-local CLI agent product. Meta-Harness is an optional same-host consumer; Liquid is an optional client of Meta-Harness. Neither is a prerequisite.

Flow Agent owns

  • fixture-bounded local execution in M1;
  • deterministic FSM behavior;
  • the building-block / script runtime;
  • deterministic in-process policy enforcement/emulation in M1;
  • local runtime events;
  • local transcript/session persistence;
  • its standalone CLI integration surfaces.

Flow Agent does not own

Meta-Harness responsibilities: same-host multi-agent process ownership, central config, AgentPulse, scheduling and a local-or-remote client API.

Liquid responsibilities: local-first Pages, Blocks, Views, responsive desktop/mobile UI, workspace data, action history and workspace CLI/API. Liquid may render Flow Agent sessions through Meta-Harness-backed Blocks; neither layer reads Flow Agent storage directly, and Liquid edits use Liquid's mutation pipeline.

M1 can

Load strictly validated Flow definitions; build deterministic Flow structures and context manifests; execute fixture/stub Flows; persist and stream canonical events; replay, tail and resume sessions; and evaluate declared policies deterministically in process.

M1 cannot

Call a real provider; run arbitrary external tools or processes; provide a complete POSIX shell; guarantee OS isolation; allow positive network destinations; or export, delete and prune session bundles.

Meta-Harness consumes Flow Agent's public surfaces from the same host (see Meta-Harness V-Spec); it does not own the runtime internals. M1 ships the human CLI plus machine-readable event stream. Local machine control is a designed-for seam (ADR-0035); direct Rust embedding remains open.

3. Standalone runtime surfaces

Flow Agent must expose the M1 surfaces below and preserve the designed-for seams. The CLI owns its output transport. CLI/fixture behavior is decided by ADR-0034; surface scope by ADR-0035.

A. Human CLI

flow run hello-flow
flow run "hello-flow"
flow chat
/hello-flow
flow resume <session-id>
flow sessions
flow tail <session-id>

Direct human use; nice terminal rendering is allowed. /hello-flow is entered inside the interactive flow chat terminal, not in the OS shell.

B. Headless JSONL event stream

flow run smoke-flow --emit jsonl
flow run hello-flow --emit jsonl

The CLI owns stdout and streams newline-delimited committed events for automation, CI, custom terminal UIs and same-host Meta-Harness ingestion. CI captures and diffs this stream against the ADR-0034 goldens.

C. Local machine-control surface (designed-for)

flow --mode rpc
# or: flow rpc

Bidirectional external control is a post-M1 seam. ADR-0055 selects local JSON-RPC over stdio (ADR-0029) with a minimal flow.start, flow.status, flow.cancel, flow.tail and flow.export command set; it carries the same runtime events instead of adding cmd.* event types.

D. Rust integration (open)

D-020 will decide whether other Rust programs call Flow Agent in-process or through its command and protocol surfaces. M1 makes no external embedding commitment.

E. Local session/transcript persistence

Flow Agent owns its own local session store, independent of Meta-Harness, mirroring the public event stream:

.flow/sessions/<session_id>.jsonl
.flow/sessions/<session_id>.000002.jsonl
.flow/sessions/<session_id>.object.sha256-<digest>
.flow/logs/<session_id>.log
.flow/logs/<session_id>.contexts.jsonl
.flow/logs/<session_id>.contexts.000002.jsonl

Event and context-manifest streams use the bounded, record-preserving segmentation defined in PROTOCOL.md. Each event is appended before a bounded live notification is attempted (ADR-0059, ADR-0062, ADR-0068). The store enables resume, replay, tail and debugging. Run, replay, tail, resume, listing and quota/bundle accounting share canonical session paths and namespace rules. Resume and complete quota/bundle validation use the full inventory of events, manifests, immutable objects, metadata and active ownership; listing alone does not prove complete resumability. M1.1 adds public export, delete, prune, retention, quota and storage-status operations over the complete bundle. This is not project VCS/history handling; .flow stays protected per SECURITY.md.

The .log sidecar records definition identity. Context-manifest segments record each provider turn and reference its exact canonical source bytes through session-owned immutable SHA-256 objects; identical objects are stored once. Events, manifests, objects and metadata form one logical session bundle, and export/deletion must treat them as one unit. Neither metadata nor context manifests are runtime event streams.

The <session_id> filename segment is the lowercase path-safe v0 session_id token defined in PROTOCOL.md. Replay, tail and resume reject invalid, uppercase or path-like IDs before touching .flow/sessions.

Minimum local M1 semantics: under --emit jsonl, flow replay <session-id> emits stored event objects unchanged in original sequence order and flow tail <session-id> emits the current valid prefix followed by new events; default human mode renders status. flow resume <session-id> is local-only, rejects selected-definition-closure or flow-definition drift before side effects, reconstructs state from the valid log prefix, then appends a new session.resumed event with the next sequence. Unrelated registry additions do not create drift. None of these commands rewrites prior events. Replay and resume reject corrupt or incomplete logs before tool side effects. Active ownership creates .flow/sessions/<session_id>.lock. Every controlled success or error explicitly attempts lock removal and returns a cleanup failure without losing an earlier operation or writer-finalization failure; an empty, unactivated reservation may roll back, while any valid event, context or metadata prefix remains for diagnosis and replay. Drop is only a best-effort fallback for panic or uncontrolled unwinding and cannot report a failed physical removal as success. A new run derives its base session ID from the selected Flow and searches a bounded sequence of suffixed candidates when a bundle member or lock already exists; run APIs do not accept a caller-selected session ID. Resume targets the caller-supplied session ID and refuses any lock. An abrupt process stop or power loss may leave a lock, and M1 never classifies or auto-steals it as stale. Manual recovery requires verifying no Flow Agent process owns the session, preserving or inspecting the bundle if needed, removing the lock, then retrying.

Canonical storage limits are defined in PERFORMANCE.md. Replay requires complete valid event JSONL; resume additionally requires complete valid context-manifest JSONL and every referenced immutable object. Tail validates complete prefixes across segments, uses a sequence cursor, buffers an incomplete trailing line only in the final active segment and rejects bytes after a terminal event.

Ownership is authorship, not crash consistency: local M1 append and notification follow the flush/sync boundaries in PROTOCOL.md and never expose an event that was not first appended. M1 does not promise power-loss atomicity across filesystem directory entries, sidecars and tool side effects. In ephemeral/cloud runs, replication plus durable storage—not container lifetime—provides survival; a persistent .flow volume covers standalone use. Remote replication cadence, crash recovery and a durable session-ownership lease remain post-M1 under ADR-0039.

4. Differentiators / core principles

Recursive building blocks

Tools, Instructions, Phases and Flows share one modular configuration model. A Flow is itself a building block, so flows can contain subflows without a second abstraction.

Simpler terminology

Scripts, instructions, connections and flows replace agent-specific vocabulary such as skills directories, agent markdown files and runtime-tool lists.

Deterministic FSM

The harness controls phase order, step transitions, available tools, instruction loading and event handling deterministically. LLM/tool outputs are inputs; the state machine remains deterministic. This is determinism of orchestration, not of model output (see §7).

Event-driven runtime

Normal progress is driven by events, not polling. M1 emits implemented completion and failure events; designed timeout and attention emitters join the same protocol after M1.

Flows as AI-native processes

Each flow run can be measured and compared. This enables optimizing specific flows rather than endlessly tuning one generalized agent setup.

Security claims by evidence

Scripts declare capabilities and the runtime compiles policy artifacts. M1 emulates policy decisions in process; M1.2 must prove the OS boundary. Prompt intent and allowlists alone are never security boundaries.

5. MVP boundary

M1 scope: standalone CLI, scripts, pure deterministic planning, exactly-once fixture apply, public event stream, JSONL headless mode, local session/transcript store, context manifests, in-process policy emulation, Subflows and golden Flows.

M1 exclusions: real providers, general external process execution, a complete POSIX shell, OS isolation, positive network grants, public session export/delete/prune, Flow Agent UI, cross-host process control, central Meta-Harness behavior, Liquid Pages/Blocks and any Watershed project-history/VCS engine. See PLAN.md for M1.1 and M1.2.

A same-host Meta-Harness is an optional consumer; Liquid is an optional client of Meta-Harness. Neither is required to run Flow Agent.

Flow Agent may run inside normal Git projects. M1 performs no real Git tool command. M1.1 may treat Git as a declared bounded tool, and M1.2 must isolate it; Flow Agent never owns commits, branches, slices or project history. The local session store (§3E) is runtime state, not project VCS/history.

6. Architecture

Instruction loader

  • CLI: accepts a selected Flow reference and implemented output/event mode (human or JSONL); future RPC/control mode follows ADR-0055 after M1.
  • Building-block registry: parses Tools, Instructions, Connections, Phases, Flows and Subflows.
  • FSM engine: owns deterministic state transitions.
  • Instruction loader: resolves active flow/phase/step instructions; the agent does not self-load them.
  • Context compiler: produces the bounded, reproducible provider context and manifest defined below.
  • Runtime kernel: interprets declared fixture tools deterministically in process with bounded inputs and policy checks. External subprocess timeouts, bounded stdout/stderr and per-tool run logs are post-M1.
  • Session manager: uses one serial writer to append each canonical event before a bounded non-blocking notification; callers replay committed events by sequence and own delivery (§3E; PROTOCOL.md).
  • Protocol adapter: emits normalized events per PROTOCOL.md.

Crate boundaries (ADR-0033)

The runtime engine and CLI front-end are separate crates so the engine can be tested headlessly and reused by the CLI. Any external embedding contract remains D-020:

  • core/core-script — building-block model, parser, registry and composition rules.
  • core/core-policy — capability model and canonical policy-artifact compiler.
  • proto/ — proto: event schema and serialization.
  • flow-agent/flow-agent-core — FSM engine, runtime kernel, session manager, local log, bounded live notification and runtime entry.
  • flow-agent/flow-agent-cli — interactive terminal, slash commands, machine-readable mode, flow run, tail/replay/resume.

The building-block model lives in core-script and is serializable over proto. Same-host Meta-Harness consumes it through core-script as a config resolver; Liquid renders derived state through Meta-Harness-backed Blocks. Neither consumes Flow Agent internals.

Build strategy & reuse

Orchestration is built in-house; non-differentiating plumbing (model/provider I/O, tool execution, OS-isolation wrappers, MCP client and context handling) is reused via general-purpose crates where it fits. Flow Agent is not built on or forked from Codex; Codex integrates as a Meta-Harness adapter. Rationale/licensing: ADR-0028.

Deterministic Tiered Context Compiler v0 (ADR-0050, ADR-0058)

M1 has one internal context compiler and one public, fixed profile: flow-context-v0. It minimizes model-visible tokens subject to preserving the best achievable task outcome, deterministic orchestration, provenance and replay. M1 exposes neither user-configurable per-source budgets nor a general context-document format.

Durable session history

The complete append-only event history and source artifacts. Its events are authoritative for replay; the full history is authoritative for resume, audit, debugging and future retrieval. Context optimization never deletes either.

Resolved flow state

The current invocation, phase, step, active instructions/tools, connections and runtime state, plus values supplied by runtime interfaces whose source/schema is defined.

Provider context

The deterministic, bounded projection compiled for one model turn. It is deliberately smaller than durable session history.

Budget, identity and cache-stable order

input budget = model context limit - fixed output reserve - fixed safety margin. The selected versioned model/context profile fixes all three values plus tokenizer or estimator identity. An exact provider tokenizer is used when available; otherwise M1 uses the conservative utf8-byte-v0 estimator (one estimated token per canonical UTF-8 byte). The same durable state, resolved flow state, flow definition, model profile, runtime version and context-profile version produce the same ordered canonical provider-context bytes and lowercase SHA-256 context hash.

Tier 0 is serialized in this exact order:

  1. base runtime and security instructions;
  2. active flow instructions;
  3. active phase instructions;
  4. active step instructions;
  5. only tool definitions available to the active phase or step;
  6. a compact snapshot of current FSM and flow state;
  7. typed inputs arriving through explicit connections to the current step;
  8. the current user input;
  9. unresolved call/result state required to continue the turn.

Resolved declaration order is preserved for instructions, tools and connections; canonical maps sort keys. Inactive instructions, unavailable tools, unrelated outputs and incidental volatility such as collection iteration order are excluded. The first five, scope-stable sections form the longest reusable provider-cache prefix; turn-specific state and inputs follow, then Tier 1. Cache-boundary metadata is deterministic and recorded in the manifest. Provider-specific cache hints may annotate those boundaries but must not reorder content, alter the logical context or change its context hash.

The current M1 CLI/stub runtime has no decided user-input value, predefined-command invocation-value, typed connection-value or artifact/tool-output source schema. The corresponding Tier 0 sections carry deterministic absence markers, and M1 emits no artifact/tool-output projection. Values or projections enter provider context only after their runtime source and schema are decided.

All Tier 0 content is mandatory. If it exceeds the input budget, Flow Agent emits the existing typed error event with code context_budget_exceeded and fails before contacting the provider. It never silently drops mandatory content or relies on provider-side truncation.

Tier 1: bounded continuity

Only the remaining budget may be used, in this selection order, for: the current incomplete turn when applicable; at most the most recent complete interaction turn; once their runtime source/schema is defined, bounded projections of directly referenced artifacts or tool outputs not already represented by typed connection inputs; and a compact deterministic checkpoint required to interpret state. Optional units are ordered by source sequence, then by this category order. If they do not fit, the oldest optional unit is omitted first. Ordinary user/assistant messages remain whole, and tool calls stay paired with their results. A directly connected typed output and unresolved continuation state belong to Tier 0, not this historical tail.

Tier 2 and Tier 3: retained, not sent in M1

Older turns beyond the single Tier 1 tail, unrelated phase/step outputs, inactive instructions, unavailable tool schemas, full old tool logs, full large artifacts and diagnostic history are omitted from M1 provider context, never deleted from durable history or artifact storage. M1 does not use model-generated compaction, embeddings, semantic RAG, adaptive relevance ranking, nondeterministic selection or regenerated summaries during resume/replay.

Conditional projections and manifest

When a directly referenced artifact source/schema is defined, it may use only a versioned deterministic projection algorithm registered by flow-context-v0; an unregistered type is omitted rather than heuristically summarized. The algorithm's decided parameters and manifest fields must make the projection byte-reproducible, and the complete source remains outside provider context.

Every provider turn stores a reproducible context manifest with its durable session data; this is an implementation artifact, not a new runtime event family. The manifest records context-profile ID/version, model profile/context limit, tokenizer or estimator ID/version, output reserve, safety margin, ordered included source IDs, projection hashes and session-object URIs, deterministic cache boundaries, omitted-source counts by category, estimated input tokens and final context hash. The immutable objects preserve the exact canonical source bytes even if the original workspace source later changes or disappears. Complete ordinary messages are never cut; tool calls/results remain paired; a result never appears without its call; unresolved required calls, current user input and required instructions are never silently removed. Resume verifies every object and uses the recorded context-profile version and compiler.

Post-M1 context architecture

The following evolution is explicitly outside M1. Persisted structured compactions may be generated once, stored with provenance and reused unchanged on resume/replay; originals are never deleted and summaries are never regenerated during replay. Future provider context may combine active typed flow state, a persisted checkpoint/summary, a small raw tail, direct connection inputs and automatically retrieved evidence selected for the turn when relevant. Retrieved memory remains outside the building-block registry; only bounded, provenance-bearing results enter a turn.

Retrieval should first use deterministic graph identities and relationships—flow, phase, step, connection, artifact, tool-call and message IDs, tags and content hashes. Optional semantic retrieval may follow only with versioning, recorded queries/results, provenance, quality/token evaluation and a deterministic fallback. A retrieval subflow receives isolated declared inputs/instructions/tools and returns a small typed result with citations; its transcript does not leak into the parent. Later versions retain lazy scoped instructions/tools and are accepted only when evaluation shows token savings without measurable task-quality loss.

7. Deterministic FSM

The FSM is deterministic over declared flow state and inputs — deterministic orchestration over a non-deterministic generator, not identical output. The LLM may produce stochastic content; the harness consumes it as data for deterministic transition rules, giving four guarantees: bounded (a step can only do what its phase declares), reproducible structure (same phases/steps/tool-scopes every run), measurable (runs compare because the scaffold is held constant), and governable (every transition is attributable). The trade is autonomy for control — strongest for processes run more than once or that must be trusted, wrong for open-ended exploration.

  • Phase order is declared by the script.
  • Available tools/instructions are a pure function of current phase/step.
  • Subflows start through explicit building-block references.
  • Failures become typed events in M1; designed timeout and attention events remain post-M1.
  • Tests assert transitions, allowed tool sets, instruction loading and event ordering.

8. Building-block scripts

Scripts use YAML 1.2 with strict parser validation and canonical serialization (ADR-0031). Checked-in JSON Schema files document the intended shape, but M1 does not run a separate schema engine. They are human-reviewable security/capability artifacts, so the parser must produce one unambiguous model for reviewers, audits and golden tests, including when scripts are machine-generated.

Example registry entries below are separate files under one registry root; each file contains exactly one top-level block.

registry/tools/read-file.yaml

tool:
  id: read-file
  name: ReadFile
  tool_kind: predefined-command
  command:
    command_id: agent-read
    argv: []
  allowed_parameters:
    - name: "--file"
      value_type: workspace-relative-path
      required: true
  read_scope: ["workspace"]
  write_scope: []
  protected_path_grants: []
  network: deny

registry/instructions/summarize-findings.yaml

instruction:
  id: summarize-findings
  name: SummarizeFindings
  prompt: "Summarize only facts from tool output."

registry/phases/research.yaml

phase:
  id: research
  name: Research
  tool_refs: [read-file]
  instruction_refs: [summarize-findings]
  steps:
    - id: gather
      name: Gather
    - id: summarize
      name: Summarize
      connection_refs: [research-refresh]

registry/connections/research-refresh.yaml

connection:
  id: research-refresh
  name: ResearchRefresh
  connection_kind: refresh
  from_ref: research.gather
  to_ref: research.summarize

registry/flows/hello-flow.yaml

flow:
  id: hello-flow
  name: HelloFlow
  phase_refs: [research]
  subflow_refs: []
  connection_refs: [research-refresh]

Minimum v0 schema surface: every block requires id and name; references use explicit id/name values and the resolver rejects missing or ambiguous references. Tools require tool_kind (predefined-command or own-script), exact command, allowed_parameters, read_scope, write_scope, protected_path_grants and network. A predefined-command tool uses command as an object with command_id and literal argv; command_id matches ^[a-z][a-z0-9_-]{0,63}$ and resolves through the predefined-command registry, not PATH lookup, a shell, environment expansion or globbing. M1 uses fixture stubs only when fixture_profile: stub-model and stub_model: deterministic are explicitly selected; every normal workspace fails closed before provider/tool side effects with execution_backend_unavailable. Parameter-token validation is canonical in SECURITY.md; the current M1 fixture runtime supplies no invocation parameter tokens. An own-script tool uses command: script:<tool-id>, requires script_runtime: posix-sh and script_body as UTF-8 source owned by that Tool block, and forbids host script paths, shebang-selected interpreters and runtime-specific extra args in v0. M1 interprets only the fixture write subset; M1.1 adds the bounded fixed runner, and M1.2 applies the compiled policy to runner processes and children. Instructions require prompt. Phases require ordered instruction_refs, tool_refs and steps; every step requires id and name, may declare ordered connection_refs, and step_id events use the step id. Step ids are phase-local; connection endpoint references to steps use <phase_id>.<step_id>. Connections require connection_kind (data, trigger or refresh), from_ref and to_ref, and endpoints may target Tools, Instructions, Phases, Flows or scoped Steps. Flows require ordered phase_refs plus optional subflow_refs and connection_refs; every Step connection_ref must resolve to a Connection also listed by the enclosing Flow. Runtime step.started/step.completed payloads emit connection_ids and connection_kinds in the resolved Step connection_refs order. Checked schema files and parser fixtures enforce this contract; no additional top-level block kind is added without a new decision.

Tool network is either scalar deny or { default: deny, allow: [...] }, with default fixed to deny. Allow entries and enforcement scope are canonical in SECURITY.md. core-policy copies the resolved grammar into commands[].network (ADR-0051, ADR-0052).

Workspace configuration

.flow/config.yaml
registry_root: registry

registry_root is required and workspace-relative. Checked-in deterministic fixtures additionally pair fixture_profile: stub-model with stub_model: deterministic; normal workspaces omit both.

Composition happens through the building-block registry with explicit by-name/id references; Safe-YAML acceptance is canonical in SECURITY.md. The v0 registry container is a configured registry root discovered recursively; every .yaml/.yml file is one UTF-8 YAML 1.2 document containing exactly one top-level block key (tool, instruction, phase, connection or flow) and one block object. Multi-document streams, files with multiple blocks, top-level block arrays/maps and non-registry YAML files are rejected. File paths are stable addresses for review and diagnostics only; identity and references come from the block id/name. The loader safely scans every entry into a bounded identity catalog, then materializes and resolves only the selected root Flow's transitive closure: referenced Phases, Subflows, Connections and their endpoints, Instructions and Tools. Each definition is retained once even when referenced repeatedly; unrelated definitions are not retained. The resolver rejects duplicates, ambiguity, missing selected references and cycles, resolves only within the configured root, and rejects nesting deeper than 16 levels, counting the root as level 1. Each Flow may directly reference at most 32 subflows. Later package/archive formats may provide registry entries, but they must normalize to the same one-block entry model before parsing. Connections must make data/control flow explicit instead of hiding it in agent-specific config files.

M1 registry limits are 128 KiB per YAML file, 16 MiB and 1,024 visited entries per root, and 1 MiB of source in the selected closure. Registry traversal accepts at most 64 nested directory components below each configured root; this filesystem limit does not constrain Flow composition. Block/Step names allow 256 Unicode characters; Instruction prompts and own-script bodies allow 64 KiB of UTF-8. The runtime safety envelope is defined in PERFORMANCE.md. Limits are fixed M1 safeguards, not configuration.

Canonical serialization is deterministic UTF-8 JSON of the strictly parsed, validated and resolved selected closure, not a re-emission of source YAML. Object keys are sorted lexicographically; parser defaults are materialized; optional fields without defaults are omitted; arrays preserve declared order except allowed_parameters, which sorts by name; unordered collections are represented as maps keyed by id/name; strings are NFC-normalized; comments and source formatting are discarded; null is rejected unless explicitly allowed; NaN and infinity are always rejected. Canonical bytes are the review/audit/golden-test form.

9. Events & measurement

Flow Agent's event stream is a stable public runtime contract, not just an internal log. Every meaningful runtime transition appends one normalized event; JSONL mode (§3B), future RPC mode (§3C) and replay from the local session log (§3E) expose the same events. Live notifications report the earliest pending and highest committed sequences, never a second event copy. Golden flows compare expected event streams, which makes individual flows measurable and optimizable.

These are the same normalized events defined in PROTOCOL.md (single source of truth for the event-envelope fields and runtime event families). Exact v0 names are decided by ADR-0036; do not introduce a competing naming convention. Command/request shape is a separate post-M1 surface selected by ADR-0055.

PROTOCOL.md defines the envelope, canonical JSONL, event families and lifecycle; TESTING.md defines the emitted ADR-0034 test subset; PERFORMANCE.md defines delivery budgets.
