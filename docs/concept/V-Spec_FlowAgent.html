V-Spec — Flow Agent

M1.2 Flow Agent OS isolation (CLI binary: flow, ADR-0013), extending the M1.1 practical-execution foundation. Current milestone status is canonical in PLAN.md. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & scope

Flow Agent is a standalone CLI agent product first. M1 is its deterministic, script-defined runtime foundation: it validates Flow definitions, plans and runs explicit fixture/stub profiles, emits canonical events and persists replayable sessions. M1.1 adds practical provider/Tool execution; M1.2 adds the Flow-owned Executor and OS-isolation boundary. Direct Rust embedding remains D-020.

Accepted post-M1.1 direction: Flow Agent uses Global Flow configuration with no Workspace-discovered config layer, supports offline-after-provisioning execution through device-local Runtime bindings, and continues a portable terminal checkpoint as a new child Run. Global configuration storage is implemented; offline and portable implementation remains blocked on D-058/D-059 plus the local-runtime and archive-authenticity boundaries in D-061/D-062.

A Meta-Harness on the same host may integrate through Flow Agent's public runtime surfaces; neither Meta-Harness nor Liquid is required to run Flow Agent. Flow Agent exposes only its CLI and public event stream. Liquid reaches agent sessions through Meta-Harness and owns the optional UI.

Flow Agent is the Watershed platform's execution layer and its developer/open-source credibility wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: run repeatable, auditable AI-agent workflows from my CLI. It is a deterministic, auditable, reusable agent-flow runtime — not another generic coding agent.

2. Product boundary

Flow Agent is a standalone host-local CLI agent product. Meta-Harness is an optional same-host consumer; Liquid is an optional client of Meta-Harness. Neither is a prerequisite.

Flow Agent owns

  • fixture-bounded local execution in M1;
  • productive provider and bounded Tool execution in M1.1;
  • Executor selection, lifecycle, protocol and the official Default Sandbox Executor in M1.2;
  • deterministic FSM behavior;
  • the building-block / script runtime;
  • deterministic in-process policy enforcement/emulation in M1;
  • local runtime events;
  • local transcript/session persistence;
  • its standalone CLI integration surfaces.

Flow Agent does not own

Meta-Harness responsibilities: same-host multi-agent process ownership, central config, AgentPulse, scheduling and a local-or-remote client API.

Liquid responsibilities: local-first Pages, Blocks, Views, responsive desktop/mobile UI, workspace data, action history and workspace CLI/API. Liquid may render Flow Agent sessions through Meta-Harness-backed Blocks; neither layer reads Flow Agent storage directly, and Liquid edits use Liquid's mutation pipeline.

M1 can

Load strictly validated Flow definitions; build deterministic Flow structures and context manifests; execute fixture/stub Flows; persist and stream canonical events; replay, tail and resume sessions; and evaluate declared policies deterministically in process.

M1 cannot

Call a real provider; run arbitrary external tools or processes; provide a complete POSIX shell; guarantee OS isolation; allow positive network destinations; or export, delete and prune Run bundles.

Meta-Harness consumes Flow Agent's public surfaces from the same host (see Meta-Harness V-Spec); it does not own runtime internals, Executor selection or Tool Sandboxes. M1 ships the human CLI plus machine-readable event stream. Local machine control is a designed-for seam (ADR-0035); direct Rust embedding remains open.

3. Standalone runtime surfaces

Flow Agent must expose the M1 surfaces below and preserve the designed-for seams. The CLI owns its output transport. CLI/fixture behavior is decided by ADR-0034; surface scope by ADR-0035.

A. Human CLI

flow run hello-flow
flow run "hello-flow"
flow chat
/hello-flow
flow resume <conversation-id>
flow resume <conversation-id> --from-entry <entry-id>
flow resume <conversation-id> <run-session-id>
flow replay <conversation-id> <run-session-id>
flow sessions status
flow tail <conversation-id> <run-session-id>

Direct human use; nice terminal rendering is allowed. flow chat reads exactly one nonblank Flow reference from stdin, accepts an optional leading / such as /hello-flow, runs it, then exits. One-id Resume continues the newest committed Conversation entry in a new Run; --from-entry branches from an older entry. The two-id form is exact interrupted-Run recovery. Replay and Tail always use the exact Conversation/Run pair. A future tree-navigation surface may expose the same Conversation entries and branches in the style of Pi's /tree; it is a view over this authority, and exact command spelling remains part of D-058.

B. Headless JSONL event stream

flow run smoke-flow --emit jsonl
flow run hello-flow --emit jsonl

The CLI owns stdout and streams newline-delimited committed events for automation, CI, custom terminal UIs and same-host Meta-Harness ingestion. CI captures and diffs this stream against the ADR-0034 goldens.

C. Local machine-control surface (designed-for)

flow --mode rpc
# or: flow rpc

Bidirectional external control is a post-M1 seam. ADR-0055 selects local JSON-RPC over stdio (ADR-0029) with a minimal flow.start, flow.status, flow.cancel, flow.tail and flow.export command set; it carries the same runtime events instead of adding cmd.* event types.

D. Rust integration (open)

D-020 will decide whether other Rust programs call Flow Agent in-process or through its command and protocol surfaces. M1 makes no external embedding commitment.

E. Local conversation/session persistence

Flow Agent owns FLOW_AGENT_HOME, defaulting to ~/.flow, independently of the Workspace and Meta-Harness. Its config.yaml and configured registry are the sole implicit technical authority; each canonical Workspace path selects only one versioned runtime store. Productive Conversations use this layout:

<workspace-store>/sessions/<conversation_id>/status.json
<workspace-store>/sessions/<conversation_id>/history.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/events.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/events.000002.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/contexts.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/contexts.000002.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/run-log.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/recovery.jsonl
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/objects/<64-lowercase-hex>
<workspace-store>/sessions/<conversation_id>/runs/<run_session_id>/session.lock

Derived overview only: this section summarizes M1.1 capacity behavior; the M1.1 budget matrix is the sole normative numeric contract.

history.jsonl is one append-only, filterable tree. Every node names its parent and a committed point in one owned linear run. Selecting any earlier node and continuing creates a child in a new run; every existing descendant remains in the same file. Branch navigation changes context only and never rolls back filesystem, process, network, provider or other external effects.

Each runtime Event session_id is its run_session_id. Replay and Tail address the exact <conversation-id> <run-session-id> pair. One-id Resume starts a new Run from the newest entry or the explicit --from-entry; two-id Resume continues only that incomplete Run. A productive entry carries the hash of its terminal bounded recovery snapshot, so continuation reads only that selected compact state instead of scanning ancestor Event streams.

Run event and context streams remain the linear replay authority under the finite limits in the budget matrix. Before provider or Tool intent, the concrete writer must admit the complete durability envelope or start no external effect. recovery.jsonl is exact Resume's bounded orchestration snapshot: it binds deterministic requests and Phase, loop, Transition, Flow and terminal boundaries to durable objects and Run Log results. Exact Resume verifies the Event/context prefix and restores completed provider or Tool results without redispatch; uncertain attempts and any divergence fail closed. run-log.jsonl begins with the definition identity and hashes required for both Resume forms' pre-dispatch registry-drift check; later records durably track provider and Tool dispatch attempts, and per-Tool logs project Tool records. Context manifests reference verified immutable Run objects. Exact schemas, reservation and lease behavior are canonical in PROTOCOL.md.

flow sessions status uses human output by default and one bounded page record under --emit jsonl. It reads only bounded canonical status.json summaries and never scans retained histories, Run Logs or Run directories. Each summary is updated with one bounded identity-bound transaction under the conversation lease, and recovery examines only that transaction and its named append or Run target. Missing, corrupt, oversized, unknown or contradictory state fails closed. A non-final JSONL page returns the opaque conversation-order cursor resubmitted through --continuation-token; tokens do not create snapshots, and the final page omits the token. Storage maintenance and rollback behavior are canonical in PROTOCOL.md. Automatic scratch cleanup assumes cooperative same-OS-identity writers; hostile replacement by that identity is outside the M1.1 guarantee.

Deferred export/share behavior is canonical in PROTOCOL.md. Portable continuation is a later public export/import contract, never direct private-store copying: a verified terminal checkpoint starts a new child Run under destination-local authority and Runtime binding; disconnected continuations become separate branches. Exact archive/tree-navigation behavior remains D-058 and archive authenticity remains D-062. The session store is runtime state, not project VCS/history.

A deterministic Fixture Run holds its session lease. A productive mutation holds the Conversation lease and, when mutating a Run, its Run lease, in that order, for the complete operation. These operating-system file leases live with the selected global Workspace store; SQLite is not ownership authority. They serialize Run creation, shared-history mutation and Tool reconciliation. The persistent session.lock leaf is observability only; marker mutation cannot grant or revoke ownership. Replay and Resume reject corrupt history, events, context manifests, Run Logs or referenced objects before effects. Append, notification and durability retain the M1 contracts; external providers, Tools, mutable environments and undeclared side effects remain non-reproducible.

4. Differentiators / core principles

Recursive building blocks

Tools, Instructions, Phases and Flows share one modular configuration model. A Flow is itself a building block, so flows can contain subflows without a second abstraction.

Simpler terminology

Tools, Instructions, recursive Phases and Flows replace agent-specific vocabulary such as skills directories, agent markdown files and runtime-tool lists.

Deterministic FSM

The harness controls Phase order, loops, Transitions, available Tools, Instruction loading and event handling deterministically. Provider and Tool outputs are inputs; the state machine remains deterministic. This is determinism of orchestration, not of model output (see §7).

Event-driven runtime

Normal progress is driven by events, not polling. M1 emits completion and failure events, M1.1 adds Tool timeout emission, and attention remains a designed later emitter.

Flows as AI-native processes

Each flow run can be measured and compared. This enables optimizing specific flows rather than endlessly tuning one generalized agent setup.

Security claims by evidence

Scripts declare capabilities and the runtime compiles policy artifacts. M1 emulates policy decisions in process; M1.2 must prove the official Executor and OS boundary on each exact claimed target. Prompt intent, probes and allowlists alone are never security boundaries.

5. MVP boundary

M1 scope: standalone CLI, scripts, pure deterministic planning, exactly-once fixture apply, public event stream, JSONL headless mode, user-global session/transcript store, context manifests, in-process policy emulation, Subflows and golden Flows.

M1 exclusions: real providers, general external process execution, a complete POSIX shell, OS isolation, positive network grants, public session export/delete/prune, Flow Agent UI, cross-host process control, central Meta-Harness behavior, Liquid Pages/Blocks and any Watershed project-history/VCS engine. See PLAN.md for M1.1 and M1.2.

A same-host Meta-Harness is an optional consumer; Liquid is an optional client of Meta-Harness. Neither is required to run Flow Agent.

Flow Agent may run inside normal Git projects. Git is an ordinary declared Tool behind the same Executor boundary; Flow Agent never owns commits, branches, slices or project history. The user-global session store (§3E) is runtime state, not project VCS/history.

Current crate dependencies and major runtime responsibility paths are mapped in the implementation architecture. The M1.2 Executor and Sandbox architecture explains the responsibility split, selection/readiness path, supported platform boundary and Pi/Codex comparisons. M1.2 boundary: Flow Agent validates each Tool call, compiles policy and manages a fresh one-shot Executor and Sandbox. The official Ubuntu 24.04 x64 path also gives that Tool invocation a fresh cgroup-v2 process-capacity boundary inside a transient systemd user scope. The standard installation resolves its sibling flow-executor; administrators may explicitly opt out or configure an absolute Custom Executor without a Flow Agent compatibility or security guarantee. All productive Tool execution is limited to that platform; macOS, Windows and other targets fail closed. Provider-only Flows do not use the Executor boundary.

  • CLI: accepts a selected Flow reference and implemented output/event mode (human or JSONL); future RPC/control mode follows ADR-0055 after M1.
  • Building-block registry: parses Tools, Instructions, recursive Phases and Flows; a referenced Flow is a subflow, not a fifth kind.
  • FSM engine: owns deterministic state transitions.
  • Instruction loader: loads optional global-home and harness-start Workspace AGENTS.md guidance in that order, separately from technical configuration, then resolves the active leaf Phase's declared Instructions.
  • Context compiler: produces the bounded, reproducible provider context and manifest defined below.
  • Runtime kernel: retains the deterministic Fixture executor and owns the provider loop, one-shot Executor client, durable attempt intent, canonical enforcement receipt and per-Tool Run Log projections. A Tool definition grants availability, never automatic execution.
  • Session manager: uses one serial writer to append each canonical event before a bounded non-blocking notification; callers replay committed events by sequence and own delivery (§3E; PROTOCOL.md).
  • Protocol adapter: emits normalized events per PROTOCOL.md.

Crate boundaries (ADR-0033)

The runtime engine and CLI front-end are separate crates so the engine can be tested headlessly and reused by the CLI. Any external embedding contract remains D-020:

  • core/core-script — building-block model, parser, registry and composition rules.
  • core/core-policy — capability model and canonical policy-artifact compiler.
  • proto/ — proto: event and Executor wire schemas/types.
  • flow-agent/flow-agent-core — FSM engine, runtime kernel, session manager, local log, bounded live notification and runtime entry.
  • flow-agent/flow-agent-cli — human CLI, one-reference chat input, machine-readable mode, flow run, tail/replay/resume.
  • flow-agent/flow-agent-executor — one-shot Ubuntu isolation companion implementing the Executor wire contract.

The building-block model lives in core-script and is serializable over proto. Same-host Meta-Harness consumes it through core-script as a config resolver; Liquid renders derived state through Meta-Harness-backed Blocks. Neither consumes Flow Agent internals.

Build strategy & reuse

Orchestration is built in-house; non-differentiating plumbing (model/provider I/O, tool execution, OS-isolation wrappers, MCP client and context handling) is reused via general-purpose crates where it fits. Flow Agent is not built on or forked from Codex; Codex integrates as a Meta-Harness adapter. Rationale/licensing: ADR-0028.

The exact Flow-owned Codex OAuth wire, credential lifecycle and subscription request contract are canonical in PROTOCOL.md. Agentic Engineers define Tools, exact mounts, runtime_profile and process/thread capacity; other users may run predefined Flows without widening them. Durable intent gives each provider request and Tool call at-most-once Flow Agent dispatch; an attempt without a terminal result remains uncertain and never relaunches automatically. Productive Tools run without an extra warning through the Executor boundary. The canonical cancellation, receipt and error rules live in PROTOCOL.md and SECURITY.md.

ADR-0126 fixes the lock-linearized productive-operation and terminal-completion boundary for the interrupt behavior above.

Deterministic Tiered Context Compiler v0 (ADR-0050, ADR-0058)

M1 has one internal context compiler and one public, fixed profile: flow-context-v0. It minimizes model-visible tokens subject to preserving the best achievable task outcome, deterministic orchestration, provenance and replay. M1 exposes neither user-configurable per-source budgets nor a general context-document format.

Durable session history

The canonical definition is in GLOSSARY.md; exact Resume authorities are in PROTOCOL.md. Provider context is only a bounded projection and never deletes durable history.

Resolved flow state

The current Flow invocation, recursive Phase stack, iteration, active Instructions and available Tools, plus validated input and prior Phase result.

Provider context

The deterministic, bounded projection compiled for one model turn. It is deliberately smaller than durable session history.

Budget, identity and cache-stable order

input budget = model context limit - fixed output reserve - fixed safety margin. The selected versioned model/context profile fixes all three values plus tokenizer or estimator identity. An exact provider tokenizer is used when available; otherwise M1 uses the conservative utf8-byte-v0 estimator (one estimated token per canonical UTF-8 byte). It bounds the complete model-visible Responses request: instructions, retained input and function schemas. The same durable state, resolved flow state, flow definition, model profile, runtime version and context-profile version produce the same ordered canonical provider-context bytes and lowercase SHA-256 context hash.

Tier 0 is serialized in this exact order:

  1. base runtime and security instructions;
  2. optional global-home then harness-start Workspace AGENTS.md guidance;
  3. active leaf-Phase Instructions with validated parameter substitution;
  4. only Tool definitions available to the active leaf Phase;
  5. a compact snapshot of current FSM and Flow state;
  6. the canonical selected-root-Flow input and the validated result handed off by the previous Phase;
  7. the current user input;
  8. unresolved call/result state required to continue the turn.

The AGENTS.md item is a bounded instruction/context channel, not Flow configuration. The local file has later context precedence; neither file's content can select or alter providers, models, registries, Runtime bindings, credentials or resource policy. Project-specific executable composition remains an explicitly selected Flow from the global registry.

Resolved declaration order is preserved for Instructions, Tools and child Phases; canonical maps sort keys. Inactive Instructions, unavailable Tools, unrelated outputs and incidental volatility such as collection iteration order are excluded. The first five, scope-stable sections form the longest reusable provider-cache prefix; turn-specific state and inputs follow, then Tier 1. Cache-boundary metadata is deterministic and recorded in the manifest. Provider-specific cache hints may annotate those boundaries but must not reorder content, alter the logical context or change its context hash.

M1.1 passes the complete validated result of one successful Phase to its next selected sibling. Ordered inline Transitions may select a later sibling through exact typed equality, but cannot project or remap the result. A leaf Phase exposes its declared Tools to the provider loop; merely referencing a Tool never invokes it. The finite grammar is recorded in ADR-0110. Arbitrary projections, mappings, expression languages, backward edges and failure routing remain explicitly deferred.

All Tier 0 content is mandatory. If it exceeds the input budget, Flow Agent emits the existing typed error event with code context_budget_exceeded and fails before contacting the provider. It never silently drops mandatory content or relies on provider-side truncation.

Tier 1: bounded continuity

Only the remaining budget may be used in M1.1, in this selection order, for the current incomplete turn when applicable, at most the most recent complete interaction turn, and a compact deterministic checkpoint required to interpret state. Optional units are ordered by source sequence, then by this category order. If they do not fit, the oldest optional unit is omitted first. Ordinary user/assistant messages remain whole, and tool calls stay paired with their results. Bounded Tool/artifact projections require a later milestone's explicit source schema and are not an implicit Tier 1 extension.

Tier 2 and Tier 3: retained, not sent in M1

Older turns beyond the single Tier 1 tail, unrelated Phase outputs, inactive Instructions, unavailable Tool schemas, full old Tool logs, full large artifacts and diagnostic history are omitted from M1 provider context, never deleted from durable history or artifact storage. M1 does not use model-generated compaction, embeddings, semantic RAG, adaptive relevance ranking, nondeterministic selection or regenerated summaries during resume/replay.

Conditional projections and manifest

A later milestone may add a directly referenced Tool/artifact projection only through a versioned deterministic algorithm registered by flow-context-v0; an unregistered type remains omitted rather than heuristically summarized. The future decision must make its source identity, selection, bounds, parameters and manifest fields byte-reproducible, while the complete source remains outside provider context.

Every provider turn stores a reproducible context manifest with its durable session data; this is an implementation artifact, not a new runtime event family. The manifest records context-profile ID/version, model profile/context limit, tokenizer or estimator ID/version, output reserve, safety margin, ordered included source IDs, projection hashes and session-object URIs, deterministic cache boundaries, omitted-source counts by category, estimated input tokens and final context hash. The immutable objects preserve the exact canonical source bytes even if the original workspace source later changes or disappears. Complete ordinary messages are never cut; tool calls/results remain paired; a result never appears without its call; unresolved required calls, current user input and required instructions are never silently removed. Resume verifies every object and uses the recorded context-profile version and compiler.

Post-M1 context architecture

The following evolution is explicitly outside M1. Persisted structured compactions may be generated once, stored with provenance and reused unchanged on resume/replay; originals are never deleted and summaries are never regenerated during replay. Future provider context may combine active typed Flow state, a persisted checkpoint/summary, a small raw tail, explicitly routed typed inputs and automatically retrieved evidence selected for the turn when relevant. Retrieved memory remains outside the building-block registry; only bounded, provenance-bearing results enter a turn.

Retrieval should first use deterministic graph identities and relationships—Flow, Phase, Transition, artifact, Tool-call and message IDs, tags and content hashes. Optional semantic retrieval may follow only with versioning, recorded queries/results, provenance, quality/token evaluation and a deterministic fallback. A retrieval subflow receives isolated declared inputs/Instructions/Tools and returns a small typed result with citations; its transcript does not leak into the parent. Later versions retain lazy scoped Instructions/Tools and are accepted only when evaluation shows token savings without measurable task-quality loss.

7. Deterministic FSM

The FSM is deterministic over declared Flow state and inputs — deterministic orchestration over a non-deterministic generator, not identical output. The provider may produce stochastic content; the harness consumes it as data for deterministic rules, giving four guarantees: bounded (a leaf Phase can use only its declared capabilities), reproducible structure (the same Phase tree, loop bounds and Tool scopes every run), measurable (runs compare because the scaffold is held constant), and governable (every Transition and iteration is attributable). The Agentic Engineer decides how much structure a Flow imposes.

  • Phase order, forward Transitions and loop bounds are declared by the script.
  • Available Tools and Instructions are a pure function of the active leaf Phase.
  • Subflows start through explicit building-block references.
  • Only the provider decides whether and how often to call an available Tool; the runtime validates every request.
  • Failures become typed events and never take a Transition or start another loop iteration.
  • Tests assert Transitions, loops, Tool availability, Instruction loading and event ordering.

8. Building-block scripts

Scripts use YAML 1.2 with strict parser validation and canonical serialization (ADR-0031). Checked-in JSON Schema files document the intended shape, but M1 does not run a separate schema engine. They are human-reviewable security/capability artifacts, so the parser must produce one unambiguous model for reviewers, audits and golden tests, including when scripts are machine-generated.

Example registry entries below are separate files under one registry root; each file contains exactly one top-level block.

registry/tools/read-file.yaml

tool:
  id: read-file
  name: ReadFile
  tool_kind: predefined-command
  command:
    command_id: agent-read
    argv: []
  allowed_parameters:
    - name: "--file"
      value_type: workspace-relative-path
      required: true
  runtime_profile: exact
  max_concurrent_processes_and_threads: 8
  read_only_mounts: ["workspace"]
  writable_mounts: []
  network: deny

registry/instructions/summarize-findings.yaml

instruction:
  id: summarize-findings
  name: SummarizeFindings
  prompt: "Summarize only facts from Tool output."
  parameters: []

registry/phases/research.yaml

phase:
  id: research
  name: Research
  tool_refs: [read-file]
  instruction_refs: [summarize-findings]
  output:
    type: string

registry/flows/hello-flow.yaml

flow:
  id: hello-flow
  name: HelloFlow
  phase_refs: [research]
  subflow_refs: []
  transitions: []

Minimum v0 schema surface: every block requires id and name; references use explicit id/name values and the resolver rejects missing or ambiguous references. Tools require tool_kind (predefined-command or own-script), exact command, allowed_parameters, positive max_concurrent_processes_and_threads, read_only_mounts, writable_mounts and network; runtime_profile defaults to exact and accepts explicit host-system-read. A predefined-command Tool resolves a declared command_id through the registry, never through PATH lookup, a shell, environment expansion or globbing. An own-script Tool owns its UTF-8 POSIX-shell source; host script paths and shebang-selected interpreters are forbidden. Productive execution applies the compiled policy through the Executor boundary. Instructions contain a prompt and optional typed {{name}} parameter contracts. A prompt source filename has no semantics and may be SYSTEM.md. Optional global-home and harness-start Workspace AGENTS.md files remain separate context inputs without technical configuration authority. A Phase declares one output contract and is either a provider-driven leaf with Instructions and available Tools, or a non-model composite with ordered child phase_refs and one result_from child. A Phase may declare one bounded loop; a Flow or composite Phase may declare ordered exact-typed forward-sibling Transitions. A Flow requires ordered direct phase_refs and may reference subflows. Each Flow file is the canonical composition point for that Flow; referenced subflows retain their own Flow files. Tool, Instruction, recursive Phase and Flow are the only registry kinds. Checked schema files and parser fixtures enforce the current contract.

Tool network is either scalar deny or { default: deny, allow: [...] }, with default fixed to deny. Allow entries and enforcement scope are canonical in SECURITY.md. core-policy copies the resolved grammar into commands[].network (ADR-0051, ADR-0052).

Global Flow configuration

FLOW_AGENT_HOME/config.yaml
registry_root: registry
provider: openai-codex
model: explicit-model-id
model_context_limit: 128000
output_reserve: 16384

FLOW_AGENT_HOME/config.yaml is at most 1 MiB; the home defaults to ~/.flow. registry_root is required and resolves only beneath that home. Productive execution requires exactly provider: openai-codex, an explicit model id of 1–256 Unicode scalars without control characters, and positive token counts for model_context_limit and output_reserve. The operator supplies the selected model’s context limit and a response reserve; Flow rejects a profile that leaves no input budget after its fixed safety margin. The shown counts are examples. Checked-in deterministic fixtures instead pair fixture_profile: stub-model with stub_model: deterministic and omit productive fields.

Flow Agent resolves configuration and Building Blocks only from that global authority. It never probes, merges, inherits or falls back to a Workspace .flow/config.yaml, a Workspace registry or another agent's project-local convention. Project-specific executable behavior is implemented by authoring and explicitly selecting a Flow in the global registry. Optional global-home and harness-start Workspace AGENTS.md files remain ordered instruction/context inputs only. A Flow's model/runtime requirements remain separate from the host's Runtime binding, which resolves the provider endpoint and fields owned by D-059; credential material remains in the Flow-owned protected store.

M1.1 adds non-interactive flow init, flow create <kind> and flow validate authoring for all four registry entry kinds (ADR-0091, ADR-0097, ADR-0104, ADR-0155). One-block YAML remains authoritative. The complete long-flag and delimited-group grammar is canonical in PROTOCOL.md. Init uses a durable identity-bound transaction. Commands never prompt, discover references implicitly, adopt existing targets or overwrite files.

  • flow init defaults its registry root to registry and accepts --registry-root <path>. It preflights that FLOW_AGENT_HOME/config.yaml, the registry root and their complete write sets are disjoint from each other and all reserved Flow runtime namespaces and are absent. Before capability-relative creation it commits a durable identity-bound transaction record. Retry recognizes only that exact transaction and either completes or reverse-cleans proven creations; identity mismatch fails without deleting a replacement.
  • flow create <tool|instruction|phase|flow> writes <registry-root>/<plural-kind>/<id>.yaml. The canonical PROTOCOL.md mapping names every scalar flag and the exact parameter, mount, runtime-profile, loop, Transition and network group delimiters. Long prompt or script bodies come from exactly one UTF-8 file or stdin source; stdin may be consumed once. The 64 KiB semantic body limit is also the raw source cap: reading rejects incrementally on byte 65,537 before UTF-8 decoding or filesystem mutation and does not wait for later EOF. Own-script command/runtime fields derive from the Tool id and cannot be overridden.
  • Creating a Tool, Instruction, Phase or Flow creates only that independent definition. Ordered repeated groups express typed Instruction parameters; leaf Phase Instructions/Tools; composite child Phases, loops and Transitions; Flow Phases, subflows and Transitions; and Tool command, parameters, read-only/writable mounts, runtime-read profile and network declarations. An absent repeated flag means an empty optional list.
  • flow validate [flow-reference] writes nothing. A reference validates its selected closure; no reference parses every entry and resolves every Flow closure.
  • Unknown or non-UTF-8 arguments, duplicate singleton arguments and incomplete repeated groups fail before filesystem mutation. Commands preflight the complete write set and emit stable global_config_already_initialized, definition_exists, invalid_definition or invalid_reference diagnostics with kind, id and safe path where applicable. Usage exits 64; rejected data or state exits 65.

Composition happens through the building-block registry with explicit by-name/id references; Safe-YAML acceptance is canonical in SECURITY.md. The v0 registry container is a configured registry root discovered recursively; every .yaml/.yml file is one UTF-8 YAML 1.2 document containing exactly one top-level block key (tool, instruction, phase or flow) and one block object. Multi-document streams, files with multiple blocks, top-level block arrays/maps and non-registry YAML files are rejected. File paths are stable addresses for review and diagnostics only; identity and references come from the block id/name. The loader safely scans every entry into a bounded identity catalog, then materializes and resolves only the selected root Flow's transitive closure: recursive Phases, subflows, Instructions and Tools. Each definition is retained once even when referenced repeatedly; unrelated definitions are not retained. The resolver rejects duplicates, ambiguity, missing selected references and cycles, resolves only within the configured root, and rejects composition deeper than 16 levels, counting the root as level 1. Each Flow may directly reference at most 32 subflows. Later package/archive formats must normalize to the same one-block entry model before parsing. M1.1 has no registry Connection, projection or mapping construct.

M1 registry limits are 128 KiB per YAML file, 16 MiB and 1,024 visited entries per root, and 1 MiB of source in the selected closure. Registry traversal accepts at most 64 nested directory components below each configured root; this filesystem limit does not constrain Flow composition. Block names allow 256 Unicode characters; Instruction prompts and own-script bodies allow 64 KiB of UTF-8. The runtime safety envelope is defined in PERFORMANCE.md. Those limits are fixed safeguards. The Tool process/thread capacity is instead an explicit Agentic-Engineer capability with no default; Flow users, providers and Tools cannot widen it.

Canonical serialization is deterministic UTF-8 JSON of the strictly parsed, validated and resolved selected closure, not a re-emission of source YAML. Object keys are sorted lexicographically; parser defaults are materialized; optional fields without defaults are omitted; arrays preserve declared order except allowed_parameters, which sorts by name; unordered collections are represented as maps keyed by id/name; strings are NFC-normalized; comments and source formatting are discarded; null is rejected unless explicitly allowed; NaN and infinity are always rejected. Canonical bytes are the review/audit/golden-test form.

9. Events & measurement

Flow Agent's event stream is a stable public runtime contract, not just an internal log. Every meaningful runtime transition appends one normalized event; JSONL mode (§3B), future RPC mode (§3C) and replay from the user-global session log (§3E) expose the same events. Live notifications report the earliest pending and highest committed sequences, never a second event copy. Golden flows compare expected event streams, which makes individual flows measurable and optimizable.

These are the same normalized events defined in PROTOCOL.md (single source of truth for the event-envelope fields and runtime event families). Exact v0 names are decided by ADR-0036; do not introduce a competing naming convention. Command/request shape is a separate post-M1 surface selected by ADR-0055.

PROTOCOL.md defines the envelope, canonical JSONL, event families and lifecycle; TESTING.md defines the emitted ADR-0034 test subset; PERFORMANCE.md defines performance design and evidence.
