Standalone native workspace and app-building product. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & product boundary

Liquid is a standalone native workspace and app-building product. It lets users compose dashboards, views, components, scripts, data sources and automations into custom workflows across desktop and mobile, with local workspace storage, an internal workspace action history/VCS and a workspace CLI/API. Liquid remains useful without Loop Agent or Meta-Harness. External agents and tools interact with Liquid through its workspace CLI/API, and all workspace mutations are recorded in Liquid's internal action history so changes can be reviewed and reverted.

Liquid is the Watershed platform's workspace/action layer and its long-term workspace/action wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: let humans and agents safely co-edit a workspace with reversible history. It is an agent-editable native workspace with action history and safe revert — not a Notion clone and not merely the UI for Meta-Harness. Its defensible niche is the long tail of personal/internal/data-centric apps — agent-built, inside a sovereign, local-first, reversible workspace where the data and agent governance also live, a combination generative-app tools and SaaS workspaces do not offer; the ambition is that long tail, not literally "most applications."

The clean product model across the three Watershed tools:

Loop Agent    = standalone agent runtime
Meta-Harness  = standalone headless many-agent control plane
Liquid        = standalone native workspace / app-building product

Liquid can integrate Loop Agent and Meta-Harness as optional runtime/control-plane providers, but neither is a prerequisite. Liquid is not merely a UI for Meta-Harness. When Liquid does consume Meta-Harness it renders that backend rather than reimplementing it (boundary: D-025).

Liquid owns

  • native app shell (desktop/mobile);
  • workspace, dashboard, view and component models;
  • component runtime, rendering and layout;
  • PowerBar;
  • local workspace storage;
  • internal workspace action history / VCS;
  • workspace CLI/API for external agents/tools;
  • local user data model;
  • connections / data-source model;
  • script component runtime;
  • extension / component SDK;
  • Liquid AI workspace assistant;
  • workspace permissions and review/revert flow;
  • import/export; sync/collaboration later.

Liquid does not own

  • Loop Agent execution internals;
  • Loop Agent deterministic FSM / runtime kernel;
  • Meta-Harness session registry;
  • Meta-Harness adapter logic;
  • Meta-Harness central config resolution;
  • Meta-Harness AgentPulse computation;
  • Meta-Harness scheduling engine;
  • any arbitrary project-code VCS/history engine.

Liquid's workspace action history is a workspace VCS over Liquid's own data, not a project-code VCS over arbitrary software projects (see §6). It is distinct from the deferred Watershed project-history engine and from Loop Agent's local session store.

2. Standalone & integration modes

Mode A — Liquid alone (no Loop Agent, no Meta-Harness)

Liquid Desktop/Mobile
  workspace, dashboards, views, components
  scripts, local data
  PowerBar, Liquid AI
  internal action history
  workspace CLI/API

Notes/documents, custom dashboards, tables and charts, local script components, data analysis, personal productivity, workspace/app building, LLM-assisted dashboard/component creation, and external agents reading/editing workspace data through the Liquid CLI/API.

Mode B — Liquid + Loop Agent direct

Liquid
  connects directly to Loop Agent public runtime surfaces
    JSONL / tail-export surfaces / RPC when implemented

Simple local workflows: start a local loop from PowerBar, display a live transcript, render loop progress, inspect loop artifacts, replay/tail a Loop Agent session through public surfaces. Optional and thinner than the Meta-Harness integration.

Mode C — Liquid + local Meta-Harness sidecar

Liquid
  starts local Meta-Harness sidecar
    manages Loop Agent, Codex CLI,
    Claude Code, Pi Agent, ...

Default agent-enabled single-user setup. Liquid renders sessions, transcripts, approvals, the config editor, AgentPulse, schedules, automation views and the artifact inbox.

Mode D — Liquid + remote Meta-Harness

Liquid Desktop/Mobile
  connects to remote Meta-Harness

Team/mobile/server setup: team sessions, remote runners, mobile monitoring, shared dashboards, shared config and long-running automations.

In every integrated mode Liquid consumes the provider's public surfaces and renders them; it does not duplicate provider backends. See the Meta-Harness and Loop Agent V-Specs.

3. Differentiators / core principles

Self-contained workspace product

Workspace → dashboards → views → components is enough to build custom tools inside Liquid (e.g. a table component plus a script component generating an analysis diagram) with no agents installed.

Agent-editable workspace

Liquid exposes a workspace CLI/API so external agents and tools can read and edit workspace data through a permissioned, fully-recorded mutation pipeline.

Workspace history is first-class

Every mutation is appended to an internal action history/VCS with actor and origin, so changes are auditable and revertible.

Native cross-device app

Desktop/mobile native across Linux, Windows, macOS and mobile. Users should not need separate provider apps on each device.

LLMs build functionality in place

Describe a dashboard/component/automation; Liquid AI proposes it through the same mutation pipeline and the user reviews/runs it without per-platform build/deploy flows.

Optional protocol-native integrations

Loop Agent and Meta-Harness integrate as protocol clients, not compiled-in UI modules, and are never prerequisites.

liquid-storage

liquid-cli
  workspace read/edit commands
  action-history commands, export/import

liquid-api
  local service/API for app, CLI and external agents
  workspace event subscriptions
  mutation proposal/apply/revert endpoints

liquid-ui
  native Dart/Flutter candidate UI
  dashboards, views, components, PowerBar
  action-history / revert UI

liquid-ai
  workspace assistant; uses the same mutation/action-history pipeline

integrations
  Loop Agent client, Meta-Harness client, external data-source clients
  • Core: Rust for the workspace/component/history models, permissions, mutation pipeline and protocol clients.
  • UI: Dart-based native cross-platform target; exact framework is open in D-009.
  • Storage/history: local-first store + append-only action log + snapshots/checkpoints (D-029, D-028).
  • Components: built-in components plus SDK/extensions; sandboxed script components (D-034).
  • Integration: Loop Agent and Meta-Harness through PROTOCOL.md.

5. Workspace & component model

Workspace — top-level user/agent container: dashboards, sources, settings, action history
Source — anything addressable in a workspace: a Link (external reference) or a Dashboard
Dashboard — composition of views; has layout and permissions
View — representation of one or more components; filters and presentation state
Component — smallest composable unit: id, type, state, input/output ports, permissions, actions, events
Connection — explicit relation between components, scripts, sources or loops: source, target, mapping, trigger/refresh behavior

This model is what the CLI/API and action history read and mutate. The minimal typed component contract for the MVP is D-033; it must align with the GLOSSARY.md Liquid primitives rather than introduce competing terms. Built-in component types for the MVP: note/document, table, chart, script, and file/link/source.

In the MVP a script component computes (e.g. produces an analysis/diagram) and visualization is via built-in components wired by connections; ADR-0040/D-045 keeps the MVP fixed-palette while preserving later arbitrary interactive UI (the "generate an app" capability).

6. Internal action history / workspace VCS

Liquid maintains an internal action history / workspace VCS to support undo/redo, change review, attribution (who/what changed what), reverting faulty external-agent changes, auditability, historical views, future sync/collaboration, and robustness as an agent-editable workspace.

Scope (in): Liquid workspace data — workspace metadata, dashboards, views, components, component state, documents/notes, tables/databases, script components, data-source definitions, connections, automations defined in Liquid, user-defined PowerBar commands, and permissions/settings where applicable.

Scope (out): managing arbitrary external code repositories; replacing Git in software projects; Loop Agent project-history behavior; Meta-Harness/provider session logs except where represented as Liquid components/views.

Liquid's internal action history is a workspace VCS, not a project-code VCS.

Conceptual model (D-028)

Action
  id
  timestamp
  actor:     human | liquid-ai | external-agent | meta-harness | system
  origin:    ui | cli | api | automation | import | sync
  target:    workspace / dashboard / view / component / source / script / ...
  operation: create | update | delete | move | connect | disconnect | run | import | revert
  before/after or patch
  permissions result
  review/approval status
  correlation_id
  revert metadata

History / VCS capabilities

append action            list actions             show action
diff actions/states      undo recent action       revert selected action
revert action range      create checkpoint/snapshot   restore checkpoint
attribute action to actor/origin       mark external-agent changes
review proposed changes before apply

Recommended MVP model: append-only action log + snapshots/checkpoints (D-028); revert uses compensating actions, falling back to user prompt or checkpoint restore on conflict (D-031).

7. Workspace CLI/API for external agents

Liquid exposes itself to external agents and tools through CLI/API surfaces so they can inspect workspace structure; read documents, tables, dashboards, views and components; propose or apply workspace edits subject to permissions; create/update dashboards/components/scripts; query action history; revert faulty changes or request a revert; and act as a workspace data source and controlled mutation target for Meta-Harness and BYOA agents.

CLI verbs below are target product shape, not final syntax (D-027):

liq workspace list
liq workspace open <workspace-id>
liq dashboard list
liq dashboard get <dashboard-id>
liq component list --dashboard <dashboard-id>
liq component get <component-id>
liq component update <component-id> --patch patch.json
liq source list
liq source query <source-id> --query query.json
liq action-history list --workspace <workspace-id>
liq action-history show <action-id>
liq action-history revert <action-id>
liq diff <before-action-id> <after-action-id>
liq export <workspace-id>

Target API/protocol capabilities: read workspace tree; read dashboard/view/component state; query workspace data sources; create/update/delete components; create/update/delete dashboards/views; run or update script components; propose workspace mutations; apply approved workspace mutations; inspect action history; diff workspace states/actions; revert actions; subscribe to workspace events.

  • The CLI/API must not bypass permission, review or action-history recording.
  • Every mutation through the CLI/API produces an action-history entry.
  • External-agent edits are distinguishable from human edits (actor/origin attribution).
  • External-agent edits are reversible.

8. External-agent edit safety

External agents read through explicit permissions and write through proposed or policy-gated mutations. Sensitive workspace changes require approval. All writes are recorded in the action history, all applied external-agent mutations are revertible, and the user can inspect a proposed diff before applying it. Liquid AI and external agents use the same mutation pipeline — there are no special hidden writes.

external agent requests workspace context
Liquid returns permitted workspace data
external agent proposes mutation
Liquid validates schema and permissions
Liquid shows diff or applies if policy allows
Liquid appends action-history entry
Liquid emits workspace event
user or agent can revert via action-history API

The permission model for external agents is D-030 (recommended: scoped grants with explicit approval for sensitive writes).

9. Liquid AI vs external agents

Liquid AI is Liquid's built-in workspace assistant. External agents may interact with Liquid through the CLI/API, and Meta-Harness may orchestrate external agents that read/edit Liquid. Liquid AI and external agents both go through the same permissioned mutation/action-history pipeline (D-032).

Liquid AI helps with: creating dashboards; adding/editing components; writing script components; explaining workspace data; building views; connecting data sources; suggesting automations; and reverting/reviewing previous actions.

When Liquid AI needs to run or coordinate coding/agent tasks, it calls Loop Agent or Meta-Harness through their public surfaces; it does not embed their runtimes.

10. LLM-built functionality inside Liquid

Liquid makes app-building feel like workspace customization: describe the desired dashboard, component or automation; Liquid AI proposes components/scripts/connections; the user reviews and runs them inside Liquid. The proposal flows through the same pipeline as any other mutation (§8) and is recorded in the action history (§6).

User: "Build a dashboard that tracks open sessions, compares AgentPulse scores,
and charts rework ratio by loop."

Liquid AI (via the mutation pipeline):
  - proposes a new dashboard
  - adds a session table component
  - adds an AgentPulse metric view
  - adds a chart component
  - connects the metric source to the chart
  - asks before enabling scheduled refresh
  -> every applied step appends an action-history entry and is revertible

Security-sensitive automations and external data access go through explicit capability prompts and policy gates (see §11).

11. Security & permissions

Cross-cutting security stance is in SECURITY.md ("scripts define, sandbox enforces"). Liquid-specific expectations:

  • CLI/API access requires explicit workspace permission; agent reads and writes are scoped.
  • External-agent writes are attributed (actor/origin) in the action history.
  • Sensitive changes require approval; nothing bypasses the permissioned mutation pipeline.
  • The action history must be tamper-evident enough for product needs; exact cryptographic guarantees are open.
  • Revert is available for applied external-agent mutations.
  • Secrets/credentials in workspace data require special handling.
  • Script components and external-agent edits are different risk classes and are treated separately (D-034).

External-agent permission model is D-030.

13. M3 implementation packet

M3 delivers Liquid as a self-contained product (see PLAN.md M3). It should define or implement:

  • native Rust + Dart app shell (after D-009 closes);
  • local workspace store;
  • internal action-history / workspace-VCS model;
  • workspace/dashboard/view/component model;
  • PowerBar;
  • built-in components: note/document, table, chart, script, file/link/source;
  • component connection model;
  • Liquid CLI for workspace read/edit;
  • local API/service for external agents/tools;
  • action-history UI and CLI commands;
  • Liquid AI assistant skeleton;
  • local script component sandbox;
  • optional Meta-Harness client component;
  • optional Loop Agent transcript/session component.

M3 pass/fail includes: a user can create a useful dashboard without agents; add/edit/connect components; run a script component over local data; use PowerBar for workspace actions; Liquid AI can propose or modify a dashboard/component through the same mutation pipeline; an external agent can read permitted workspace info through the CLI/API; an external agent can propose/apply a permitted workspace mutation; every mutation is recorded in the action history; a faulty external-agent mutation can be reverted; and, optionally, a user can add a Meta-Harness session/AgentPulse widget.
