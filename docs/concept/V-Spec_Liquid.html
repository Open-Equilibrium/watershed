V-Spec — Liquid

Local-first workspace and app-building product for humans and agents. Shared contracts: terms, integration, protocol, security, delivery.

1. Product boundary

Liquid is a standalone local-first workspace and app-building product. It stays useful offline and without Flow Agent or Meta-Harness. Its job is to let humans and agents build and safely co-edit Workspace state with attributed, reviewable and reversible History.

Flow Agent    = host-local CLI agent runtime
Meta-Harness  = host-scoped agent control plane
Liquid        = local-first workspace and App platform

Liquid owns

  • Pages, Blocks, Views, Sources and responsive layout;
  • Connections, Workspace Automations and Roles;
  • local replicas, History and the mutation pipeline;
  • App Runtime, App SDK, Block SDK and Block Registry;
  • Workspace CLI/API, Liquid AI and MCP adapters;
  • Sync Server and optional headless Liquid replicas.

Liquid does not own

  • CLI agent processes or Flow Agent internals;
  • Meta-Harness adapters, sessions, config resolution, agent schedules or AgentPulse computation;
  • another product's private storage;
  • project-code VCS/history.

2. Core experience: act first, arrange later

Liquid's authored surface is the Page. A Page opens blank and type-neutral so the user can start working before designing a layout.

New Page
→
First action selects Block Type
→
Content-first flow
→
Optional Arrange mode
  • Typing creates a Text Block; / opens the Block chooser; paste/drop/drawing create the deterministic matching Block.
  • Text shortcuts format the current Text Block. For example, > plus space applies toggle formatting; a toggle is not a Block.
  • Blocks begin in one ordered vertical flow. Arrange mode reveals a responsive grid with move/resize handles, like placing mobile widgets without a separate container.
  • Page templates create useful starting compositions, such as an AI Project with Agent Session, Database and App Blocks. A template is not a Page Type.
  • The Explorer shows Pages and Sources as peer entries. Opening either follows one navigation model; the internal object types remain distinct.
  • The PowerBar finds Workspace objects, creates Blocks and invokes permitted Workspace or agent actions.

3. Workspace, Page, Block and View model

Workspace
├── Pages ───── arrange ─────┐
├── Blocks ◄── represented by ─ Views
├── Sources
├── Connections
├── Automations
├── Roles
├── History
└── Settings
  • A Block is the canonical typed content/functionality instance. A View is one representation and placement of that Block.
  • A Block may support several View kinds, such as Database table/board/calendar or App UI/code. Switching or adding a View does not create a Block.
  • The same Block may appear through synchronized Views on several Pages. Editing any View changes the same canonical state everywhere.
  • Duplicate copies current state into a new independent Block. Add View reuses the existing Block.
  • Removing the last View deletes the Block in the same atomic, reversible History Action. There is no orphan Block pool or separate Trash.
  • That deletion also removes its Connections and owned Automations. Independent Workspace Automations that reference it are disabled and surfaced as Needs attention; deletion shows this impact when dependencies exist.
  • A full-page representation counts as a View. Deleting its Explorer entry therefore follows the same last-View rule.

4. Connections, formulas and Automations

1 — Direct logic

Connections and formulas move typed data or invoke actions among Blocks and Sources. They are the default for understandable calculations and data flow.

2 — Workflow logic

Automations express when/if/then behavior using events, conditions and actions. They are Workspace objects and use Roles.

3 — App logic

App Blocks cover custom interactive functionality that would be awkward as formulas or rules.

Connections and Automations are the medium through which Pages, Blocks and Sources communicate. Layout proximity never creates a Connection or permission. Liquid Automations may call a Meta-Harness public action, while Meta-Harness separately owns agent-process schedules and orchestration on its host.

5. Apps, extensions and MCP

App SDK: Workspace-local functionality

A user should be able to ask, “Build an interactive fitness overview over Database Block X,” and receive a working App Block without knowing runtimes, SDKs, CI, builds or deployment. Liquid AI writes the App through the same reviewed mutation pipeline as a human.

  • The App SDK declares UI, versioned state, typed actions, Connections and capabilities with minimal code.
  • The App Runtime executes restricted JavaScript/TypeScript locally with declarative UI and resource limits. WASM is a later extension.
  • Simple logic uses formulas/Connections or Automations; complex interactive logic uses an App.
  • An App is Workspace-local, synchronizes with its Workspace, inherits History/version recovery and is immediately available to authorized collaborators.
  • An App Block can be opened as a page-like full View or embedded through Views on other Pages, like a reusable Database Block.
  • Permitted App actions are exposed through Liquid's compact CLI/API so agents need not consume a UI or repeat large tool descriptions.

Block SDK: reusable product extensions

The Block SDK serves maintainers and the open-source community. It defines complete reusable Block Types, including state/migrations, Views, responsive behavior, ports/actions, permissions and lifecycle. Users install compatible Block Types from the signed, sandboxed Block Registry and then use them like built-in Blocks. The initial model loads no arbitrary third-party native code.

MCP: adapter, not user mental model

Liquid can connect to an external MCP server and map its capabilities into the same typed App actions, Roles and capability checks. The integration may power an App Block or remain headless when no UI is useful. Users see the App/integration and its permissions. Liquid supplies the MCP client boundary; agents call the resulting permitted action through Liquid's CLI/API when that is more compact than MCP discovery.

6. Roles and safety

A Role is an editable composition of allow-only permissions over named Workspaces, Pages, Blocks, Sources, App actions, agent controls and administrative capabilities. Roles can be assigned to users, groups, agent profiles, sessions and Automations.

effective permission =
  Role allow
  ∩ system boundary
  ∩ App capability
  ∩ session grant
  ∩ provider/host boundary
  • Anything not allowed is denied by default. Explicit deny/blacklist rules are deferred until real policy conflicts require them.
  • Capabilities distinguish discovery/read, propose, execute/apply, approve and manage where the resource supports them.
  • In the M3 MVP, resource-scoped discovery/read permissions govern Liquid surfaces but do not hide bytes in a complete plaintext replica from its authorized device owner or same-identity local processes.
  • Agents may receive narrower per-session authority than their reusable agent profile.
  • Every Workspace write uses the same mutation pipeline and records actor, origin, permission result and reversible change in History.
  • Visibility, View placement, Connection existence and sync access never imply execution authority.

Sandbox and supply-chain requirements are canonical in SECURITY.md.

7. Local-first replicas, central sync and headless Liquid

Laptop replica ──┐
Phone replica ───┼── Sync Server
Headless replica ┘
  • Every authorized M3 MVP client reads and writes a complete local Workspace replica; network loss never switches Liquid into a remote-only mode.
  • Replicas connect to the central Sync Server, not directly to one another. The server persists and exchanges committed changes resumably.
  • Authorized user devices sync the full plaintext Workspace. The Workspace is therefore the local confidentiality boundary, while Liquid still enforces resource-scoped action and API checks.
  • Workspace admission and resource authorization remain separate. Resources keep stable identities, committed changes remain resource-addressed and sync is versioned so a later protocol can add a finite authorized-resource closure. Selective replication is not part of the MVP.
  • A headless Liquid replica is an optional normal replica without UI. It requires workspace-level opt-in because it introduces a server execution boundary.
  • Same-host agents use the headless replica's normal CLI/API, Roles and mutation pipeline even while user devices are offline.
  • The Sync Server does not execute Apps or agents. It and headless Liquid may be co-located in one hosted deployment while remaining separate logical services.
  • Conflict semantics remain D-035.

8. Agent experience

  1. A user or developer configures a harness in Liquid and gives its execution location a friendly name such as “My laptop” or “Liquid Cloud Server.”
  2. The user selects harness, that adapter's configuration and a location, then names the session by intent, such as “Refactor project X.” Flow Agent requires an explicit Flow from its global authority; other harnesses retain their documented selection model. Global-config management is a separate surface; infrastructure IDs and any device-local Runtime binding remain internal.
  3. Liquid calls the Meta-Harness that owns the location; a Meta-Harness schedule or event trigger may start the same run.
  4. Meta-Harness starts, observes and controls the CLI agent on its own host.
  5. Liquid shows connection/freshness state, progress, transcript and prompt/steering controls. The user can add follow-ups or supervise approvals.
  6. The run proposes or executes project actions and permitted Liquid actions. Liquid changes always use the assigned Role, CLI/API and History pipeline.
  7. Meta-Harness retains execution/session records; Liquid retains Workspace History and cached projections.
  8. When a verified terminal checkpoint is available on another device, the user may continue it at a new execution location as a child Run. Liquid renders the resulting Conversation branch and rechecks destination authority rather than presenting a runtime transfer as the same live Run.

Liquid may combine several Meta-Harness projections visually, but every live command returns to the owning instance and unreachable state is clearly offline/stale. A provisioned same-host stack may execute locally without Internet; remote sessions remain stale while unreachable. Portable continuation transfers no credential-store records/references, Roles, approvals or live process ownership, but its recorded content remains sensitive; disconnected continuations from one checkpoint appear as separate branches.

9. Responsive layout, mobile and widgets

  • Canonical View order is device-independent. Responsive spans produce desktop grids and mobile stacks without changing content ownership.
  • Every Block remains visible in the Liquid mobile app.
  • Text, lists and safe compact controls may edit inline. Code, wide databases, whiteboards and complex App Views open a focused/full-screen surface.
  • Mobile Arrange mode uses long-press or an explicit command instead of desktop hover handles.
  • OS home-screen widgets are a separate post-MVP surface, not editable Blocks. Only safe compact Views/actions qualify; sensitive or complex interaction opens Liquid.

10. Architecture boundaries

liquid-core
  object model, Roles, mutation/History contracts
  Block SDK, App SDK, responsive layout

liquid-storage
  local replica and History persistence/indexes

liquid-runtime
  restricted App execution with Role and capability checks

liquid-api / liq
  typed Workspace reads, proposals, mutations and App actions

liquid-sync-server
  central resumable replica exchange only

liquid-ui
  Explorer, Pages, Views, Arrange mode, PowerBar

integrations
  Meta-Harness projection clients and MCP adapters

Package names are design targets, not frozen implementation names. The UI framework and storage engine remain open decisions. All cross-product access uses public IDs and protocol surfaces; no product reads another product's private store.

11. History and Workspace CLI/API

History covers Liquid Workspace data only: Pages, Blocks, Views, Sources, Connections, Automations, Roles, App state, layout and settings. It supports attribution, diff, undo/revert and sync; it is not project-code VCS.

request → validate → effective permission → diff/proposal
        → apply atomically → record Action → emit event

UI, Liquid AI, CLI/API, App, Automation, import and sync all use this path. The CLI/API exposes small typed operations rather than one unrestricted document interface; final syntax remains D-027. History storage/revert details remain D-028, D-029 and D-031.

12. Delivery and open decisions

The target model above is delivered in four stages: local Workspace foundation; Apps and agent actions; central sync/mobile/headless execution; then Block Registry and MCP adapters. Scope and Definitions of Done are canonical in PLAN.md.

Remaining Liquid implementation decisions: UI framework (D-009), CLI/API syntax (D-027), History/storage/revert (D-028, D-029, D-031) and sync conflicts (D-035).
