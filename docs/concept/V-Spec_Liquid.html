Standalone native workspace and app-building product. Canonical shared docs: GLOSSARY.md, VISION.md, PROTOCOL.md, SECURITY.md, PERFORMANCE.md, TESTING.md.

1. Purpose & product boundary

Liquid is a standalone local-first native workspace and app-building product. Users compose Pages from typed Blocks, switch a Block between its supported Views, connect Blocks explicitly and work across desktop and mobile. Liquid always reads and writes a local workspace replica through its action-history pipeline. Liquid remains useful without a network, Loop Agent or Meta-Harness.

Liquid is the Watershed platform's workspace/action layer and its long-term workspace/action wedge (see PLAN.md wedge sequencing and ADR-0018). Standalone job: let humans and agents safely co-edit a workspace with reversible history. It is an agent-editable native workspace with action history and safe revert — not a Notion clone and not merely the UI for Meta-Harness. Its defensible niche is the long tail of personal/internal/data-centric apps — agent-built, inside a sovereign, local-first, reversible workspace where the data and agent governance also live, a combination generative-app tools and SaaS workspaces do not offer; the ambition is that long tail, not literally "most applications."

The clean product model across the three Watershed tools:

Loop Agent    = standalone agent runtime
Meta-Harness  = standalone headless many-agent control plane
Liquid        = standalone native workspace / app-building product

Liquid can integrate one or more Meta-Harness instances as optional control-plane providers, but neither Meta-Harness nor Loop Agent is a prerequisite. Liquid does not manage CLI agent processes directly. It renders public Meta-Harness projections without reimplementing their backends and preserves the owning instance for every command (boundary: D-025).

Liquid owns

  • native app shell (desktop/mobile);
  • Workspace, Page, Block, Block Type and View models;
  • Block runtime, rendering, responsive layout and Block SDK;
  • PowerBar;
  • local workspace storage;
  • internal workspace action history / VCS;
  • workspace CLI/API for external agents/tools;
  • local user data model;
  • connections / data-source model;
  • Script Block runtime;
  • Liquid AI workspace assistant;
  • workspace permissions and review/revert flow;
  • import/export and optional local-first sync.

Liquid does not own

  • CLI agent process ownership or Loop Agent execution internals;
  • Loop Agent deterministic FSM / runtime kernel;
  • Meta-Harness session registry;
  • Meta-Harness adapter logic;
  • Meta-Harness central config resolution;
  • Meta-Harness AgentPulse computation;
  • Meta-Harness scheduling engine;
  • any arbitrary project-code VCS/history engine.

Liquid's workspace action history is a workspace VCS over Liquid's own data, not a project-code VCS over arbitrary software projects (see §6). It is distinct from the deferred Watershed project-history engine and from Loop Agent's local session store.

2. Standalone & integration modes

Mode A — local-only workspace

Liquid Desktop/Mobile
  local replica + action history
  Pages, Blocks, Views, Connections
  PowerBar, Liquid AI, workspace CLI/API

The complete standalone path. All interactive reads and writes remain local and continue offline.

Mode B — local workspace + sync host

Liquid local replica
  exchanges committed actions resumably
  with optional sync host when reachable

Sync is opportunistic, not a remote operating mode. Interrupted exchange resumes later; conflict semantics remain D-035.

Mode C — local Meta-Harness sidecar

Liquid → local Meta-Harness API
            → host-local CLI agents

Default agent-enabled setup. Meta-Harness owns the local CLI processes; Liquid renders their sessions, metrics, approvals and automations.

Mode D — one or more Meta-Harness APIs

Liquid → Meta A (this host)
       → Meta B (server host)
       → Meta C (edge host)

One pane of glass, not one fictional controller. Every projection retains instance identity, freshness and authority; commands return to the owning instance.

Workspace sync and live Meta-Harness control are separate planes. Offline Liquid may show explicitly stale cached agent state, but live commands are unavailable until the owning instance is reachable.

3. Differentiators / core principles

Self-contained workspace product

Workspace → Page → Block is enough to build custom functionality inside Liquid: for example, a Database Block connected to a Script Block, with no agents installed.

Agent-editable workspace

Liquid exposes a workspace CLI/API so external agents and tools can read and edit workspace data through a permissioned, fully-recorded mutation pipeline.

Workspace history is first-class

Every mutation is appended to an internal action history/VCS with actor and origin, so changes are auditable and revertible.

Native cross-device app

Desktop/mobile native across Linux, Windows, macOS and mobile. Users should not need separate provider apps on each device.

LLMs build functionality in place

Describe a Page, Block or automation; Liquid AI proposes it through the same mutation pipeline and the user reviews/runs it without per-platform build/deploy flows.

Optional protocol-native integrations

Meta-Harness instances integrate through public APIs, not compiled-in UI modules, and are never prerequisites.

  action-history commands, export/import

liquid-api
  local service/API for app, CLI and external agents
  workspace event subscriptions
  mutation proposal/apply/revert endpoints

liquid-ui
  native Dart/Flutter candidate UI
  Pages, Blocks, Views, Arrange mode, PowerBar

  workspace assistant; uses the same mutation/action-history pipeline

integrations
  Meta-Harness clients, sync client, external Source clients
  • Core: Rust for workspace/Block/history models, permissions, mutation pipeline and protocol clients.
  • UI: Dart-based native cross-platform target; exact framework is open in D-009.
  • Storage/history: recommended local-first store + append-only action log + snapshots/checkpoints (D-029, D-028).

  • Integration: Meta-Harness and sync clients use public contracts in PROTOCOL.md; neither becomes part of the local workspace core.

5. Page, Block & View model

Workspace — Pages, Sources, settings and action history
Page — top-level authored surface with canonical Block order and responsive layout metadata
Block — typed, addressable content or functionality placed on a Page
Block Type — behavior, state contract, supported Views, ports/actions, permissions and responsive capabilities
View — one representation/interaction surface over its owning Block's state
Connection — typed, permissioned Block-to-Block relation independent of layout and active View
Source — external or shared data input; never a Page container

View ownership: a Block owns its state and supported Views. A Database Block may expose table, board, calendar and gallery Views; a Script Block may expose code, UI and output/log Views. Changing View does not duplicate state. The MVP shows one active View per Block; larger screens may support a split View within that Block.

Connections: adjacency never grants access. A Script Block beside a Database Block reads or writes it only through an explicit typed Connection and permission grant. Writes return through Liquid's mutation pipeline and action history. Moving or resizing either Block changes only Page layout.

Block SDK: one contract covers built-in and future third-party Block Types: identity, state serialization/migrations, Views, typed ports/actions, permissions, responsive behavior and lifecycle. The MVP ships a fixed trusted palette under ADR-0040; the SDK contract does not imply loading untrusted custom UI in M3.

Creation and arrangement

  • A new Page is blank and type-neutral. Typing creates a Text Block; / opens the Block chooser; paste/drop and explicit drawing create deterministic matching Blocks.
  • Text shortcuts format within a Text Block; for example, > plus space applies toggle formatting. A toggle is not its own Block.
  • Content starts as an ordered vertical flow. Explicit Arrange mode reveals the responsive grid and resize/reorder handles; there is no second container or layout mode.
  • Desktop uses drag handles. Mobile uses long-press or an explicit arrange command. The grid never shakes.

Responsive and mobile behavior

Canonical Block order is device-independent; responsive spans derive desktop grids and mobile stacks. Every Block remains visible in the Liquid mobile app, but compact inline editing is capability-based: text, lists and safe controls may edit inline, while code, wide database tables and whiteboards open a focused/full-screen View. Blocks advertise compact, standard and expanded size support through the Block SDK.

OS home-screen widgets are a separate post-MVP surface, not miniature editable Blocks. Only safe, compact Views/actions qualify (for example quick note, task list, KPI, session status or a safe shortcut); scripts, sensitive actions and complex editing open Liquid.

6. Internal action history / workspace VCS

Liquid maintains an internal action history / workspace VCS to support undo/redo, change review, attribution (who/what changed what), reverting faulty external-agent changes, auditability, historical views, future sync/collaboration, and robustness as an agent-editable workspace.

Scope (in): Liquid workspace data — Workspace metadata, Pages, Blocks, Block state and Views, Sources, Connections, responsive layout, automations, PowerBar commands and applicable permissions/settings.

Scope (out): managing arbitrary external code repositories; replacing Git in software projects; Loop Agent project-history behavior; Meta-Harness/provider session logs except where projected through Liquid Blocks.

Liquid's internal action history is a workspace VCS, not a project-code VCS.

Provisional conceptual model (D-028)

Action
  id
  timestamp
  actor:     human | liquid-ai | external-agent | meta-harness | system
  origin:    ui | cli | api | automation | import | sync
  target:    workspace / page / block / view / connection / source / ...
  operation: create | update | delete | move | connect | disconnect | run | import | revert
  before/after or patch
  permissions result
  review/approval status
  correlation_id
  revert metadata

History / VCS capabilities

append action            list actions             show action
diff actions/states      undo recent action       revert selected action
revert action range      create checkpoint/snapshot   restore checkpoint
attribute action to actor/origin       mark external-agent changes
review proposed changes before apply

Recommended MVP models: append-only action log + snapshots/checkpoints (D-028); compensating revert actions, falling back to user prompt or checkpoint restore on conflict (D-031).

7. Workspace CLI/API for external agents

Liquid exposes CLI/API surfaces so external agents and tools can inspect Pages, Blocks, Views, Connections and Sources; propose or apply permissioned workspace edits; query action history; and request or perform allowed reverts. The same APIs are the controlled data boundary for Meta-Harness-orchestrated and BYOA agents.

CLI verbs below are target product shape, not final syntax (D-027):

liq workspace list
liq workspace open <workspace-id>
liq page list
liq page get <page-id>
liq block list --page <page-id>
liq block get <block-id>
liq block update <block-id> --patch patch.json
liq source list
liq source query <source-id> --query query.json
liq action-history list --workspace <workspace-id>
liq action-history show <action-id>
liq action-history revert <action-id>
liq diff <before-action-id> <after-action-id>
liq export <workspace-id>

Target capabilities: read workspace/Page/Block/View state; query Sources; create/update/delete/reorder Blocks and Pages; switch Block Views; connect/disconnect typed ports; run or update Script Blocks; propose/apply approved mutations; inspect/diff/revert action history; and subscribe to workspace events.

  • The CLI/API must not bypass permission, review or action-history recording.
  • Every mutation through the CLI/API produces an action-history entry.
  • External-agent edits are distinguishable from human edits (actor/origin attribution).
  • External-agent edits are reversible.

8. External-agent edit safety

External agents read through explicit permissions and write through proposed or policy-gated mutations. Sensitive workspace changes require approval. All writes are recorded in the action history, all applied external-agent mutations are revertible, and the user can inspect a proposed diff before applying it. Liquid AI and external agents use the same mutation pipeline — there are no special hidden writes.

external agent requests workspace context
Liquid returns permitted workspace data
external agent proposes mutation
Liquid validates schema and permissions
Liquid shows diff or applies if policy allows
Liquid appends action-history entry
Liquid emits workspace event
user or agent can revert via action-history API

The permission model for external agents is D-030 (recommended: scoped grants with explicit approval for sensitive writes).

9. Liquid AI vs external agents

Liquid AI is Liquid's built-in workspace assistant. External agents may interact with Liquid through the CLI/API, and Meta-Harness may orchestrate external agents that read/edit Liquid. Liquid AI and external agents both go through the same permissioned mutation/action-history pipeline (D-032).

Liquid AI helps create Pages, add/edit Blocks, write Script Blocks, explain workspace data, choose Views, create Connections, suggest automations and review/revert actions.

When Liquid AI needs to run or coordinate agent tasks, it calls the owning Meta-Harness through its public surface; it does not embed agent runtimes or own CLI processes.

10. LLM-built functionality inside Liquid

Liquid makes app-building feel like workspace customization: describe the desired Page, Block or automation; Liquid AI proposes Blocks, Views and Connections; the user reviews and runs them inside Liquid. The proposal flows through the same pipeline as any other mutation (§8) and is recorded in the action history (§6).

User: "Build a page that tracks open sessions, compares AgentPulse scores,
and charts rework ratio by loop."

Liquid AI (via the mutation pipeline):
  - proposes a new Page
  - adds a session Database Block
  - selects its table View
  - adds a Chart Block
  - connects an AgentPulse Source to the Chart Block
  - asks before enabling scheduled refresh
  -> every applied step appends an action-history entry and is revertible

Security-sensitive automations and external data access go through explicit capability prompts and policy gates (see §11).

11. Security & permissions

Cross-cutting security stance is in SECURITY.md ("scripts define, sandbox enforces"). Liquid-specific expectations:

  • CLI/API access requires explicit workspace permission; agent reads and writes are scoped.
  • External-agent writes are attributed (actor/origin) in the action history.
  • Sensitive changes require approval; nothing bypasses the permissioned mutation pipeline.
  • The action history must be tamper-evident enough for product needs; exact cryptographic guarantees are open.
  • Revert is available for applied external-agent mutations.
  • Secrets/credentials in workspace data require special handling.
  • Script Blocks and external-agent edits are different risk classes and are treated separately (D-034).

External-agent permission model is D-030.

13. M3 implementation packet

M3 delivers Liquid as a self-contained local-first product (see PLAN.md M3). The working scope pending the cited open decisions:

  • native Rust + Dart app shell (after D-009 closes);
  • local workspace replica and optional resumable sync client;
  • internal action-history / workspace-VCS model;
  • Workspace/Page/Block/View model and Block SDK contract;
  • deterministic first-action creation, text formatting shortcuts and / Block chooser;
  • content flow, Arrange mode and responsive/mobile behavior;
  • PowerBar;
  • trusted built-in Text, Database, Chart, Code, Formula, Script, Media/Embed and agent-session Blocks;
  • typed Block Connection model;
  • Liquid CLI for workspace read/edit;
  • local API/service for external agents/tools;
  • action-history UI and CLI commands;
  • Liquid AI assistant skeleton;
  • Script Block runtime (local sandbox recommended; D-034);
  • optional multi-instance Meta-Harness client projections with provenance, freshness and authority.

Provisional M3 pass/fail (pending D-026, D-028, D-031, D-034 and D-035): offline, a user can start a blank Page by acting immediately, edit/connect multi-View Blocks, arrange them responsively and run a Script Block over local data; every human, AI, CLI/API and sync mutation uses the action-history pipeline and can be reviewed/reverted as permitted; interrupted sync resumes without blocking local work. Optional agent integration projects multiple Meta-Harness instances without losing provenance and rejects live commands while the owning instance is unreachable.
