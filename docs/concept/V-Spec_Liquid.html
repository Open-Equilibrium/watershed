V-Spec — Liquid

Local-first workspace and app-building product for humans and agents. Shared contracts: terms, integration, protocol, security, delivery.

1. Product boundary

Liquid is a standalone local-first workspace and app-building product. It stays useful offline and without Flow Agent or Meta-Harness. Its job is to let humans and agents build and safely co-edit Workspace state with attributed, reviewable and reversible History. Native desktop targets and current availability follow PLATFORMS.md.

Liquid owns

  • Pages, Blocks, Views, Sources and responsive layout;
  • Connections, Workspace Automations and Roles;
  • local replicas, History and the mutation pipeline;
  • App Runtime, App SDK, Block SDK and Block Registry;
  • Workspace CLI/API, Liquid AI and MCP adapters;
  • Sync Server and optional headless replicas.

Liquid does not own

  • CLI agent processes or Flow Agent internals;
  • Meta-Harness adapters, sessions, config resolution, agent schedules or AgentPulse computation;
  • another product's private storage;
  • project-code VCS/history; Meta-Harness runs Git operations on agent projects and Liquid only presents them.

Web links follow after M3a as read-only Sources that load only when opened and show in a built-in browser, as T3 Code's isolated preview does: a native WebView per platform (WKWebView, WebView2, WebKitGTK), whose dependency is chosen when it is built; it gives pages no access to Liquid or the Rust–Flutter bridge and keeps cookies per Workspace; agent control of it comes later (ADR-0236).
  • Media come from local attachments (ADR-0305); a PDF's pages and an image take ink in place with the Whiteboard's tools, kept as the Block's drawing while the file never changes (ADR-0307): a PDF's pages scroll in a 560-point frame, an image takes ink over itself, a highlighter joins the tools, and up to 2,000 pages take ink, each with a board's caps and all together ten boards'. The system's renderer (PDFKit on macOS) draws pages through Liquid's own channel, not a prebuilt third-party engine, and ⌘V reads files through Liquid's own macOS clipboard reader, not CocoaPods' super_clipboard (ADR-0216); a pasted web link is a link in its line that fetches nothing, and an embed loads remote content only after a click (ADR-0235).
  • The PowerBar without a prefix searches and jumps; / adds a Block and > lists actions; @ is kept for people (ADR-0236, Pages mockups). ⌘K, the sidebar's search row or a tap of the Liquid key opens it over the current Page; a held Liquid key shows the shortcuts instead. Empty, it lists the three recent Pages of this device and the actions. Search matches the start of each word in Page titles, Table names and text, with accents ignored (ADR-0237); a text hit opens its Page with the caret in that Block. A Block from / goes below the Text Block last edited, otherwise at the Page's end.

3. Workspace, Page, Block and View model

Workspace

├── Blocks ◄── represented by ─ Views

  • A Block may support several View kinds, such as App UI/code; a Table's layouts (Table, Board, Calendar) belong to its View's tabs. Switching or adding a View does not create a Block. A Table's View holds tabs, as Notion's database views, each with its own layout (Table, Board or Calendar), group, sort and filter, for everyone who sees that View (ADR-0311); they do not change the Block or its other Views.
  • The same Block may appear through synchronized Views on several Pages. Editing any View changes the same canonical state everywhere.
  • Duplicate copies current state into a new independent Block. Add View reuses the existing Block. Pasting a copied Block duplicates it; a View is always explicit (ADR-0235).
  • Removing the last View deletes the Block in the same atomic, reversible History Action. There is no orphan Block pool or separate Trash.
  • That deletion also removes its Connections and owned Automations. Independent Workspace Automations that reference it are disabled and surfaced as Needs attention; deletion shows this impact when dependencies exist.
  • A Table's View has its own title (the first one typed also names a new Table); Table and Board group by a Select or Checkbox field, the replica's device table remembers each View's last used tab, and Blocks other than Tables stay in their home Page's document; a note at its right names the Table and opens the Table's page. Below the title, its tabs, at most 50; ＋ adds one of a chosen layout, and the active tab's menu renames it, changes its layout, duplicates or deletes it. Below the tabs, Group, Sort and Filter show what they hold; a Calendar shows Date and its month instead of Sort and Search, a click on a column's name sorts by it, then reverses, then clears, and the column's menu opens from ⌄ beside the name, a right-click or a long press. Search narrows the rows and is never saved. ··· on the title line duplicates the Table, copies the View or deletes it. A Board's card and a Calendar's row open the row beside them; dragging a card moves it, also into another group, and dragging a Calendar's row sets its day. Pasting a copied View adds a copy of its Table, with Paste as View to show the same Table instead. The slash commands Board and Calendar make a ready Table; Existing Table… adds a View of a chosen Table with one tab of a chosen layout, or copies another View's tabs once.
  • A Table's page shows all its rows and where it is shown; there a click on its name renames it for every View, sorting and search are not saved, and ··· holds Delete Table…, which deletes its Views too. A View whose Table was deleted says so.
  • A full-page representation counts as a View. Deleting its Explorer entry therefore follows the same last-View rule. A Table's entry in the sidebar's Tables section is such a representation, so removing its last View on a Page asks whether to delete the Table too (ADR-0309).

One store, three views

  • Accepted target (ADR-0228): Pages and Blocks in M3; files like a drive and media like a photo library later, as views on the same store. M3 builds attachments only.
  • Metadata lives in one CRDT document per Page; Pages group into areas, the unit for Roles, replication and keys. Moving a Block between Pages changes both documents in one History Action, and a reference to a Page a device does not hold shows a placeholder.
  • Contents are content-addressed, chunked, encrypted blobs outside the CRDT, loaded on demand; a device indexes a file for search when it first loads it. Binary files cannot merge, so concurrent edits keep both versions.
  • Rich text is text with formatting marks; Tables (ADR-0244) are typed fields and rows (text, number, select, date, checkbox, file, link to a row, formula and button; a new Table starts with a text field "Name"), with a total row, kept each in a document of its own that belongs to an area and listed in the sidebar's Tables section (ADR-0309), and read in windows that Rust filters and sorts, Whiteboards and annotated Media Blocks keep each stroke, shape and text of their drawing as an element that merges on its own (ADR-0306, ADR-0307), and Markdown and HTML serve only import and export. Later drive and media views add OS integration (macOS File Provider, Windows Cloud Files, Linux FUSE) and on-device previews and indexing.
  • A Code Block shows code and never runs it (ADR-0302); its language is stored as Markdown names it, and Liquid's own highlighter colours every language alike, so no package comes in before one is needed. Lines never wrap, and past 24 lines the code scrolls inside, as a table does.
  • Math is set from LaTeX with KaTeX's commands and never computed (ADR-0316). A Math Block shows one formula centred; a click opens its LaTeX below it in place, the formula follows as it is typed, and esc, a click outside or an arrow key at the LaTeX's edge leaves it. /Math adds one, $$ at the start of an empty Text Block turns it into one, and ⌫ in an empty one turns it back. LaTeX that cannot be set shows as written, with KaTeX's reason. In a Text Block, $…$ is set until the caret enters it, and the text keeps its dollars: a dollar opens math only before a character other than a space, and closes it only after one and never before a digit, as Pandoc reads Markdown, so "$5 and $10" stays text and \$ never opens math. Markdown import and export, with their slice, keep both forms: $$ lines for a Math Block, $…$ in a paragraph.

4. Connections, formulas and Automations

1 — Direct logic

Connections and formulas move typed data or invoke actions among Blocks and Sources. They are the default for understandable calculations and data flow.

2 — Workflow logic

Automations express when/if/then behavior using events, conditions and actions. They are Workspace objects and use Roles.

3 — App logic

App Blocks cover custom interactive functionality that would be awkward as formulas or rules.

Connections and Automations are the medium through which Pages, Blocks and Sources communicate. Layout proximity never creates a Connection or permission. Liquid Automations may call a Meta-Harness public action, while Meta-Harness separately owns agent-process schedules and orchestration on its host.

Formulas use Excel's functions and operators, as = 2000 − SUM(Expenses.Amount), with references as chips bound to stable IDs, so renaming keeps a formula (ADR-0315). liquid-core parses and computes them over 64-bit floats shown to 15 significant digits, with Excel's error values #DIV/0!, #VALUE!, #REF!, #NAME? and #NUM!: a deleted reference, two formulas that need each other, or formulas and the references they follow nested more than 128 levels deep give #REF!, and a result too large for a 64-bit float gives #NUM!, in a total too; a Chart leaves out a group whose sum overflows. A formula holds at most 8,192 characters and 64 nested brackets, and text it builds at most 32,767 characters, as in Excel.

  • Calculation Block: lines of a label and a value or formula, values right-aligned; a line is plain, a heading, a subtotal or the total, and SUM(ABOVE) adds the plain lines up to the heading above. A value typed without = stays a number or text. Typing a formula suggests the Block's lines, the fields of up to 50 Tables and the functions; a chosen one becomes a chip. "Add a line" grows one value into a report, up to 500 lines.
  • Formula field: computes each row from its fields and is edited in the field menu; it takes no typing and is not sorted, filtered or grouped by.
  • Button field: each row shows a button with the field's name, in the grid and the row's popover, that runs the Automations it starts; it holds no value, has no total and is not sorted or filtered by.
  • Total row: a Table's footer shows its row count and, per field, Sum, Average, Count, Min, Max, Empty or Filled over the rows the tab shows, so a filter or search changes it; a sum, an average, a minimum or a maximum needs a number or formula field. Each tab keeps its own.
  • Chart Block: bars, a line or a pie, drawn by Liquid itself, from a Table, grouped by a select, checkbox or text field and counting rows or adding or averaging a number, or from a Calculation Block's plain lines in their order. A line needs two points, and a Chart draws at most 100. Its panel picks the data and lists what it uses and what uses it; the data list offers the Tables and this Page's Calculation Blocks.

The Automation editor reads as sentences, as Trello's Butler rules do: When, If, Then, each part a token that opens a short list. M3a Automations start on events and buttons only; schedules follow the headless replica, so no two devices run one (ADR-0235, ADR-0317).

  • Where: "Automations" at the Explorer's foot opens a dialog over the current Page listing each one with what it belongs to, when it runs, the Role it runs as and its status; the foot counts those that need attention. The editor opens in the same dialog.
  • When: a row is added to a Table, a field of a Table changes, or a button field is clicked. Only a person's change or click starts one: what an Automation changes starts no other, so no chain or loop can form.
  • If: conditions on the row's fields, all of which must hold, use the Table filters' tests plus is not, more than and less than (before and after for dates); a formula or button field takes none.
  • Then: set a field of the row, add a row to a Table, or show a notification, whose text shows a field's value where it names {Field}; the notification is a toast at the window's foot. A run is one Action, by the Automation, in History; a step that fails undoes the run and the toast says why.
  • Test runs the steps once on the trigger Table's last row, without the conditions, as a run like any other. An Automation starts on, and its switch turns it off.
  • Belongs to: an Automation that uses only its trigger's Table belongs to it and is deleted with it; one that uses other Tables belongs to the Workspace. Deleting a Table it uses, or removing a field it uses, turns it off and marks it Needs attention with the reason, in the same Action; a removed field also takes the conditions and actions that used it, and a notification keeps its name as text. Choosing another Table or field clears the mark, and so does turning it on once nothing it uses is missing.
  • Runs as: the Workspace owner's access until Roles are built, shown as Can manage.
  • Bounds: 500 Automations per Workspace, 20 conditions and 20 steps each, a name, message or value of 1,000 characters.

5. Apps, extensions and MCP

App SDK: Workspace-local functionality

A user should be able to ask, “Build an interactive fitness overview over Table X,” and receive a working App Block without knowing runtimes, SDKs, CI, builds or deployment. Liquid AI writes the App through the same reviewed mutation pipeline as a human.

  • Simple logic uses formulas/Connections or Automations; complex interactive logic uses an App.
  • An App is Workspace-local, synchronizes with its Workspace, inherits History/version recovery and is immediately available to authorized collaborators.
  • An App Block can be opened as a page-like full View or embedded through Views on other Pages, like a reusable Database Block.
  • Permitted App actions are exposed through Liquid's compact CLI/API so agents need not consume a UI or repeat large tool descriptions.

Block SDK: reusable product extensions

The Block SDK serves maintainers and the open-source community. Users install compatible Block Types from the signed, sandboxed Block Registry and then use them like built-in Blocks.

MCP: adapter, not user mental model

Liquid can connect to an external MCP server and map its capabilities into the same typed App actions, Roles and capability checks. The integration may power an App Block or remain headless when no UI is useful. Users see the App/integration and its permissions. Liquid supplies the MCP client boundary; agents call the resulting permitted action through Liquid's CLI/API when that is more compact than MCP discovery.

Accepted target: App, Block package and MCP security

  • App code runs locally in the restricted App Runtime. The first target is isolated JavaScript/TypeScript with declarative UI, explicit capabilities, CPU/memory/time limits, no ambient filesystem/process/environment access and deny-by-default network access. WASM is a later runtime target.
  • App state changes and App-driven workspace writes use the mutation pipeline. App code cannot edit another Block merely because a View is nearby; a Connection plus an effective permission is required.
  • An App action is capability-scoped and may be invoked by UI, Connection, Automation or agent only when the caller and App both allow it.
  • External MCP servers remain outside the App Runtime. Liquid's MCP adapter is the client boundary, validates declared inputs/outputs and maps only granted capabilities to typed App actions. MCP connectivity never grants broader Workspace access.
  • Block Registry packages are signed, versioned, sandboxed and capability-scoped. Initial support loads no arbitrary third-party native code; package update and migration are explicit, reviewable actions.
  • App execution, external MCP calls and external-agent edits are separate risk classes and keep separate capability grants.

6. Roles and safety

Accepted target (M3). What ships today is listed in SECURITY.md; Roles, the Workspace CLI/API and the rules below follow.

A Role is an editable composition of allow-only permissions over named Workspaces, Pages, Blocks, Sources, App actions, Meta-Harness projections, agent controls and administrative capabilities.

effective permission =
  Role allow
  ∩ system boundary
  ∩ App capability
  ∩ session grant
  ∩ provider/host boundary
  • Workspace CLI/API access requires an authenticated identity and an assigned allow-only Role. Anything not allowed is denied by default. Explicit deny/blacklist rules are deferred until real policy conflicts require them.
  • Effective authority is the intersection above: no layer can grant a capability another boundary denies.
  • Capabilities distinguish discovery/read, propose, execute/apply, approve and manage where the resource supports them.
  • Discovery and read permissions govern Liquid surfaces but do not hide replica bytes (§7); that grants no write, execution or administrative authority.
  • Agents may receive narrower per-session authority than their reusable agent profile.
  • Every Workspace write, from the UI, Liquid AI, the CLI/API or an external agent, uses the same mutation pipeline and records actor, origin, permission result and reversible change in History; no hidden write bypasses it.
  • External-agent writes are attributed (actor/origin) and revertible; sensitive changes require approval, and a proposed diff can be reviewed before apply.
  • Secrets and credentials are never Workspace data; Workspace data holds only references to a keychain or a company secret manager (ADR-0224).
  • Visibility, View placement, Connection existence and sync access never imply execution authority.
  • Rights inherit from an area to its Pages and Blocks. A protected Page, Block or Source stops inheriting them, so only Roles allowed on it may change it. A Block's rights follow its home (for a Table, its area), never the Page that shows a View of it. Read access is never finer than an area; in M3 every authorized device holds the complete Workspace, so the Workspace stays the confidentiality boundary (ADR-0235).
  • M3a assigns Roles to Automations; people follow with sync and agent profiles with M3b (ADR-0235). Three editable Role templates follow Notion's access levels: Can view (read), Can edit (read and apply) and Can manage (every capability). The person who creates a Workspace holds Can manage, which protection never removes, so no one can lock the owner out (History and Roles mockups).

Accepted target (ADR-0223, ADR-0224, ADR-0229, ADR-0255):

  • An agent acts with its own identity and a grant signed by the person it works for, naming an area, actions and an expiry. Its authority never exceeds that person's: it is the intersection of the agent's Role, the person's authority and the grant.
  • Agents change Workspace data only through the Workspace CLI/API and mutation pipeline, never in a store: of the person's Liquid on a default agent host, otherwise of their agent host's headless replica, which receives only the areas the agent Roles allow once selective replication follows the complete M3 replicas (ADR-0224, ADR-0255).
  • Each Role sets which changes are sensitive and wait for the person's approval, by default deletion, permission, grant and Automation changes. A grant may waive these approvals, at the discretion of the person who issues it.
  • History records the agent as actor and the person it acts for. Revoking the session or grant makes the Sync Server refuse the agent's further changes.
  • A subagent's authority comes from its parent's grant and is never larger; agent hosts pair and start their own processes as in Meta-Harness orchestration (ADR-0253).
  • Liquid AI is a built-in agent profile on an agent host, local or remote, limited to Liquid actions (ADR-0229).
  • Where agents run and what they reach is the accepted agent-host risk in SECURITY.md (ADR-0254).

7. Local-first replicas, central sync and headless replicas

Laptop replica ──┐
Phone replica ───┼── Sync Server
Headless replica ┘

Accepted enterprise target

  • Accepted target (ADR-0223, ADR-0224): each device holds everything its person may access; a headless replica holds only the areas its Roles allow. M3 starts with complete replicas on a data model divided into areas.
  • An agent host runs by default under the account Meta-Harness is installed on, as in T3 Code, so on a person's laptop its agents reach what that account reaches, Liquid's files included; it has no replica of its own, and its agents use the person's Liquid through the Workspace CLI/API. A separate machine, VM, container or account the person sets up and links keeps them apart, and a Mac project needs a Mac agent host; such an agent host has a headless replica, which syncs through the Sync Server like every replica, and a later offline path through the device's Liquid is required; the Sync Server verifies signed changes either way (ADR-0228, ADR-0254, ADR-0255).
  • Liquid accounts sign in with passkeys from M3; companies add single sign-on through OIDC or SAML, with SCIM provisioning (ADR-0224).
  • Each device holds its own key in the Secure Enclave or TPM and connects over TLS 1.3. Every change is signed, and from M3 the Sync Server accepts a change only if its signer's Role allows it; a refused change is visibly undone on its device (ADR-0224, ADR-0228).
  • Signed changes make History tamper-evident, and the Sync Server keeps an audit log that companies can export to their security monitoring.
  • Liquid is self-hosted: an organization runs its own Sync Server, with its own region and keys (ADR-0276). A hosted offering is at most a later option.
  • Devices encrypt Workspace content per area from M3. Each area key is wrapped for every device and headless replica allowed in the area and, unless the Workspace chooses end-to-end encryption, for the Sync Server; choosing it later removes the server's copy. A company may run a compliance replica with its own key for search, legal hold and data-loss checks (ADR-0228).
  • A new device receives keys only after a signed-in device approves it or a recovery key restores access; area keys are also wrapped for that key, which the person or their company holds. A fault in key approval, rotation, revocation or recovery loses data, so each has dedicated tests. Liquid ships native apps only, with no web client.
  • Every authorized M3 MVP client reads and writes a complete local Workspace replica; network loss never switches Liquid into a remote-only mode.
  • Replicas connect to the central Sync Server, not directly to one another. The server persists and exchanges committed changes resumably.
  • Sync applies received actions through the same mutation pipeline. Sync credentials authorize Workspace exchange only, not Meta-Harness control. Interrupted or untrusted sync never disables access to the local replica.
  • Authorized user devices sync the full plaintext Workspace. The Workspace is therefore the local confidentiality boundary: Roles do not hide replica bytes from the device's owner or from processes running as that user, while Liquid still enforces resource-scoped action and API checks.
  • Workspace admission and resource authorization remain separate. Resources keep stable identities, committed changes remain resource-addressed and sync is versioned so a later protocol can add a finite authorized-resource closure. Selective replication is not part of the MVP.
  • A headless replica requires workspace-level opt-in because it introduces a separate execution boundary: it receives only Workspaces explicitly enabled for it, then enforces the same Roles and mutation pipeline as a UI replica.
  • Agents and Automations on its host use its normal CLI/API, Roles and mutation pipeline even while user devices are offline.
  • The Sync Server does not execute Apps or agents. It and a headless replica may be co-located in one hosted deployment while remaining separate logical services.
  • Replicas merge with Automerge 3, which keeps both values of a concurrent edit to one field (ADR-0238).

8. Agent experience

Planned (ADR-0239, ADR-0241): every conversation becomes a Chat; an agent's work folder is a folder Source, chosen in the system dialog through the Flutter team's file_selector, and the steps below then start a Chat rather than a session (the app's structure).

  1. A user or developer configures a harness in Liquid and gives its execution location a friendly name such as “My laptop” or “Team server.”
  2. The user selects harness, that adapter's configuration and a location, then names the session by intent, such as “Refactor project X.” Flow Agent requires an explicit Flow from its global authority; other harnesses retain their documented selection model. Global-config management is a separate surface; infrastructure IDs and any device-local Runtime binding remain internal.
  3. Liquid calls the Meta-Harness that owns the location; a Meta-Harness schedule or event trigger may start the same run.
  4. Meta-Harness starts, observes and controls the CLI agent on its own host.
  5. Liquid shows connection/freshness state, progress, transcript and prompt/steering controls. The user can add follow-ups and answer the approvals and questions the harness itself asks (ADR-0252).
  6. The run proposes or executes project actions and permitted Liquid actions. Liquid changes always use the assigned Role, CLI/API and History pipeline.
  7. Meta-Harness retains execution/session records; Liquid retains Workspace History and cached projections.
  8. When a verified terminal checkpoint is available on another device, the user may continue it at a new execution location as a child Run. Liquid renders the resulting Conversation branch and rechecks destination authority rather than presenting a runtime transfer as the same live Run.

Liquid may combine several Meta-Harness projections visually, but every live command returns to the owning instance and unreachable state is clearly offline/stale. A provisioned same-host stack may execute locally without Internet; remote sessions remain stale while unreachable. Portable continuation transfers no credential-store records/references, Roles, approvals or live process ownership, but its recorded content remains sensitive; disconnected continuations from one checkpoint appear as separate branches.

Accepted target (ADR-0233): a company can keep agents off its laptops, which then only attach to allowed agent hosts. It may limit where agent hosts run: the Sync Server then wraps no area keys and accepts no grants for other agent hosts, and Liquid follows the company's device-management policy, starting no local Meta-Harness. Agents installed outside Liquid are the device management's to block.

Accepted target (ADR-0230): a reply that cites Liquid content carries a reference, a Page or Block with a revision, “latest” or a History id, never a copy; the Workspace CLI/API returns a ready reference for every change, so any harness can cite it. Liquid renders it from the person's replica with the Page's Block View, a breadcrumb, the revision, which a menu changes, and “Open”, which opens the Page at the Block, or a placeholder without access. The live read-only embed comes first; the agent's edits, marked against the current state with who changed them on whose behalf, when, that History can revert them and a filter to the person's own changes, once History has revision ids; editing in place later.

9. Responsive layout, mobile and widgets

  • Canonical View order is device-independent. Responsive spans produce desktop grids and mobile stacks without changing content ownership.
  • Every Block remains visible in the Liquid mobile app.
  • Text, lists and safe compact controls may edit inline. Code, wide databases, whiteboards and complex App Views open a focused/full-screen surface.
  • Mobile Arrange mode uses long-press or an explicit command instead of desktop hover handles.
  • OS home-screen widgets are a separate post-MVP surface, not editable Blocks. Only safe compact Views/actions qualify; sensitive or complex interaction opens Liquid.

11. History and Workspace CLI/API

History covers Liquid Workspace data only: Pages, Blocks, Views, Sources, Connections, Automations, Roles, App state, layout and settings. It supports attribution, diff, undo/revert and sync; it is not project-code VCS (SECURITY.md). Attribution of entries to the extension that produced them is out of scope.

request → validate → effective permission → diff/proposal
        → apply atomically → record Action → emit event

UI, Liquid AI, CLI/API, App, Automation, import and sync all use this path. The CLI/API exposes small typed operations rather than one unrestricted document interface; final syntax remains D-027. History is a sequence of Actions plus save points. A revert records a new reversing Action, as git revert does; Restore version returns a Page to an earlier point, also when later changes conflict; ⌘Z reverts the person's last Action as an Undo entry (ADR-0235).
